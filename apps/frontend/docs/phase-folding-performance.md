# 위상 접기 성능 개선 사례와 회고 자료

`S15P21C206-184`의 주기 미세 조정·그래프 표시 개선을 회고와 포트폴리오에 재사용하기 위한 기술 기록이다. 2026-09-16의 로컬 구현·측정 결과를 다루며, 운영 성능이나 실제 사용자 효과를 입증한 자료는 아니다. 기능 계약과 전체 완료 범위는 [위상 접기 개발 안내](phase-folding.md), 요구사항과 성능 검증 원칙은 [분석 프론트 명세](../../../docs/development/analysis-frontend-spec.md)를 따른다.

이 문서는 Canvas 개선, GPU 비교 실험, 개발용 앱 연결까지의 판단과 결과를 순서대로 기록한다. 상세 재현 절차와 GPU 검증 진행표는 [Canvas·WebGL 실험 기록](phase-folding-gpu-experiment.md)에 둔다. 최초 Canvas 측정 기준 커밋은 `53e0d4e`이며, 개선 구현과 검증 코드·측정 기록은 이 문서를 추가한 커밋에 함께 포함한다. 이후 안내 깜빡임 수정은 별도 절에 기록하며 기존 측정값을 새 구현의 재측정 결과로 취급하지 않는다.

## 배경과 해결하려던 문제

분석 화면에서 사용자가 반복 주기를 조금씩 바꾸면 관측점을 새 주기로 접고 그래프를 갱신한다. 계산을 Worker로 옮겨도 React 상태 갱신, 상태 문구의 배치, 메인 스레드의 Canvas 그리기는 별도 비용으로 남는다. 사용자는 기존 목업에서 재접기 상태를 계속 표시하면서 반복 렌더링이 발생했던 경험을 공유했다.

이 경험을 현재 코드의 원인으로 단정하지 않고, 다음 세 가지를 확인하는 것부터 시작했다.

1. 조작을 멈춘 뒤에도 불필요한 렌더링이 계속되는가?
2. 계산 중/완료 표시가 바뀌면서 그래프가 움직이는가?
3. 많은 점을 표시할 때 계산과 그리기 중 어디에서 지연되는가?

개선 조건은 모든 유효 관측점과 원본 과학 입력을 보존하고, 계산 중 후속 입력 잠금과 실패 복구를 유지하는 것이었다. 실제 백엔드가 없어 합성 응답으로 검증했으며, 시각 리디자인은 범위에서 제외했다.

## 원인 분석: 계산과 화면 처리를 분리해 측정

2026-09-16에 `53e0d4e`의 배포 코드를 기준으로 측정하고 같은 환경에서 수정 후 비교했다. 무조작 1초 동안 React 추가 커밋·Canvas 그리기는 모두 0회였다. 이번 구현에서 무한 렌더링은 재현하지 못했지만, 미세 조정마다 계산 중/완료 문구와 취소 버튼이 교체되면서 차트가 세로로 57px 이동했다. 30만 점 전체 보기에서는 Worker보다 점별 Canvas 그리기가 병목이었다.

## 선택한 개선 방법

- 상태 문구와 동작 버튼을 고정된 두 열 영역에 배치하고, 일반 상태 문구에 필요한 높이와 버튼 공간을 유지한다. 완료 때 취소 버튼은 숨기고 비활성화한다. 계산 중/실패 상태 알림과 취소·재시도 동작은 그대로 제공한다. 지연을 숨기는 타이머나 매 프레임 React 상태 갱신은 추가하지 않는다.
- 화면에 반복 표시되는 점이 50,000개를 넘으면 모든 가시 관측점을 재사용하는 화면 크기의 RGBA 버퍼에 합성한 뒤 Canvas로 한 번 전송한다. 각 원의 중심은 기존 위상·밝기 좌표이며 반지름은 기존 1.2 CSS px다. 원 가장자리의 픽셀 피복률로 알파를 계산하므로 브라우저 내장 원과 가장자리 안티앨리어싱이 조금 다를 수 있다. 숫자 조회·위상·BTJD·flux와 Worker 배열은 바꾸지 않는다.
- 50,000은 이 환경에서 비교한 렌더 방식 전환 기준이며 데이터 상한·과학 계약이 아니다. 두 방식 모두 가시점 전부와 두 주기 반복을 처리한다. 픽셀 버퍼를 매 결과마다 비우므로 이전 점이 남지 않는다. 화면 크기/DPR가 바뀌면 버퍼를 다시 만들고 희소한 확대 화면은 기존 원 그리기를 사용한다.
- 단일 큰 경로, 256점 경로 묶음, 점 이미지 재사용도 비교했으나 실제 타이머 지연이 개선되지 않거나 악화돼 채택하지 않았다. 특히 단일 경로는 Canvas 호출 시간이 짧아져도 이후 화면 처리가 느려져 호출 시간만으로 판단하면 안 됐다.

## 재현 방법과 측정 조건

[전용 Playwright 설정](../playwright.performance.config.ts), [측정 시나리오](../tests/performance/fold-performance.spec.ts), [테스트 전용 계측](../tests/performance/fold-metrics.ts)을 사용한다. 기존 설치한 Chromium 캐시 경로가 필요하면 `PLAYWRIGHT_BROWSERS_PATH`를 지정한 뒤 `apps/frontend`에서 실행한다.

```powershell
npm run test:performance
```

이 명령은 배포 빌드를 만들고 58264 포트에서 검증한다. `test:production`과 같은 포트를 사용하므로 동시에 실행하지 않는다. 실제 앱에 테스트가 가로챈 합성 API 응답을 넣는다. Worker 처리 시간은 테스트에서 배포 Worker의 메시지 핸들러를 감싸 측정한다. 별도 타이머·React DevTools 후크·Canvas/DOM 계측은 테스트에서만 주입하며 앱 번들에는 넣지 않는다. 콘솔의 `FOLD_PERF`와 `test-results/performance`의 JSON 첨부·밀집 그래프 이미지로 결과를 확인한다.

- 환경: Windows, Intel Core Ultra 9 185H, 논리 CPU 22개, 시스템 메모리 64GiB, Chromium 153.0.8010.12, 1440×900, DPR 1, CPU 제한 없음. 지원 기기 전체를 대표하지 않는다.
- 입력: 17,281점 기존 샘플과 100,000/300,000점 부하 입력. 모두 합성 Sector 1개, binning revision 2, 120일 범위다. 큰 입력은 기존 밝기 배열을 반복하고 간격을 더 촘촘하게 설정한다. 실제 항성·BLS·서비스 최대 규모를 뜻하지 않는다.
- 조작: ×1·×32 각각 실제 미세 조정 버튼의 핸들러를 16ms 타이머 간격으로 증가/감소 40회 호출한다. 긴 작업이 있으면 실제 입력 간격도 늘어나므로 일정한 60Hz 부하라고 해석하지 않는다. 취소·대기열에서 교체된 중간 입력은 화면 결과로 나타나지 않을 수 있다.
- Worker 시간은 계산과 결과 `postMessage` 호출까지이며 왕복·화면 반영 지연이 아니다. Canvas 시간은 그리기 명령 처리 범위이며 GPU 완료 시간이 아니다. 입력→표시는 최종 반영된 결과의 DOM 변경 관측까지이며 실제 픽셀 출력 시각이나 모든 중간 입력의 지연이 아니다. 16ms 타이머 간격과 Long Tasks를 함께 기록한다.
- React 수치는 루트 커밋 횟수다. 컴포넌트 함수 호출 수와 구분한다. 40회 조정의 전체 보기에서는 변경 전후 모두 대체로 80커밋(계산 시작/성공)이 있었고 정지 뒤 추가 커밋은 없었다. 실제 계산 중 후속 입력 잠금을 위해 필요한 상태 전이를 숨기지 않았다.

## 후속 실험: GPU 표시와 실제 앱 연결

### 남은 병목과 선택한 범위

Canvas 개선 후에도 합성 30만 점 전체 보기의 그리기 중앙값은 74.9ms였고 50ms 이상의 긴 작업이 남았다. 사용자가 GPU 활용 가능성을 질문하고 성능 실험을 요청해, 계산을 다시 옮기기보다 표시 비용을 줄일 수 있는지 확인했다.

기존 Worker의 Float64 위상 계산과 원본 관측 배열은 유지한다. WebGL2는 결과를 표시할 때만 Float32로 변환하고 모든 관측점의 반복 위치를 그린다. 밝기는 초기 한 번, 위상은 재접기 결과가 바뀔 때 전송하며 확대·이동은 화면 범위만 변경한다. 점을 줄이는 샘플링이나 과학 계산의 GPU 전환은 포함하지 않는다. Canvas도 브라우저 내부에서 GPU를 사용할 수 있으므로 이 비교를 단순한 CPU 대 GPU 비교로 부르지 않는다.

### 렌더러 단독 실험에서 확인한 효과와 비용

먼저 React 화면을 제외하고 개선된 Canvas와 WebGL을 비교했다. Windows·Intel Arc/D3D11·Chromium 153 headless, 1024×280 CSS px·DPR 1에서 같은 Worker 결과를 사용했다. 아래는 첫 실험의 전체 보기 재접기 결과이며, 각 범위는 실행 순서를 뒤집은 두 라운드 중앙값의 범위(ms)다.

| 합성 관측점 | Canvas CPU 호출 | WebGL CPU 호출 | WebGL GPU 처리 |
| ----------- | --------------: | -------------: | -------------: |
| 100,000     |       29.1–29.4 |        0.3–0.4 |      1.67–1.73 |
| 300,000     |       69.2–72.6 |            0.7 |      5.52–6.81 |

30만 점의 긴 작업 수는 라운드별 Canvas 40/40회에서 WebGL 0/0회로 줄었다. 다만 CPU 호출 시간은 GPU 완료 시간이 아니며, 별도 GPU 타이머도 전체 업로드·합성·실제 화면 출력 시간을 포함하지 않는다. 이 결과를 앞의 Canvas 개선 수치와 이어 붙여 하나의 개선 배수로 계산하지 않는다.

초기 비용은 증가했다. 30만 점의 WebGL CPU 초기화는 31.2–43.5ms였고 Canvas는 0.1–0.7ms였다. 위상·밝기 GPU 버퍼만 2.4MB를 사용하며 원본 배열·프레임버퍼·드라이버 메모리는 이 값에 포함하지 않는다. 정상상태 그리기 개선만으로 최초 진입이나 전체 메모리까지 개선됐다고 판단하지 않았다.

### 실제 앱에서도 효과가 이어지는지 확인

다음으로 개발 화면에 선택형 WebGL과 자동 Canvas 전환을 연결했다. GPU 준비 중에는 Canvas로 최신 성공 결과를 보여주고, 모듈 로드 실패·WebGL 미지원·셰이더/자원 초기화 실패·context 손실 때 새 Canvas로 복구한다. 렌더러 전환으로 주기·확대 위치·숫자 조회·포커스를 초기화하지 않는다. 화면 해제와 렌더러 교체 때 GPU 자원을 정리하고, 반복 미세 조정에는 기존 버퍼를 재사용한다.

앱 비교에는 **배포용 React에 개발 GPU 선택 기능만 켠 별도 실험 빌드**를 사용했다. 일반 배포 빌드와 다르며 배포하면 안 되는 테스트 산출물이다. Intel Arc/D3D11·Chromium 153·1440×900·DPR 1에서 합성 API 응답을 넣고 실제 미세 조정 버튼을 16ms 타이머로 40회 조작했다. 아래 지연은 실행 순서를 뒤집은 두 라운드의 입력→DOM 중앙값 범위(ms)이며, 긴 작업은 라운드별 횟수다.

| 관측점 / 배율 | Canvas 입력→DOM | WebGL 입력→DOM | Canvas 긴 작업 | WebGL 긴 작업 |
| ------------- | --------------: | -------------: | -------------- | ------------- |
| 100,000 / ×1  |       33.6–37.1 |       8.5–10.9 | 0 / 0          | 0 / 0         |
| 300,000 / ×1  |       93.1–93.7 |      13.1–15.3 | 37 / 38        | 0 / 0         |
| 300,000 / ×32 |       25.1–25.2 |      15.4–15.9 | 0 / 0          | 0 / 0         |

30만 점 전체 보기의 타이머 간격 p95도 104.6–104.7ms에서 19.8–20.1ms로 줄었다. 반면 기존 17,281점 샘플의 ×32에서는 Canvas 7.8–10.1ms, WebGL 8.7–10.7ms로 일관된 이득이 없었다. 전체 여섯 조건과 재현 명령은 [앱 성능 비교 기록](phase-folding-gpu-experiment.md#앱-성능-비교와-재현)을 따른다.

입력→DOM은 마지막으로 관측한 입력부터 주기 DOM 변경까지이며 실제 픽셀 출력 완료 시각이 아니다. 긴 작업이 클릭 타이머를 늦추고 Worker가 중간 요청을 대체하므로, 30만 점 전체 보기의 실제 그리기 횟수도 Canvas 37/38회와 WebGL 19/26회로 달랐다. 모든 40건의 완료 지연이나 고정 60Hz 부하의 비교로 해석하지 않는다. 무조작 1초의 추가 그리기는 양쪽 모두 0회였으며 이 앱 비교에서는 React 커밋 수를 측정하지 않았다.

### 측정 과정에서 확인한 함정

Vite 개발 모드에서는 WebGL을 사용해도 10만 점에서 100ms 이상의 긴 작업이 남았다. React DevTools 계측 훅을 제거해도 반복됐으므로 훅만의 문제로 단정하지 않았다. 설치된 React 개발 코드에 변경 props의 깊은 비교와 User Timing 기록이 있는 것은 확인했지만, 각 원인이 차지하는 CPU 비중은 아직 프로파일링하지 않았다. 배포용 React 실험 결과와 개발 화면의 지연을 분리해 기록하고, 개발 모드의 원인 분석은 남은 과제로 유지한다.

브라우저 이름만으로 하드웨어 가속 여부를 판단할 수도 없었다. 강제 GPU 옵션 없는 기능 검사에서는 번들 Chromium이 SwiftShader, 설치 Chrome이 NVIDIA RTX 4070 Laptop GPU, Edge가 Intel Arc를 사용했다. 따라서 소프트웨어 렌더링의 기능 통과와 하드웨어 성능 측정을 구분했다.

### 정확성·복구 검증과 현재 결정

저장된 TOI-270·L 98-59·CM Draconis 관측 자료의 해시를 확인하고, 다중 Sector와 DPR 1/2에서 전체 보기·×32 경계의 예상 중심 픽셀 및 원본 값 보존을 검사했다. 표시 검사 전용 주기 3.125/3.126일을 사용했으므로 실제 공전 주기나 행성 검출의 검증은 아니다. 폭 641px·×32에서 위상 Float32 변환 오차는 최대 약 0.000306 CSS px였으며, 이는 모든 GPU 연산의 정확성이나 픽셀 단위 동등성을 증명하는 수치는 아니다.

빠른 연속 조정·위치 유지·숫자 조회·취소/재시도·실패 복구·리사이즈·DPR 2와 자원 정리를 검사했다. 최종 GPU 관련 11개 시나리오는 Chromium·Chrome·Edge에서 각각 통과했다. 렌더러 8회 왕복과 화면 이탈 때 버퍼 해제를 확인했지만, 이를 장시간 전체 메모리 누수가 없다는 증거로 확대하지 않는다. 단위 99개, 타입·일반 배포 빌드·개발 코드 제외 검사, 배포 동작 3개와 앱 성능 비교 3개도 통과했다. 실행 시점과 세부 범위는 [최종 검증 기록](phase-folding-gpu-experiment.md#최종-검증-기록)에 남긴다.

현재 결정은 **개발용 선택 기능을 유지하고 일반 배포의 기본값은 Worker·Canvas로 유지한다**는 것이다. 일반 배포에는 GPU 모듈·선택 UI를 포함하지 않는다. API·DB 테이블·과학 계산 명세는 변경하지 않았다. 기본 적용 전에는 다음을 추가로 확인한다.

- Firefox·Safari·저사양·모바일과 실제 브라우저 확대, 모니터 간 DPR 변화에서의 기능과 복구.
- 초기 모듈 로딩·셰이더 준비를 포함한 첫 표시, DPR 2 성능, 지원 기기별 지연 목표. Q08 기준 확정 전에는 성능 인수 완료로 취급하지 않는다.
- 10분 이상 사용 중 전체 JS/GPU 메모리·GC·전력 추세와 실제 기기의 자원 부족.
- 실제 API·서버 공통 수치 fixture, 세 항성의 실제 주기도와 연결한 전체 분석 흐름.
- 개발 모드의 긴 작업 원인, 디자인 통합 후 상태 표시·포커스·스크린리더 사용성.

## 후속 사용성 수정: 미세 조정 중 안내 깜빡임

사용자는 슬라이더를 계속 조정할 때 계산이 너무 짧아 취소를 누를 여유도 없는데, 상태 문구와 취소 버튼이 반복해서 나타나는 점을 지적했다. 앞의 상태 영역 높이 고정은 차트 위치 이동을 줄였지만 안내 내용의 깜빡임까지 해결한 것은 아니었다.

빠른 계산 중에는 마지막 완료 결과를 표시한다는 안내를 유지하고, 대기가 길어질 때만 진행 안내와 취소를 노출하도록 수정했다. 오류·재시도는 즉시 표시하며 실제 계산·최신 요청 처리·후속 입력 잠금은 지연하지 않는다. 타이머는 안내 컴포넌트 안에만 두고 연속 대기 중 입력마다 다시 예약하지 않는다. 현재 표시 지연과 정확한 동작은 [개발 안내](phase-folding.md#연속-미세-조정의-상태-표시)를 따른다.

이번 변경은 시각적 안정성을 위한 수정이다. 기존 성능 수치는 수정 전 기록이며, 새 응답시간 향상이나 사용자 만족도 개선을 측정했다고 주장하지 않는다. 디자인 통합 후 실제 드래그와 보조기술 사용성은 다시 확인한다.

## 포트폴리오에 옮길 때 사용할 요약 초안

> 주기 미세 조정 시 화면 지연을 Worker 계산·React 상태 갱신·Canvas 그리기로 나눠 측정했다. 무조작 시 반복 렌더링은 재현되지 않았지만, 상태 전환에 따른 차트 이동과 대량 점 그리기 병목을 확인했다. 상태 영역의 높이를 안정시키고 밀집 화면을 픽셀 버퍼 합성 방식으로 바꿔, 동일 로컬 환경의 합성 10만·30만 점 전체 보기에서 그리기 중앙값을 각각 240.7→28.0ms, 762.7→74.9ms로 줄였다.
>
> 남은 밀집 표시 비용은 원본 과학 계산을 유지한 WebGL 표시로 추가 실험했다. 배포용 React를 사용한 별도 앱 실험의 합성 30만 점 전체 보기에서 입력→DOM 중앙값은 Canvas 93.1–93.7ms에서 WebGL 13.1–15.3ms로 줄었고, 라운드별 긴 작업은 37/38회에서 0/0회로 줄었다. 개발 화면에 선택 기능과 자동 Canvas 복구를 연결했으며, 일반 배포는 Canvas를 유지한다. 이 결과는 단일 하드웨어·합성 응답의 측정으로, 실제 서비스 성능과 지원 기기·장시간 안정성 검증은 남아 있다.

참여 기록: 사용자는 목업의 문제 경험을 공유하고 GPU 활용 가능성을 질문했으며 성능 실험과 후속 개발·검증 방향을 승인했다. 코드 작성·계측·테스트 실행에는 Codex를 활용했다. 실제 포트폴리오 작성 시에는 본인이 맡은 문제 정의·설계 판단·검증 범위와 설명할 수 있는 코드 내용을 구체화한다.

그리기 시간 감소를 전체 서비스 속도 개선으로 표현하지 않는다. 합성 데이터·단일 환경·중앙값이라는 조건을 유지하고, 운영 사용자 수·트래픽·만족도 효과를 덧붙이지 않는다. 구현 버전은 이 문서를 추가한 커밋에서 추적하고, 후속 측정에는 해당 코드의 커밋 해시와 재현 조건을 함께 남긴다.
