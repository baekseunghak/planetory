# #190 개인 기록 상세 개발 안내

2026-09-20 기준 `S15P21C206-190`의 계약 확정 기록이다. 기준은 [탐사 API 8.1·8.2·8.3·5.2](../../backend/docs/exploration-api-spec.md)와 Jira A08-1의 완료 조건이다. 앞선 [#188 결과 해설](analysis-result.md) 위에 얹는다.

백엔드는 **이미 있다.** C14(`S15P21C206-148`)가 완료되어 develop에 들어와 있으므로, 이 작업은 개발용 응답이 아니라 **실제 응답으로 인수한다.**

## 이 티켓이 만드는 둘

| 무엇                                 | 지금 상태                                                                           |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| `/history/:historyId` 개인 기록 상세 | 라우트만 있고 화면이 없다                                                           |
| 공용 읽기 전용 그래프 렌더러         | [HistoryGraph.tsx](../src/features/history/HistoryGraph.tsx)에 **슬롯이 비어 있다** |

슬롯은 `App.tsx`의 `historyGraphRenderer`이며 기본값이 `null`이다. 커뮤니티의 `MaterialCards`가 이미 `SharedHistoryGraph`를 쓰고 있어 지금은 「공용 그래프 화면은 연결 준비 중입니다」가 뜬다. **이 티켓이 렌더러를 꽂으면 게시글 첨부 그래프도 함께 살아난다.**

와이어프레임에는 **개인 기록 상세 화면이 없다.** SC-01~11 어디에도 없고 SC-08은 마이페이지(하서진)다. 그래서 배치와 문구는 명세와 [#188 결과 화면](analysis-result.md)의 말을 따른다.

## 불변과 현재를 가른다

8.2가 한 응답 안에 **성격이 다른 두 묶음**을 담는다. 섞어 보여 주면 「그때 이랬다」와 「지금 이렇다」를 구분할 수 없다.

| 묶음                        | 필드                                                                            | 뜻                                                                    |
| --------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 불변(당시)                  | `original` · `serverDerived` · `match` · `judgment` · `achievement.result`      | 제출 당시 값이 정본이다. 다시 계산하지 않는다                         |
| 현재                        | `achievement.star` · `progress` · `publication` · `judgmentStatistics`          | 조회 시점에 구성한다                                                  |
| 저장값이되 현재 근거가 아님 | `newlyRecognized` · `unlockedStars` · `skyVersion` · `tutorial` · `nextActions` | 저장 응답에 남아 있을 뿐이다. **현재 행동 허가의 근거로 쓰지 않는다** |

`relabel`은 `{relabeledAt, newDisposition}`이며 「기록이 갱신됨」 표시에만 쓴다(GRD-06). 외부 라벨이 바뀌어도 당시 판정·성과는 그대로다.

`versions`의 `preprocess`·`pipeline`은 **null일 수 있다.** 143이 따로 보존하지 않은 값이므로 **현재 처리 버전으로 꾸며 채우지 않는다.**

기록은 불변이다(HIS-06, NFR-12). 수정·삭제 API가 없고 그래프는 이미지가 아니라 재현 파라미터로만 보관한다.

## 두 모드는 서로의 빈칸이다

`GET /api/v1/histories/{historyId}/graph?mode=CURRENT|SUBMITTED`. 생략은 `CURRENT`이고 허용값 밖은 400이다.

|                                            | `CURRENT`        | `SUBMITTED` |
| ------------------------------------------ | ---------------- | ----------- |
| `curve`                                    | 현재 판 곡선     | **null**    |
| `snapshot`                                 | **null**         | 150칸 배열  |
| `selection.currentPhaseStart/End`          | 현재 T 기준 환산 | **null**    |
| `selection.epochBtjd`·`durationHours`·주기 | 보존             | 보존        |

한쪽만 오는 것이 아니라 **한쪽이 오면 다른 쪽은 반드시 비어야 한다.** 둘 다 오거나 둘 다 없으면 어긋난 응답이다(develop의 `readHistoryGraph`가 이미 이 대조를 한다).

접기는 **`userPeriodDays`(원본 주기)로 한다.** 정정 주기는 참고 표시다.

## SUBMITTED를 현재 T로 재환산하지 않는다

당시 선택 창은 **제출 당시 T·원본 P 기준으로 저장된 값**이다.

- 위상 i = `-0.5 + (i + 0.5) / bins` — **칸의 중심**이다. 시작이 아니다.
- 표시할 때 `[-0.5, 0.5)`로 순환시키되 **경계를 넘는 창은 나누어 표시한다.**
- `reproduction.currentFoldReferenceTimeBtjd`는 **현재 판 메타데이터**다. SUBMITTED의 선택·모델 정렬에 쓰지 않는다.

현재 T로 옮기는 환산은 `CURRENT`에만 있다. 여기서 편의로 맞추면 당시 기록이 당시 기록이 아니게 된다.

**1.0을 넘는 것은 경계를 넘는 것이 아니다.** 8.2절 예시의 `0.995 ~ 1.005`는 옮기면 `-0.005 ~ 0.005`로 **이어진다.** 실제로 쪼개지는 것은 `±0.5`를 넘는 창(예: `0.4 ~ 0.6`)이고, 그때 한 구간으로 이으면 **고르지 않은 가운데가 전부 칠해진다.** 검사가 두 경우를 따로 본다.

이미 `[-0.5, 0.5)` 안인 값은 나머지 연산을 태우지 않는다. 태우면 값이 미세하게 달라져 저장된 좌표와 어긋난다.

## 버전이 없으면 정렬을 보장하지 않는다

배열이 있는데 `snapshotVersion`이 null이면 **저장 배열을 그대로 그리되** 「스냅샷 버전 정보가 없어 선택 영역과의 정렬을 보장할 수 없습니다」를 표시한다.

- `folded-mad-v0`·`v1` **어느 쪽으로도 간주하지 않는다.** 값이 없다고 최신으로 추정하지 않는다.
- 배열을 **이동·보정하지 않는다.** 정밀한 선택·모델 정렬을 보장하는 표시도 하지 않는다.
- `CURRENT`에도 저장 버전이 전달되지만 **현재 곡선의 렌더링 기준으로 쓰지 않는다.**

## 같은 값이 두 곳에서 다른 뜻이다

`fallbackReason: "RETIRED_CANDIDATE"`가 모드에 따라 다른 말을 한다. **한 문구로 뭉치면 거짓이 된다.**

| 모드        | 뜻                                                                            | 화면의 말                                                 |
| ----------- | ----------------------------------------------------------------------------- | --------------------------------------------------------- |
| `CURRENT`   | 은퇴 후보가 있어 그 조합을 재현하지 못해 **원본으로 대체했다**                | 「원본 곡선으로 대체됨」                                  |
| `SUBMITTED` | 현재 판에서 당시 조합을 재현할 수 없다는 **참고값**이다. 당시 배열은 멀쩡하다 | 「현재 데이터에서는 당시 잔차 조합을 재현할 수 없습니다」 |

명세가 「SUBMITTED 화면의 "원본으로 대체됨" 안내에는 사용하지 않는다」고 못박았다.

`RESIDUAL_NOT_AVAILABLE`은 공개 CURRENT에서 캐시 잔차가 없을 때다. 이때 원본의 `residual`이 `COMPLETED`·jobId null로 오는데 **잔차 작업이 완료됐다는 뜻이 아니다.**

## 없음이 세 가지다

`curve.residual`을 한 가지로 읽으면 안 된다.

| 응답                                      | 뜻                                                          |
| ----------------------------------------- | ----------------------------------------------------------- |
| `segments: null`                          | 잔차 단계가 캐시에 없다. **200을 유지한다**                 |
| `residual: {status: null, jobId: null}`   | 결과도 작업도 없다. 상태가 아니라 **작업 생성 전 표현**이다 |
| `residual: {status: "...", jobId: "..."}` | 실제 작업이 있다                                            |

**히스토리 조회는 작업을 자동으로 만들지 않는다.** 매칭 실패 기록의 `snapshot: null`도 409가 아니라 200이다.

## 503 셋을 구분한다

| 무엇                             | 언제                                                                               | 화면                                                                                                  |
| -------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `DEPENDENCY_UNAVAILABLE`         | 최초 응답(`response_snapshot`)이 없는 기록의 **상세 전체**                         | 목록의 `detailAvailable=false`로 미리 구분한다. 「최초 응답이 없어 상세를 제공할 수 없는 기록입니다」 |
| `GRAPH_TEMPORARILY_UNAVAILABLE`  | CURRENT 조회 중 판이 `archived`가 되어 서버가 1회 재시도했는데도 한 판으로 못 맞춤 | 다시 시도할 수 있다고 안내한다                                                                        |
| `DEPENDENCY_UNAVAILABLE`(그래프) | 현재 판이 아예 없거나 같은 판 필수 배열이 손상됨                                   | 저장 스냅샷을 없애거나 재계산하지 않는다                                                              |

**이 셋을 정상 `snapshot: null`·잔차 미계산과 합치지 않는다.** 없는 것과 못 읽는 것은 다르다.

읽기 조회이므로 판 교체를 `BUNDLE_CHANGED`로 거절하지 않는다. [#187](analysis-submission.md)의 제출 경로와 다른 점이다.

## 같은 본문인데 열거형이 넓다

8.2가 「6.4절 `submissionResult` 본문 전체」라고 적지만 **공개 상태만은 집합이 다르다.**

| 절              | `publication.state`            | 왜                                              |
| --------------- | ------------------------------ | ----------------------------------------------- |
| 6.4 (제출 직후) | `UNPUBLISHED` · `NOT_ELIGIBLE` | 방금 낸 제출이 이미 공개돼 있을 수 없다         |
| 8.2 (기록 상세) | + `PUBLISHED` · `HIDDEN`       | 시간이 지났다. 공개했거나 운영이 숨겼을 수 있다 |

**6.4 파서를 넓히지 않는다.** 넓히면 제출 응답이 「공개됨」이라고 말해도 통과한다. 대신 `readResultExplanation`이 **읽는 쪽에서 집합을 받는다.** 기본값은 6.4의 둘이고 기록 상세만 넷을 넘긴다. 이 파서의 일이 어긋난 응답을 거절하는 것이므로, 한 곳을 느슨하게 만들어 두 곳을 만족시키지 않는다.

## 남의 파서를 감싼다

`readHistoryGraph`·`SharedHistoryGraph`는 **하서진 님이 `S15P21C206-213`에서 만든 것**이다(`features/history/` 안에 있지만 작성자가 다르다). 고치지 않고 **감싼다.**

- 이미 `export`돼 있고 반환 타입이 `Record<string, unknown> & {...}`이라 **추가 필드가 그대로 넘어온다.** 우리 모듈이 그것을 부른 뒤 `selection` 내부·`snapshotVersion`·`fallbackReason`만 더 읽는다.
- 실패는 `invalidMaterial()`이 `ApiError(0, "INVALID_RESPONSE")`를 던진다. **우리 오류 처리와 같은 타입**이라 그대로 흐른다.
- **복제하지 않는다.** 이 파서의 일이 「어긋난 응답을 거절하는 것」이라 두 벌이 되면 계약이 둘이 된다. 감싸면 213이 파서를 바꿨을 때 우리 쪽이 시끄럽게 깨지고, 그게 원하는 동작이다.

213과 합칠지는 두 화면이 다 붙은 뒤에 정한다.

## 두 모드를 한 좌표계로 모은다

당시 배열은 `[-0.5, 0.5)`인데 현재 곡선을 접으면 `foldTimes`가 `[0, 1)`을 준다. **그대로 두면 같은 위상이 같은 화면에서 다른 자리에 찍힌다.** 현재 쪽을 옮겨 맞춘다(`0.5` 이상은 `-1`).

접기는 워커 없이 한다. `foldTimes`가 순수 함수라 읽기 전용 화면에서는 동기로 충분하고, 분석 화면의 차트는 조작·뷰 상태·워커를 함께 들고 있어 기록 화면에 맞지 않는다.

**그릴 것이 없으면 왜 없는지 말한다.** 빈 그래프를 「값이 0」으로 보이게 두지 않는다.

| 없음          | 언제                                                    |
| ------------- | ------------------------------------------------------- |
| `no-period`   | 특수 제출이라 고른 주기가 없다                          |
| `no-curve`    | 이 단계의 곡선이 아직 계산되지 않았다(`segments: null`) |
| `no-snapshot` | 매칭 실패 기록이라 당시 배열이 없다                     |

값이 없는 칸은 **건너뛴다.** 0으로 바꾸면 밝기가 0인 관측이 된다.

공용 슬롯에 꽂는 어댑터는 **선택 창을 그리지 않는다.** 창은 개인 상세의 `original` 또는 공개 내용에서 오는데 213의 props에는 없다. 개인 상세 화면만 창을 함께 넘긴다.

## 자리표시자를 대신한다

`dev/FixturePages.tsx`의 「분석 기록 연결 자리」는 **이 화면을 기다리던 자리표시자**였다(하서진, 201·215). 실제 화면을 `historyDetail`에 꽂으면 그 자리가 사라지므로, 거기 걸려 있던 **W03 왕복 문맥 검사**(`foundation.spec.ts`)가 함께 깨진다.

그 검사가 지키는 것은 문구가 아니라 경로다 — `ticId`·`returnTo`를 싣고 들어와 새로고침 뒤에도 살아 있고, 「분석으로 돌아가기」로 분석 화면에 복귀하고, 다시 「← 이전 화면」으로 지도까지 간다.

**그래서 화면이 그 계약을 그대로 만족하게 했다.** 남의 검사를 고치지 않았다.

- 기록 번호를 `분석 기록 {historyId}`로 적는다.
- `returnTo`로 「분석으로 돌아가기」를 낸다. 목적지는 **주소가 들고 온다** — 기록으로 들어오는 길이 분석·지도·게시글 셋이라 화면이 정할 수 없다.
- **읽을 수 없는 기록에도 돌아가는 길을 남긴다.** 막다른 길에서 나갈 수 있어야 한다.

## 이 티켓이 맡지 않는 것

- **History 목록**(`S15P21C206-196`·A13)과 **공개 History 권한·대체 표시**(`S15P21C206-191`·A08-2). 191은 이 티켓이 만든 컴포넌트를 소비한다
- **SC-11 공개 검토 화면**(`S15P21C206-195`)
- 별도 공개용 그래프 배열 형식. 같은 공용 DTO를 쓴다
- 이전 판 전체 보존

## 미결

- **6.6절(`GET /submissions/{id}`)도 `PUBLISHED`를 주는가.** 명세는 8.2에만 넓은 집합을 적어 두었는데, 6.6도 「조회 시점」 값이라 공개된 제출을 읽으면 같은 문제가 난다. 지금은 명세 문구 그대로 6.6을 좁은 집합으로 두었다. C02 확인이 필요하다.
- **`detailAvailable=false` 기록으로 들어왔을 때.** 목록이 막는 것이 정상 경로지만 주소를 직접 치면 상세 503이 온다. 안내만 하고 재시도를 권하지 않는다.
