# 위상 곡선 Canvas·WebGL 성능 실험

2026-09-16, `S15P21C206-184`의 **실험 결과**다. [기존 성능 개선](phase-folding-performance.md) 후에도 남은 밀집 그래프의 메인 스레드 비용을 줄일 수 있는지 확인한다. 기능 계약은 [위상 접기 개발 안내](phase-folding.md)를 따른다. 첫 실험 뒤 개발 환경의 실제 분석 화면에 선택형 GPU 표시와 자동 Canvas 전환을 연결했다. 일반 배포의 기본값은 기존 Worker·Canvas이며 GPU 모듈·개발용 선택 UI는 배포에서 제외한다. 명세·API·DB 변경과 GPU 계산 도입은 포함하지 않는다.

## 비교 대상과 입력

- Canvas: 현재 앱의 `drawFoldedCurve`를 그대로 호출한다. 가시 반복점 50,000개 초과 시 픽셀 버퍼 합성, 그 이하는 기존 원 그리기를 사용한다. 이전의 느린 점별 그리기와 비교한 결과가 아니다. Canvas 내부에서도 브라우저가 GPU를 사용할 수 있다.
- WebGL2: 같은 Worker의 Float64 위상 결과를 표시용 Float32 배열로 변환·전송하고, 인스턴스 그리기로 모든 관측점의 반복 위치를 처리한다. 정규화 밝기는 초기 한 번, 위상은 재접기 때 전송한다. 이동·확대는 화면 범위 uniform만 변경한다. 샘플링·binning은 하지 않는다.
- 입력: 기존 합성 밝기 배열을 반복하고 관측 시각을 120일에 배치한 100,000/300,000점, Sector 1개다. 같은 주기·좌표 범위·1024×280 CSS px·DPR 1로 비교한다. 실제 서비스 자료의 분포나 최대 크기를 대표하지 않는다.
- 전체 보기 재접기, ×32 재접기, ×32 이동, ×1→2→4→8→16→32 확대 순환을 각각 40회 실행한다. 같은 시나리오에서 Canvas/WebGL 순서를 뒤집는 2라운드로 측정한다. 각 실행 전 4회 그리기로 준비한다.

## 재현 방법과 환경

`apps/frontend`에서 기존 Playwright Chromium 설치를 사용한다. 별도 의존성 설치는 필요하지 않다.

```powershell
npm run test:gpu
```

[전용 설정](../playwright.gpu.config.ts)은 [실험 HTML](../tests/performance/gpu/index.html)만 빌드해 58265 포트에서 실행한다. 산출물은 `test-results/gpu-build`, JSON 요약과 비교 이미지는 `test-results/gpu-results`에 저장한다. 둘 다 Git 제외 생성물이다. 콘솔의 `GPU_PERF`로도 결과를 확인한다. 다른 성능 검사와 동시에 실행하지 않는다.

Windows·Intel Core Ultra 9 185H·논리 CPU 22개·64GiB·Chromium 153.0.8010.12 headless, 브라우저 viewport 1200×900, CPU 제한 없음이다. `--use-angle=d3d11` 옵션으로 실행했고 두 방식에 동일하게 적용했다. GPU 식별값은 `ANGLE (Intel, Intel(R) Arc(TM) Graphics (0x00007D55) Direct3D11 vs_5_0 ps_5_0, D3D11)`이며 소프트웨어 GPU가 아님을 확인했다. 일반 브라우저의 기본 설정이나 다른 OS·GPU를 검증한 결과는 아니다. 다른 환경에서는 옵션을 조정하고 실제 renderer를 다시 확인해야 한다.

## 측정 지표를 읽는 방법

- `cpuSubmitMs`: 메인 스레드에서 그리기 함수 호출이 반환될 때까지다. WebGL은 Float64→Float32 변환·버퍼 전송 API 호출을 포함하며 GPU 완료 시간은 아니다.
- `gpuDrawMs`: `EXT_disjoint_timer_query_webgl2`로 측정한 격자·점 GPU 명령 구간이다. 위상 버퍼 업로드 호출 뒤에 시작하므로 전체 업로드·합성·화면 출력 지연이 아니다. 확장 미지원이나 disjoint 상태는 미측정으로 다루며 0ms로 바꾸지 않는다.
- `workerRoundTripMs`: 기존 FoldClient의 프레임 예약·Worker 전송·계산·반환을 포함한다. 이전 문서의 Worker 내부 계산 시간과 직접 비교하지 않는다.
- `nextFrameMs`: 요청 시작부터 그리기 후 두 번의 requestAnimationFrame까지다. 화면 갱신 기회를 기다리는 보조 지표이며 실제 픽셀 출력 완료·사용자 입력 지연·FPS가 아니다. 재접기는 프레임 예약 때문에 약 50ms, 이동/확대는 약 33ms의 대기 바닥이 생긴다.
- `timerGapMs`: 16ms 타이머의 실제 간격이다. `longTasksMs`는 측정 루프 중 메인 스레드의 50ms 이상 작업이다. GPU 지연이나 초기 진입 비용 전체를 대신하지 않는다.

React 화면을 통과하지 않는 렌더러 비교다. 매 요청의 결과를 기다리므로 입력 폭주·취소·최신 요청 교체·React 상태 갱신은 이번 비교의 대상이 아니다. 이전 앱 통합 측정과 숫자를 섞지 않는다.

10만 점 전체 재접기의 nextFrame 중앙값은 양쪽 모두 약 50ms였고 ×32 재접기·이동도 같은 프레임 대기 바닥에 도달했다. 따라서 그리기 호출 시간이 크게 줄어도 모든 조작의 화면 갱신 시간이 같은 비율로 줄었다고 해석할 수 없다. 30만 점 확대 순환의 GPU p95는 8.96~14.77ms로 변동했으므로 GPU 시간을 고정 비용으로 가정하지 않는다.

현재 환경에서 **밀집 화면의 GPU 표시를 후속 적용 후보로 검토할 근거는 확보했다.** 적용 결정을 위해서는 아래 통합 검증이 남아 있다. GPU 테스트 3개(좌표·복구 1개, 규모별 비교 2개)가 통과했고, 총 32개 측정 구간의 각 40회, 1,280회 조작을 비교했다. GPU의 16개 구간 모두 40개의 유효 타이머 결과를 수집했다. 속도 합격 기준을 둔 테스트는 아니다.

타입 검사·일반 배포 빌드·개발 fixture 제외 검사가 통과했고, 일반 배포 JS/HTML에 실험 식별자가 없는지도 확인했다. 기존 성능 테스트는 `testMatch`를 지정해 이 실험을 자동으로 함께 실행하지 않도록 분리했다. 첫 렌더러 실험 당시에는 기존 앱의 단위·브라우저 전체 검사를 재실행하지 않았다. 후속 앱 연결의 검증은 아래에 별도로 기록한다.

## 정확성·복구 확인과 남은 비용

- DPR 1·2 각각 희소한 4개 점을 전체 보기·×32 양끝 경계에서 반복 표시하여 예상 중심 픽셀 12곳을 확인했다. GPU context loss를 발생시켜 그리기 실패 감지 후 **새 Canvas를 만들어 명시적으로 다시 그리는 경로**도 검사했다. 첫 실험 당시 자동 fallback은 없었다. 후속 개발 연결에서 자동 Canvas 전환을 추가했으며 GPU context 자체의 자동 복원은 사용하지 않는다.
- 10만·30만 점 전체 보기의 Canvas/WebGL 이미지를 비교했다. 점 분포는 유지된다. GPU 원 가장자리 피복률과 브라우저의 내장 원 안티앨리어싱이 완전히 같다는 픽셀 단위 동등성 검증은 아니다.
- 측정 입력의 위상을 Float32로 변환할 때 생긴 오차는 ×32·폭 1024px 환산 최대 약 0.00049px였다. 원본 시각·밝기·Float64 Worker 결과는 바꾸지 않는다. 이 수치는 위상 변환 오차만의 계산값이며 모든 GPU 연산·모든 입력의 과학적 정확성 증명은 아니다.
- GPU의 위상·밝기 버퍼 합계는 10만 점 0.8MB, 30만 점 2.4MB다. CPU 원본/변환 배열·프레임버퍼·드라이버 메모리는 제외한 크기다. 전체 메모리·GC·전력·장시간 누수는 측정하지 않았다.
- 초기화와 첫 표시 비용은 정상상태 그리기에서 분리한다. 셰이더 준비·GPU context 생성·밝기 변환/전송이 추가되며 `setupMs`의 WebGL CPU 초기화 비용은 10만 점 17.7–27.3ms, 30만 점 31.2–43.5ms였다. Canvas는 0.1–0.7ms였다. 이는 GPU 준비 완료나 최초 화면 출력까지의 총시간은 아니다.

일반 배포에 적용하기 전 남은 검증은 아래 진행표를 따른다. 이번 결과만으로 모든 그래프를 GPU로 교체하거나 60fps 달성을 선언하지 않는다.

## 후속 개발: 실제 분석 화면 연결

2026-09-16, 사용자 요청에 따라 개발용 선택 옵션을 연결했다. 현재 상태는 **개발용 구현 완료, 일반 배포 기본 적용 보류**다. 백엔드 응답·DB·명세의 과학 계산은 변경하지 않는다.

### 직접 확인하는 방법

기존 개발 서버의 주기도 정상 샘플에서 봉우리를 선택하면 `개발용 접기 렌더러` 선택 상자가 나타난다. 기본은 Canvas이고 WebGL을 선택하면 같은 주기·확대 위치에서 렌더러만 바뀐다. 처음부터 선택하려면 개발 주소에 `foldRenderer=webgl`을 붙인다. 예: `/analysis/259377024?returnTo=%2Fsky&foldRenderer=webgl`. 선택 상자의 변경은 현재 차트에서만 유지하며 URL을 자동 변경하지 않는다.

GPU 준비 중에는 Canvas로 최신 성공 결과를 표시한다. 모듈 로드 실패, WebGL 미지원, 셰이더 연결/자원 초기화 실패, GPU context 손실은 새 Canvas로 전환한다. 전환 자체는 주기·보기 범위·숫자 조회·그래프 포커스를 초기화하지 않는다. 계산 실패·취소 복구는 기존 Worker/session이 계속 담당한다.

같은 차트에서 실패 뒤 매 프레임 GPU를 재시도하지 않는다. Canvas를 선택한 뒤 WebGL을 다시 선택하면 새 GPU context로 시도한다. 개발 모듈 로드 자체가 실패해 캐시된 경우에는 페이지를 다시 불러와야 한다. 이전 GPU context의 손실 이벤트는 정리된 뒤 새 Canvas 상태를 덮지 않는다.

### 구현 경계

- [Canvas 표시](../src/features/analysis/FoldCanvasSurface.tsx)를 기존 차트에서 분리해 기본 표시와 fallback에서 재사용한다. 기본 Canvas도 주기 변경마다 다시 만들지 않는다.
- [GPU 표시 연결](../dev/FoldGpuSurface.tsx)은 `import.meta.env.DEV` 아래에서 지연 로드한다. 모듈 로드 실패도 Canvas로 복구한다. 크기·DPR·주기·보기 변경은 기존 GPU 자원을 재사용한다.
- [GPU 렌더러](../dev/fold-webgl-renderer.ts)는 원본 Float64 배열을 변경하지 않고 표시용 배열만 전송한다. 변하지 않는 밝기는 초기화 때만, 위상은 결과 변경 때만 전송한다. 확대·이동은 uniform만 바꾼다. GPU 계측·readPixels는 앱 동작에 넣지 않는다.
- 화면 해제·자료 교체·렌더러 변경 때 버퍼·셰이더·프로그램·context를 해제한다. React StrictMode의 effect 재실행에서는 새 canvas를 만들어 폐기된 context를 재사용하지 않는다.
- `npm run build`의 배포 제외 검사에 개발 선택 UI·URL 옵션·GPU 셰이더 오류 식별자를 추가했다. 개발용 GPU 모듈이 일반 배포에 포함되면 빌드를 실패시킨다.

표의 통과는 해당 시나리오 범위만 뜻한다. 브라우저 밖 GPU 메모리 전체를 버퍼 개수로 대신하지 않는다. 메모리 안정성과 장시간 사용은 다음 검증에서 실제로 측정한다.

### 관측 자료 검증

저장된 관측 export의 manifest SHA-256을 확인한 후 기존 decode/buildFoldData를 사용했다. 과학적으로 추정한 주기 대신 표시 검사 전용 주기 3.125/3.126일을 사용했으므로 실제 행성의 주기·검출을 검증한 것이 아니다. 각 주기에서 전체 보기·×32 위상 0/1 주변과 DPR 1/2의 예상 중심 픽셀을 확인했다.

| 항성        | 유효점 | Sector | 예상 중심 픽셀 확인 수 |
| ----------- | -----: | ------ | ---------------------: |
| TOI-270     |  9,016 | 3·4·5  |                 76,412 |
| L 98-59     |  9,627 | 2·5·8  |                 81,752 |
| CM Draconis |  2,727 | 16     |                 23,288 |

원본 점·Float64 위상이 그리기 후 동일했고, 위상 Float32 변환 오차는 폭 641px·×32 환산 최대 약 0.000306 CSS px였다. 점이 밀집해 겹칠 수 있으므로 이 검사는 모든 점이 각각 독립적으로 보인다는 증명이나 완전한 픽셀 동등성 검사는 아니다. 로컬 export가 없는 환경의 해당 3개 검사는 명시적으로 skip하며 성공으로 세지 않는다.

### 앱 성능 비교와 재현

`npm run test:gpu:app`은 58266 포트의 **배포용 React + 개발 GPU 선택 기능을 켠 별도 실험 빌드**의 실제 화면에서 두 렌더러를 비교한다. 17,281/100,000/300,000점·×1/×32마다 버튼 클릭을 16ms 타이머 간격으로 40회 보낸다. 각 결과를 기다리지 않으므로 중간 요청이 대체될 수 있다. 동일 크기에서 실행 순서를 뒤집어 두 라운드를 기록한다.

`inputToDOM`은 마지막으로 관측한 입력에서 주기 DOM 변경까지이며 모든 중간 입력의 지연이나 실제 GPU 출력 완료 시각이 아니다. 타이머 간격·긴 작업·최종 선택/결과 일치·차트 위치·무조작 그리기도 확인한다. 이 비교에서는 React DevTools 계측 훅을 설치하지 않으며 커밋 수는 측정하지 않는다. 기존 배포 빌드 측정이나 분리 렌더러 수치와 직접 합치지 않는다. 결과 JSON은 `test-results/gpu-app`에 저장한다. 기본 기능 검사의 SwiftShader 결과와 하드웨어 비교 결과를 구분한다.

[전용 빌드 설정](../tests/gpu-app/vite.config.ts)은 React의 production 코드를 사용하면서 GPU 선택을 위해 테스트 빌드에서만 DEV 조건을 켠다. 결과는 `test-results/gpu-app-build`에 만들고 API는 Playwright의 합성 응답으로 대체한다. 이 빌드는 배포하면 안 된다. 일반 `npm run build`의 GPU 제외 정책은 유지한다.

측정 중 Vite 개발 모드에서는 10만 점의 WebGL에서도 100ms 이상 긴 작업이 남았다. React DevTools 계측 훅을 빼도 반복돼 훅만의 문제로 단정하지 않는다. 현재 설치된 React 개발 코드에는 변경 props의 깊은 비교와 User Timing 기록이 있으며 production 코드와 비용이 다르다. 원인별 CPU 비중은 별도 프로파일링 과제다. 이 개발 모드 결과를 숨겨 최종 효과로 대체하지 않고, 배포용 React 실험과 구분한다. 개발 화면에서 대량 입력이 여전히 느리면 이 차이를 먼저 재현한다.

실행 환경은 앞선 Intel Arc·D3D11·Chromium 153이고 앱 viewport는 1440×900·DPR 1이다. 3개 규모 비교가 통과했다. 아래 지연은 두 라운드 중앙값의 범위(ms), 긴 작업은 라운드별 횟수다.

| 관측점 / 배율 | Canvas 입력→DOM | WebGL 입력→DOM | Canvas 긴 작업 | WebGL 긴 작업 |
| ------------- | --------------: | -------------: | -------------- | ------------- |
| 17,281 / ×1   |       15.2–16.6 |        9.6–9.8 | 0 / 0          | 0 / 0         |
| 17,281 / ×32  |        7.8–10.1 |       8.7–10.7 | 0 / 0          | 0 / 0         |
| 100,000 / ×1  |       33.6–37.1 |       8.5–10.9 | 0 / 0          | 0 / 0         |
| 100,000 / ×32 |       12.2–12.7 |        8.9–9.2 | 0 / 0          | 0 / 0         |
| 300,000 / ×1  |       93.1–93.7 |      13.1–15.3 | 37 / 38        | 0 / 0         |
| 300,000 / ×32 |       25.1–25.2 |      15.4–15.9 | 0 / 0          | 0 / 0         |

30만 점 전체 보기의 타이머 p95는 Canvas 약 104.6–104.7ms, WebGL 19.8–20.1ms였다. 이 시나리오의 실제 그리기 수는 Canvas 37/38회, WebGL 19/26회로 달랐다. 긴 작업으로 클릭 타이머가 지연되고 Worker의 최신 요청 정책이 중간 요청을 대체하므로, 고정된 60Hz 입력이나 모든 40건의 완료 지연 비교로 해석하지 않는다. 무조작 1초의 추가 그리기는 두 렌더러 모두 0회였다.

이 결과는 앱 연결의 성능 근거를 추가하지만 초기 모듈 로딩·셰이더 준비·GPU 출력 완료·실제 API·저사양 기기의 성능 인수를 대신하지 않는다.

### 최종 검증 기록

- `npm test`: 단위 99개 통과.
- 기존 기능을 포함한 Chromium 전체 실행 67개 통과 후, 모듈 실패·앱 DPR 2 시나리오를 추가했다. 최종 GPU 검사 11개를 Chromium·설치된 Chrome·Edge에서 각각 실행해 **33개 모두 통과**했다. 겹치는 검사를 합산해 별도 테스트 수로 주장하지 않는다.
- 강제 GPU 옵션이 없는 headless 실행에서 renderer는 번들 Chromium=SwiftShader, 설치 Chrome=NVIDIA GeForce RTX 4070 Laptop GPU/D3D11, Edge=Intel Arc/D3D11이었다. 소프트웨어 결과는 기능 검사로만 사용한다. 이 33개는 성능 인수 시험이 아니다.
- `npm run build`와 `npm run test:production`: 타입·일반 배포 빌드·개발 코드 제외 검사와 배포 동작 3개 통과.
- `npm run test:gpu:app`: 하드웨어를 확인한 앱 비교 3개 통과. 재현 조건은 위 기록을 따른다.
- 브라우저 생성물 경로를 `test-results/browser`로 분리해 일반 브라우저 검사 시작 시 다른 실험 결과 디렉터리를 지우지 않도록 했다.
- web-design-guidelines로 `FoldedCurveChart.tsx`, `folded-curve.css`, 두 표시 컴포넌트의 선택 이름·키보드·상태 알림·포커스 유지·기본 반응형을 검토했다. 명시적 select 색상·focus-visible·name과 로딩 말줄임표를 반영했다. Chrome DPR 2 화면 이미지도 확인했다. 이 변경 범위의 미해결 정적 지적은 없으며 실제 스크린리더 검증은 남아 있다.

`npm run test:gpu`도 공유 렌더러로 다시 실행해 좌표·복구와 두 규모의 비교 3개가 통과했다. GPU 16개 구간 모두 40개의 타이머 표본을 다시 수집했다. 앞의 분리 실험 표는 최초 측정값으로 유지하며 재실행 JSON은 생성물 디렉터리에 남긴다. 변경 파일 포맷·문서 상대 링크·git diff --check도 통과했다.

## 회고·포트폴리오에 남길 판단

Worker로 계산을 분리한 뒤에도 메인 스레드 그리기는 병목으로 남을 수 있다. GPU 실험에서는 과학 계산을 그대로 유지하고 표시만 분리했으며, CPU 호출 시간·GPU 처리 시간·긴 작업·타이머 지연을 함께 확인했다. 성능 개선 범위를 설명할 때는 실제 앱에 반영한 Canvas 개선과 이 WebGL 프로토타입을 구분한다. 사용자는 GPU 가능성을 질문하고 실험을 요청했으며 구현·측정에는 Codex를 활용했다.
