# #191 공개 History 그래프 — 범위와 현재 상태

`S15P21C206-191`(A08-2)의 계약과 **어디까지 서 있는지**를 적는다. 기준은 [탐사 API 8.3·8.5·8.5.1](../../backend/docs/exploration-api-spec.md)과 [서비스 API 7.1·7.2](../../backend/docs/service-api-spec.md), Jira 본문의 완료 조건이다.

곡선 형식의 정본은 **탐사 API**다. 서비스 API 7.2가 「곡선 형식은 탐사 API 명세에서 한 번만 정의하고 이 절은 그것을 참조한다」고 못박았다.

## 글·댓글 첨부 경로는 서 있고, 공개 분석 경로는 비어 있다

191의 포함 범위는 **공개 그래프 어댑터와 대체 표시**다. 화면 자체는 213(글·댓글 첨부)이 만들고, `app/paths.ts`가 그 경로의 소유를 **「하서진 · 그래프는 백지웅」**으로 나눈다.

착수 시점에는 그 그래프 자리가 비어 있었다. 213이 `HistoryGraphRenderer` 슬롯을 두고 렌더러가 없으면 「공용 그래프 화면은 연결 준비 중입니다」를 띄웠고, [#190](analysis-history.md)이 `main.tsx`에서 `SharedHistoryCurve`로 그 슬롯을 채웠다. 남은 것은 **표시가 사실과 맞는지**였고, 그 수정은 213 후속 MR이 가져갔다.

**글·댓글 첨부 경로의 연결과 대체 안내는 끝났다. 공개 분석 진입 경로는 아직 연결되지 않았다.** 191의 포함 범위 첫 줄이 「공용 읽기 전용 그래프를 **공개 첨부·공개 분석** 진입 어댑터에 연결한다」이고, 완료 조건의 두 계정 검증도 **두 경로 모두**를 요구한다. 아래 표를 두 경로로 나눈 이유다.

### 공개 첨부(글·댓글) — 서 있다

| 포함 범위                                        | 어디에                                                           |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| 공용 읽기 전용 그래프를 첨부 진입 어댑터에 연결  | `main.tsx`의 `historyGraphRenderer`([#190](analysis-history.md)) |
| 캐시 잔차·미계산·원본 대체·SUBMITTED 스냅샷 구분 | `MaterialCards.fallbackMessage`(213)                             |
| 결과·작업 없으면 미계산 안내, 폴링 안 함         | 213이 폴링·진행 중 안내·재확인 버튼 제거                         |
| 원본을 잔차로 표시하지 않음                      | `curveStep === 0` 분기(213)                                      |
| SUBMITTED의 `curve:null`·`snapshot` 규칙 유지    | 213, 모드별 분기                                                 |
| 숨김·취소·삭제·계정 전환 뒤 재노출 방지          | `useReadModel`(`S15P21C206-209`)                                 |

화면 회귀는 `tests/materials/materials.spec.ts`에 있다 — 사유별 안내, 스냅샷 없는 은퇴 후보, `jobId` 거절과 폴링 부재, 권한 철회 뒤 캐시·직접 링크.

### 공개 분석(`/public-analyses/:analysisId`) — 비어 있다

| 포함 범위                                  | 상태                                                             |
| ------------------------------------------ | ---------------------------------------------------------------- |
| 공용 그래프를 공개 분석 진입 어댑터에 연결 | **미연결.** 공개 분석 조회 응답을 공용 그래프에 잇는 코드가 없다 |
| 그 경로의 대체 안내·미계산·`jobId` 거절    | **미구현.** 어댑터가 없어 소비 경계 자체가 없다                  |
| 두 계정 실제 경로 인수                     | **미수행**                                                       |

라우트(`app/paths.ts`의 `publicAnalysis`, owner 백지웅)와 첨부 카드의 링크만 있고 `main.tsx`의 `pages`에 페이지가 등록돼 있지 않다.

**상세 화면 전체의 담당과, 191에 적힌 공개 분석 진입 연결은 서로 다른 문제다.** 앞은 협의 대상이고 뒤는 191의 포함 범위다. `S15P21C206-195`는 오히려 「최종 실제 연동: … **공개 부모 그래프는 A08-2/W14에서 별도 구현·인수한다**」로 이쪽에 되민다. `S15P21C206-193`에도 이 화면을 인수한다는 명시가 없다.

## 확정된 사실

착수 문서의 첫 판은 남은 일을 잘못 짚었다. 명세와 구현을 다시 읽어 확인한 것을 적는다. **틀린 전제 위에 계획을 세우면 없는 문제를 고치게 된다.**

### 첨부는 8.5 공개 투영이다

서비스 API 7.2가 명시한다.

> 부모 응답 외형은 `parentType`, `parentId`와 **탐사 8.5 공개 투영**을 사용한다. … `viewState`, `answerViewed`, 요청 식별자·최초 응답·성과 결과 등 개인 전용 필드는 제외한다.

같은 절이 「작성자와 History 소유자 일치」를 매 조회와 반환 직전에 검사하고 「권한 철회·숨김·삭제·첨부 해제는 **작성자에게도 404**」라고 한다. **본인이 봐도 공개 투영이다.** 「첨부가 어느 티켓 것이냐」는 합의할 일이 아니었다.

### 소유자 전용 필드는 구조적으로 샐 수 없다

`HistoryViews.PublicHistory`는 `Map`이 아니라 **필드가 고정된 Java `record`**이고 그 목록이 8.5 열거와 일치한다. 개인 전용 필드(`answerViewed`·`achievementResult`·`retryOfSubmissionId`)는 개인용 `Item` record에만 있다.

**그래서 허용 목록 파서를 만들지 않았다.** 지금 막을 것이 없는데 「서버가 계약을 어길 때만 도는 코드」를 늘리는 일이다.

막아야 할 필드는 하나뿐이다. `jobId`는 서버가 `publicRead ? null : lookup.jobId()`로 비우지만, **도달하지 않는 것과 막혀 있는 것은 다르다.** 실려 오면 213이 소비 경계에서 응답을 거절한다 — 이 값만이 프런트를 실제로 잘못 행동하게 만든다.

### 재노출 방지는 `S15P21C206-209`가 이미 세웠다

`useReadModel`이 **영속 캐시를 두지 않는다.** `pagehide`·`hidden`에 상태를 비우고 진행 중 요청을 abort하며, `focus`·`pageshow(persisted)`에 다시 읽고, 세대 카운터로 늦게 온 응답을 버린다. 착수 문서가 적었던 `lastMeta`는 초기 213(`577a2f3d`)에 있었고 160의 `978cffc`가 `includeGraph=false` 권한 재조회로 교체했다.

### 옛 폴링은 당시 계약을 구현한 것이었다

213이 넣은 5초 재조회는 **개인 작업 API 호출이 아니라 같은 공개 부모 첨부 GET**이었고, `c6627965` 이전 서비스 API 7.2는 「진행 중이면 기존 `curve.residual.jobId`로 **폴링한다**」고 지시하고 있었다. 계약이 바뀐 뒤 소비자가 따라가지 못한 것이며, 213 후속 MR이 정리했다.

## 없음이 네 가지다

공개 CURRENT에서 곡선이 없을 수 있는 이유가 서로 다르고, **한 문구로 뭉치면 거짓이 된다.**

| 무엇        | 응답                                    | 뜻                                                                  |
| ----------- | --------------------------------------- | ------------------------------------------------------------------- |
| 캐시된 잔차 | `curve.segments` 있음, `curveStep > 0`  | 그 단계 곡선이다                                                    |
| 원본 대체   | `fallbackReason` 있음, `curveStep = 0`  | 잔차를 재현하지 못해 원본을 준다. **원본을 잔차로 표시하지 않는다** |
| 미계산      | `residual: {status: null, jobId: null}` | 결과도 작업도 없다. 기다리는 상태가 아니다                          |
| 장애        | 503                                     | 못 읽은 것이다. **정상 `snapshot: null`과 합치지 않는다**           |

다만 **공개 경로에서 미계산·실패까지 내려오기는 어렵다.** `HistoryService.buildGraph`가 `publicRead`이고 잔차가 완료되지 않았으면 제거 조합을 비워 **현재 원본으로 갈아타고** `RESIDUAL_NOT_AVAILABLE`을 붙인다. 그때 `residual`은 원본 계약대로 `COMPLETED`·jobId null이며 **잔차 작업이 완료됐다는 뜻이 아니다**(8.3절).

`RESIDUAL_NOT_AVAILABLE`이 **공개 전용**이라는 점도 여기서 나온다. 개인 조회에 오는 사유는 `null`과 `RETIRED_CANDIDATE` 둘뿐이다([#190](analysis-history.md)의 배지가 그 둘만 다루는 이유).

SUBMITTED의 `snapshot: null`은 매칭 실패 기록이다. 409가 아니라 200이고, 당시 토글을 비활성으로 두되 **현재 자료를 당시 자료로 대신 보여 주지 않는다.**

## 이 티켓이 맡지 않는 것

- 타인 잔차 생성·개인 작업 조회 권한 확대
- 개인 History 직접 조회 우회
- 별도 공개용 그래프 계산기나 스키마. **같은 공용 DTO를 쓴다**
- 게시·취소(`S15P21C206-195`)와 글·댓글 구현(`S15P21C206-213`)
- 첨부 카드의 조회·캐시·권한 구조

## 미결

- **두 계정 실제 인수.** 완료 조건이 「두 계정으로 공개 첨부와 공개 분석을 열어 … 네트워크 기록에서 타인 잔차 재계산 및 개인 job 조회가 없음을 확인」이다. 지금까지의 검증은 **개발용 합성 응답**이며 로컬 OAuth 설정이 없어 실제 경로로 하지 못했다([#190](analysis-history.md)과 같은 제약). **이것이 닫히기 전에는 티켓을 완료로 보지 않는다.**
- **공개 분석 진입 어댑터 연결.** 191의 포함 범위인데 **아직 남아 있다.** 공개 분석 조회 응답을 공용 그래프에 잇는 코드가 없다.
- **공개 분석 상세 화면의 담당.** 위 어댑터와 **별개 문제다.** 라우트(owner 백지웅)와 링크만 있고 페이지가 없다. 191의 산출물은 「공개 그래프 **어댑터**」이고 SP 근거도 「A08-1 렌더러를 **재사용**한다」이므로 화면 전체를 짓는 것이 이 티켓인지는 협의가 필요하다. 다만 `S15P21C206-195`가 「공개 부모 그래프는 A08-2/W14에서 별도 구현·인수한다」로 되밀고 `193`에도 인수 명시가 없으므로, **어댑터만 191이고 화면은 미정**으로 둔다. 어느 쪽이든 그 화면이 생기면 **같은 파서·같은 곡선**을 쓴다.
