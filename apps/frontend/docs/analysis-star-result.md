# 193 별 결과 화면

Jira: S15P21C206-193. 기준: [프론트 명세 §4.3](../../../docs/development/analysis-frontend-spec.md#43-sc-05-별-결과와-히스토리-재현), [탐사 API §8.4](../../backend/docs/exploration-api-spec.md).

## 구현 범위

`/results/:ticId`에서 개인 결과를 GET으로 읽는다. 결과 카드·별 상세 패널의 기존 링크와 본인 별 목록에서 진입한다. 신호 수와 중복 포함 제출 수, 성과·등급·진행·미게시 상태를 구분한다. 서버 집계로 등급이나 새 별을 다시 계산하지 않는다. 당시 판단·현재 분류·AI·통계를 별도로 표시한다.

일시적 실패는 재시도하고 403/404는 동일한 접근 불가 안내를 제공한다. TIC 변경·이탈 시 조회를 취소한다. 공개 검토에서 돌아오면 같은 TIC도 재조회한다. 기존 1024px 데스크톱 기준과 좁은 화면 안내를 유지한다.

## 곡선과 제출 기록

사용자 승인 결정: `curveSteps`는 과거 제출 문맥의 계산 상태다. 집계에는 그 문맥의 Bundle·계산 버전이 없어 `COMPLETED`를 현재 데이터 준비 완료로 해석하지 않는다. 특정 단계 직접 진입은 계약 확인까지 보류한다.

대표 기록은 History 상세로 연결한다. 나머지 제출은 `GET /v1/submissions/{id}`의 제출 ID·TIC·History를 확인한 뒤 연결한다. 그래프와 재현 불가 안내는 190을 재사용한다. [분석 계속]은 기존 진입에서 최신 `analysis-context`를 읽으며 호환되는 저장 초안은 기존 정책대로 복원한다. 재분석은 192의 원 제출 확인·`retry-draft`를 사용한다. 별 단위 `RETRY`는 모든 개별 제출의 복원 가능성을 보장하지 않아 서버에서 최종 검증한다. 은퇴 신호에는 재분석 링크를 주지 않는다.

## 195 공개 검토 연결

- 개별: `/publication/:historyId?ticId=…&returnTo=…`. 대표 History 전달.
- 일괄: `/publication?ticId=…&returnTo=…`. 새 예약 경로. 195는 서버 후보 목록을 조회하며 임의 History를 대표시키지 않는다.
- `PUBLISH_ALL`은 `nextActions` 기준이다. 미게시 신호 수로 게시 대상 수를 계산하지 않는다.
- 검토 진입은 게시 요청이 아니다. 현재는 연결 준비 화면이며 실제 후보 검토·게시·취소는 195 범위다.
- `returnTo`는 같은 TIC 결과 URL. 복귀 시 재조회한다. [나중에 게시하기]·지도 이동은 쓰기 없이 TIC만 전달한다.
- 지도 선택 문맥은 기존 `/sky?star=:ticId` 계약을 사용한다. 원래 복귀 주소가 지도이면 필터 쿼리도 보존한다. 새로 열린 별 역시 `star`로 선택한다.

## 검증 범위

fixture는 API 8.4 모양의 합성 회귀 자료이며 실제 항성 자료/서버 집계 검증이 아니다. 운영 번들에서 제외한다. 단위 검사로 중복 집계·잘못된 ID·현재 판 부재·곡선 문맥·스레드 목록을 확인한다. 브라우저 검사로 상태 구분·읽기 전용 이동·공개 검토 문맥과 복귀·오류·빈 상태·과거 제출·은퇴·화면 너비를 확인한다.

실제 OAuth/API/DB 인수, 195 게시 후 왕복, 다른 브라우저와 스크린리더 실기 검증은 남는다. fixture 통과를 실제 API 완료 조건의 대체로 취급하지 않는다.

### 2026-09-22 잔차 계산 중 상태 회귀 수정

초기 파서가 API 2.4절의 중간 상태 3종을 거부하여 별 결과 전체를 오류로 처리했다. 기존 공용 residualStates를 재사용하고 표시 문구를 ResidualStatus에 대해 빠짐없이 정의했다. RESIDUAL_READY는 잔차 준비·주기도 대기로 표시하며 전체 계산 완료로 표현하지 않는다. 계약에 없는 RUNNING·CANCELLED는 허용하지 않는다.

검증: 운영 빌드, 단위 417개, 별 결과 Chromium 10개 통과. 단위 검사는 서버 상태 6종과 null을, 브라우저 검사는 중간 상태 3종에서 집계·History 링크가 유지되는 것을 확인한다. 실제 API 인수는 별도다.

### 2026-09-22 MR !175 리뷰 반영

- 하서진 리뷰: 현재 분류와 분류 변경값이 같은 `Record<Disposition, string>` 표기를 사용한다. `relabel.newDisposition`도 기존 공용 `dispositions`로 검증한다. 세 분류의 relabel fixture·브라우저 회귀와 미지원 값 거부 검사를 추가했다. 당시 판단·채점 결과는 변경하지 않는다.
- 강재민 리뷰: API 8.4 예시의 원본 단계에 `removedCandidateIds: []`를 추가하고 모든 예시 residual에 `jobId`·`computedAt`을 명시했다. 서버 `StarResultService.curveSteps`는 원본에도 제거 목록을 직렬화한다. 빈 목록과 누락을 구분하는 파서를 유지한다.
- 단계 불변식의 근거는 탐사 API 2.1절과 6.3절이다. `SubmissionRequest`와 `AnalysisService`도 단계와 제거 집합 크기를 검증한다. 단계는 작업 횟수가 아니므로 두 후보 조합은 2단계다. 8.4절에 이 근거를 연결했다. DB CHECK 유무와 별개이며 새 스키마 제약은 이번 범위가 아니다.
- `publicationBatch`는 193이 필요한 진입·복귀 문맥을 예약한 슬롯이고 실제 컴포넌트·게시 처리는 195 범위다. 나머지 열거형의 일괄 공용화와 지연 로딩 제안은 이번 필수 수정에서 제외한다.
- 검증: 운영 빌드·단위 419개·별 결과 Chromium 13개 통과. 분류 변경 3종에서도 History와 기존 판단을 유지한다. 실제 API·DB 인수와 데스크톱 타 브라우저·스크린리더 실기 검증은 수행하지 않았다.
