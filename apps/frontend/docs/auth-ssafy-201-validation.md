# 201 실제 SSAFY 로그인 검증 · 2026-09-15

## 결과

**실제 SSAFY 로그인에 성공했다.** 사용자가 제공한 앱 등록 정보를 Git에서 제외된 개인 설정 파일에 넣고, 로컬 시험 제공자 대신 SSAFY의 실제 인가·토큰·사용자 정보 서버를 사용했다. 백엔드는 MR !42 `1cf1cca` 원본이며 승인·병합·인증 우회·state 검증 해제 없이 실행했다.

`SSAFY 동의 → localhost:8080 백엔드 콜백 → /sky → GET /api/v1/me → 공통 회원 표시`를 사용자 Chrome에서 확인했다. 개인정보 제공 동의는 회원번호·이메일·이름·기수를 설명하고 사용자의 명시적인 승인을 받은 뒤 진행했다. 설정값·쿠키·인가 코드·SSAFY 사용자 식별값·동의 화면 캡처는 이 기록에 남기지 않는다.

## 확인한 증거

- 기존 환경과 분리된 `planetory-201-ssafy` Docker 프로젝트에서 Nginx·MR 백엔드·PostgreSQL을 실행했다.
- 프론트와 백엔드는 `http://localhost:8080`의 같은 출처를 사용한다. 콜백은 `/login/oauth2/code/ssafy`이며 MR 안내 주소로 실제 성공했다.
- 로그인 전 `/api/v1/me`는 401, 로그인 후 실제 프론트의 요청은 200. Nginx 로그에서 개인정보를 제외하고 확인한 상태 순서는 `401, 200, 200, 200, 200`이다.
- 전용 DB에 SSAFY 회원 1명, 기본 설정 1개, 최초 별 발견 1개가 생성됐다. 개인 값 대신 개수만 조회했다.
- 공통 레이아웃에 서버가 생성한 닉네임이 표시됐고 서비스 재진입·새로고침 후에도 같은 회원이 유지됐다.
- 개인 설정은 백엔드의 `apps/backend/.env.oauth.properties`에만 저장했다. Git ignore와 Docker build 제외 규칙을 확인했고, 컨테이너에는 읽기 전용 파일로 연결했다. 코드·Compose·문서에 실제 앱 비밀값을 넣지 않았다.

브라우저 주소창으로 API JSON을 직접 열려는 추가 확인은 Chrome의 `ERR_BLOCKED_BY_CLIENT`로 차단됐다. 우회하지 않고 서비스 화면과 서버의 HTTP 200을 증거로 사용했다. 이 차단은 화면에서 발생한 로그인 실패가 아니다.

## 완료 판단과 한계

**201-07의 실제 인증된 백엔드 GET·세션 연결은 확인됐다.** 403/404·오류 단위 검사는 직전 [실제 백엔드 + 시험 제공자 검증](auth-backend-201-validation.md)을 함께 근거로 사용한다. 아래 추가 확인에서 실제 SSAFY 세션의 CSRF·로그아웃도 성공했다. 30분 만료를 실제 제공자로 새로 기다려 검사한 것은 아니다.

이 실행 당시 실제 입력 기능 fieldErrors와 서버 추적 ID를 대기로 적었으나, 최신 대조에서는 새 기능 API나 추적 기능을 201의 필수 선행으로 추가하지 않는다. 실제 입력 기능의 종단 오류 검증은 미실행으로 구분한다. 현재 판단은 [인수 상태](ticket-201-readiness.md)를 따른다.

실제 A 화면 연결 시험, 배포 HTTPS·Safari, 리뷰·develop 병합은 남아 있다. 이 SSAFY 실행 후 [실제 Google 로그인](auth-google-201-validation.md)도 별도로 검증했다. 두 제공자의 실행 커밋과 DB는 서로 구분한다.

DB는 MR의 V1 스키마와 가상 튜토리얼 TIC 1·2·3·4·5를 사용하는 로컬 전용 DB다. 실제 제공자 로그인 성공이 최신 develop DB·운영 튜토리얼 데이터와의 호환성까지 보증하지 않는다. 기존 데이터·백엔드 코드·202·203·204 코드·GitLab MR·Jira는 이번 단계에서 수정하지 않았다.

## 사용자 요청에 따른 로그아웃 버튼 추가

실제 화면에 로그아웃이 보이지 않는다는 사용자 요청으로 201 공통 헤더의 닉네임 옆에 버튼을 추가했다. 202의 전체 로그인·온보딩 흐름을 가져온 것은 아니다. 해당 티켓의 기존 SessionProvider 기반 로그아웃과 합칠 때는 중복 동작을 정리한다.

- `ServiceLayout.tsx`: CSRF를 포함하는 공통 요청으로 POST `/v1/auth/logout`을 한 번 보낸 뒤, 성공 또는 이미 만료된 401에서 회원 상태를 비운다. 처리 중 중복 클릭을 막고 실패 시 로그인 상태를 지우지 않는다. 응답 유실 때는 쓰기를 자동 반복하지 않고 사용자가 회원 상태를 확인할 수 있다.
- 실제 Chrome 버튼 클릭에서 `GET /api/v1/auth/csrf` 200 → `POST /api/v1/auth/logout` 204 → 새로고침 `/api/v1/me` 401을 확인했다. 로그인 화면으로 돌아온 뒤에도 로그아웃 상태가 유지됐다.
- 검증 후 같은 SSAFY 계정으로 다시 로그인했고 `/me` 200과 로그아웃 버튼 표시를 확인했다. 사용자가 버튼을 볼 수 있도록 로그인된 화면을 열어 두었다.
- 타입·운영 빌드·개발 코드 미포함 검사와 Chromium 화면 9개 통과(기존 6개 + 로그아웃 성공/거절/응답 유실 3개). Git 업로드와 Jira 상태 변경은 하지 않았다.
