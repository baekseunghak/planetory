## HTTP 및 복구 규칙

- 기존 세션 쿠키와 공유 API 클라이언트를 사용한다. 매 쓰기 전 CSRF를 조회하며 401은 개인 화면/초안을 제거한다. 초안을 localStorage나 다른 회원의 캐시에 저장하지 않는다.
- `POST /api/v1/posts`는 `{title, body, purposeTag, ticId}`를 전송한다. `ticId: null`은 자유 게시판, 문자열은 별 게시판이다. 성공201의 `postId/createdAt`을 검사한다. POST를 자동 재시도하거나 동일 제목을 요청 식별자로 삼지 않는다.
- `PATCH /api/v1/posts/:postId`는 변경 필드만 보낸다. `ticId: null`로 자유 게시판 전환을 표현한다. ETag/If-Match/version/요청 멱등 키를 추가하지 않는다. 서버가 확정한 마지막 저장을 따른다.
- PATCH 유실 GET은 **현재 읽은 필드가 요청 내용과 같은지** 보여 준다. 같아도 특정 요청이 성공했다는 인과관계까지 확정하지 않는다. 다르면 양쪽 내용을 보여 주고 사용자가 선택한 뒤 직접 저장한다.
- `DELETE /api/v1/posts/:postId` 성공204 뒤 원래 게시판으로 이동한다. 유실 시 GET 확인 후, 여전히 조회되면 명시적으로 다시 삭제할 수 있다. 서버의 본인 반복 DELETE204 계약을 사용한다. GET404는 삭제/숨김 등을 구별할 수 없으므로 삭제 성공이라고 단정하지 않는다.
- 잘못된2xx DTO도 이미 저장되었을 수 있으므로 결과 불명확으로 처리한다. CSRF 획득 실패처럼 쓰기 전 실패는 별도로 표시하며 자동으로 쓰지 않는다.
- 편집 중 새로고침/창 닫기는 미저장 안내, 취소는 명시적 확인을 제공한다. 초안은 현재 페이지 메모리에만 유지한다. 사이트 메뉴·뒤로가기로 페이지를 떠나면 초안 자동 복원은 제공하지 않는다. 서버 저장 여부는 목록/상세에서 확인한다.
- 직접 URL/탭 복귀는 편집 권한을 다시 읽는다. 입력 중 제목/본문과 비교 기준을 서버 응답으로 자동 교체하지 않는다. 상세의 삭제 복구 상태는 탭 복귀 재조회 중에도 유지하고 부모 접근 불가 시 본문을 가린다.

## 상대 화면에서 연결

```ts
pagePath(
  "postCreate",
  {},
  { ticId: "259377017", returnTo: "/results/259377017" },
);
// /posts/new?ticId=259377017&returnTo=%2Fresults%2F259377017
```

TIC가 없으면 자유 게시판, `board=STAR`이면 별 번호 입력 상태로 시작한다. 선택적 `purposeTag` 쿼리는 허용된 다섯 값만 미리 선택한다. `returnTo`는 기존 안전한 서비스 내부 경로 검사로 제한한다. `historyId`를 전달받아도 자동 첨부·POST하지 않으며213에서 자료 선택을 연결한다. 결과/분석 화면 자체는 지웅 담당이며 이번 작업에서 수정하지 않았다.

- Windows, Node24.18/npm11.16, 기존 고정 의존성 사용.
- 단위68개(210의 입력/변경 필드/응답 검증5개 포함) 통과.
- 글쓰기14개 시나리오 × Chromium·Chrome·Edge·정식 Firefox =56개 통과. Unicode 경계, CSRF, 요청 중 잠금, POST/PATCH/DELETE 유실, 동시 수정/삭제, 타인/숨김/401, native 키보드 입력 포함.
- 209 커뮤니티 회귀13개, 공통 라우트/인증 회귀12개, 배포 코드7개 통과.
- 타입 검사·빌드·개발 fixture 제외·변경 파일 형식·문서 상대 링크 검사 통과. 글쓰기와 목록의 데스크톱 화면도 직접 확인했다.
- Firefox BiDi의 `fill`이 element.value를 대입해 React의 입력 추적값만 갱신하는 차이를 확인했다. 검사에서는 뒤에 native Space/Backspace 편집을 실행하고 별도로 실제 키 입력→게시를 검증했다. 운영 입력 코드를 테스트 도구에 맞춰 변경하지 않았다. BiDi의 요청 본문 조회가 null인 차이는 실제 fetch 경계에서 전송 본문을 관찰해 보완했다. 유실 시험은 실제 개발 HTTP 저장 후 응답을 차단하거나 명시적으로 요청을 차단한다.
