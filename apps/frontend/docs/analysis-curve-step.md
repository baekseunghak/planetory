# #189 곡선 단계 전환 개발 안내

2026-09-20 기준 `S15P21C206-189`의 계약 확정 기록이다. 기준은 [탐사 API 5.1·5.2·7.1·7.2·2.4](../../backend/docs/exploration-api-spec.md), [와이어프레임 SC-03·SC-04](../../../docs/requirements/planetory-wireframe.html)(v0.13), Jira A07의 완료 조건이다. 앞선 [#187 제출 접수·복구](analysis-submission.md)·[#188 결과 해설](analysis-result.md) 위에 얹는다.

## 무엇이 정본인가

셋이 같은 화면을 말하고 **서로 어긋나는 데가 있다.** 순서를 먼저 정한다.

| 순위 | 문서                             | 맡는 것                                                |
| ---- | -------------------------------- | ------------------------------------------------------ |
| 1    | 탐사 API 명세                    | 값·상태·순서·조건. 다른 둘과 다르면 이것이 맞다        |
| 2    | 와이어프레임 SC-03·SC-04 (v0.13) | 배치와 **화면의 말**. 명세가 정하지 않는 자리를 채운다 |
| 3    | 클릭 프로토타입 (v0.3)           | 참고만. 요구사항 v0.8 기준이라 낡았다                  |

**실제로 어긋난 예.** 와이어프레임 SC-04의 「확인된 행성 · 판단 일치」 카드에 「일반 토론 쓰기」가 있다. 명세 6.4절은 **`DISCUSS`를 `not_matched`에서만** 제공한다고 적는다(COM-10). 명세를 따른다. [#188](analysis-result.md)이 서버 힌트를 그대로 내놓으므로 이미 명세 쪽이다.

## 진입 응답이 주는 것

**다음 단계의 제거 조합을 프론트가 계산하지 않는다.** 5.1절이 문맥을 통째로 준다.

| 필드                                           | 뜻                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `currentCurveContext`                          | 마지막 제출 단계의 문맥. 제출이 없으면 원본(step 0)                                                     |
| `nextCurveContext`                             | 매칭한 활성 후보 **전체를 제거한** 문맥. [다음 곡선]의 기본 대상. **남은 탐색 가능 신호가 없으면 null** |
| `residualForCurrentStep`·`residualForNextStep` | 각 문맥의 잔차 캐시 상태. `curveStep=0`이면 `COMPLETED` 고정                                            |
| `progress.matchedCandidateIds`                 | 이 판에서 회원이 매칭한 활성 후보                                                                       |

그래서 **누르기 전에 다음 곡선이 이미 계산돼 있는지 안다.** 캐시면 곧바로 전환하고, 아니면 작업을 요청한다. 「누르면 무조건 POST」가 아니다.

`nextCurveContext`가 null이면 다음 단계가 없다. 이때 `residualForNextStep`도 null이다. **둘 중 하나만 null인 응답은 거절한다.**

### 파서가 대조하는 것

- **`nextCurveContext`와 `residualForNextStep`은 함께 있거나 함께 없다.** 한쪽만 오면 다음 단계가 있는지 없는지 알 수 없으므로 거절한다.
- **다음 단계가 지금보다 앞일 수는 없다.** 지금 문맥의 제거 조합은 매칭한 후보의 부분집합이고(7.1절) 다음 문맥은 그 전부를 제거한 것이다. **같을 수는 있다** — 아직 하나도 매칭하지 않았으면 둘 다 원본이다.

개발용 응답이 `nextCurveContext`로 **현재 문맥을 그대로** 돌려주고 있었다. 파서가 값을 읽기 시작하자 드러났다. 현재 단계를 손으로 바꾸는 fixture도 매칭 집합을 함께 올리지 않아 같은 규칙을 깼다. 두 곳이 `withMatched`로 한 번에 다시 맞추도록 했다.

## 잔차 작업 (7.1·7.2)

`POST /api/v1/stars/{ticId}/residual-jobs` — 매칭 후 [다음 곡선], 원본·이전 단계 복귀 시 캐시 없음, 재시도.

**요청 ID가 없다.** 같은 `target`을 다시 POST하면 진행 중 작업이나 캐시 결과가 그대로 온다. 그래서 **응답을 잃어도 같은 `target`으로 다시 부르면 된다.** [#187](analysis-submission.md)의 요청 ID 사다리를 여기에 가져오지 않는다. 결과가 회원과 무관한 캐시이고 요청 자체가 상태를 만들지 않기 때문이다.

| 응답                                            | 뜻                                                                           |
| ----------------------------------------------- | ---------------------------------------------------------------------------- |
| 200 `cacheHit: true`                            | 이미 계산돼 있다. 곧바로 전환                                                |
| 202                                             | 작업이 생겼거나 이미 진행 중이다. `pollAfterSeconds`만큼 쉬고 7.2절로 묻는다 |
| 429 `RESIDUAL_QUEUE_FULL` + `retryAfterSeconds` | 대기열이 찼다                                                                |
| 429 `RESIDUAL_QUEUE_FULL` + `activeJobId`       | **같은 회원의 다른 작업이 진행 중**(회원당 1개, D-4)                         |
| 409 `BUNDLE_CHANGED`                            | 판이 바뀌었다                                                                |

**429 두 가지를 같은 말로 안내하면 안 된다.** 앞은 기다리는 것이고 뒤는 **내가 이미 돌리고 있는 작업**이라 그쪽으로 데려가야 한다.

### 상태와 화면의 말

명세 2.4절의 6상태를 와이어프레임 SC-03이 이렇게 부른다.

| 상태                      | 화면        |
| ------------------------- | ----------- |
| `QUEUED`                  | 대기        |
| `RESIDUAL_CALCULATING`    | 잔차 계산   |
| `RESIDUAL_READY`          | 잔차 준비   |
| `PERIODOGRAM_CALCULATING` | 주기도 계산 |
| `COMPLETED`               | 완료        |
| `FAILED`                  | 실패        |

이 순서로만 전이하며 `FAILED`는 어느 단계에서든 갈 수 있다(DAT-14). 조회 응답의 `status: null`은 **상태가 아니라** 「결과도 작업도 없음」이다(D-14). 그때는 폴링하지 않는다.

### 폴링 간격은 서버가 정한다

`pollAfterSeconds`를 그대로 따른다(D-3, Q08). 우리가 고르면 서버가 부하를 조절할 수 없다.

**한도는 두지 않는다.** 계산이 길어질 수 있고, 멈추는 것은 사용자가 화면을 떠나거나 중단할 때다. 다만 서버가 0초를 주더라도 최소 간격(`MIN_POLL_MS`)을 두어 쉬지 않고 두드리지 않는다.

### 개발용 응답은 시계가 아니라 조회 횟수로 전진한다

[residual-job-fixtures.ts](../dev/residual-job-fixtures.ts)가 부를 때마다 한 단계씩 나아간다. 시계에 기대면 검사가 느려지거나 흔들리고, 화면이 순서를 진짜로 그리는지 보이지 않는다.

캐시는 **완료를 돌려주는 그 응답에서** 적는다. 다음 조회까지 미루면 완료를 본 클라이언트가 같은 목표를 다시 요청했을 때 캐시가 없다. 계약 검사가 이걸 잡았다.

## 곡선은 `COMPLETED`에서만 바꾼다

완료 조건이 「**합의한** 완료 시점에만 전환한다」이고 제외 범위가 「완료 전 부분 그래프 선노출의 **임의** 확정」이다. `RESIDUAL_READY`에서 곡선만 먼저 보여 주면 주기도가 아직 없어 봉우리를 고를 수 없고, 그 결정은 이 티켓이 혼자 할 수 없다.

**그래서 `COMPLETED`까지 기다린다.** 그 전까지 화면은 마지막 정상 곡선을 그대로 두고 진행만 알린다. 부분 노출은 미결로 남긴다.

### 갈 수 있는 곳을 우리가 고르지 않는다

| 이동 | 목표를 어디서 얻나 |
| --- | --- |
| 다음 | 서버가 준 `nextCurveContext` 그대로 |
| 이전 | **이번 세션에서 지나온 문맥.** 내가 왔던 길이다 |
| 원본 | 제거 조합이 빈 문맥. 계산이 필요 없다(5.2절) |

어떤 후보를 뺄지 프론트가 고르지 않는다. 조합은 어떤 순서든 허용되고(EXP-09) 그 선택은 사용자가 매칭으로 이미 했다. [이전]을 「하나 적게 뺀 조합」으로 계산하면 **어느 것을 뺄지 우리가 정하는 셈**이라 사용자가 보던 곡선과 달라질 수 있다.

캐시 상태를 아는 목표만 계산을 건너뛴다. **모르면 요청한다.** 캐시가 있으면 200으로 곧바로 끝나므로 지레짐작해서 건너뛰는 것보다 싸다.

## 늦은 응답을 버린다

전환·재조회가 겹치면 **과거 판이나 과거 단계의 응답이 나중에 도착할 수 있다.** 그대로 그리면 현재 판과 섞인다.

전환마다 세대 번호를 올리고 **자기 세대가 아닌 응답은 버린다.** 요청을 중단(`AbortSignal`)하는 것만으로는 부족하다. 이미 네트워크를 떠난 응답이 돌아올 수 있기 때문이다. D-7이 지도 타일에 같은 규칙을 적는다.

## 화면

[CurveStepBar](../src/features/analysis/CurveStepBar.tsx)가 상단 분석 단계 줄 안에 붙는다. 「이 별에서 찾은 신호 N · 곡선 단계 M」과 이동 버튼 셋이다.

**`잔차 N단계`를 `곡선 단계 N`으로 바꿨다.** 「잔차」는 개발자 말이다. 와이어프레임 SC-03이 화면 전체에서 「곡선 단계 N」을 쓰고 별 지도 카드도 그렇다.

진행은 여섯 상태를 **순서 전체로** 보여 준다. 지금 어디인지만 보이면 얼마나 남았는지 알 수 없다. 지나온 단계는 `✓`, 지금은 `▶`로 표시해 **색만으로 가르지 않는다.**

예상 시간은 보여 주지 않는다. 빗나간 예상은 기다림을 더 나쁘게 만든다. 대기 순번만 알린다.

### 자리를 두 번 옮긴 이유

처음에는 분석 그리드의 새 칸으로 넣었다. 그런데 차트·패널이 `grid-row`를 **명시적으로** 쓰고 있어 새 요소가 맨 아래로 밀렸고, 한 칸만 차지했을 때는 기존 분석 단계 줄을 차트 밑으로 밀어냈다. 그리드 행 번호를 전부 다시 매기는 대신 **상단 분석 단계 줄 안**으로 넣었다. 그 줄은 이미 두 칸을 모두 차지한다.

## 실패해도 잃지 않는 것

잔차 실패·통신 단절에서 **저장된 매칭·성과·완료와 마지막 정상 곡선을 유지한다.** 실패는 전환이 안 된 것이지 앞선 결과가 사라진 것이 아니다. 같은 문맥으로 다시 시도할 수 있어야 한다.

**과거 단계로 가도 서버의 누적 진행·성과·완료는 되돌아가지 않는다.** 단계 이동은 보는 곡선을 바꾸는 것뿐이다.

## 판이 바뀌었을 때

분석 도중 새 판이 공개되면 상단에 안내하고 다시 불러온다(EXP-01·AT-117). **곡선 단계·제거 조합은 유지하고 주기·위상 선택만 초기화한다.** [#187](analysis-submission.md)이 제출 응답에서 판 차이를 알리는 것과 다른 경로다. 이쪽은 읽기 조회의 갱신이다.

저장된 조합에 **은퇴 후보**가 생기면 서버가 현재 진행 문맥으로 대체하고 `notice: "STEP_NOT_RESTORABLE"`을 붙인다(C02-R1, Q09). 프론트는 그 안내를 보여 줄 뿐 조합을 스스로 고치지 않는다.

## 제출 결과와 잇는 곳

**[다음 곡선 단계로]는 같은 화면에서 일어난다**(SRS 3.2 흐름의 「EXP-09 · 같은 화면」). 라우팅이 아니라 결과를 닫고 단계를 옮긴다. 주소가 바뀌지 않는다.

목표는 **접수 결과의 `progress.matchedCandidateIds`**로 만든다(6.4절). 진입 때 받은 `nextCurveContext`는 **제출 전 값**이라 방금 매칭한 후보가 빠져 있다. 개발용 접수 결과도 제거 조합을 그대로 돌려주고 있어 이 제출로 맞힌 후보를 더하도록 고쳤다.

`SUBMISSION_CONTEXT_NOT_READY`([#187](analysis-submission.md))에는 [이 단계 계산 준비하기]를 준다. **이동이 아니라 제자리 계산**이다. 보고 있는 단계의 잔차를 계산시킬 뿐 다른 곳으로 옮기지 않는다. 서버가 「접수를 예약하거나 배경에서 대신 제출하지 않는다」고 못박았으므로 사용자가 눌러야 시작된다.

### 결과 화면에 「더 없음 의견」을 두지 않는다

와이어프레임 SC-04는 FP를 맞힌 카드에 이 버튼을 둔다. 두지 않기로 했다.

- **`nextActions`가 표현할 수 없다.** 열거형에 그 값이 없어서 서버가 「지금 이 별에 더 없음이 의미 있다」고 알려 줄 방법이 없다(6.4절).
- **결과를 닫으면 분석 화면에 그 버튼이 그대로 있다.** 클릭 한 번 차이다.
- 와이어프레임의 카드는 **전체 화면 상태**였다. 우리 결과는 분석 화면 위의 대화상자라 맥락이 다르다.

넣으려면 C02에 힌트 추가를 요청하는 것이 제대로 된 길이다. 그 전에 프론트가 조건을 판단해 버튼을 내면 「서버 힌트를 다시 계산하지 않는다」는 규칙이 무너진다.

## 이 티켓이 맡지 않는 것

- **잔차·주기도 계산 자체**와 Redis·worker(I10, D13/D14)
- **다시 풀기**(`S15P21C206-192`). 당시 곡선·입력 복원은 6.8절이고 여기서는 단계 이동만 한다
- **UI 이탈을 서버 작업 취소로 처리하는 것.** 화면을 떠나도 작업은 계속된다

## 미결

- **실제 API가 없다.** 명세 645행이 「잔차 결과·작업 상태 읽기는 `S15P21C206-147`이 구현하며, 그전까지 잔차 단계는 항상 미계산(`status: null`)이다」라고 적는다. 개발용 응답으로만 검증하며 **이 작업으로 티켓을 닫지 않는다.**
- **`RESIDUAL_READY`에서 곡선만 먼저 보여 줄지.** 지금은 `COMPLETED`까지 기다린다. 열려면 C02·C13과 합의가 필요하다.
- **결과 화면의 「더 없음 의견」.** 와이어프레임 SC-04는 FP를 맞힌 카드에 함께 두는데 `nextActions` 열거형에 그 값이 없다([#188](analysis-result.md) 참고). 서버 힌트로 표현할 수 없어 6단계에서 자리를 정한다.
- **`estimatedSeconds`·`queuePosition`을 얼마나 보여 줄지.** 명세가 주지만 빗나가면 기다림이 더 나빠진다.
