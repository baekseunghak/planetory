## 성능 결과

최초 baseline(최신 develop 전체 화면)은 Chrome1440/DPR1에서 지도 이동 p95 291.8ms, 최악341.6ms, 힙451.1MB였다. 첫 실제 별 표시245.4ms와 전체 적재6.89초를 별도로 기록했다.

중간 실행 `final-b`는 같은 Chrome/DPR1에서 이동 p95 8.4ms, 확대 상태 이동16.7ms, 힙233.2MB로 개선됐지만 휠 검사 최악33.4ms가33ms를 넘어 전체 합격이 아니다. 원시 값과 이전 실패는 [요약 증거](performance-215-evidence.json)에 함께 보존한다.

최종 측정 표. p95/최악은 **적재 완료·유효 창 각각의 값 중 최댓값**이다. 5초짜리 서로 다른 동작을 하나의 분포로 합치지 않았다. ms 표시 반올림 전 값으로 판정했다.

- Chrome/DPR1의 전체 지도 이동 p95는291.8→16.6ms, 같은 실행의 힙 최고는451.1→276.4MB였다. 원본 별을 줄여 얻은 결과가 아니다. 반면 남은 최악33.6ms를33ms로 반올림해 합격시키지 않았다.
- 확대 드래그 중 새 페이지를 받은 창은 인수 수치에서 제외하고 raw의 `pendingFrames`와 함께 남겼다. 복귀 후 같은 드래그를 재생한 `near-drag-warm`에서도 Edge p95 33.3ms/최악49.9ms, Firefox41.66ms/58.32ms로 미달했다. 적재 중에는 이보다 긴 지연도 있었다.
- 초기 Edge `final-c` 첫 정지 창은5초에4프레임(약1Hz)만 기록됐다. 시작 시 가시성을 기록하지 않아 원인을 확정하지 않았다. 각 창 전 `bringToFront`·시작 가시성 기록을 추가한 `final-d`로 재측정했다. 초기 결과를 삭제하거나 합격 근거로 사용하지 않았다.
- 별32개 선택 뒤 별도 GPU timer 창의 p95는 Chrome/DPR1 약5.7ms, Chrome/DPR2 약10.6ms, Edge 약6.4ms였다. 카메라·가시 수가 완전히 같은 통제 실험은 아니므로 fill-rate 단독 원인으로 단정하지 않는다. 확대 시 가시 배열 재패킹/업로드 비용과 GPU 비용을 추가로 줄여야 한다.
- Firefox의 timer query는 미지원이고 CDP JS heap은 측정하지 못했다. renderer 문자열도 `or similar`가 붙은 근삿값이므로 세부 GPU 모델을 확정하지 않는다. 모든 실행의 기능 assertion/pageerror 검사는 성공했지만 이것은 프레임 합격과 별개다.
- CPU profile·원시 프레임·페이지·GPU 기록은 로컬 `performance-results`에, 해시/요약은 커밋되는 증거 파일에 보존했다. OS의 다른 작업·전원/주사율을 실험실처럼 고정하지 않은 로컬 측정이며, 다른 기기의 보장이나 배포 인수 결과가 아니다.

3. MR 리뷰/비작성자 승인·develop 병합·Jira 근거 등록은 별도다. 작성자가 자기 MR을 승인하거나 티켓을 자동 완료하지 않는다.
