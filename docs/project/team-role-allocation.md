## 1. 목적

요구사항 명세서를 여섯 개 도메인으로 나누고 각 도메인의 책임자, 분석 범위, 산출물과 협업 경계를 정의한다. 현재 단계의 목표는 바로 구현하는 것이 아니라 각 담당자가 자신의 요구사항을 분석해 구조·정책·인터페이스와 후속 구현 작업을 구체화하는 것이다.

각 담당자는 AI 에이전트를 조사, 초안 작성, 반복 작업과 검증 보조에 활용할 수 있다. 도메인 결정, 요구사항 해석, 인터페이스 합의와 최종 검수 책임은 담당자에게 있다.

요구사항 명세서와 상태표·와이어프레임·프로토타입이 다르면 요구사항 명세서 v0.12를 정본으로 사용한다.

### v0.12 역할 분배 반영 사항

- 잔차 곡선과 잔차 주기도는 배치 저장물이 아니라 EC2의 온라인 파생 계산으로 제공한다.
- Gold에는 원본 정제곡선 전 점·품질 마스크·`fold_reference_time_btjd`, 후보별 transit model과 계산 설정 버전이 포함되어야 한다.
- 신규 분석 세션은 `current`에서 PublicationBundle을 고정한다. EC2는 `current`·`previous`를 기본 보존하고, 진행 중 세션·재시도·보존기간 내 히스토리가 참조하는 이전 Bundle과 캐시는 보호한다.
- 온라인 계산은 `QUEUED → RESIDUAL_CALCULATING → RESIDUAL_READY → PERIODOGRAM_CALCULATING → COMPLETED/FAILED` 상태를 구분한다.
- 김동혁이 온라인 계산 위치·캐시·큐·관측 구조를, 윤성용이 배치와 EC2 계산의 과학적 일치 기준을, 강재민이 요청 상태·캐시 키·API 경계를 분석한다.
- 외부 라벨이 갱신되어도 v1에서는 기존 성과·등급·발견한 별·통계 스냅샷을 유지하고 재분류 표식만 남긴다.
- 동의·비동의 합계와 반응한 회원 닉네임 목록은 모든 회원에게 공개한다.
- 회원 차단은 v1 범위 밖이다. 신고·운영 숨김만 다루며 UserBlock과 차단 UI를 기획 범위에 넣지 않는다.
- 등급 상승으로 열리는 별은 전체 미발견 대상에서 무작위로 고르며 주변 반경·확률 가중을 사용하지 않는다.

## 3. 담당자별 기획 책임

### 3.1 김동혁 — 데이터 플랫폼·DevOps

#### 분석 범위

- GCP 6계정 Node 1~6의 역할과 계정 간 네트워크
- Node 1의 NameNode·ResourceManager·Airflow 제어 역할과 Node 2의 Standby NameNode·Worker 병행 자원 범위
- HDFS Raw/Bronze/Silver 저장 구조, 복제 계수와 보존 정책
- YARN/Spark 자원 배분과 Airflow 배치 제어
- 원천 수집의 checksum, 재시도, 멱등성과 부분 재처리
- PublicationBundle 검증과 GCP에서 EC2로의 Gold 전달
- EC2 release 검증, `current`·`previous` 전환과 롤백
- EC2 온라인 파생 계산의 구현 위치, 캐시 저장소, 큐와 동시 실행 상한
- Gold 필수 입력의 PoC용 최소 계약과 표본 용량 측정
- 온라인 계산 시간·큐 길이·캐시 적중률·실패율 관측
- HDFS·YARN·Spark·Airflow·Gold 버전 관측 지표
- 30일 운영을 위한 저장 용량과 컴퓨팅 자원 가정

#### 기획 산출물

- GCP 노드 역할·자원 배분표
- 네트워크 및 서비스 배치도
- 데이터 계층별 저장·복제·보존 계획
- 전체 배치 및 Gold 전달 흐름도
- 온라인 파생 계산·캐시·큐 아키텍처 결정안
- Gold 스키마·EC2 용량 후속 결정에 사용할 PoC 측정 결과
- 실패·재시도·복구·롤백 계획

## 5. 교차 리뷰 체계

- 김동혁 ↔ 윤성용: 저장·실행 환경과 과학 처리 파이프라인
- 강재민 ↔ 백승학: 탐사 트랜잭션과 서비스 이벤트·권한
- 백지웅 ↔ 하서진: 분석 화면과 전체 서비스 사용자 흐름
- 데이터 계약은 제공자와 소비자가 함께 승인한다.
- 명세서 충돌이나 정책 누락은 담당자가 임의로 결정하지 않고 팀 결정 항목으로 등록한다.

## 6. 공통 완료 조건

각 담당자의 기획 Task는 다음 조건을 모두 충족해야 완료한다.

- [ ] 관련 요구사항 ID가 빠짐없이 분류되어 있다.
- [ ] 담당 범위와 제외 범위가 명시되어 있다.
- [ ] P0, P1, P2와 범위 밖 항목이 구분되어 있다.
- [ ] 입력 데이터, 출력 데이터와 주요 상태가 정의되어 있다.
- [ ] 정상·실패·재시도 흐름이 정리되어 있다.
- [ ] 다른 담당자와 주고받는 인터페이스가 정의되어 있다.
- [ ] 명세서의 충돌·누락·미결정 사항이 기록되어 있다.
- [ ] 기술 검증이 필요한 항목이 분리되어 있다.
- [ ] 후속 Jira Task가 브랜치·MR 단위로 제안되어 있다.
- [ ] 교차 리뷰 결과와 분석 문서 링크가 Jira에 등록되어 있다.

## 7. AI 에이전트 사용 원칙

- AI 에이전트에는 확정된 요구사항과 담당 범위를 함께 제공한다.
- API와 데이터 스키마는 담당자 간 합의 후 정본으로 사용한다.
- AI가 명세서의 미결정 사항을 임의로 확정하지 않도록 한다.
- 생성된 설계·코드·테스트는 담당자가 직접 검증한다.
- 다른 담당자의 영역을 변경해야 할 때는 먼저 인터페이스 변경을 합의한다.
- 구현 Task를 만들 때 관련 요구사항 ID와 검증 기준을 포함한다.
- 정상 사례뿐 아니라 실패·중복·재시도·버전 변경 사례도 검토한다.

## 8. 기획 이후 진행 순서

1. 여섯 담당자가 각 Jira 기획 Task를 기준으로 요구사항을 분석한다.
2. 담당 페어끼리 데이터·API·화면 경계를 교차 리뷰한다.
3. 전체 회의에서 명세 충돌과 미결정 사항을 확정한다.
4. 확정된 분석 결과로 구현 Epic 또는 기존 적합한 Epic을 선택한다.
5. 각 담당자가 `Task 1개 = 브랜치 1개 = MR 1개` 원칙으로 구현 Task를 제안한다.
6. 팀이 Story Point, 우선순위와 선행 관계를 검토한 뒤 구현에 착수한다.
