## 0. 원칙

1. **상태는 후보 단위다.** 별은 상태를 갖지 않고, 후보들과 내 제출에서 파생값을 계산해 그린다.
2. **전역과 개인을 나눈다.** 라벨·AI·확정·후보표는 모두에게 같다. 성과·등급·열림·진행은 내 제출에서만 계산한다.
3. **신호와 행성은 다른 질문이다.** 주기를 맞히면 고유 후보 성과, 행성 여부는 판단(user_judgment)으로 따로 기록한다. 정답 있는 후보만 판단을 채점하고, 없는 후보는 분석글 공유를 성과로 친다.
4. **정답이 없는 것은 데이터 사정이다.** 분석형 후보에서 사용자에게 불리한 처리를 두지 않는다.
5. **등급은 희귀도다.** 후보가 많은 별을 풀수록 높고, 그만큼 밤하늘이 넓게 열린다.

| removal_step, transit_model_ref | 정수, 경로 | DAT 05 | 배치 내부 순차 탐색에서의 제거 순서와 통과 모델. 사용자용 잔차 곡선·주기도 파일 경로는 저장하지 않음 |
| tce_ref | TCE ID / 없음 | DAT 09 | 외부 비교값. 자체 값을 덮어쓰지 않음 |
| toi_disposition | `KP` / `CP` / `PC` / `APC` / `FP` / `FA` / 없음 | DAT 09, TOI 카탈로그 | 원본 그대로, 스냅샷 날짜 포함 |
| ai_score | 0.0 ~ 1.0 / 없음 | AI 03 자체 모델 | 모델·체크포인트·입력 버전 포함 |
| ai_status | `approved` / `hold` / `rejected` / `not_evaluated` | AI 04 | 실행 불가는 별도 상태(RES 04) |

| answer_class | `graded` 채점형 / `analysis` 분석형 | DAT 09 (표 B) | 판단을 채점할지 |
| planet_truth | `planet` / `not_planet` / 없음 | DAT 09 (표 B) | 채점형만 |

| 버전 | 전처리·BLS·모델·규칙·카탈로그 스냅샷 | NFR 03 | 변경 시 CandidateStatusHistory |

사용자용 잔차 곡선·잔차 주기도는 Gold의 후보 저장 필드가 아니다. EC2가 원본 전체 포인트와 공개된 통과 모델로 계산하고, `(tic_id, publication_bundle_id, 정렬한 removed_candidate_ids, residual_model_version, periodogram_config_version)` 키로 캐시한다. 활성 분석 세션은 진입 시 선택한 공개 묶음에 고정하며 새 공개 묶음은 새 세션부터 사용한다. 구버전 공개 묶음과 그 키의 캐시는 보존기간 종료 시 함께 만료한다.

## 표 B. 후보 판정 규칙 (DAT 09 · AI 04 · DEC 20)

위에서부터 먼저 맞는 행 하나. 라벨 우선, 없으면 AI 점수.

| 순서 | toi_disposition | ai_score | → ai_status | → is_confirmed | → answer_class | → planet_truth |
|---|---|---|---|---|---|---|
| 1 | KP, CP | 무관 | 점수 규칙대로 기록 | **true** | 채점형 | 행성 |
| 2 | FP, FA | 무관 | rejected | false | 채점형 | 아님 |
| 3 | APC | 무관 | approved | false | 분석형 | 없음 |
| 4 | PC | 무관 | approved | false | 분석형 | 없음 |
| 5 | 없음 | ≥ 승인 임계값 | approved | false | 분석형 | 없음 |

| 7 | 없음 | < 보류 임계값 | rejected | false | 분석형 | 없음 |

## 표 D. 제출 항목과 결과

한 번의 제출은 후보 하나를 겨냥한다. 후보를 매칭한 뒤 다음 곡선 단계로 이동하면 EC2가 원본 전체 포인트에서 공개된 통과 모델을 빼 잔차 곡선을 먼저 만들고, 그 결과로 잔차 주기도를 계산한다. 같은 캐시 키는 결과를 재사용하며 원본으로 언제든 복귀할 수 있다(결정 9·37). 온라인 요청은 `대기 → 잔차 계산 중 → 잔차 준비 → 주기도 계산 중 → 준비`를 구분하고 실패 원인과 재시도를 제공한다.

**주기 변경 규칙 (EXP 05·08·10·12·13)**

| 사용자 동작 | 주기 상태 | 접힌 곡선 | 이후 입력 | x축 확대 |
|---|---|---|---|---|
| 주기도의 다른 봉우리 선택 | 주기 재선택 | 새 주기로 다시 계산 | `phase_start`·`phase_end`, epoch·지속시간, 판단·근거·메모 초기화 | 1배로 초기화 |
| 현재 주기 허용 범위 내 이동 | 주기 미세 조정 | 조정된 주기로 다시 계산 | `phase_start`·`phase_end`, epoch·지속시간, 판단·근거·메모 초기화 | 기존 x축 확대 배율만 유지 |

두 동작 모두 현재 `curve_step`, `publication_bundle_id`, 제거 후보 조합과 주기도의 확대·이동 범위를 유지한다. 브라우저는 현재 곡선의 유효 관측점 전체와 Bundle의 `fold_reference_time_btjd`로 새 주기에 다시 접으며 주기 변경만으로 BLS·잔차 계산 API를 호출하지 않는다. 미세 조정에서 추가로 유지하는 접힌 곡선 표시값은 **x축 확대 배율(1~8배)**뿐이다. 접힌 곡선의 이동 위치·y축 표시 범위·transit 선택값은 유지하지 않고 새 접힌 곡선의 기준 위치로 다시 맞춘다. 휠은 포인터 기준 x축만 확대하고 더블클릭은 1배로 복귀한다. 차트 포커스 상태의 `+`·`-`는 차트 중앙 기준으로 1·2·4·8배 단계를 이동하고 `0`은 1배로 복귀하며 y축 범위는 바꾸지 않는다. 두 주기 변경 동작 모두 이후 단계에서 수행하면 주기 맞추기 단계로 돌아간다. 미세 조정 허용 범위는 버전된 서버 설정으로 제공한다. 브라우저 재접기 중에는 구간 선택·판단·제출을 비활성화한다. 범위 이탈이나 재접기 실패 시 그래프·확대 배율·작성 중 입력은 마지막 성공 상태로 복구하되 마지막 입력값과 오류를 보여준다. Web Worker 등 비동기 클라이언트 계산 결과의 순서가 뒤집히면 revision이 가장 최신인 성공 결과만 적용한다.

**제출 종류 1 · 후보 제출 (SUB 01)**

| 항목 | 값 | 필수 | 비고 |
|---|---|---|---|
| 주기 P | 일 | 필수 | 주기도 봉우리 재선택 또는 현재 주기의 서버 허용 범위 내 미세 조정(EXP 05) |
| `phase_start`, `phase_end` | 위상 | 필수 | **접힌 곡선에서만** 선택. 시간 영역의 원본·잔차 곡선에는 읽기 전용 예측 transit 띠만 표시 |
| epoch | BTJD | 브라우저 미리보기 / 서버 최종 파생 | 선택 중에는 위상 중심과 Bundle의 `fold_reference_time_btjd`로 즉시 미리보기. 제출 시 서버가 같은 저장값으로 다시 계산·검증하며 사용자가 입력·수정하지 않음(EXP 06) |
| 지속시간 | 시간 | 브라우저 미리보기 / 서버 최종 파생 | 선택 중에는 위상 구간 폭과 주기로 즉시 미리보기. 제출 시 서버가 다시 계산·검증하며 사용자가 입력·수정하지 않음(DEC 19) |
| 판단 | LIKELY_PLANET / UNLIKELY_PLANET / UNSURE | 필수 | POL 13 |
| 근거 체크 | 홀짝 깊이 / 2차 식 / V·U형 / 품질 구간 | 선택 | 체크박스. UNLIKELY일 때 이유를 남기는 용도. 중심 위치는 P0 근거가 아님 |
| 메모 | 자유 한 줄 | 선택 | |
| 현재 곡선 | 원본 / 잔차 단계 n | 자동 | 어느 곡선에서 제출했는지 기록 |

`selection_space` 필드는 두지 않는다. 선택 공간은 접힌 곡선으로 고정한다. 저장 좌표는 `0 ≤ phase_start < 1`, `phase_start < phase_end < phase_start + 1`인 연속 두 주기 표현을 쓰고, 위상 경계를 넘으면 `phase_end`가 1을 넘을 수 있다. 선택 핸들이 바뀔 때마다 브라우저가 epoch·지속시간 미리보기와 시간 영역의 읽기 전용 transit 띠를 즉시 갱신하며, 제출 시 서버가 위상 원본값에서 최종 epoch·지속시간을 다시 계산·검증한다. 관측 공백은 데이터가 있는 것처럼 그리지 않고 시간 영역에서는 핸들로 수정할 수 없다. P0의 중심 위치 항목은 `중심 위치: 데이터 없음`으로 비활성 표시한다. 이는 `중심 이동 없음`이라는 관측 근거가 아니며 제출·매칭·성과·등급·통계에 포함하지 않는다. 조작된 요청으로 중심 위치 근거를 보내도 서버는 유효한 `evidence_checks` 값으로 접수하지 않는다.

**제출 종류 2 · 후보 없음 의견**

"이 별에서 더 찾을 행성 후보가 없다"는 사용자 의견. `submission_kind=no_candidate`로 주기·`phase_start`·`phase_end`·epoch·지속시간 없이 선언한다. 후보표가 비었거나 찾을 수 있는 후보를 모두 매칭한 경우는 서버가 이미 자동 완료하므로 직접 제출하지 않는다. 회원이 제출할 수 있는 때는 찾을 수 있는 미매칭 후보가 남아 있을 때뿐이며 `none_wrong`으로 안내하고 후보·Post·성과를 만들지 않는다(SUB-11).

```
 └─ 후보 없음 의견                       → none_wrong 안내. 자동 글·성과 없음
```

분석형 후보의 글에는 제목, 매칭 후보·제출 수치·정정 배율, 판단, 근거 체크, 접힌 곡선·확대 구간 스냅샷(AnalysisHistory 첨부, HIS 05), 태그 `ANALYSIS`를 자동으로 채운다. `not_matched` 토론 글에는 후보를 만들지 않고 본인의 현재 제출·히스토리만 첨부하며 태그 `DISCUSSION`을 사용한다. 사용자가 [게시]하기 전에는 어느 경우에도 Post가 생기지 않는다. 운영자는 공개·미삭제·미숨김 `not_matched` 토론 글만 P1 `ExpertReport` 대상으로 수동 선택한다. 시스템이 공개 원문·댓글·첨부 히스토리·버전을 보고서로 묶고, 운영자가 내용·첨부·수신자·제목을 확인해 승인한 뒤 이메일을 보낸다. 이 절차도 BLS·AI 재실행이나 후보·성과·등급·곡선 단계 변경을 일으키지 않는다. 외부 회신을 Candidate에 반영하는 절차는 현재 범위 밖이다.

## 표 E. 성과와 별 등급 (GRD 01~07)

성과 단위는 사용자 × 고유 후보(UserCandidateAchievement). 같은 후보의 반복 제출·배수 정정·배치 버전 변경은 한 건.

| 유형 | 조건 | 등급 (TIC별 고유 후보 수) | 열림 수 |
|---|---|---|---|
| 확정 행성 | 확정 후보 매칭 | 1 / 2 / 3 / 4개 이상 → A / S / SS / SSS | 1 / 2 / 3 / 4 |
| FP 판단 | FP 후보 매칭 + UNLIKELY | A만 (개수 무관) | 1 |
| 미확정 후보 | 분석형 후보 매칭 + 분석글 게시 | 1 / 2 / 3 / 4개 이상 → A / S / SS / SSS | 1 / 2 / 3 / 4 |

- 한 별에 여러 유형이 있으면 유형별로 따로 기록·표시한다 (GRD 07, POL 23). 밤하늘의 색상 계열 = 유형, 강도 = 등급.
- 등급은 내려가지 않는다. 예외는 후보 병합·분리, 외부 disposition 정정, 부정 사용 조치이며 이력을 남기고 재계산한다 (GRD 06).
- 외부 라벨 갱신으로 분석형 후보가 채점형이 되어도 v1에서는 후보 상태와 이력 표식만 갱신한다. 기존 성과 유형·등급·발견한 별·통계는 유지하고 결과 화면에 "기록이 갱신됨"을 표시한다(GRD-06, DEC-26 재개).
- 사용자 단위 등급은 두지 않는다. 프로필은 TIC별 등급·개수 목록(ACC 05).
