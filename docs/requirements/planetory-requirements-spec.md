## 1. 문서 목적과 적용 범위

이 문서는 Planetory 서비스 정책서 v0.6과 이후 확정된 팀 결정을 구현 가능한 기능·데이터·운영·검수 요구사항으로 구체화한다. 사용자 화면과 운영 문서의 공식 서비스명은 Planetory를 사용한다.

요구사항 충돌 시 적용 우선순위는 다음과 같다.

1. 팀이 이후 확정한 명시적 결정
2. Planetory 서비스 정책서 v0.6
3. 이 요구사항 명세서
4. 이전 정책서와 기능명세 초안 (기능명세서 v0.4, 상태표 v0.1~v0.5 포함)

Planetory는 회원 전용 서비스다. 로그인 화면과 OAuth 콜백을 제외한 모든 화면·조회·분석·커뮤니티 기능은 인증 후 이용한다. 회원은 공개 상태이며 삭제·숨김 처리되지 않은 게시글·댓글·첨부 자료를 모두 열람할 수 있다.

탐사 기능은 별도 모드로 나누지 않고 하나의 분석 흐름으로 제공한다. 다만 처음 열리는 튜토리얼 별 다섯 개는 정답이 있는 별로 고정한다 `(v0.3)`. 제출 후에는 외부에서 확정된 대상과 아직 확정되지 않은 대상의 해설 근거와 표현을 구분한다.

분석은 주기·구간을 선택하고 판단을 제출하여 고유 신호를 매칭한 뒤, 남은 신호가 있으면 잔차에서 반복하는 흐름이다. 탐색 가능한 모든 신호의 매칭 여부로 별을 완료하며 판단의 옳고 그름·성과·게시와 분리한다. 자체 BLS 채택 신호가 없어 후보표가 비어 있는 무신호 별은 공개·발견·튜토리얼 대상에서 제외하고 진입 완료·보상을 제공하지 않는다. 주기 신호가 모두 FP인 별도 각 신호를 직접 매칭하고 UNLIKELY_PLANET으로 판단해야 FP 성과를 인정한다. 별 전체의 행성 부재를 선언하는 별도 유형이나 보상은 두지 않는다. 신호는 있지만 현재 관측에서 찾을 수 없는 경우는 무신호와 구분하여 SUB-11의 재개 대기 규칙을 따른다. `(v0.12)`

이 문서는 랭킹·최초 발견 순위·선착순 혜택, 별도 분석 클립보드, PostAnalysisReference·PostReanalysis·ReviewCase 기반 후보 승격, 사용자 단위 누적 등급을 범위에 포함하지 않는다. 이의 제기 기능은 정책 확정 전까지 TBD로 두며 4장 기능 범위에서는 제외한다.

### 1.3 핵심 가치

- 외계행성 탐색의 진입 장벽을 낮춰 누구나 TESS 실측 데이터를 쉽게 분석하고 탐색에 참여할 수 있게 한다.
- 더 많은 사용자가 더 많은 관측 데이터를 탐색하고 신호를 토론·재분석함으로써 새로운 외계행성 후보의 발견 가능성을 높인다.
- 제출마다 분석 근거를 재현 가능한 히스토리로 보존하고, 사용자가 선택한 분석을 커뮤니티에서 자유롭게 공유한다.
- 운영자가 가치 있다고 판단한 게시글을 재현 가능한 보고서로 정리해 전문가에게 제보할 수 있게 한다.

## 3. 전체 흐름

### 3.1 배치 흐름

대상 선정 → 원천 등록 → TESS LC 수집 → Sector별 전처리 → 원본 정제곡선·주기도 생성 → BLS 후보 탐색 → 후보 모델 적합·내부 신호 제거 → Silver 내부 잔차 BLS 반복(후보 탐색용 중간 결과, 사용자용 잔차 곡선·주기도는 저장하지 않음) → 후보 병합 → 외부 TCE·TOI 연결 → AI 입력 생성 → 자체 모델 추론·판정 → 원본 탐색 가능성 검증 → Gold용 원본 전 점·품질 마스크·후보별 통과 모델·원본 주기도와 공개 묶음 검증 → 원자적 공개 `(v0.11)`

### 3.2 사용자 흐름 `(v0.3)`

로그인 → 튜토리얼 별과 열린 별, 내 TIC별 진행이 통합된 홈 → 별 선택 → 분석 시작 시 PublicationBundle 고정 → 확정 행성 보유 여부 확인 → 현재 시간 영역 곡선·주기도 탐색 → 주기도에서 주기 재선택 또는 현재 주기 미세 조정 → 브라우저가 현재 곡선을 새 주기로 접음 → 접힌 곡선에서 transit 위상 시작·끝 선택 → 브라우저가 epoch·duration과 시간 영역 예상 구간을 즉시 미리보기 → 사용자 판단(+선택 가능한 근거 체크) 선택 → 제출 → 서버가 epoch·duration 최종 재계산·검증 → 후보표 매칭 → AnalysisHistory 자동 저장 → `(v0.11)`

- 정답 있는 후보: 매칭·판단·성과를 각각 표시 → 남은 탐색 가능 신호가 있으면 [다음 곡선] 요청 시 EC2 온라인 잔차·주기도 계산 → 다음 신호 탐색. 판단을 틀려도 매칭 진행은 유지 `(v0.12)`
- 미확정 후보: 개인 기록 저장·성과 미인정 → 게시 없이 다음 신호 탐색 가능 → 결과·히스토리에서 개별 공개 또는 종료 후 [모두 게시]/[나중에] → 공개 성공한 고유 신호만 최초 성과 인정(COM-19) `(v0.12)`
- 오답: [상세 보기] / [다시 풀기] → 제출 당시 곡선·입력 복원 후 새 제출. 수치 매칭 실패와 판단 실패를 구분한다. not_matched의 [토론하기]는 일반 DISCUSSION 글이며 공식 신호·공개 분석·성과를 자동 생성하지 않음 `(v0.12)`
- 현재 탐색 가능한 신호를 모두 매칭: 탐색 완료 표시. 마지막 제출의 성과 인정은 별도로 판정하며, 오판이면 "탐색 완료 / 판단 불일치 / 성과 미인정"을 함께 표시. 탐색 불가능 신호만 남으면 재개 대기. 완료 후에도 재도전·공개 가능 `(v0.12)`

고유 신호 성과가 인정될 때마다 새 별이 열린다(POL-27). `(v0.13)`

### 3.3 커뮤니티 흐름

회원이 별 게시판 또는 전체 피드에서 자유양식 글 작성 → 관련 별 자동 선택 또는 직접 선택 → 같은 별의 본인 히스토리 첨부·공개 출처 링크 선택 → 최종 게시. 별 미선택 자유글에는 별 자료 선택·첨부를 제공하지 않는다. 미확정 분석 공개는 별도 흐름으로, 대상 기록 검토 → 공식 신호 스레드 확보(SYSTEM 최초 생성 또는 기존 공간 재사용) → 공개 분석 목록 등록 → 성과 및 공개 판단 통계 갱신이다. 토론 댓글·반응은 자동 생성하지 않는다. 신호 스레드의 세 판단 필터와 통계는 일반 별 토론글에서도 같은 출처로 연결한다. `(v0.12)`

전문가 제보는 운영자가 공개 게시글 선택 → 시스템 보고서 생성 → 운영자 내용·수신자 확인 → 시스템 이메일 발송 → 발송 상태·수신자·시각·오류 기록 순서로 진행한다. 커뮤니티 제보 경로는 후보표·AI 판정·후보 ID를 변경하지 않는다.

| EXP-02 | 확정 보유 여부 사전 표시 | P0 | 분석 화면에서 제출 전에 해당 TIC의 확정 행성 보유 여부만 표시한다. 기준은 후보표에 실제로 있는 확정 후보이며, 자체 BLS 미통과로 후보표에 없는 확정 행성은 보유로 표시하지 않는다. 개수·행성명·주기·지속시간·epoch는 POL-05 조건 전에는 표시하지 않는다. `(v0.3)` |

| EXP-04 | 주기도 표시 | P0 | 현재 곡선(원본 또는 잔차 단계)의 주기도 전체 경향과 확대 구간을 제공한다. 주기 축 범위는 0.5일부터 그 별 후보표의 최장 주기를 넉넉히 덮는 값(최소 40일)까지로 하고, 관측 기간의 1/2(섹터 1개면 약 13.5일)을 넘는 구간은 "가려짐이 2번 미만 · 다음 관측 회차가 필요할 수 있음"으로 눈에 띄게 구분한다. 관측 회차가 늘면 이 경계도 함께 늘어난다. 주기도의 봉우리는 discoverable=true인 후보만 만들며, 찾을 수 없는 후보가 남은 별의 자동 완료는 SUB-11 (4)를 따른다. `(v0.4)` 원본 주기도는 Gold의 배치 결과를 즉시 제공한다. 잔차 주기도는 동일 Bundle·제거 조합·계산 버전의 온라인 캐시가 있으면 즉시 제공하고, 없으면 EC2가 잔차 곡선을 만든 뒤 계산하며 단계별 진행 상태를 표시하고 결과를 캐시한다. 배치 저장본이라는 표현은 사용하지 않는다. `(v0.11)` |

| EXP-06 | transit 위상 구간·epoch 자동 산정 | P0 | 사용자는 현재 곡선 단계를 선택 주기로 접은 곡선에서만 transit 양 끝 핸들을 선택·조정한다. 화면의 두 반복 구간 중 어느 쪽에서 선택해도 동등한 첫 구간으로 정규화한다. 저장 좌표는 연속된 두 주기 표현을 사용해 `0 ≤ phase_start < 1`, `phase_start < phase_end < phase_start + 1`로 두며, 위상 경계를 통과하면 `phase_end`가 1을 넘을 수 있다. 브라우저와 서버는 `phase(t) = (((t - fold_reference_time_btjd) / period) mod 1 + 1) mod 1`과 `phase_center = ((phase_start + phase_end) / 2) mod 1`을 사용한다. 이어 `epoch = fold_reference_time_btjd + (phase_center + k) × period`에서 관측 범위 안이면서 기준 시각과의 절댓값 차이가 최소인 정수 `k`를 선택하고, 동률이면 더 이른 시각을 택한다. 해당 정수 `k`가 없으면 선택을 유효한 관측 구간으로 조정하기 전까지 제출할 수 없다. `fold_reference_time_btjd`는 각 LightCurve의 DAT-02 품질 필터 후 유효 원본 관측 시각 중앙값을 Bundle에 float64로 한 번 저장한 값이며 브라우저·서버·모든 잔차 단계가 이를 그대로 쓰고 다시 산정하지 않는다. 브라우저 값은 선택 중 화면을 위한 미리보기이며 서버는 제출 시 같은 원본 위상값으로 다시 계산·검증한 값을 최종 저장한다. 주기도 봉우리 선택 시 BLS 예상 통과 위치를 제안 밴드로 표시할 수 있으나 사용자가 접힌 곡선에서 구간을 확정해야 한다. `selection_space`와 epoch 숫자 직접 입력은 제공하지 않는다. `(v0.11)` |

## 5. 매칭 업무 규칙

### 5.1 초기 허용 기준

| 항목 | 초기 기준 |
|---|---|
| 주기 | 허용 고조파를 대표 주기로 환산한 뒤, 관측된 통과 전체에서 누적되는 통과 중심 오차가 후보 지속시간의 1/2 이내여야 한다. 후보 주기 P, 후보 지속시간 D, 실제 관측된 통과 수 N(상한은 DEC-03)에 대해 abs(P_user_corrected − P) × N ≤ D/2. 다중 Sector 별에서 기준선 전체의 주기 횟수를 쓰면 허용 오차가 비현실적으로 작아지므로 N은 관측된 통과 수로 계산한다. `(v0.3)` |
| epoch | 서버가 접힌 곡선의 `phase_start`·`phase_end` 중심 위상을 고정 Bundle의 관측 시각계로 환산한 epoch를 사용한다. 후보 주기로 환산한 순환 위상 차이 min_k abs(epoch_user − epoch_candidate − kP)가 후보 지속시간의 1/2 이내여야 한다. `(v0.11)` |
| 지속시간 | 서버가 `phase_end - phase_start`와 사용자 선택 주기로 계산한 값이 후보값의 0.5배 이상 2배 이하여야 한다. `(v0.11)` |
| 통과 구간 중첩 | 사용자 예상 통과 창은 서버 산정 epoch를 중심으로 서버 산정 duration을 적용해 만든다. 실제 관측점이 존재하는 구간에서 이 창과 후보 예상 통과 창이 겹쳐야 하며, 데이터 공백은 중첩 통과로 계산하지 않는다. 최소 중첩 통과 수·비율은 실측 벤치마크로 확정한다. `(v0.11)` |
| 최소 허용 창 | epoch·통과 중첩 허용 창은 데이터 케이던스의 2배보다 좁게 설정하지 않는다. |
| 고조파 | 초기에는 1/2배와 2배만 허용한다. |
| 매칭 대상 | 현재 곡선 단계에서 아직 제거되지 않은 후보로 한정한다. `(v0.3)` |

주기·epoch·지속시간·통과 구간 중첩 조건은 모두 만족해야 한다. user_judgment는 사용자의 해석을 나타내는 별도 값이며 수치 매칭 결과를 변경하지 않는다.

### 5.2 후보 선택

1. 분석 세션에 고정되어 보존 중인 동일 PublicationBundle의 자체 BLS 후보 중 현재 곡선 단계에서 제거되지 않은 후보만 비교한다. `(v0.11)`
2. 각 후보와 허용 고조파에 대해 주기·epoch·지속시간·통과 중첩 조건을 계산한다.
3. 조건을 만족하는 후보가 없으면 not_matched.
4. 배율 1로 일치하는 후보가 있으면 고조파 일치보다 항상 우선한다. `(v0.3)`
5. 후보가 하나이면 matched 또는 matched_harmonic.
6. 후보가 여러 개이면 정규화한 거리와 통과 구간 중첩을 비교하고, 우세 후보를 안전하게 고르기 어려우면 ambiguous_match.
7. 같은 사용자가 이미 성과를 인정받은 고유 후보에 다시 일치하면 duplicate. 성과 없이 끝난 매칭은 재제출로 판단을 갱신할 수 있다. `(v0.3.1)`
8. not_matched 제출도 Submission과 AnalysisHistory에 남기고 오답 분기와 사용자 선택형 [토론하기]를 제공한다. 토론은 후보 선택·성과 판정과 독립이다. `(v0.11)`

### 5.3 사용자 판단과 별별 성과·등급 `(v0.3)`

- 사용자 판단은 LIKELY_PLANET, UNLIKELY_PLANET, UNSURE 중 하나로 저장한다. 근거 체크는 선택이며 성과에 영향을 주지 않는다.
- 확정 행성 신호는 matched 또는 matched_harmonic과 LIKELY_PLANET일 때 최초 성과를 인정한다. UNLIKELY_PLANET·UNSURE도 수치 매칭과 탐색 완료를 유지하나 성과는 없으며 올바른 재제출로 최초 인정할 수 있다. `(v0.12)`
- 확정 FP 신호에 매칭되고 판단이 UNLIKELY_PLANET이면 FP 판단 성공으로 즉시 인정한다. LIKELY_PLANET·UNSURE면 오답 분기이고, 이후 UNLIKELY_PLANET으로 재제출하면 인정한다.
- 미확정 신호 매칭 뒤 개인 기록을 저장하고 공개는 선택한다. 본인의 분석을 공식 신호 스레드의 공개 분석 목록에 등록할 때 최초 성과를 인정하며 UNSURE도 가능하다. 일반 토론글·댓글·첨부·반응은 등록을 대체하지 않는다. 인정 대기 상태 없이 공개 전에는 미인정이며 종료 후 일괄 공개·히스토리 나중 공개를 지원한다. `(v0.12)`
- 별의 탐색 완료는 현재 탐색 가능한 모든 신호의 매칭 여부로 판정한다. 판단 실패·미공개와 독립이고 완료 자체의 추가 성과는 없다. 무신호 별을 제공하지 않으며 신호가 있지만 탐색 불가능한 경우의 재개 대기는 SUB-11 (4)를 따른다. `(v0.12)`
- 오답 결과에서 [상세 보기]를 선택하고 재제출해 맞힌 경우도 위와 동일하게 인정한다. answer_viewed는 기록만 한다.
- 등급은 사용자·TIC별 표시 문자다. 인정된 고유 신호 성과 수(유형 무관) 1/2/3/4개 이상이면 A/S/SS/SSS. `(v0.13)`
- 성과가 1건 인정될 때마다 GRD-08에 따라 별을 연다. 등급 상승은 열림 조건이 아니다. `(v0.13)`
