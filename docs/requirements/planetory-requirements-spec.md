## 1. 문서 목적과 적용 범위

이 문서는 Planetory 서비스 정책서 v0.6과 이후 확정된 팀 결정을 구현 가능한 기능·데이터·운영·검수 요구사항으로 구체화한다. 사용자 화면과 운영 문서의 공식 서비스명은 Planetory를 사용한다.

요구사항 충돌 시 적용 우선순위는 다음과 같다.

1. 팀이 이후 확정한 명시적 결정
2. Planetory 서비스 정책서 v0.6
3. 이 요구사항 명세서
4. 이전 정책서와 기능명세 초안 (기능명세서 v0.4, 상태표 v0.1~v0.5 포함)

Planetory는 회원 전용 서비스다. 로그인 화면과 OAuth 콜백을 제외한 모든 화면·조회·분석·커뮤니티 기능은 인증 후 이용한다. 회원은 공개 상태이며 삭제·숨김 처리되지 않은 게시글·댓글·첨부 자료를 모두 열람할 수 있다.

탐사 기능은 별도 모드로 나누지 않고 하나의 분석 흐름으로 제공한다. 다만 처음 열리는 튜토리얼 별 다섯 개는 정답이 있는 별로 고정한다 `(v0.3)`. 제출 후에는 외부에서 확정된 대상과 아직 확정되지 않은 대상의 해설 근거와 표현을 구분한다.

분석은 주기·구간을 선택하고 판단을 제출하여 고유 신호를 매칭한 뒤, 남은 신호가 있으면 잔차에서 반복하는 흐름이다. 탐색 가능한 모든 신호의 매칭 여부로 별을 완료하며 판단의 옳고 그름·성과·게시와 분리한다. 자체 BLS 채택 신호가 없어 후보표가 비어 있는 무신호 별은 공개·발견·튜토리얼 대상에서 제외하고 진입 완료·보상을 제공하지 않는다. 주기 신호가 모두 FP인 별도 각 신호를 직접 매칭하고 UNLIKELY_PLANET으로 판단해야 FP 성과를 인정한다. 별 전체의 행성 부재를 선언하는 별도 유형이나 보상은 두지 않는다. 신호는 있지만 현재 관측에서 찾을 수 없는 경우는 무신호와 구분하여 SUB-11의 재개 대기 규칙을 따른다. `(v0.12)`

이 문서는 랭킹·최초 발견 순위·선착순 혜택, 별도 분석 클립보드, PostAnalysisReference·PostReanalysis·ReviewCase 기반 후보 승격, 사용자 단위 누적 등급을 범위에 포함하지 않는다. 이의 제기 기능은 정책 확정 전까지 TBD로 두며 4장 기능 범위에서는 제외한다.

### 1.3 핵심 가치

- 외계행성 탐색의 진입 장벽을 낮춰 누구나 TESS 실측 데이터를 쉽게 분석하고 탐색에 참여할 수 있게 한다.
- 더 많은 사용자가 더 많은 관측 데이터를 탐색하고 신호를 토론·재분석함으로써 새로운 외계행성 후보의 발견 가능성을 높인다.
- 제출마다 분석 근거를 재현 가능한 히스토리로 보존하고, 사용자가 선택한 분석을 커뮤니티에서 자유롭게 공유한다.
- 운영자가 가치 있다고 판단한 게시글을 재현 가능한 보고서로 정리해 전문가에게 제보할 수 있게 한다.

## 2. 핵심 정책 요구사항

| ID | 요구사항 |
|---|---|
| POL-01 | 로그인 화면과 OAuth 콜백 외 모든 서비스 화면과 요청은 인증된 회원만 접근한다. |
| POL-02 | 회원은 공개 상태이며 삭제·운영 숨김 처리되지 않은 일반 게시글·댓글·공식 신호 스레드·공개 분석·첨부를 열람한다. 공개 링크는 원본 공개 상태와 상위 스레드 상태를 조회 때마다 따른다. 개인 히스토리 전체는 본인과 권한 있는 운영자만 조회한다. `(v0.12)` |
| POL-03 | 후보표 매칭과 AI 판정은 항상 배치 산출물을 쓴다. 회원이 보는 잔차 곡선과 잔차 주기도는 EC2 서비스가 Gold의 원본 정제 곡선과 후보별 통과(transit) 모델로 요청 시 계산하는 온라인 파생 계산이다(DAT-14). 배치는 어떤 제거 조합의 잔차·주기도도 사용자 제공용으로 미리 저장하지 않으며, 원본 곡선의 주기도만 저장한다. 같은 Bundle·제거 조합·계산 버전의 결과는 캐시 키(DAT-14)로 재사용한다. 분석 세션은 항상 current PublicationBundle을 쓰며, 새 Bundle이 공개되면 진행 중 세션에 알리고 최신 판으로 재로드한다(EXP-01). 계산 주체·캐시 저장소·동시 실행 상한·검증 기준은 DEC-35(아키텍처 Task). `(v0.11)` |
| POL-04 | 확정 행성 보유 여부는 홈이 아니라 분석 화면에서 제출 전에 표시한다. 보유 여부는 후보표에 실제로 있는 확정 후보를 기준으로 하며, 개수와 상세값은 공개하지 않는다. `(v0.3)` |
| POL-05 | 행성명·주기·지속시간·기준 통과 시각 등 확정 상세 정보는 해당 후보를 매칭한 뒤, 또는 오답 결과에서 사용자가 [상세 보기]를 선택한 뒤 공개한다. 확정 행성 개수는 공개하지 않는다. `(v0.3)` |
| POL-06 | 학습·검증·일반 탐사 모드를 따로 만들지 않는다. 동일 분석 흐름에서 미확정 대상은 정답으로 표현하지 않고 자체 BLS 대표값·AI 후보 적합성 점수·외부 비교값을 구분해 보여준다. |
| POL-07 | 사용자는 현재 시간 영역 곡선(원본 또는 잔차)을 탐색하고 선택한 주기로 같은 곡선을 위상 접기한다. 후보를 매칭한 뒤 사용자가 [다음 곡선]을 요청하면 EC2가 Gold의 원본 정제곡선과 해당 곡선 단계의 제거 후보 조합으로 잔차 곡선을 먼저 계산하고, 그 결과로 잔차 주기도를 계산한다. 동일 캐시 키가 있으면 온라인 캐시를 즉시 사용하며, 준비된 뒤 잔차 단계로 전환한다. 사용자는 원본이나 이전 단계로 복귀할 수 있다. `(v0.11)` |
| POL-08 | transit 구간은 현재 곡선 단계를 선택 주기로 접은 곡선에서만 `phase_start`·`phase_end`로 선택한다. 브라우저는 선택 중인 위상 구간, period와 고정 PublicationBundle이 제공한 `fold_reference_time_btjd`로 미리보기 epoch·duration을 계산하고 시간 영역 곡선에 `epoch + n × period` 예상 transit 구간을 읽기 전용으로 즉시 표시한다. 서버는 제출 시 같은 원본 위상값, period와 같은 `fold_reference_time_btjd`로 epoch를 다시 환산하고 `duration = (phase_end - phase_start) × period`를 다시 계산·검증해 최종값으로 저장한다. 브라우저와 서버는 기준 시각을 각자 재산정하지 않는다. epoch·duration 숫자 직접 입력과 시간 영역 곡선에서의 구간 선택·수정은 제공하지 않는다. `(v0.11)` |
| POL-09 | 허용된 고조파·배수 주기는 대표 주기로 정정하고 matched_harmonic으로 수치 매칭을 인정한다. 성과는 정정 후 같은 고유 신호에 대해 GRD-02~04의 판단·공개 조건을 별도로 적용한다. `(v0.12)` |
| POL-10 | TCE는 외부 후보 원천·비교값이며 자체 BLS 대표 파라미터를 덮어쓰지 않는다. 자체 BLS 기준 미통과 TCE-only 신호는 매칭 후보로 사용하지 않는다. 외부에서 확정된 후보의 대표 주기·epoch를 외부값으로 정렬할지는 DEC-20에서 정한다. `(v0.3)` |
| POL-11 | AI 점수는 팀이 직접 운영하는 모델의 배치 추론으로 산출한다. ExoMiner++ 공개 카탈로그 점수는 사용하지 않으며 비교·검증 용도는 TBD다. `(v0.3)` |
| POL-12 | BLS 후보 성과와 AI 후보 판정은 서로 독립적으로 기록한다. |
| POL-13 | 신호 분석 제출(submission_kind=candidate)에는 사용자 판단 LIKELY_PLANET, UNLIKELY_PLANET, UNSURE 중 하나를 필수로 저장한다. P0에서 선택 가능한 근거 체크는 홀짝 깊이, 2차 식, V·U형의 세 종류다. 품질 플래그는 배치 전처리(DAT-02)에서만 쓰고 화면에 전달하지 않으므로 근거 항목으로 두지 않는다. 중심 위치는 필요한 픽셀·centroid 입력이 없어 `데이터 없음`인 비활성·읽기 전용 상태로 표시하며 근거로 접수하거나 후보 매칭·성과·근거 통계에 반영하지 않는다. 사용자 판단은 배치 후보값·AI·외부 상태를 덮어쓰지 않는다. no_candidate·skipped에는 판단·근거를 강제하지 않는다(SUB-01·12). `(v0.12)` |
| POL-14 | 후보표와 일치하지 않는 제출은 not_matched Submission과 AnalysisHistory로 보존하되 Candidate나 별도 후보 제안·군집·재현·검토 엔티티로 자동 전환하지 않는다. 사용자는 결과에서 [토론하기]를 선택해 같은 TIC의 별 스레드에 현재 AnalysisHistory를 첨부한 DISCUSSION 글을 직접 작성할 수 있다. 최종 게시 전에는 Post를 생성하지 않으며 게시해도 후보·성과·등급·곡선 단계는 바뀌지 않는다. `(v0.11)` |

## 3. 전체 흐름

### 3.1 배치 흐름

대상 선정 → 원천 등록 → TESS LC 수집 → Sector별 전처리 → 원본 정제곡선·주기도 생성 → BLS 후보 탐색 → 후보 모델 적합·내부 신호 제거 → Silver 내부 잔차 BLS 반복(후보 탐색용 중간 결과, 사용자용 잔차 곡선·주기도는 저장하지 않음) → 후보 병합 → 외부 TCE·TOI 연결 → AI 입력 생성 → 자체 모델 추론·판정 → 원본 탐색 가능성 검증 → Gold용 원본 곡선(비닝된 전 구간)·후보별 통과 모델·원본 주기도와 공개 묶음 검증 → 원자적 공개 `(v0.11)`

### 3.2 사용자 흐름 `(v0.3)`

로그인 → 튜토리얼 별과 열린 별, 내 TIC별 진행이 통합된 홈 → 별 선택 → 분석 시작 시 현재 PublicationBundle 로드 → 확정 행성 보유 여부 확인 → 현재 시간 영역 곡선·주기도 탐색 → 주기도에서 주기 재선택 또는 현재 주기 미세 조정 → 브라우저가 현재 곡선을 새 주기로 접음 → 접힌 곡선에서 transit 위상 시작·끝 선택 → 브라우저가 epoch·duration과 시간 영역 예상 구간을 즉시 미리보기 → 사용자 판단(+선택 가능한 근거 체크) 선택 → 제출 → 서버가 epoch·duration 최종 재계산·검증 → 후보표 매칭 → AnalysisHistory 자동 저장 → `(v0.11)`

- 정답 있는 후보: 매칭·판단·성과를 각각 표시 → 남은 탐색 가능 신호가 있으면 [다음 곡선] 요청 시 EC2 온라인 잔차·주기도 계산 → 다음 신호 탐색. 판단을 틀려도 매칭 진행은 유지 `(v0.12)`
- 미확정 후보: 개인 기록 저장·성과 미인정 → 게시 없이 다음 신호 탐색 가능 → 결과·히스토리에서 개별 공개 또는 종료 후 [모두 게시]/[나중에] → 공개 성공한 고유 신호만 최초 성과 인정(COM-19) `(v0.12)`
- 오답: [상세 보기] / [다시 풀기] → 제출 당시 곡선·입력 복원 후 새 제출. 수치 매칭 실패와 판단 실패를 구분한다. not_matched의 [토론하기]는 일반 DISCUSSION 글이며 공식 신호·공개 분석·성과를 자동 생성하지 않음 `(v0.12)`
- 현재 탐색 가능한 신호를 모두 매칭: 탐색 완료 표시. 마지막 제출의 성과 인정은 별도로 판정하며, 오판이면 "탐색 완료 / 판단 불일치 / 성과 미인정"을 함께 표시. 탐색 불가능 신호만 남으면 재개 대기. 완료 후에도 재도전·공개 가능 `(v0.12)`

고유 신호 성과가 인정될 때마다 새 별이 열린다(POL-27). `(v0.13)`

### 3.3 커뮤니티 흐름

회원이 별 게시판 또는 전체 피드에서 자유양식 글 작성 → 관련 별 자동 선택 또는 직접 선택 → 같은 별의 본인 히스토리 첨부·공개 출처 링크 선택 → 최종 게시. 별 미선택 자유글에는 별 자료 선택·첨부를 제공하지 않는다. 미확정 분석 공개는 별도 흐름으로, 대상 기록 검토 → 공식 신호 스레드 확보(SYSTEM 최초 생성 또는 기존 공간 재사용) → 공개 분석 목록 등록 → 성과 및 공개 판단 통계 갱신이다. 토론 댓글·반응은 자동 생성하지 않는다. 신호 스레드의 세 판단 필터와 통계는 일반 별 토론글에서도 같은 출처로 연결한다. `(v0.12)`

전문가 제보는 운영자가 공개 게시글 선택 → 시스템 보고서 생성 → 운영자 내용·수신자 확인 → 시스템 이메일 발송 → 발송 상태·수신자·시각·오류 기록 순서로 진행한다. 커뮤니티 제보 경로는 후보표·AI 판정·후보 ID를 변경하지 않는다.

| EXP-06 | transit 위상 구간·epoch 자동 산정 | P0 | 사용자는 현재 곡선 단계를 선택 주기로 접은 곡선에서만 transit 양 끝 핸들을 선택·조정한다. 화면의 두 반복 구간 중 어느 쪽에서 선택해도 동등한 첫 구간으로 정규화한다. 저장 좌표는 연속된 두 주기 표현을 사용해 `0 ≤ phase_start < 1`, `phase_start < phase_end < phase_start + 1`로 두며, 위상 경계를 통과하면 `phase_end`가 1을 넘을 수 있다. 브라우저와 서버는 `phase(t) = (((t - fold_reference_time_btjd) / period) mod 1 + 1) mod 1`과 `phase_center = ((phase_start + phase_end) / 2) mod 1`을 사용한다. 이어 `epoch = fold_reference_time_btjd + (phase_center + k) × period`에서 관측 범위 안이면서 기준 시각과의 절댓값 차이가 최소인 정수 `k`를 선택하고, 동률이면 더 이른 시각을 택한다. 해당 정수 `k`가 없으면 선택을 유효한 관측 구간으로 조정하기 전까지 제출할 수 없다. `fold_reference_time_btjd`는 각 LightCurve의 DAT-02 품질 필터 후 유효 원본 관측 시각 중앙값을 Bundle에 float64로 한 번 저장한 값이며 브라우저·서버·모든 잔차 단계가 이를 그대로 쓰고 다시 산정하지 않는다. 브라우저 값은 선택 중 화면을 위한 미리보기이며 서버는 제출 시 같은 원본 위상값으로 다시 계산·검증한 값을 최종 저장한다. 주기도 봉우리 선택 시 BLS 예상 통과 위치를 제안 밴드로 표시할 수 있으나 사용자가 접힌 곡선에서 구간을 확정해야 한다. `selection_space`와 epoch 숫자 직접 입력은 제공하지 않는다. `(v0.11)` |

| EXP-08 | 위상 접기 미리보기 | P0 | 브라우저는 현재 시간 영역 곡선의 유효 관측점 전체, 선택 주기와 Bundle의 `fold_reference_time_btjd`로 접힌 곡선을 생성하며 epoch 입력에 의존하지 않는다. 슬라이더 입력 중에도 클라이언트에서 새 주기로 다시 접어 즉시 표시하고, 위상 구간 선택 뒤에는 미리보기 epoch·duration과 시간 영역 예상 transit 밴드를 같은 상태에서 계산한다. 이 미리보기 계산은 BLS·잔차 온라인 계산을 다시 실행하지 않는다. 주기 재선택과 미세 조정 모두 새 주기로 다시 접고 완료 전 구간 선택·판단·제출을 비활성화한다. Web Worker 등 비동기 클라이언트 계산을 쓰면 revision으로 최신 작업만 반영하고, 실패하면 마지막 성공 주기·접힌 곡선·작성 중 상태로 원자적으로 복구한다. 제출 성공 뒤에는 서버가 같은 기준 시각으로 다시 계산한 최종 epoch·duration을 반영하며, 미리보기는 서버 검증·판정을 대체하지 않는다. `(v0.11)` |
| EXP-09 | 다중 후보 탐색·잔차 전환 | P0 | 후보를 매칭한 뒤 [다음 곡선] 요청 시 EC2가 현재 Bundle의 원본에서 해당 단계의 제거 후보 조합에 포함된 통과 모델을 제거해 잔차 곡선을 먼저 계산하고 그 잔차로 주기도를 계산한다. 요청 상태는 최소 `QUEUED → RESIDUAL_CALCULATING → RESIDUAL_READY → PERIODOGRAM_CALCULATING → COMPLETED/FAILED`를 표현한다. `RESIDUAL_READY`에서 곡선을 먼저 노출할지는 벤치마크로 정하되 주기도가 잔차보다 먼저 준비될 수 없다. 전체 결과가 준비되면 잔차 단계로 전환하며 어떤 매칭 순서의 제거 조합도 지원한다. 원본과 이전 단계로 복귀할 수 있고, 목표 시간을 넘기면 대기 안내와 재시도를 제공한다(목표 수치는 DEC-16 TBD). 판단 불일치·미공개도 수치 매칭 이후 다음 단계 요청을 허용한다. 계산 실패는 이미 저장한 매칭·완료·성과를 되돌리지 않으며 마지막 정상 곡선을 유지해 재시도한다. 과거 제출 재도전은 그 제출 단계에서 계산하되 누적 탐색 진행을 과거 상태로 덮어쓰지 않는다. `(v0.12)` |
| EXP-10 | 분석 상태·복귀 정보 보존 | P0 | 일시적 통신 오류 후 TIC, 그때의 PublicationBundle, 현재 곡선 단계·제거 후보 조합, 선택 주기, 접힌 곡선의 `phase_start`·`phase_end`, 판단·유효 근거·메모, 주기도 확대·이동 범위와 접힌 곡선 x축 확대 배율(`folded_x_zoom_ratio`)을 구분해 복원한다. 미제출 초안의 epoch·duration은 저장된 위상 원본값에서 브라우저가 다시 만드는 미리보기이고, 제출·히스토리에는 서버 최종 파생값을 사용한다. 게시글에서 진입한 경우 return_post_id를 URL 또는 임시 세션에만 유지하고, 복귀 시 Post가 같은 TIC이며 공개·미삭제·미숨김 상태인지 서버에서 다시 검사하며 영속 재분석 관계는 만들지 않는다. `(v0.11)` |
| EXP-11 | 판별 도구 | P0 | 접힌 곡선에서 홀수·짝수 통과 중앙값 비교, 위상 0.5 부근(2차 식) 확대, 통과 모양(V·U형) 확인과 품질 마스킹 구간 표시를 제공하며 선택 가능한 네 근거와 일대일로 대응한다. 중심 위치는 픽셀 이미지·difference image·사전 계산 centroid 진단값이 현재 P0 입력에 없으므로 `중심 위치: 데이터 없음`으로 비활성·읽기 전용 표시한다. 데이터 없음은 중심 이동 없음이 아니며 판단·매칭·성과·근거 통계에 반영하지 않는다. `(v0.11)` |

| EXP-13 | 접힌 곡선 조작 | P0 | 접힌 곡선은 새 접기 중심을 가운데에 두고 ±1주기 눈금을 표시한다. 평상시 휠 조작은 마우스 포인터를 기준으로 x축만 확대·축소(×1~8)하고 더블클릭하면 전체 보기 ×1로 돌아간다. 차트에 키보드 포커스가 있으면 `+`·`-`로 차트 중앙 기준 `×1 → ×2 → ×4 → ×8` 단계를 이동하고 `0`으로 ×1에 복귀하며 y축 범위는 바꾸지 않는다. 확대 상태는 절대 x 범위가 아니라 `folded_x_zoom_ratio`로 관리한다. 주기 미세 조정 시 같은 배율을 새 접기 중심에 다시 적용하고, 직전 포인터 위치·x축 이동 위치·y축 상태·transit 밴드는 유지하지 않는다. 주기 재선택 시 배율은 ×1이다. 선택 범위는 밴드와 양쪽 핸들로 표시하고 핸들을 끌어 조정한다. 주기도에는 이미 매칭한 후보의 주기를 흐린 선으로 표시하고 상위 봉우리에 번호를 붙인다. `(v0.11)` |

| SUB-12 | 튜토리얼 건너뛰기 | P0 | 같은 튜토리얼 별에서 본인 제출 중 수치 불일치(not_matched·none_wrong)와 판단 불일치(matched·matched_harmonic이지만 성과 미인정, achievement_result=judgment_mismatch)를 합한 횟수가 서버 설정 `tutorial_skip_after`(개발 환경 3, 운영 환경 0=끔) 이상이면 오답 분기의 [상세 보기] 화면 끝에 [다음 튜토리얼로]를 제공한다. 별도 건너뛰기 버튼은 두지 않으며 정답 신호 해설을 본 뒤에만 넘어갈 수 있다. 실행하면 그 별을 completion_reason=skipped로 완료 처리하고 다음 순번을 발견 처리하며, 성과·등급·별 열림은 없고 히스토리에 skipped 제출을 남긴다. 튜토리얼이 아닌 별에는 제공하지 않는다. `(v0.13)` |

| DAT-11 | 공개 묶음 | P0 | 원본 정제곡선의 모든 점(비닝된 배열)·각 LightCurveSegment의 `fold_reference_time_btjd`·원본 주기도·후보표·후보별 통과 모델·AI 결과·외부 상태·계산 설정 버전·주기 격자 간격과 미세 조정 허용 폭 규칙(EXP-05)을 하나의 PublicationBundle로 검증한 뒤 원자적으로 공개한다. `fold_reference_time_btjd`는 DAT-02 품질 필터를 통과하고 time·flux가 유한한 원본 정제곡선 관측 시각을 정렬한 중앙값으로 산정해 float64 round-trip 정밀도로 저장·전달한다. 온라인 잔차는 원본과 같은 관측 시각 인덱스와 이 기준 시각을 상속한다. 사용자용 단계별 잔차 곡선·주기도는 포함하지 않는다. 원본 정제곡선은 별·섹터 단위 세그먼트로 나누어 섹터 안에서 10분 고정 간격으로 비닝해 저장하고(한 세그먼트가 20,000점을 넘으면 간격을 넓히고 실제 간격을 함께 기록), 밝기 오차는 배열 대신 세그먼트당 산포 스칼라로 둔다. 세그먼트는 원천·전처리·비닝 revision으로 식별하며, 같은 섹터를 다시 비닝하면 기존 행을 덮어쓰지 않고 새 revision을 만들고 manifest가 참조하는 세그먼트 id 집합만 바꾼다. 어느 판도 참조하지 않게 된 세그먼트는 정리한다. 곡선 세그먼트는 판에 묶이지 않으므로 판이 바뀌어도 다시 적재하지 않고, 원본 주기도는 판 단위로 둔다. 새 Bundle이 `current`가 되면 이전 판은 곧바로 `archived`가 되어 그 판의 주기도 행과 캐시를 정리한다. 진행 중 분석은 최신 판으로 올린다(EXP-01). 판 행 자체는 과거 제출이 참조하므로 지우지 않는다. 후보가 추가되면 영향 받는 회원에게 알린다. `(v0.14)` |
| DAT-12 | 배치 실패 복구 | P0 | 새 배치가 실패하면 기존 공개본을 유지하고 실패 대상·단계만 재처리할 수 있다. |
| DAT-14 | 온라인 파생 계산 | P0 | EC2 서비스는 현재 PublicationBundle의 원본 정제곡선과 후보별 통과 모델 파라미터를 입력으로 회원이 고른 제거 조합의 잔차 곡선을 먼저 계산하고, 그 잔차로 주기도를 계산한다. 캐시 키는 (tic_id, publication_bundle_id, 정렬한 제거 후보 id 목록, residual_model_version, periodogram_config_version)이다. 상태는 `QUEUED`, `RESIDUAL_CALCULATING`, `RESIDUAL_READY`, `PERIODOGRAM_CALCULATING`, `COMPLETED`, `FAILED`를 표현하고 실패 단계·원인·재시도를 제공한다. 캐시는 재생성 가능한 데이터이므로 서비스 DB 테이블이 아니라 **Redis**에 상태와 결과를 함께 두고, Redis가 비면 다시 계산한다. 같은 키를 여러 서버가 동시에 요청하면 한 서버만 계산하도록 잠근다. 새 Bundle은 새 키를 쓰고 서로 다른 Bundle·계산 버전 사이에는 캐시를 재사용하지 않으며, 판이 `archived`가 되면 그 판의 캐시를 정리한다. 계산 위치(Java 내장/사이드카), 동시 실행 상한, 계산 시간 목표와 배포 전 잔차 일치 검증은 DEC-35. `(v0.14)` |
| DAT-15 | 재개·외부 갱신 이벤트 | P0 | 새 TESS 곡선 유입으로 후보의 discoverable이 false → true가 되거나 후보가 추가되면 완료 별 재개 이벤트(DEC-27)를 만들어 진행 단계·알림·퀘스트 카드에 반영한다. TCE/TOI 갱신은 CandidateDisposition·ai_status·CandidateStatusHistory만 바꾸고, 성과·등급·통계 스냅샷은 v1에서 바꾸지 않는다(GRD-06, DEC-26). `(v0.9)` |
| DAT-13 | 통계 집계 | P1 | 비교 기준선(STA-03, 최근 90일 제출 회원 중앙값)은 일 1회 집계해 StatsSnapshot으로 저장한다. 전체 통계(STA-02)는 materialized view로 10분마다 REFRESH CONCURRENTLY한다(회원 1만·제출 600만 규모에서 전 항목 실시간 계산은 부적합). 회원 식별 정보는 넣지 않는다. 채점형 일치율은 COM-14 (2)와 같은 산식(회원당 첫 매칭 제출 기준)을 쓰고, 미확정 공개 분석 통계는 COM-14 (1)로 별도 계산한다. `(v0.13)` |

## 5. 매칭 업무 규칙

### 5.1 초기 허용 기준

| 항목 | 초기 기준 |
|---|---|
| 주기 | 허용 고조파를 대표 주기로 환산한 뒤, 관측된 통과 전체에서 누적되는 통과 중심 오차가 후보 지속시간의 1/2 이내여야 한다. 후보 주기 P, 후보 지속시간 D, 실제 관측된 통과 수 N(상한은 DEC-03)에 대해 abs(P_user_corrected − P) × N ≤ D/2. 다중 Sector 별에서 기준선 전체의 주기 횟수를 쓰면 허용 오차가 비현실적으로 작아지므로 N은 관측된 통과 수로 계산한다. `(v0.3)` |
| epoch | 서버가 접힌 곡선의 `phase_start`·`phase_end` 중심 위상을 현재 Bundle의 관측 시각계로 환산한 epoch를 사용한다. 후보 주기로 환산한 순환 위상 차이 min_k abs(epoch_user − epoch_candidate − kP)가 후보 지속시간의 1/2 이내여야 한다. `(v0.11)` |
| 지속시간 | 서버가 `phase_end - phase_start`와 사용자 선택 주기로 계산한 값이 후보값의 0.5배 이상 2배 이하여야 한다. `(v0.11)` |
| 통과 구간 중첩 | 사용자 예상 통과 창은 서버 산정 epoch를 중심으로 서버 산정 duration을 적용해 만든다. 실제 관측점이 존재하는 구간에서 이 창과 후보 예상 통과 창이 겹쳐야 하며, 데이터 공백은 중첩 통과로 계산하지 않는다. 최소 중첩 통과 수·비율은 실측 벤치마크로 확정한다. `(v0.11)` |
| 최소 허용 창 | epoch·통과 중첩 허용 창은 데이터 케이던스의 2배보다 좁게 설정하지 않는다. |
| 고조파 | 초기에는 1/2배와 2배만 허용한다. |
| 매칭 대상 | 현재 곡선 단계에서 아직 제거되지 않은 후보로 한정한다. `(v0.3)` |

주기·epoch·지속시간·통과 구간 중첩 조건은 모두 만족해야 한다. user_judgment는 사용자의 해석을 나타내는 별도 값이며 수치 매칭 결과를 변경하지 않는다.

### 5.2 후보 선택

1. 제출을 판정하는 현재 PublicationBundle의 자체 BLS 후보 중 현재 곡선 단계에서 제거되지 않은 후보만 비교한다. `(v0.14)`
2. 각 후보와 허용 고조파에 대해 주기·epoch·지속시간·통과 중첩 조건을 계산한다.
3. 조건을 만족하는 후보가 없으면 not_matched.
4. 배율 1로 일치하는 후보가 있으면 고조파 일치보다 항상 우선한다. `(v0.3)`
5. 후보가 하나이면 matched 또는 matched_harmonic.
6. 후보가 여러 개이면 정규화한 거리와 통과 구간 중첩을 비교하고, 우세 후보를 안전하게 고르기 어려우면 ambiguous_match.
7. 같은 사용자가 이미 성과를 인정받은 고유 후보에 다시 일치하면 duplicate. 성과 없이 끝난 매칭은 재제출로 판단을 갱신할 수 있다. `(v0.3.1)`
8. not_matched 제출도 Submission과 AnalysisHistory에 남기고 오답 분기와 사용자 선택형 [토론하기]를 제공한다. 토론은 후보 선택·성과 판정과 독립이다. `(v0.11)`

### 5.3 사용자 판단과 별별 성과·등급 `(v0.3)`

- 사용자 판단은 LIKELY_PLANET, UNLIKELY_PLANET, UNSURE 중 하나로 저장한다. 근거 체크는 선택이며 성과에 영향을 주지 않는다.
- 확정 행성 신호는 matched 또는 matched_harmonic과 LIKELY_PLANET일 때 최초 성과를 인정한다. UNLIKELY_PLANET·UNSURE도 수치 매칭과 탐색 완료를 유지하나 성과는 없으며 올바른 재제출로 최초 인정할 수 있다. `(v0.12)`
- 확정 FP 신호에 매칭되고 판단이 UNLIKELY_PLANET이면 FP 판단 성공으로 즉시 인정한다. LIKELY_PLANET·UNSURE면 오답 분기이고, 이후 UNLIKELY_PLANET으로 재제출하면 인정한다.
- 미확정 신호 매칭 뒤 개인 기록을 저장하고 공개는 선택한다. 본인의 분석을 공식 신호 스레드의 공개 분석 목록에 등록할 때 최초 성과를 인정하며 UNSURE도 가능하다. 일반 토론글·댓글·첨부·반응은 등록을 대체하지 않는다. 인정 대기 상태 없이 공개 전에는 미인정이며 종료 후 일괄 공개·히스토리 나중 공개를 지원한다. `(v0.12)`
- 별의 탐색 완료는 현재 탐색 가능한 모든 신호의 매칭 여부로 판정한다. 판단 실패·미공개와 독립이고 완료 자체의 추가 성과는 없다. 무신호 별을 제공하지 않으며 신호가 있지만 탐색 불가능한 경우의 재개 대기는 SUB-11 (4)를 따른다. `(v0.12)`
- 오답 결과에서 [상세 보기]를 선택하고 재제출해 맞힌 경우도 위와 동일하게 인정한다. answer_viewed는 기록만 한다.
- 등급은 사용자·TIC별 표시 문자다. 인정된 고유 신호 성과 수(유형 무관) 1/2/3/4개 이상이면 A/S/SS/SSS. `(v0.13)`
- 성과가 1건 인정될 때마다 GRD-08에 따라 별을 연다. 등급 상승은 열림 조건이 아니다. `(v0.13)`

| NFR-20e | 렌더 객체 재사용 | 별 본체·성운은 인스턴스 렌더링(드로우콜 배율당 1~2개)으로 그린다. 궤도는 별마다 객체를 만들지 않고 화면 안 궤도만 하나의 버퍼로 합쳐 그린다. 툴팁·퀘스트 배지·궤도 라벨 같은 DOM 요소는 화면에 보이는 것만 재사용 풀에서 꺼내 쓰고 화면을 벗어나면 회수한다. `(v0.7)` |
