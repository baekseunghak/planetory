## 1. 목적과 작성 방법

회원·커뮤니티·통계 백엔드의 기능을 하나씩 검토하고, 구현할 조건과 제외할 조건을 결정한다. 기능명만 나열하지 않고 누가 어떤 상태에서 요청했는지, 무엇을 저장·공개하는지, 실패·중복·변경 시 어떤 결과를 보장하는지까지 정한다.

표기 규칙:

- **기준 확정:** SRS v0.12에 이미 명시된 정책. 다시 선택하지 않는다.
- **결정 질문:** 구현 전에 답해야 할 누락·모호함. 질문의 선택지는 확정 정책이 아니다.
- **충돌:** 기준 문장들을 동시에 적용하기 어려운 경우. 관련 담당자와 정리한다.
- **계약 초안:** API·데이터·이벤트에 담아야 할 의미. URL·테이블·메시지 제품은 확정하지 않는다.
- **검증 사례:** 결정 후 기대 결과까지 채워 인수 조건으로 사용한다. 미결정 사례는 현재 통과 조건이 아니다.

각 기능은 `기준 확인 → 결정 질문 답변 → 포함/제외 범위 확정 → 계약 작성 → 사례 검토 → 합의 완료` 순서로 진행한다. 결정 기록은 7장에 남기고 해당 기능에 반영한다. 적용 순서는 최신 사용자 보충 결정 → SRS v0.12 → 충돌하지 않는 이전 결정이다. 보충 결정은 명시한 항목만 대체하며 미결정 사항은 합의 전 확정하지 않는다. 별도 보충 결정이 없는 상태표와의 충돌은 SRS를 따른다.

### 이번 작업의 범위

### F01. OAuth 회원 식별·가입

**v0.12 가입 초기화:** 튜토리얼은 1번만 먼저 발견하고 완료 시 다음 순번을 연다. 무신호 별 자동 완료·가입 보상은 없으며 챌린지 별은 튜토리얼 5개 완료 후에만 발견한다. 프로필 초기값과 실패 재시도 계약은 계속 협의한다.

**2026-09-07 검토 반영:** 초기 개발에서는 다중 제공자 연결을 제공하지 않는다. Google·SSAFY 로그인은 서로 다른 계정으로 운영하고 연결·병합은 추후 검토한다(SB-D01). 서비스 내 이메일 수정 기능은 제공하지 않는 방향이며, 수집 여부·제공자 이메일 변경 동기화·실제 스키마는 아직 미정이다(SB-D02). F01-Q1은 초기 범위 결정, Q2~Q5는 일부/전체 미결정이다.

**기준 확정:** SSAFY·Google 제공자 고유 ID로 회원을 식별한다. 같은 제공자 고유 ID의 재로그인은 동일 회원이다. 제공자가 다른 같은 이메일 계정을 자동 병합하지 않는다(ACC-01~02).

**결정 질문**

- F01-Q1: 초기 다중 제공자 연결·병합은 제외 확정(SB-D01). 제공자별 식별 조합의 물리 컬럼·유일성 제약은 DB 담당자와 정한다.
- F01-Q2: 이메일·이름 등 제공자 정보 중 필수 수집·선택 수집·미수집 항목은 무엇인가? 이메일이 없거나 바뀌어도 같은 subject를 유지하는가?
- F01-Q3: 최초 닉네임을 자동 생성하는가, 별도 입력 완료 후 가입하는가? 가입 도중 이탈 상태를 저장할 필요가 있는가?
- F01-Q4: 탈퇴한 제공자 ID 재로그인은 거부·재가입·복구 중 무엇인가? F04와 함께 결정한다.
- F01-Q5: 최초 회원 생성에 튜토리얼 발견·첫 방문 설정까지 포함하는가? 초기화 실패 시 회원 생성도 취소하는가, 재로그인으로 재시도하는가?

**계약 초안:** 제공자 식별 정보 → 내부 회원 ID·신규 여부·프로필 완료 여부. 제공자 원본 ID를 공개 프로필 응답에 포함하지 않는다. 중복 가입 방지는 제공자 식별 조합을 기준으로 정의한다.

**검증 사례:** 동일 ID 동시 첫 로그인 / 서로 다른 제공자의 동일 이메일 / 제공자 이메일 변경 / 필수 정보 누락 / 탈퇴 후 재로그인 / 튜토리얼 초기화 실패.

**범위 결정:** 초기 계정 연결·병합은 제외 확정. 계정 복구·추가 가입 단계는 미결정이다. OAuth 연결 설정과 인증 코드는 후속 구현이다.

### F02. 인증 상태·로그아웃·회원 상태

**최신 방향(SB-D11):** 세션 방식 로그인을 우선 검토한다. 최종 기술 확정은 아니며 저장소(메모리/Redis), 유휴 만료·활동 갱신, 재시작 후 유지 정책은 별도 결정한다. 세션을 선택해도 401/403 계약은 유지한다. 후속 인증 설계에는 세션 쿠키의 HttpOnly·Secure·SameSite, 프론트 배치에 따른 쿠키 전달·CSRF 방어, 로그인 시 세션 ID 교체·로그아웃 무효화를 포함한다.

**실행 구성 결정(2026-09-09, SB-D07):** 사용자 요청을 받는 Spring Boot는 EC2 한 대에서 실행한다. 필요에 따라 각 EC2에 저장된 서비스 RDB·Gold 데이터를 조회한다. EC2 두 대는 데이터 배치 구분이며 동일 백엔드 두 인스턴스를 뜻하지 않는다. Spring Boot를 어느 EC2에 배치할지, 원격 Gold 접근을 내부 API 등 어떤 방식으로 제공할지는 별도 설계한다. 서버 간 세션 공유는 현 구성의 필수 요구가 아니며 Redis 도입은 로그인 보존·운영 요구에 따라 검토한다.

**2026-09-07 검토 반영:** 인증 없음/만료는 401이며 프론트가 재로그인을 안내한다. 인증됐으나 권한이 부족하면 기본 403과 권한 부족 안내를 사용한다(SB-D03). 존재를 숨길 자원의 404 적용 대상은 미결정이다. 유휴 30분·화면 조작이 있는 경우 5분 간격 갱신은 검토안이다. Redis는 세션 저장소 후보이며 서버 간 공유를 필수 도입 근거로 삼지 않는다(SB-D07). 프로필 변경과 탈퇴 등 회원 상태 변경은 구분하며, 프로필 변경 시 토큰 이중 갱신은 확정하지 않는다.

활동 갱신 추가 검토: ‘마지막 조작 후 5분 기다림’과 ‘5분마다 지난 구간 활동 확인’을 구분한다. 후자는 지속 조작에도 주기적으로 갱신할 수 있다. 자동 폴링의 세션 연장 여부, 백그라운드 탭/절전 복귀, 이미 만료된 세션의 갱신 거부, 다중 탭, 서버 수신 시각 기준 유휴 시간의 오차를 합의해야 한다. Spring Session 기본 접근 시간 갱신과 사용자 활동 기준이 자동으로 일치한다고 가정하지 않는다.

**기준 확정:** 로그인·콜백 외 보호 요청은 인증 필요. 로그아웃 후 보호 데이터에 재접근할 수 없다. 서버에서 역할·소유권을 검사한다(ACC-03~04, NFR-06~07).

**결정 질문**

- F02-Q1: 회원 상태와 전이는 무엇인가? 정상·탈퇴 외 이용정지 등은 도입 여부부터 정한다. 회원 차단과 운영 제재를 혼동하지 않는다.
- F02-Q2: 로그아웃은 현재 로그인만 종료하는가, 모든 기기를 종료하는가? 이미 종료된 로그인에 재요청하면 어떤 결과인가?
- F02-Q3: 인증 없음/만료 401·일반 권한 부족 403은 확정(SB-D03). 존재를 숨길 자원의 404 적용 대상과 오류 응답 형식만 추가 결정한다.
- F02-Q4: 회원 상태 변경 시 기존 로그인 무효화 시점과 처리 중 요청의 허용 기준은 무엇인가? 탈퇴와 콘텐츠 작성의 경합은 SB-D04로 결정했다(F04). 로그인 무효화 구현과 그 외 상태 변경은 별도 합의한다.
- F02-Q5: 단일 Spring Boot에서 로그인 유지 기간·활동 연장·동시 로그인·애플리케이션 재시작 후 로그인 유지 정책은 무엇인가? 메모리 세션 또는 Redis 등 저장 기술은 별도 선택이며, EC2 두 대에 데이터가 있다는 이유로 공유 세션을 요구하지 않는다.

**계약 초안:** 인증 상태 조회는 내부 회원 식별·상태·권한·최소 프로필만 반환. 인증 실패와 권한 부족을 구분하며 토큰·비밀값은 응답·로그에 노출하지 않는다.

**검증 사례:** 만료 후 요청 / 로그아웃 반복 / 애플리케이션 재시작 후 요청 / 탈퇴 직전 시작된 쓰기 / 일반 회원의 운영 API 요청.

### F04. 탈퇴·보관·익명화

**우선순위 변경(2026-09-08, SB-D05):** 탈퇴 데이터 처리는 P1로 미룬다. 보관·익명화·표시·재가입 정책은 지금 선택하지 않고 P1 착수 시 검토한다. SB-D04의 탈퇴·작성 경합 규칙은 유지하며, 이번 변경을 이유로 soft delete나 글 보존을 확정하지 않는다.

**구현 시점 구분:** 경합 규칙의 P0 표시는 인증·쓰기 설계에서 지킬 제약이며 탈퇴 API의 P0 출시 확정을 뜻하지 않는다. 탈퇴 API 제공 시점은 보류다. 탈퇴를 제공하는 시점에는 접근 차단과 경합 처리를 함께 적용하고, 보관 정책이 미정인 채 탈퇴 API만 먼저 출시하지 않는다. 현재 P0에서는 이 정책을 설계 조건으로 기록하며 미제공 기능을 위한 별도 처리 흐름을 선행 구현하지 않는다.

**2026-09-07 검토 반영:** 탈퇴 순간 처리 중인 작성 요청을 모두 완료시키는 안 대신, 탈퇴와 작성의 DB 저장 확정 순서로 처리하기로 결정했다(SB-D04). 회원 soft delete, 기존 글 보존, 프로필 접근 제한은 계속 검토한다. Soft delete는 기록을 남기는 방법이며 탈퇴 후 쓰기 권한을 유지한다는 뜻이 아니다. 프로필의 ‘비공개 계정’ 문구, 제공자 ID·개인정보 보관 정책도 별도 결정한다.

**부분 확정 — 탈퇴와 콘텐츠 작성의 동시 처리(SB-D04)**

- 기준은 클라이언트 요청/응답 시각이나 서버 접수 시각이 아니라 DB 저장 확정 순서다. 탈퇴 효력 발생 시점은 탈퇴 상태가 DB에 확정된 시점이다.
- 글·댓글 작성이 먼저 확정되면 작성은 성공한 것으로 처리한다. 그 콘텐츠의 이후 보존·익명화·공개 여부는 별도 탈퇴 정책을 따른다.
- 탈퇴가 먼저 확정되면 아직 확정되지 않은 글·댓글 작성은 거부한다. 탈퇴 전에 접수된 요청이라도 예외를 두지 않는다.
- 거부한 작성과 연결된 Post/Comment·첨부·성과·등급 변경·별 발견·알림 사건은 새로 생성하거나 반영하지 않는다. 연관 저장을 일부만 남기지 않는다.
- 이미 별도 요청으로 확정된 Submission·AnalysisHistory 등은 거부된 게시 요청 때문에 되돌리지 않는다. 기존 데이터의 탈퇴 처리는 F04-Q2~Q4에서 결정한다.
- 탈퇴 완료 후 작성 재요청으로 신규 콘텐츠가 생성되지 않아야 한다. 탈퇴 전에 성공한 요청도 재전송으로 중복 생성하지 않는다. 탈퇴 후 과거 성공 응답 재조회 허용 여부와 거부 응답 코드는 API 계약에서 별도 결정한다.
- 요청 시작 시 회원 상태 확인만으로 완료하지 않는다. 단일 백엔드 안에서 여러 요청이 동시에 실행돼도 탈퇴와 작성의 순서를 DB에서 보장하고, 탈퇴 확정 뒤 작성이 커밋되지 않도록 한다. 구체적인 잠금·트랜잭션 방식은 후속 설계 대상이다.
- 탈퇴 전에 확정된 글에서 이미 생성된 알림 사건의 지연 발송·취소 여부는 F15와 별도 결정한다. 이번 결정은 거부된 작성에서 새 사건을 생성하지 않는 범위다.

| 검증 사례 | 기대 결과 |
|---|---|
| 글 작성 확정 후 탈퇴 확정 | 작성 성공. 이후 콘텐츠 처리는 별도 탈퇴 정책 적용 |
| 탈퇴 확정 후 처리 중 글 작성이 저장 시도 | 작성 거부. 새 글·첨부·연관 성과·알림 사건 없음 |
| 분석글 게시와 탈퇴가 동시에 요청됨 | DB에서 순서 보장. 게시가 먼저면 연관 처리를 함께 확정, 탈퇴가 먼저면 게시와 연관 신규 반영 모두 거부 |

### F07. 공개 분석 등록·취소·미확정 성과

**기준 확정:** 미확정 고유 신호를 매칭한 본인의 불변 History를 공식 스레드에 최초 공개 등록할 때 사용자×고유 신호당 성과를 한 번 인정한다. 세 판단 모두 허용한다. 일반 Post 게시·첨부·댓글·링크·반응은 인정 조건이 아니다(GRD-04, COM-18).

**구현 계획**
1. 인증·회원 상태·History 소유·TIC·매칭 신호·공개 자격 검증.
2. F22 공식 스레드 확보. 운영 숨김이면 새 공개를 거부하고 미공개 기록 보존.
3. 작성자+History의 공개 기록을 확보한다. 같은 기록 재전송/재공개는 재사용, 새 제출은 별도 공개 기록이다.
4. 신호별로 공개 등록·최초 성과·등급/별 열림·통계를 일관되게 반영한다. 인정 대기 상태를 만들지 않는다.
5. 본인 공개 취소는 운영 숨김과 독립적으로 저장한다. 취소·숨김·복원 시 F16의 유효 공개 집합을 다시 계산한다.
6. 성과·개인 History·탐색 완료는 일반 공개 취소/숨김으로 되돌리지 않는다. 자동 댓글·반응을 생성하지 않는다.

**데이터·API 계약:** 공개 기록은 작성자·TIC·고유 신호·History·공식 스레드·공개 시각·본인 공개 여부·운영 숨김을 연결한다. 조회에는 선택 공개 필드·그래프·작성자·제출 시각·출처만 제공한다. 개인 History 전체 열람 권한을 주지 않는다. 물리 테이블은 별도 설계한다.

**결정 질문**
- F07-Q1: 공개 대상 필드의 상세 응답, 메모 공개 검토 UI, 그래프 생성 실패 처리 방식은 무엇인가?
- F07-Q2: 최초 공개 전에 라벨/후보 연결이 변경된 옛 제출의 최초 성과 자격은 어느 시점 기준인가? 기존 공개 기록의 라벨 변경 후 보존은 확정돼 있다.

### F08. 일반 글·공식 스레드 토론 댓글

**기준 확정:** 공개 일반 Post 또는 공식 신호 스레드의 토론에 1단계 댓글을 작성·조회하고 본인 댓글을 수정·삭제한다. 공개 분석 등록은 댓글을 자동 생성하지 않는다(COM-06, AT-114).

**구현 계획:** 부모 종류/ID와 공개 상태·작성자 검사 → 본문 및 같은 TIC 자료 검사 → 댓글 저장. 분석 목록과 댓글 목록을 분리한다. 개인 History 첨부는 F09, 공개 출처는 F24 규칙을 적용하고 댓글 반응을 임의 추가하지 않는다.

**결정 질문**
- F08-Q1: 일반 Post와 공식 스레드의 댓글 부모 관계를 어떻게 저장하는가? 개별 공개 분석에 직접 댓글을 다는 기능은 명시 범위를 넘어 자동 추가하지 않는다.
- F08-Q2: 본문 길이·첨부만 있는 댓글·정렬·페이지·중복 요청·수정 충돌 규칙은 무엇인가?
- F08-Q3: 부모 숨김/삭제 중 본인 댓글 접근과 삭제 표시·댓글 수, 알림 발생 기준을 정한다.

**검증:** 부모 숨김과 동시 작성 / 2단계 답글 거부 / 타인 수정 거부 / 별 없는 일반 글의 자료 첨부 거부 / 탈퇴 선확정 시 작성·첨부·알림 거부 / 공개 분석 등록 후 댓글 수 불변.

### F09. 본인 히스토리 직접 첨부

**기준 확정:** 관련 별이 연결된 일반 글·댓글에 같은 TIC의 본인 History를 첨부할 수 있다. 원글은 카드, 댓글은 요약에서 분석 상세로 연결한다. 별 미선택 글·댓글은 별 자료 선택/첨부를 제공하지 않는다. 타인 개인 History는 직접 첨부할 수 없으며 공개 자료는 F24 출처 링크로 연결한다(COM-07, HIS-05, NFR-13).

**구현 계획:** 인증·History 소유·부모 TIC를 작성/별 변경/게시 시 검사 → 원본 참조와 첨부 시점 재현 파라미터 보존 → 조회 시 부모 및 대상 공개 상태 검사. 원본 수정·성과 인정·공식 통계 갱신 없음. **일반 자유글도 별을 연결했다면 첨부 가능하다.**

**결정 질문**
- F09-Q1: 첨부 개수·순서·중복·교체 규칙과 공개할 필드/메모 범위를 정한다.
- F09-Q2: 이미지 생성 실패·구 Bundle 부재 시 처리와 공개 취소/숨김 후 캐시 접근 제어를 정한다.
- F09-Q3: 개인 History 원본 API와 첨부용 제한 응답의 경계를 탐사 담당자와 합의한다.

**검증:** AT-110~112·114. 별 변경 후 부적합 자료 거부 / 타인 History 거부 / 공개 첨부로 원본 전체 조회 불가 / 글 삭제·숨김 후 첨부 직접 조회 차단. 과거 History는 고정 Bundle·제거 조합·위상 원본·서버 파생값·버전으로 재현한다(HIS-02).

### F10. 동의·비동의·반응자 목록

**v0.12 대상 제한:** 동의·비동의는 일반 Post에만 적용한다. 공식 신호의 세 판단은 F16 공개 분석 통계이며, 분석 공개로 반응을 자동 생성하지 않는다(COM-08).

**기준 확정:** 회원·Post당 agree/disagree 중 최대 하나. 변경·취소·멱등 처리 지원. 본인 글 반응 가능. 합계와 반응한 회원 닉네임 전원을 인증 회원에게 공개한다. 성과와 과학 판정에는 사용하지 않는다(COM-08, NFR-14).

**결정 질문**

- F10-Q1: 클릭을 ‘토글’로 처리하는가, API는 원하는 최종 반응/없음을 전달하는가? 동일 요청 반복 결과를 명시한다.
- F10-Q2: 여러 탭의 반응 변경이 순서가 바뀌어 도착할 때 최종 상태 기준은 무엇인가?
- F10-Q3: 삭제·숨김 대상의 새 반응·변경·취소와 복원 후 반응 유지 기준은 무엇인가?
- F10-Q4: 목록의 정렬·페이지 크기·최신 닉네임·탈퇴 회원 표시, 반응 변경 중 합계와 목록 조회 기준은 무엇인가?
- F10-Q5: 전원 공개는 전원 일괄 전송이 아니라 페이지 순회로 모두 볼 수 있게 해도 되는가?

**상태 분석:** 없음 → 동의/비동의, 동의 ↔ 비동의, 동의/비동의 → 없음. 같은 최종 상태 반복 요청은 수를 추가하지 않는다.

**계약 초안:** Post·요청 반응 → 내 반응·동의/비동의 수. 목록은 반응 종류별 공개 회원 ID/닉네임·페이지 정보. 취소·변경을 성과 이벤트로 발행하지 않는다.

**검증 사례:** 본인 글 반응 / 같은 요청 반복 / 동시에 동의·비동의 / 취소 반복 / 닉네임 변경 / 숨김 후 목록 접근 / 탈퇴 회원 반응.

### F11. 신고 접수·처리

**우선순위:** 최신 사용자 결정 SB-D09(2026-09-09)에 따라 신고 접수·처리는 **P1**이다. v0.12 COM-13의 신고 우선순위만 변경하며 F12 운영 숨김·복원·감사는 P0를 유지한다. 아래 신고 조건은 P1 착수 시 적용한다.

**기준 확정:** 일반 글·댓글·공개 분석·공식 신호 스레드를 신고할 수 있다. 운영 숨김이 원본 개인 History를 삭제하지 않는다. 회원 차단은 제외다.

**구현 계획:** 대상 종류·ID·현재 접근 권한 검증 → 신고 사유/원문 버전·신고자·접수 상태 저장 → 운영 검토·F12 조치와 연결. 신고 접수가 자동 숨김을 뜻하지 않는다.

**결정 질문**

- F11-Q2: 신고 당시 내용 보관, 접수/검토/조치/기각 상태, 다중 신고 일괄 처리를 정한다.
- F11-Q3: 신고자·작성자·운영자의 열람 필드와 동시 운영 처리 규칙을 정한다.
- F11-Q4: 자동 숨김·회원 자체 신고는 현재 범위에 자동 포함하지 않는다.

**검증:** 네 종류 대상 신고 / 신고 후 원문 수정·삭제·공개 취소 / 중복 신고 / 일반 회원의 신고자 신원 조회 차단 / 원본 History 보존.

### F12. 운영 숨김·복원·감사

**우선순위:** v0.12 COM-13·17~18, OPS-01·06에 따라 **P0**. SB-D05의 P1 하향을 대체한다.

**기준 확정 및 구현 계획**
- 일반 Post·댓글·공개 분석·공식 신호 스레드를 숨김/복원한다. SYSTEM 자동 생성과 운영자 작업의 계정·시각·사유·변경 전후를 구분 기록한다.
- 본인 공개 취소와 운영 숨김을 독립 상태로 보존한다. 운영 복원은 본인 취소를 해제하지 않는다.
- 공식 스레드 숨김은 하위 분석·토론·첨부·출처·검색·직접 URL을 차단하고 신규 공개와 대체 스레드 생성을 막는다.
- 부모 복원만으로 개별 운영 숨김이나 본인 취소를 해제하지 않는다.
- 공개 분석의 유효성 변경은 F16 통계 재선택에 반영한다. 기인정 성과·History·탐색 완료는 유지한다. 일반 Post 삭제/숨김은 독립 공개 분석을 취소하지 않는다.

**결정 질문**
- F12-Q1: 숨김 일반 글의 작성자 조회·수정·삭제와 작성자 삭제 복구 권한은 무엇인가?
- F12-Q2: 감사 보관·열람·동시 조치·오래된 버전 복원 실패와 캐시 무효화 목표를 정한다.
- F12-Q3: 부모 숨김 중 하위 본인 취소 요청 허용과 관리자 조회 응답을 정한다.

**검증:** AT-108·109·113. 최신 공개 숨김 시 이전 유효 공개 판단 복귀 / 전부 무효면 참여자 제외 / 본인 취소 후 운영 복원해도 비공개 / 공식 스레드 숨김 중 대체 생성·신규 성과 없음.

### F13. 전체 피드·검색·핫 토픽

**우선순위:** 최신 사용자 결정 SB-D08(2026-09-09)에 따라 전체 피드·검색·필터·핫 토픽은 P0다. v0.12 COM-03·09의 P1 우선순위만 상향하며 기능 정책은 유지한다. 팔로우는 계속 P1이다.

**구현 계획:** 일반 글과 SYSTEM 공식 스레드를 종류별로 구분해 반환한다. 공개 분석은 독립 작성자 기록이며 SYSTEM 원글 작성자로 사용자를 표시하지 않는다. 공식 스레드 카드/상세는 신호 요약·세 판단 통계·공개 분석·토론을 제공한다. 모든 경로에서 동일한 유효 공개 조건 적용.

**결정 질문**
- F13-Q1: P0 탭 노출과 내 스레드에 본인 일반 글·공개 분석·토론 참여를 어떻게 포함할지 정한다.
- F13-Q2: 종류를 섞는 정렬·동률·페이지, 작성자 검색에서 SYSTEM 처리 기준을 정한다.
- F13-Q3: 아래 SB-D10 방향을 기준으로 검색 일치 방식·조건 조합, 핫 토픽 임계값·기간·정렬을 정한다(DEC-09).
- F13-Q3의 검색 대상은 SB-D10으로 TIC ID·제목과 일반 글·공식 스레드로 좁힌다. 제목 부분 일치·대소문자·공백 처리, TIC 정확 일치 여부, 두 조건의 AND/OR, 기본 정렬·페이지 방식은 추가 합의한다. 본문·작성자·태그 검색은 이번 최소 범위에 포함하지 않으며 COM-03 원본 반영 대상으로 기록한다.
- F13-Q4: 공개 취소·복원·댓글 삭제·반응 취소가 핫 토픽 점수에 미치는 영향을 정한다. 분석 공개와 반응을 같은 활동으로 자동 취급하지 않는다.

**검증:** 일반 글/공식 스레드 구별 / 숨김 하위 기록 검색 차단 / 취소된 출처 카드 미노출 / SYSTEM 작성 주체 / 새 글 사이 페이지 이동.

**최신 검색·핫 토픽 방향(SB-D10)**

| 항목 | 구현 방향 | 남은 결정 |
|---|---|---|
| 검색 | 열람 가능한 일반 글과 공식 스레드를 TIC ID·제목으로 필터한다 | 공식 스레드 제목 생성 규칙, 일치 방식·조건 조합·페이지 |
| 핫 토픽 진입 | 댓글 수 기준 또는 세 판단 합계 기준 중 하나를 충족하면 선정한다(OR). 가중 점수 도입은 현재 계획하지 않는다 | 댓글 임계값 C, 판단 임계값 J, 각각 이상/초과의 정확한 비교 |
| 일반 글 | 해당 글의 유효 댓글 수를 사용한다. 일반 글 agree/disagree를 세 판단 합계로 변환하지 않는다 | 삭제·숨김 댓글 제외, 동일 회원 다수 댓글 산정·기간 |
| 공식 스레드 | 해당 스레드의 유효 토론 댓글 수 또는 F16의 LIKELY_PLANET+UNLIKELY_PLANET+UNSURE 합계 N을 사용한다 | 누적/최근 기간, 기준 미달 시 탈락 여부·복귀 |
| 판단 수 | 기존 공개 분석의 회원×신호당 최신 유효 판단을 재사용하는 해석으로 작성했다. 재제출 횟수를 합산하거나 별도 투표 기능을 추가하지 않는다 | 사용자가 말한 세 선택이 별도 투표라면 F16과 분리하여 추가 협의 필요 |
| 노출 | 일반 글·공식 스레드 모두 대상. 삭제·운영 숨김은 즉시 제외한다 | 다수 선정 시 정렬·동률, 공식 공간 전체 숨김 후 복원 |

임계값·기간·정렬은 미정이며 임의 숫자를 확정하지 않는다. 댓글/판단 취소·숨김 후 현재 유효 수를 다시 산정하고, 기준 미달 시 핫 토픽 유지 여부는 별도 결정한다. 검증에는 C/J 직전·동일·초과, 한 조건만 충족, 같은 회원 재제출, 최신 공개 취소 시 이전 판단 복귀를 포함한다.

### F14. 회원·별 팔로우

**v0.12 추가 협의:** SYSTEM 원글은 회원이 작성한 글이 아니다. 회원 팔로우 피드에 독립 공개 분석을 포함할지, 별 팔로우에서 공식 스레드 생성과 공개 분석 추가를 어떻게 구분할지는 COM-16만으로 확정하지 않는다.

**기준 확정:** 회원 및 별 팔로우는 P1. 팔로우 피드에는 회원 원글·별의 새 원글을 모은다. 별의 새 원글·재개 사건은 알림 대상이며 설정으로 끌 수 있다. 차단 연동 없음(COM-16).

**결정 질문**

- F14-Q1: 자기 자신, 탈퇴 회원, 본인 미발견 별, 아무도 발견하지 않은 별, 공개 중단 별을 팔로우할 수 있는가?
- F14-Q2: 팔로잉·팔로워 수에서 별 팔로우를 구분하는가? 전체 목록도 공개하는가?
- F14-Q3: 회원과 별이 겹치는 글은 한 번만 표시하는가? 팔로우 이전 글과 언팔로우 직전 글의 피드 기준은 무엇인가?

### F17. 주간 챌린지·튜토리얼 완료 연계

**우선순위:** P0. POL-24, CHL-01, 삭제된 CHL-02, DEC-10과 ChallengeRound v0.12를 따른다.

**기준 확정:** 회차별 미확정·AI 승인 별 하나를 제공한다. 튜토리얼 5개 완료 회원에게만 발견시킨다. 챌린지 전용 달성 조건·성공 판정·진행도·보상·소급 반영은 없다. 일반 별의 탐색 진행·성과는 별개로 적용한다. 튜토리얼은 1번부터 순차 발견하고 건너뛰기는 서버 설정 기준이며 무신호 별을 사용하지 않는다.

**구현 계획:** 운영자가 대상 자격·기간·소개를 설정 → 대상 회원의 튜토리얼 완료 확인 → 회차 별 발견 멱등 반영 → 기간·대상·소개·스레드 참여 수 조회. 예약/진행/종료/취소 등 운영 상태 세부는 합의한다. 완료 보상 Job·성공 사건 집계·사용자 챌린지 달성 테이블을 계획하지 않는다.

**남은 충돌:** CHL-03의 ‘목표 달성·완료 성과·마감 제출 반영’은 삭제된 기능의 문구다. SRS 수정 요청 대상으로 남기고 성공 기능을 재도입하지 않는다.

**결정 질문**
- F17-Q1: 기간 시간대·경계·진행 중 대상 변경·공개 중단 처리와 회차 종료 후 별 접근 정책은 무엇인가?
- F17-Q2: 회차 진행 중 튜토리얼을 완료한 회원의 발견 시점과 이미 발견한 대상의 경로 기록은 무엇인가?
- F17-Q3: 스레드 참여 수는 공개 분석 참여자인지 토론 참여자인지 정의한다. STA-02 참여 수도 같은 용어로 정합화한다.
- F17-Q4: P0 시작 안내는 아래 첫 접속 방식으로 한정한다. 요일·시각·시간대, 확인 완료 기준과 튜토리얼 미완료 회원 안내 여부를 정한다.

**최소 챌린지 안내 계획(SB-D12, 사용자 방향 반영)**

1. 운영 회차의 시작 요일·시각 이후 첫 인증 접속에서 현재 진행 중인 새 챌린지를 조회하고 ‘이번 주 챌린지가 새로 생겼습니다’를 안내한다. 해당 요일에 접속하지 못한 경우에도 회차 진행 중 다음 접속에서 안내하는 안을 권장하며 세부 기준은 합의한다.
2. 서버가 회차 ID·기간·안내 여부를 반환하고 프론트가 표시한다. 회원×회차의 안내 확인 기록을 저장하는 안으로 기기 변경·재로그인 시 반복 안내를 막는다. 조회만으로 확인 처리할지, 표시 후 확인 요청으로 기록할지는 미정이다.
3. 새 회차가 실제 공개·진행 중인지 확인한다. 종료·취소 회차를 새 챌린지로 안내하지 않는다. 안내 확인과 별 발견은 별개이며 튜토리얼 5개 완료 자격 검사는 유지한다. 미완료 회원에게 소개만 보여줄지는 별도 결정한다.
4. 접속 시 조회로 처리하며 정시 푸시·이메일·알림함·실시간 전송·일반 수신 설정은 P1이다. 안내를 위한 별도 예약 발송 Job은 계획하지 않는다. 이미 접속 중인 회원은 다음 홈 진입 등 재조회 시 확인하는 안이며 재조회 시점은 프론트와 합의한다.

**추가 검증:** 시작 경계 전후 / 시작일 미접속 후 주중 접속 / 같은 회차 재로그인·다중 탭 / 확인 요청 재전송 / 종료·취소 / 튜토리얼 미완료·도중 완료. 표시와 확인 사이 실패 시 재노출 가능성은 허용 기준을 정하며 정확히 한 번의 화면 표시를 보장한다고 가정하지 않는다.

**검증:** 미완료 회원 챌린지 발견 차단 / 5개 완료 후 별 1개 발견 / 반복 사건 중복 없음 / 챌린지 별 분석에 추가 챌린지 보상 없음 / CHL-02 관련 성공 Job 없음.

<a id="f22"></a>

### F22. SYSTEM 공식 신호 스레드

**범위:** COM-17, OPS-01 P0.

**구현 계획:** 최초 유효 공개 분석 요청에서 TIC·고유 신호의 공식 공간을 확보한다. 사용자·판단·주기/고조파·Bundle별 새 스레드를 만들지 않는다. 첫 공개 성공과 생성은 원자적이며 SYSTEM 주체를 기록한다. 관리자 로그인 계정은 자동 생성 조건이 아니다. 신호 요약·공개 분석 목록·별도 토론을 제공한다.

일반 회원은 공식 원글 수정/삭제 불가. 운영자는 완전 삭제 대신 숨김/복원한다. 숨김 중 새 공개는 실패로 안내하고 원본 미공개 기록을 보존하며 대체 스레드·성과를 생성하지 않는다.

**계약·결정:** 논리 유일성은 고유 신호당 하나(TIC 적합성 포함). 물리 테이블/Post 통합 여부, SYSTEM 표현, 요약 버전/재분류 표시, 동시 생성 충돌 반환 계약은 DB·탐사와 합의한다. 이미 생성된 스레드를 라벨 변경만으로 소급 삭제하지 않는다.

**검증:** AT-102·109·113. 두 회원 최초 공개에도 공간 하나 / 고조파·다른 Bundle 중복 없음 / 일반 회원 편집 거부 / 숨김 중 재생성 금지.

<a id="f23"></a>

### F23. 개별·일괄 공개 검토

**범위:** COM-19, HIS-04, MY-03 P0.

**구현 계획:** 개인 기록 기본 보존 → 분석 공개 또는 TIC 종료 화면의 모두 게시/나중에 → 신호별 대표 기록(기본 미공개 최신 제출)과 판단·그래프·수치·근거·메모 검토 → 선택 항목 전송 → 항목별 성공/실패 반환. 이미 공개 중인 동일 기록은 제외하되 같은 신호의 새 분석은 가능하다.

원자성 단위는 신호별 최초 공간 확보·공개 등록·성과·통계 반영이다. 일괄 전체를 무조건 롤백하지 않는다. 성공 항목만 반영하고 실패 항목만 재시도한다. 다수 신호의 최초 성과/등급 상승/별 열림은 순차 개별 인정과 동등하게 보장한다. 공개 실패·나중에·취소는 탐색 완료를 되돌리지 않는다.

**결정 질문:** F23-Q1 요청 항목 상한·대표 기록 변경·동일 신호 복수 선택 처리, F23-Q2 항목별 멱등 키·공통/개별 오류, F23-Q3 동시 성과 반영의 등급 상승 순서와 서버 응답 계약.

**응답 초안:** 항목별 신호/History·공개 기록/스레드 ID·미게시/게시 중/공개됨/게시 실패 표시·최초 성과 여부·실패 원인·재시도 가능 여부. 전송 상태와 성과 인정 상태를 혼동하지 않는다.

**검증:** AT-103·107. UNSURE 공개 허용 / 일부 성공 뒤 실패만 재시도 / 성공분 중복 없음 / 순차 인정과 별 열림 동등 / 완료 상태 유지.

<a id="f24"></a>

### F24. 공식 신호·공개 분석 출처 링크

**범위:** COM-20, NFR-13~14 P0.

**구현 계획:** 별 연결 일반 글/댓글에 동일 TIC의 공식 스레드 또는 공개 분석 참조를 연결한다. 타인의 공개 분석은 작성자·출처를 보존하며 개인 History 첨부나 전체 조회 권한으로 바꾸지 않는다. 작성·별 변경·게시·조회 때 TIC·원본·상위 공간 공개 상태를 재검증한다.

스레드 카드는 신호 요약·F16 전체 통계·전체/세 판단 필터 링크를 제공한다. 필터는 통계 전체 분모를 바꾸지 않는다. 공개 취소/숨김 후 카드·직접 링크·캐시에서 내용 노출 금지. 일반 본문 URL과 별 자료 선택 기능은 구분한다. 출처 연결로 분석 등록·성과·반응·판단 통계 생성 없음.

**결정 질문:** F24-Q1 카드 개수·순서·중복·비공개 전환 시 안내 문구, F24-Q2 참조 종류/ID와 API 필드·캐시 무효화 구현.

**검증:** AT-106·110~112·114. 타인 같은 별 공개 분석 연결 / 다른 TIC 거부 / 취소 후 미노출 / 필터 분모 유지 / 개인 원본 API 우회 불가.

## 4. 공통 권한·상태·데이터 계약

| 자원·행동 | 본인 인증 회원 | 다른 인증 회원 | 운영자 |
|---|---|---|---|
| 일반 글 수정/삭제 | 본인만, 별 변경 시 자료 재검증 | 불가 | 대리 수정 정책 미정 |
| 공식 스레드 생성 | 본인 분석 공개 요청으로 유발 | 동일 | 운영자 로그인·수동 생성 조건 아님 |
| 공식 원글 수정/삭제 | 불가 | 불가 | 숨김/복원, MVP 완전 삭제 없음 |
| 공개 분석 등록/취소/재공개 | 본인 History만, 운영 숨김 해제 불가 | 불가 | 개별 숨김/복원; 본인 취소 유지 |
| 유효 공개 분석·출처 열람 | 선택 공개 필드만 | 동일 | 업무상 비공개 열람 범위 별도 |
| 개인 History 원본 | 본인 가능 | 불가 | 권한 있는 운영자만 |
| 일반 Post 반응 | 본인 글 포함 가능 | 가능 | 동일 인증 조건; 공식 분석 자동 반응 없음 |
| 신고 | 네 콘텐츠 종류 가능 | 동일 | 처리·감사 권한 |
| 비공개 별 목록 | 본인 가능 | 불가 | 업무상 범위 미정 |

SYSTEM은 로그인 가능한 운영자 역할이 아니라 자동 생성·감사의 처리 주체다. F22의 최초 유효 공개 요청에서만 공식 스레드 생성을 수행하며, SYSTEM 표기 자체가 숨김·복원·개인 History 열람 권한을 부여하지 않는다. 운영 조치는 실제 운영자 권한·계정으로 검사하고 기록한다. 신고 행은 F11 P1에서 적용한다.

비인증은 로그인/콜백 외 보호 자원에 접근 불가. 401 재로그인·기본 403 안내는 SB-D03 유지, 존재 비노출 404 대상은 미정이다. 상위 스레드 숨김은 하위 직접 조회·검색·첨부·출처 카드에도 적용한다.

**논리 데이터 관계**
- 회원↔제공자 식별, 회원↔설정; DB 스키마는 담당자 협의.
- TIC↔고유 신호↔공식 공간 1개; Bundle/고조파별로 공간을 나누지 않는다.
- 작성자+History↔공개 기록 1개. 새 제출은 별도 기록, 취소·재공개는 기존 재사용.
- 공개 기록은 본인 공개 여부·운영 숨김을 독립 보존, 상위 공간 상태와 함께 유효 공개 판정.
- 일반 Post/Comment의 본인 History 첨부와 공식 공개 등록 및 공개 출처 참조는 서로 다른 관계.
- 사용자×고유 신호 성과는 최초 한 번. 공개 최신 판단·누적 수치 매칭·완료 상태와 분리.
- History는 고정 Bundle·제거 조합·위상·viewport·버전을 보존. 재도전은 새 초안/새 제출로 처리.
- 신고·감사·팔로우·알림·스냅샷의 관계/유일성은 기능별 계약 확정 후 스키마에 반영.

**교차 검증:** 동일 공개 동시 요청, 숨김 직전 등록, 공개 취소와 운영 복원, 최신 분석 취소, 과거 제출 늦은 공개, 탈퇴 경합, 응답 유실, 일괄 일부 실패. 클라이언트 상태만 신뢰하지 않고 저장/조회 시 서버가 자격을 검사한다.
