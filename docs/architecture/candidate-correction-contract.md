# 후보 병합·분리 정정 계약

> 상위 문서: [아키텍처 문서 안내](README.md) · 테이블 정본: [서비스 DB ERD](database-erd.md)

- 작성: 강재민 / 탐사 코어. [S15P21C206-153](https://ssafy.atlassian.net/browse/S15P21C206-153) (계획 추적 ID C18)
- 상태: **결정 요청 초안.** 2장은 스키마에서 확인한 사실, 3.1은 정본에서 그대로 오는 확정 규칙, 3.1.1과 3.2의 병합·분리 열은 **이번 제안**, 4장은 **미확정**이다. 제안과 미확정을 구현자가 확정 규칙으로 인용하거나 임의로 정하지 않는다.
- 범위: 후보가 병합·분리되거나 외부 라벨만 바뀔 때 서비스 DB의 기록·성과·공개 관계를 어떻게 처리하는지. 실행은 [S15P21C206-154](https://ssafy.atlassian.net/browse/S15P21C206-154)(C19)가 맡고 이 문서는 그 수행 범위를 가른다.
- 이 문서는 운영 데이터를 바꾸지 않고 운영 화면·운영 API를 만들지 않는다(OPS v1.0, [탐사 API 9.5절](../../apps/backend/docs/exploration-api-spec.md#95-외부-라벨-갱신-표식-grd-06-dec-26)).

## 1. 세 가지 사건

| 사건 | 뜻 | 누가 판정하나 |
| --- | --- | --- |
| 라벨 변경 | 외부 TCE/TOI의 disposition만 바뀐다. 후보 ID는 그대로다 | 배치(자동) |
| 병합 A+B→C | 서로 다른 후보 두 개가 같은 신호였다 | 데이터 담당(D05-2, D08) |
| 분리 A→B+C | 후보 하나가 서로 다른 신호 둘이었다 | 데이터 담당(D05-2, D08) |

라벨 변경은 [탐사 API 9.5절](../../apps/backend/docs/exploration-api-spec.md#95-외부-라벨-갱신-표식-grd-06-dec-26)에서 확정됐고 배치가 자동으로 처리한다. **단순 라벨 표식과 승인된 성과 정정은 별개다.** 이 문서는 나머지 둘을 다룬다.

병합·분리의 판정 기준(주기·중심 시각 허용 오차, 고조파 별칭)은 데이터 담당이 정한다([ERD 미결 2](database-erd.md), [재처리 규칙](../data/tess-pipeline/validation-and-reprocessing.md)). 이 문서는 **그 판정이 이미 내려졌다고 보고** 그 뒤 DB에서 무엇을 하는지만 정한다.

## 2. 스키마가 이미 정해 놓은 것

아래는 결정이 아니라 `apps/backend/src/main/resources/db/migration`의 `V1__initial_schema.sql`·`V2__gold_roles.sql`에서 확인한 제약이다.

**이 제약들은 정정을 금지하지 않는다.** 대부분은 순서와 비용을 정할 뿐이다. 참조를 먼저 지우면 후보도 지울 수 있고, 성과를 지우면 등급도 다시 계산된다. 그러므로 「스키마가 막아 준다」를 보존 정책의 근거로 쓰지 않는다. 이 표는 어떤 처리를 고르든 **반드시 같이 결정해야 하는 것**을 드러낼 뿐이다.

| # | 제약 | 그래서 같이 결정해야 하는 것 |
| --- | --- | --- |
| S1 | `candidates.id`를 참조하는 외래 키 아홉 개에 `ON DELETE` 절이 없다 | **후보 행을 지우려면 참조 아홉 종류를 먼저 정리해야 한다.** 별칭·외부 참조·disposition·AI 평가·제출·성과·공식 스레드·공개 분석·변경 이력이다. 조용한 부분 삭제는 DB가 막지만, 순서대로 지우는 것까지 막지는 않는다. 이 문서는 삭제 대신 `status='retired'`를 제안한다(3.3) |
| S2 | `uq_posts_system_candidate` — `UNIQUE(candidate_id) WHERE kind='system_thread'` | **공식 스레드 두 개를 한 후보로 모으기** |
| S3 | `user_candidate_achievements`의 `UNIQUE(user_id, candidate_id)` | **한 회원의 성과 두 건을 한 후보로 옮기면 두 행을 유지할 수 없다.** 한쪽을 지우거나 옮기지 않거나 둘 중 하나이며, 지우면 그 회원의 성과 수와 등급이 내려간다. 어느 쪽을 택할지가 C18-Q2다 |
| S4 | `star_unlocks.trigger_achievement_id` 외래 키와 `UNIQUE(trigger_achievement_id, seq)` | **성과 행을 지우려면 그 성과가 연 별 행을 먼저 지워야 한다.** 순서를 강제할 뿐 회수를 금지하지는 않는다. 별을 닫을지 말지는 스키마가 아니라 DEC-26이 정한다 |
| S5 | `planetory_gold_writer`의 권한은 Gold 12개 테이블(묶음 B)에만 있다. 회원·커뮤니티 테이블은 **읽기 권한조차 없다**(V5·V6·V11·V13~V16이 그쪽을 `planetory_app`에 준다) | **배치 역할은 성과·별·공개 분석·스레드를 고칠 수도, 셀 수도 없다.** 사전검사와 적용이 서로 다른 계정이어야 한다는 뜻이다(5.1) |
| S6 | `analysis_histories`에는 `candidate_id`도 `relabeled_at`도 없다 | **히스토리 행에 직접 표식 남기기.** 화면의 "기록이 갱신됨"은 `user_candidate_achievements`를 `(user_id, candidate_id)`로 조인해 만든다 |

**S5의 결과가 이 문서에서 가장 크다.** 후보 쪽 정정과 회원 쪽 정정은 권한이 다르므로 한 트랜잭션에 들어가지 않는다. 회원 쪽을 고치려면 v1에 없는 역할을 새로 만들어야 하고, 그 역할을 만드는 것 자체가 승인 대상이다(C18-Q6).

다만 **V2가 만든 GRANT만으로 이 경계가 성립하지는 않는다.** 마이그레이션 주석이 적은 대로 배포에서 마이그레이션·서비스·배치 계정을 셋으로 나눠야 하고, 그 운영 적용은 `S15P21C206-83`의 범위다. 계정이 나뉘어 있지 않으면 S5는 문서상의 경계일 뿐이므로 현재 상태를 인프라 담당에게 확인한다.

**S6은 정본끼리 어긋난 곳이다.** [SRS GRD-06](../requirements/planetory-requirements-spec.md)은 "AnalysisHistory와 UserCandidateAchievement에 재분류 표식"이라고 적었지만 스키마·탐사 API 9.5절·현재 구현은 성과 행에만 둔다. 그 결과 **성과가 없는 히스토리는 어떤 정정에서도 표식을 가질 수 없다.** 정합화 요청은 [원본 문서 정합화](../project/planetory-doc-sync-requests.md)에 남겼다.

## 3. 확정된 규칙과 이번 제안

### 3.1 정본에서 그대로 오는 것 (확정)

[GRD-06·OPS-03](../requirements/planetory-requirements-spec.md)이 정한 것은 아래까지다.

- **자동 회수 금지의 범위.** 작성자의 일반 게시글 삭제, 공개 분석의 공개 취소, 일반 운영 숨김, AI 재평가 **만으로는** 인정된 등급을 회수하지 않는다.
- **외부 라벨 갱신은 v1에서 보존한다.** 후보 상태만 갱신하고 회원의 성과 유형·등급·발견한 별·통계 스냅샷은 바꾸지 않으며 표식만 남긴다(v1 임시 규칙, [탐사 API 9.5절](../../apps/backend/docs/exploration-api-spec.md#95-외부-라벨-갱신-표식-grd-06-dec-26)).
- **기존 공식 스레드·공개 분석을 라벨 변경만으로 소급 삭제하지 않는다.**
- **히스토리와 제출은 불변이다**(HIS-06, SUB-05 원본값 보존).

> **병합·분리는 여기에 들어가지 않는다.** GRD-06은 「후보 병합·분리, 외부 disposition 정정, 부정 사용 조치가 필요한 경우 **이력을 남겨 재계산한다**」고 적었고, OPS-03도 「재계산이 허용된 변경은 발견 개수·등급 영향을 검증한다」고 한다. 보존을 우선하라는 문구는 **외부 라벨 갱신의 v1 처리**에만 걸려 있다. 즉 병합·분리의 정본 방향은 보존이 아니라 **이력 기반 재계산**이다.

### 3.1.1 병합·분리에 대한 이번 제안 (승인 전, 확정 아님)

그럼에도 이 문서는 **v1 병합·분리에서 회원 데이터를 바꾸지 않을 것을 제안한다.** 정본 규칙이 아니라 제안이며, 채택 여부는 4장의 C18-Q2~Q5가 정한다. 근거는 셋이다.

1. **재계산 정책 자체가 미정이다.** DEC-26이 `achievement_type` 변경·등급 재계산·개수 반영 방식·별 유지·스냅샷 재계산을 v1.1 이후로 미뤘다. 정책 없이 재계산하면 구현자가 정하는 것이 된다.
2. **유일 제약이 회원마다 다른 결과를 만든다.** S3 때문에 양쪽에 성과를 가진 회원만 성과가 줄고 나머지는 그대로다. 같은 정정이 회원에 따라 다르게 작용하는 것을 승인 없이 실행할 수 없다.
3. **되돌릴 근거가 남지 않는다.** 성과를 옮기거나 지운 뒤 원래 상태를 복원할 기록이 현재 스키마에 없다(5.4).

승인 전까지 C19는 이 제안을 기본값으로 삼되, **이것을 정본 규칙으로 인용하지 않는다.**

### 3.2 사건별 기대값

**보존** = 행을 건드리지 않는다. **정정** = 정해진 값으로 바꾼다. **거절** = 사전검사에서 막고 실행하지 않는다. **미정** = 4장의 결정 전에는 손대지 않는다.

**라벨 변경 열만 확정이다**(9.5절). 병합·분리 두 열은 3.1.1의 **제안**이며 C18-Q2~Q5가 바꿀 수 있다.

| 대상 | 라벨 변경 | 병합 A+B→C | 분리 A→B+C |
| --- | --- | --- | --- |
| `candidates` | 보존 | **정정**: 대표 후보 한쪽의 id를 유지하고 다른 쪽을 `retired`로 바꾼다(3.3) | **정정**: 아래 세 줄의 사전 거절을 통과했을 때만 A를 `retired`로 두고 B·C를 새 행으로 추가한다(3.4) |
| `candidate_dispositions`·`candidate_aliases`·`external_signal_references` | **정정**: 배치가 새 값으로 갱신 | **정정**: 대표 후보로 모은다. 남는 쪽은 은퇴한 후보에 딸린 채로 둔다 | **정정**: 거절되지 않았으면 새 후보에 각각 만든다 |
| `user_candidate_achievements` | **보존 + 표식**: `relabeled_at`·`relabel_disposition`만 설정하고 `achievement_type`은 그대로 | **미정 C18-Q2.** 확정 전 기본값은 보존이다 | **거절**: 성과가 한 건이라도 있으면 분리 정정을 실행하지 않는다(3.4) |
| `star_unlocks` | 보존 | **미정 C18-Q7.** 확정 전 기본값은 보존이다 | 보존. 성과가 있으면 3.4에서 거절하므로 이 문제가 생기지 않는다 |
| `published_analyses` | 보존 | **미정 C18-Q3.** 확정 전 기본값은 보존이다 | **거절**: 공개 기록이 있으면 실행하지 않는다 |
| 공식 스레드(`posts.kind='system_thread'`) | 보존 | **미정 C18-Q4.** S2 때문에 둘을 합칠 수 없으므로 확정 전 기본값은 양쪽 보존이다 | **거절**: 스레드가 있으면 실행하지 않는다 |
| `analysis_histories` | 보존(불변 테이블). 표식은 성과 행 조인으로 표시(S6) | 보존 | 보존 |
| 판단 통계(COM-14) | 보존. 공개 기록 기준이라 라벨과 무관하다 | 후보별로 갈린 채 남는다. C18-Q3을 따라간다 | 해당 없음 |
| 채점형 일치율 | **자동으로 달라진다.** `planet_truth` 기준이라 별도 조치가 없다(9.5절) | 후보별로 갈린 채 남는다. `matched_candidate_id`를 옮기지 않기 때문이다(3.1) | 해당 없음 |
| `stats_snapshots`·`global_stats` | 보존 | **미정 C18-Q5.** 확정 전 기본값은 보존이다 | 보존 |

이 표는 **계약상의 기대값**이다. 그중 지금 실제로 실행할 수 있는 것은 더 좁으며 6장이 따로 정한다. 관계 이동과 후보 추가는 복구 절차가 없어 아직 실행하지 않는다(5.4).

### 3.3 병합에서 새 후보 행을 만들지 않는다

"A+B→C"의 C는 **A나 B 중 대표로 고른 쪽의 id를 그대로 쓴다.** 새 행을 만들면 A·B가 모두 `retired`가 되어 기존 성과·스레드·공개 기록·제출이 전부 은퇴한 후보를 가리키게 된다. [ERD 4장 결정 2](database-erd.md)의 "`candidates.id`는 별에 고정된 신호 식별자"와 S1이 같은 곳을 가리킨다.

어느 쪽을 대표로 고르는지는 **데이터 담당이 정한다**(C18-Q1). 회원 영향이 이 선택에 직접 달려 있다. 대표로 고른 쪽의 성과·스레드·공개 기록은 그대로 살아 있고 남는 쪽의 것은 은퇴한 후보에 붙은 채로 남기 때문이다.

### 3.4 분리는 별도 정정 작업이 아니다

분리에서 "A의 성과를 가진 회원이 B를 찾은 것인가 C를 찾은 것인가"는 **DB만 보고 답할 수 없다.** 제출이 `submitted_period`·`matched_period`를 보존하므로 되짚을 수 있는 경우가 있지만, 고조파 관계이거나 두 신호의 주기가 허용 오차 안이면 갈리지 않는다. GRD-06이 병합·분리에 재계산을 허용하지만 **어느 산물로 옮길지를 정하는 규칙은 어디에도 없으므로**, 지금 옮기면 그것은 승인된 재계산이 아니라 구현자의 임의 결정이다. 한쪽을 지우면 S3 없이도 성과가 줄고, 양쪽에 넣으면 성과가 복제된다.

그래서 이 문서는 v1에 이렇게 제안한다.

- **A에 성과·공개 기록·공식 스레드가 하나라도 있으면 분리 정정을 실행하지 않는다.** 5.2의 사전검사에서 막는다.
- 그런 참조가 없으면 분리는 정정이 아니라 **새 판 적재의 일반 경로**다. A를 `retired`로 두고 B·C를 새 후보로 추가하는 것으로 끝난다. 다만 **그 추가도 복구 절차가 정해진 뒤에 한다**(5.4·6장).

즉 지금 실행할 수 있는 분리 작업은 사전검사뿐이다. 배분 규칙(C18-Q2)이 정해지면 이 절의 사전 거절 범위도 다시 본다.

### 3.5 정정이 사용자에게 어떻게 보이나

병합을 3.2의 기본값대로 실행하면 회원 데이터는 하나도 바뀌지 않지만 **화면에는 흔적이 남는다.**

- 같은 신호인데 공식 스레드가 둘이고 각각의 판단 통계가 따로 집계된다.
- 채점형 일치율도 둘로 갈린다.
- 은퇴한 후보에 붙은 성과·공개 기록이 계속 보인다.

이것은 결함이 아니라 **보존을 제안한 대가**다. 합치는 쪽을 택하면 S3 충돌 회원의 성과·등급이 줄고 스레드 하나를 정리해야 한다(S2). GRD-06은 병합·분리에 재계산을 허용하므로 합치는 쪽도 정본 위반이 아니다. 어느 쪽이 나은지는 4장의 결정이고, 결정 전까지만 보존을 기본값으로 둔다.

**「이미 발견한 별 유지」를 확정에서 내렸다(2026-09-21).** 앞선 초안은 GRD-06과 S4가 같은 답을 준다는 이유로 이것을 확정으로 적었는데, 둘 다 근거가 되지 못한다. GRD-06의 자동 회수 금지 목록은 게시글 삭제·공개 취소·운영 숨김·AI 재평가뿐이라 병합·분리를 덮지 않고(3.1), S4는 순서를 강제할 뿐 회수를 금지하지 않는다(2장). 근거 둘이 모두 빠졌으므로 C18-Q7로 옮겼다.

**확정과 미확정을 가른 뒤에도 남는 것은 하나뿐이다.** 병합·분리에서 v1이 지금 확실히 말할 수 있는 것은 "재계산의 방향은 정본이 허용하지만 그 방법은 정해지지 않았다"까지다. 3.1.1의 보존 제안은 그 공백을 메우는 기본값이지 규칙이 아니다.

**승인 조건은 선택지를 막는 자리가 아니다.** 각 항목의 승인 조건은 "무엇을 고르든 그 영향을 숫자로 내놓고 승인받아라"를 요구할 뿐, 특정 선택지를 미리 배제하지 않는다. 3.1이 병합·분리의 정본 방향을 재계산으로 정리했으므로, 승인 단계에서 보존만 통과시키면 앞에서 열어 둔 선택지를 도로 닫는 것이 된다.

**임의 결정 금지.** 위 일곱 항목은 구현자가 코드나 SQL에서 정하지 않는다. 승인 기록이 없으면 C19는 6장의 범위만 실행한다.

## 5. 승인·적용·기록·복구

### 5.1 승인과 적용 역할

| 대상 | 승인 | 적용 역할 |
| --- | --- | --- |
| 사전검사(5.2, 읽기만) | 불필요 | **`planetory_app` 또는 전용 읽기 역할.** Gold 적재 계정으로는 돌아가지 않는다 |
| Gold 쪽 적용(후보 status·disposition·별칭·외부 참조·변경 이력) | 데이터 담당 판정과 사전검사 결과 확인 | `planetory_gold_writer` |
| 회원 쪽 정정(성과·공개·스레드·통계) | 4장의 해당 항목이 결정되고 데이터·탐사·서비스 3인이 승인 | **v1에 없다.** C18-Q6에서 정한다 |

**사전검사와 적용은 같은 계정으로 하지 않는다.** `planetory_gold_writer`에는 회원·커뮤니티 테이블의 SELECT 권한이 아예 없어(S5) 5.2의 건수를 셀 수 없다. 반대로 `planetory_app`에는 Gold 테이블 쓰기 권한이 없다. 두 단계를 두 계정으로 나누어 실행하고, 필요한 최소 조회 권한만 쓴다. 전용 읽기 역할을 따로 만들지는 **아직 정하지 않았다** — 만든다면 대상 테이블 목록이 승인 대상이다.

운영 화면과 운영 API를 만들지 않으므로 적용은 DB 작업이다([ERD 4장 결정 11](database-erd.md), OPS v1.0). 어느 단계도 테이블 소유자로 실행하지 않는다. 소유자로 접속하면 S5의 권한 경계가 무력화된다.

### 5.2 사전검사(dry-run)

적용 전에 영향 건수를 먼저 센다. **읽기 전용이므로 적용 계정이 아니라 조회 계정으로 실행한다**(5.1). 여섯 개를 세지만 **승인 문턱이 되는 것은 제출을 제외한 다섯 항목이다.** 다섯 중 하나라도 0이 아니면 회원 영향이 있다는 뜻이므로 5.1의 회원 쪽 승인 없이 진행하지 않는다.

**제출을 문턱에서 뺀 근거(C18 결정).** 제출을 옮기지 않는 것은 이번 제안이 아니라 3.1의 확정 규칙이다(HIS-06 히스토리 불변, SUB-05 원본값 보존). 옮기지 않는 값은 정정으로 달라질 수 없으므로 승인을 물을 대상이 아니다. 그래서 집계만 한다. 다만 **제출이 0이 아니면 흔적은 남는다** — 채점형 일치율의 모집단이라 정정 뒤에도 그 후보에 붙어 있다(3.5). 사전검사는 이 경우 통과시키되 출력에 그 사실을 적는다. 이 구분을 바꾸려면 3.1을 먼저 바꿔야 한다.

| 세는 것 | 기준 |
| --- | --- |
| 성과 | `user_candidate_achievements` 행 수 |
| 성과로 연 별 기록 | `star_unlocks.trigger_achievement_id`가 그 성과를 가리키는 **행 수**. 여러 회원이 같은 별을 열 수 있으므로 고유 TIC 수가 아니다 |
| 공개 분석 | `published_analyses` 행 수(유효·취소·숨김 구분) |
| 공식 스레드 | `posts` 중 `kind='system_thread'` 행 수 |
| 제출(승인 판정 제외) | `submissions.matched_candidate_id` 행 수. 옮기지 않으므로 집계용이다. 채점형 일치율이 정정 뒤 어디에 남는지를 보여준다 |
| S3 충돌 회원 | 병합 대상 양쪽 모두에 성과가 있는 회원 수 |

마지막 항목이 0보다 크면 C18-Q2를 "옮긴다"로 정하더라도 그 회원들은 옮길 수 없다. 사전검사 결과는 승인 요청에 그대로 붙인다.

### 5.3 변경 이력 기록

정정은 `candidate_status_history`에 남긴다. 열은 `candidate_id, bundle_id, field, old_value, new_value, rule_version, reason, changed_at`이다. `reason` 형식을 아래로 제안한다(초안, C19에서 확정).

| 사건 | field | old_value → new_value | reason |
| --- | --- | --- | --- |
| 병합에서 남는 쪽 | `status` | `active` → `retired` | `merged_into:<대표 candidate_id>` |
| 병합에서 대표 쪽 | 바뀐 열마다 한 행 | 실제 값 | `merged_from:<남는 candidate_id>` |
| 분리 원본 | `status` | `active` → `retired` | `split_into:<새 id>,<새 id>` |
| 분리 산물 | `status` | (없음) → `active` | `split_from:<원본 candidate_id>` |

`bundle_id`는 정정을 반영한 판이다. 정정만 하고 새 판을 만들지 않는 경우에 이 값을 무엇으로 쓸지는 C19에서 정한다. 열이 `NOT NULL`이라 비워 둘 수 없다.

### 5.4 재실행과 복구

- **재실행:** `status` 갱신은 같은 값을 다시 써도 결과가 같다. 반면 `candidate_status_history`는 덧붙이기만 하므로 재실행하면 같은 내용의 행이 늘어난다. 중복을 막을지, 늘어나도 두고 조회에서 걸러낼지는 C19에서 정한다.
- **복구: `status`를 되돌리는 것은 복구가 아니다.** 6장이 허용하는 Gold 쪽 적용에는 상태 전환 말고도 별칭·외부 참조·disposition의 `candidate_id`를 대표 후보로 옮기는 것과, 분리에서 새 후보 행을 넣는 것이 들어 있다. 상태만 되돌리면 옮겨진 관계는 옮겨진 채로, 추가된 후보는 추가된 채로 남는다.
- **복구하려면 변경 대상별 이전 값을 먼저 보관해야 한다.** 최소한 아래 셋이다. 보관 형식과 보관 위치는 C19에서 정한다.
  - 옮긴 행마다 `(테이블, 행 id, 이전 candidate_id)`
  - 분리로 새로 넣은 후보 id 목록
  - 바꾼 `candidates.status`의 이전 값
- **그 보관·복원 절차가 정해지기 전에는 관계 이동과 후보 추가를 실행하지 않는다.** 되돌릴 수 있는 것은 상태 전환뿐이므로 6장의 실행 범위도 거기까지다.
- **회원 쪽을 바꾼 정정은 어떤 경우에도 복구되지 않는다.** 성과를 옮기거나 지운 뒤 원래 어디에 있었는지가 현재 스키마 어디에도 남지 않기 때문이다. 이것이 회원 쪽 정정을 v1 범위 밖에 두는 마지막 이유다.
- 복구가 필요한 상황을 줄이려면 5.2의 사전검사 결과를 승인 시점에 보관하고, 적용 후 같은 여섯 건수를 다시 세어 사전검사와 일치하는지 확인한다.

## 6. C19(S15P21C206-154)의 v1 수행 범위

C19의 실행 범위는 **서로 독립인 문턱 셋**에 걸려 있다. 먼저 풀리는 것부터 범위가 늘어난다.

| 문턱 | 풀리면 가능해지는 것 |
| --- | --- |
| **C18-Q1 확정**(대표 후보 선택) | 은퇴 대상이 정해져 아래 2~4번이 시작된다 |
| **5.4 복구 절차 확정** | 관계 이동과 분리 산물 추가 |
| **4장 Q2~Q7 승인** | 회원 데이터(성과·별·공개·스레드·통계) 정정 |

**할 수 있는 것**

1. 5.2의 사전검사 — 영향 건수 여섯 개를 세어 보고한다. 읽기 전용이라 되돌릴 것이 생기지 않는다. **문턱과 무관하게 언제든 할 수 있다.** **구현 완료**([S15P21C206-154](https://ssafy.atlassian.net/browse/S15P21C206-154), 읽기 전용 명령 `candidate-correction-precheck`, 절차는 [사전검사 런북](../operations/candidate-correction-runbook.md)).
2. **아래 셋이 모두 갖춰진 병합 건에 한해** 남는 후보의 `status`를 `retired`로 바꾼다. 지금 되돌릴 수 있는 유일한 적용이다.
   - **C18-Q1이 확정돼 어느 쪽이 대표인지 정해져 있다.** 정해지기 전에는 "남는 쪽"을 지목할 수 없으므로 실행 대상 자체가 없다.
   - 그 병합 건을 데이터·탐사 담당이 승인했다(5.1).
   - 5.2 사전검사를 통과했다. 회원 영향이 있으면 5.1의 회원 쪽 승인까지 받는다.
3. 5.3의 `candidate_status_history` 기록. 2번과 같은 작업에서만 남긴다.
4. 5.4의 적용 후 재검증. 2번을 실행했을 때만 해당한다.

**Q1이 확정되기 전에는 1번만 한다.** 2~4번은 대상이 정해지지 않았으므로 시작하지 않는다. 조회는 되돌릴 것을 만들지 않으므로 그동안에도 영향 건수를 모아 승인 요청을 준비할 수 있다.

**아직 할 수 없는 것**

1. 성과·별·공개 분석·공식 스레드·통계 스냅샷 변경 — 4장 미결이고 S5의 권한도 없다.
2. **별칭·외부 참조·disposition을 대표 후보로 옮기는 것** — 5.4의 보관·복원 절차가 없어 되돌릴 수 없다. 복구 절차가 정해지면 풀린다.
3. **분리로 새 후보 행을 넣는 것** — 같은 이유다. 사전 거절을 통과해도 추가는 복원 절차가 정해진 뒤에 한다.
4. 후보 행 삭제 — 참조 아홉 종류를 함께 정리해야 하고(S1), 그 정리가 곧 회원 데이터 변경이다.
5. 참조가 있는 후보의 분리 — 3.4에서 거절한다.
6. 운영 화면·운영 API·범용 정정 API 추가 — [OPS v1.0](../development/service-backend/statistics-and-operations.md)과 탐사 API 9.5절의 범위 밖이다.
