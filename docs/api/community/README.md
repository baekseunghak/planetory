## 범위와 재현

[search-cases.json](search-cases.json)은 S16(169)과 W20 검색 화면이 공유할 합성 입력·기대 결과다. 회원·TIC·게시글은 실사용자 데이터가 아니다. `query`는 중복 키와 URL 인코딩을 검사할 수 있도록 키/값 쌍 배열이다. `expectedIds`는 **조회 가능한 데이터 집합에서** 검색 조건·정렬을 적용한 전체 결과다. 실제 응답 DTO나 운영 권한 검사를 대신하지 않는다. `pages`는 페이지 경계의 기대 ID이며 opaque 커서의 직렬화 형식을 지정하지 않는다.

```powershell
node docs/api/community/validate-search.cjs
# 기존 프론트 입력 계약 확인(설치된 tsx 사용)
cd apps/frontend
node --import tsx --test tests/unit/feedSearch.test.ts
node --import tsx ../../docs/api/community/validate-search.cjs --frontend
```

검증기는 표본의 문자 매칭·순서·URL 왕복·오류를 확인하는 참조 구현이다. SQL의 collation, LIKE 이스케이프, 실제 API, 커서 위변조, 접근 제어, 집계 성능은 검사하지 않는다. 프론트는 결과 목록을 로컬 필터링하지 않고 서버 응답을 사용한다.

`--frontend`는 위 `cd` 이후 실행한다. 루트에서 검증기에 이 옵션만 넘기면 실행 위치 안내와 종료 코드 1을 반환한다. `node --import tsx` 자체를 루트에서 실행해 로더를 찾지 못하는 경우는 검증기 실행 전 오류이므로 먼저 apps/frontend로 이동한다.

## 공유 검증 항목

| --- | --- | --- |

| 빈 결과 | 200, items=[], nextCursor=null, hasNext=false | 검색 조건 유지·조건 초기화·상세 진입 후 목록 복귀 확인 |
| 동적 상태 | 고정 스냅샷을 보장하지 않음 | 첫 페이지 후 새 글·숨김·삭제·닉네임 변경을 적용하고 다음 페이지 조회. 화면 ID 중복 제거 |

공백 종류(ASCII 공백 외 NBSP 등), author의 빈 값·길이·trim, 빈 ticId·board·tag·cursor, 미지의 쿼리 키는 정본에 완전히 명시되지 않았다. 기존 프론트는 폼의 빈 필드를 생략하고 q에 JS trim을 사용한다. 백엔드에 그대로 동치라고 가정하지 않으며 169·프론트 교차 검토에서 확정한다. 표본에 없는 입력까지 검증기가 운영 계약을 결정하지 않는다.

검증기는 빈 필터·author 앞뒤 공백·ASCII 공백 이외 공백·미지의 키와 지원하지 않는 cursor/size 입력을 `UNSPECIFIED`로 거절한다. 이는 **API 오류 코드나 400 판정이 아니라 이 참조 구현의 정의 범위 밖이라는 표시**다. JSON의 `unspecifiedCases` 11건은 정상/오류를 결정한 `cases` 30건과 분리하며 프론트 정상/오류 비교에도 넣지 않는다. 실제 API 테스트로 이식할 때 `UNSPECIFIED`를 서버 응답으로 구현하지 않는다.

참조 정렬은 `Date.parse`로 순간을 비교한 뒤 숫자 posts.id를 비교한다. 오프셋이 달라도 같은 순간인 경우, 소수초·동률 ID를 검증한다. JavaScript Date의 밀리초 정밀도까지만 다루므로 PostgreSQL 마이크로초 정렬·커서는 169의 DB 테스트로 확인한다.

## 공개 범위·후속 경계

- 합성 표본의 모든 visible 대상은 조회 회원이 열람 가능한 것으로 전제한다. 실제 게시판 열림·세션 검사는 164·169 통합에서 검증한다.
- 162의 공개 취소·개별 숨김·부모 숨김 판정을 후속 169에서 적용한다. 이 브랜치는 162 코드를 가져오지 않는다.
- 공개 분석 취소와 부모 공식 스레드 숨김은 다르다. 하나의 분석 취소만으로 부모 스레드 전체를 제거하지 않는다. 공개 요약·참여자 집계는 현재 유효 분석만 사용하며, 스레드 자체 목록 노출은 부모 접근 정책을 따른다.
- 숨김·삭제 글/스레드와 숨김 하위 콘텐츠는 검색·직접 URL에서 노출하지 않는다. 독립 History 첨부 권한은 공식 공개 여부와 혼합하지 않는다.

## 공식 제목·본문의 구현 차이

161의 `PublicAnalysisService`는 `TIC {ticId} 신호 c-{candidateId} 밝기 분석`을 제목으로 저장한다. 검색은 저장된 제목을 대상으로 하며 s- 접두 예제를 추가하지 않는다.

현재 생성 본문은 빈 문자열이다. API의 목표 계약인 **시스템 신호 요약 본문 검색**은 아직 구현되지 않았다. `official-body-current`는 이 현재 상태를 보여주는 표본이며 목표 계약을 빈 본문으로 변경하지 않는다. 164·169 담당 백승학이 요약에 포함할 공개 필드, 작성·갱신 시점, 기존 스레드 채움 여부를 정리한 뒤 목표 본문 표본을 추가한다. 회원 메모·개인 History·개별 공개 분석 본문을 암묵적으로 합쳐 검색하지 않는다. 요약 본문 처리는 169 최종 완료 전 해결 항목이다.

## 인덱스·실행 계획 기준

V1에 `pg_trgm`, `ix_posts_title_trgm`, `ix_posts_body_trgm`, `ix_posts_tic_kind_created`, `ix_posts_user_created`가 이미 있다. 170에서 새 마이그레이션이나 board/tag 인덱스를 추가하지 않는다.

[search-plan.sql](search-plan.sql)은 **일회용 PostgreSQL**에서 임시 합성 테이블만 만드는 측정 절차다. pg_trgm이 준비된 환경에서 psql의 `ON_ERROR_STOP`을 켜 실행한다. 실제 posts 조인·권한·커서 쿼리의 성능 인수는 169에서 수행한다.

합성 본문은 1500행 중 1499행이 동일한 반복 문자열인 매우 편향된 분포다. GIN·BitmapOr·Seq Scan 관찰은 이 분포와 선택도에 따른 결과이므로 실제 데이터에서 같은 계획을 전제하지 않는다. 169의 성능 인수에는 실제에 가까운 본문 길이·어휘·검색어 빈도 분포를 별도로 사용한다.

| 시나리오 | 확인 항목 |
| --- | --- |
| 충분한 길이의 드문 검색어 | 기존 GIN을 쓸 수 있는 원본 열 ILIKE 조건인지, 실제 rows·buffers·재검사 비용 |
| 제목 OR 본문 | 두 GIN의 BitmapOr 등 선택 계획과 결과 일치. 특정 노드를 무조건 요구하지 않음 |
| 1~2자·흔한 검색어 | 많은 행을 읽는 비용과 순차 스캔 선택 이유 기록. 인덱스 강제 사용을 합격 기준으로 삼지 않음 |
| TIC·board·tag 조합 | 필터 후 행 수·정렬 비용·LIMIT, 기존 복합 인덱스의 유효 범위 |
| 최신순·다음 페이지 | 실제 (created_at,id) 경계에서 누락/중복과 Sort·temp I/O 확인 |
| 닉네임 정확 일치 | 실제 users 조인·대소문자 처리 계획은 169 쿼리로 확인. author도 LIKE를 쓰면 와일드카드를 문자로 이스케이프 |

기록에는 PostgreSQL 버전, collation, 행 수·문자 길이·선택도, 인덱스 정의, ANALYZE 여부, 동일 쿼리 3회 각각의 계획·시간·버퍼를 포함한다. 대표 데이터 양은 합성값이며 운영 규모가 아니다. 10만 행 예제에서 1회 성공했다고 운영 성능을 충족했다고 보고하지 않는다. `enable_seqscan=off`로 강제한 결과나 근거 없는 ms 임계값을 인수 기준으로 쓰지 않는다. `lower(title)`처럼 원본 열에 함수를 씌우는 쿼리는 기존 인덱스와 일치하는지 별도로 검토한다.

## 핫 토픽·담당자 인계

DEC-09와 P0는 확정이다. 공식 스레드의 현재 유효 공개 판단 회원×신호당 최신 한 건으로 N을 계산하고 N>=10, 기간 제한 없이 선정한다. 일반 글·댓글·반응 수는 더하지 않는다. 정렬은 N DESC → 스레드 생성 시각 DESC → ID DESC다.

171에서는 9/10/11명 경계 외에 같은 회원 재제출(인원 불변), 최신 공개 취소 후 이전 공개 존재(인원 유지), 마지막 공개 취소(1명 감소), 숨김 제외·복원·재진입·정렬 동률을 실제 집계로 검증한다. JSON의 hotTopics는 임계값 예제일 뿐 집계 검증이 아니다.

- 백승학(169·171, 연계 164): 공통 표본을 실제 API 테스트로 이식하고 권한·커서·SQL 계획을 검증한다. 위 미결 본문 계약을 해소한다.
- 하서진(검색·핫 토픽 프론트): 동일 표본의 query를 URL에 한 번 인코딩해 요청하고 입력 오류·검색 조건 유지·결과 복귀·빈 목록을 확인한다. 서버 매칭 구현 완료를 fixture 기반 브라우저 통과로 대신하지 않는다.
- 프론트 문서 후속: [ticket-217-readiness.md](../../../apps/frontend/docs/ticket-217-readiness.md)와 [ticket-218-readiness.md](../../../apps/frontend/docs/ticket-218-readiness.md)의 “서비스 API에 P1/P0 상향 요청 문장이 남아 있다”는 설명은 이번 정정 이후 낡았다. 하서진 담당 교차 검토 시 이 두 문서를 갱신한다.
- 강재민(탐사 집계 연계): 회원×신호 최신 유효 공개 집합과 핫 토픽 N이 기존 판단 집계와 같은 원천인지 교차 확인한다.

170 산출물 검증과 BE·FE 교차 검토 완료는 별도로 기록한다. 이 문서는 리뷰 요청을 실제 전송했거나 팀 승인이 끝났다는 의미가 아니다.

## 2026-09-20 실제 검증

- 표본 검증: 검색 30건·페이지 예제 1건·핫 토픽 임계값 4건·Unicode 길이 경계 2건 통과.
- 공통 JSON 입력 30건을 기존 프론트 `readFeedSearch`에 직접 적용해 정상/오류 일치 확인. 기존 `feedSearch.test.ts` 5건도 통과. 검색 결과 SQL·브라우저 화면 검증은 아니다.
- `search-plan.sql`: 포트·볼륨을 노출하지 않은 일회용 `postgres:18.6-alpine`, PostgreSQL 18.6 / en_US.utf8 / 합성 10만 행 / ANALYZE 후 4개 EXPLAIN ANALYZE 생성 성공. 드문 제목은 title GIN, 제목 OR 본문은 두 GIN의 BitmapOr, 2자 검색은 Seq Scan, TIC 조합은 기존 형태의 복합 인덱스를 사용했다. 절차 재현 확인으로 각각 1회만 실행했으며, 위 3회 측정 기준이나 운영 성능 인수를 완료한 것은 아니다.
- 최초 SQL 실행에서 PostgreSQL 18의 `lc_collate` 설정 조회가 실패해 `pg_database.datcollate` 조회로 수정한 뒤 전체 SQL을 재실행했다.
- 애플리케이션·Flyway 마이그레이션은 변경하지 않았다. 실제 API·권한·cursor·users 조인과 BE·FE 공동 리뷰는 후속 인수다.

## 2026-09-21 리뷰 보완 검증

미정 입력 11건의 UNSPECIFIED 구분과 시각 정렬 3건을 추가했다. 검색 표본 30건·페이지 1건·핫 토픽 4건·Unicode 2건, 기존 프론트 입력 30건 비교·단위 5건을 재검증해 모두 통과했다. 루트에서 --frontend 실행 시 안내와 종료 코드 1도 확인했다. SQL은 변경하지 않았으며 앞선 1회 절차 재현을 성능 인수로 확대하지 않는다.
