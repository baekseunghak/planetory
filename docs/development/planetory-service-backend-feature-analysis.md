## 1. 목적과 작성 방법

회원·커뮤니티·통계 백엔드의 기능을 하나씩 검토하고, 구현할 조건과 제외할 조건을 결정한다. 기능명만 나열하지 않고 누가 어떤 상태에서 요청했는지, 무엇을 저장·공개하는지, 실패·중복·변경 시 어떤 결과를 보장하는지까지 정한다.

표기 규칙:

- **기준 확정:** SRS v1.0에 이미 명시된 정책. 다시 선택하지 않는다.
- **결정 질문:** 구현 전에 답해야 할 누락·모호함. 질문의 선택지는 확정 정책이 아니다.
- **충돌:** 기준 문장들을 동시에 적용하기 어려운 경우. 관련 담당자와 정리한다.
- **계약 초안:** API·데이터·이벤트에 담아야 할 의미. URL·응답은 제안이며 테이블은 ERD v1.0을 따른다. 메시지 제품 도입을 뜻하지 않는다.
- **검증 사례:** 결정 후 기대 결과까지 채워 인수 조건으로 사용한다. 미결정 사례는 현재 통과 조건이 아니다.

각 기능은 `기준 확인 → 결정 질문 답변 → 포함/제외 범위 확정 → 계약 작성 → 사례 검토 → 합의 완료` 순서로 진행한다. 결정 기록은 7장에 남기고 해당 기능에 반영한다. 적용 순서는 최신 사용자 보충 결정 → SRS v1.0 → 충돌하지 않는 이전 결정이다. 보충 결정은 명시한 항목만 대체하며 미결정 사항은 합의 전 확정하지 않는다. 별도 보충 결정이 없는 상태표와의 충돌은 SRS를 따른다.

### 이번 작업의 범위

- 포함: 정책, 논리 데이터 관계, 권한, 상태 전이, API·이벤트·집계 계약, P0/P1 범위, 후속 MR 분해.

### F01. OAuth 회원 식별·가입

**v1.0 가입 초기화:** 튜토리얼은 1번만 먼저 발견하고 완료 시 다음 순번을 연다. 무신호 별 자동 완료·가입 보상은 없으며 챌린지 별은 튜토리얼 5개 완료 후에만 발견한다. 프로필 초기값과 실패 재시도 계약은 계속 협의한다.

**2026-09-07 검토 반영:** 초기 개발에서는 다중 제공자 연결을 제공하지 않는다. Google·SSAFY 로그인은 서로 다른 계정으로 운영하고 연결·병합은 추후 검토한다(SB-D01). 서비스 내 이메일 수정 기능은 제공하지 않는 방향이며, 수집 여부·제공자 이메일 변경 동기화·수집 정책은 미정이며 식별 스키마는 ERD users.provider/provider_user_id로 확정됐다(SB-D02). F01-Q1은 초기 범위 결정, Q2~Q5는 일부/전체 미결정이다.

**기준 확정:** SSAFY·Google 제공자 고유 ID로 회원을 식별한다. 같은 제공자 고유 ID의 재로그인은 동일 회원이다. 제공자가 다른 같은 이메일 계정을 자동 병합하지 않는다(ACC-01~02).

**결정 질문**

- F01-Q1: 초기 다중 제공자 연결·병합은 제외 확정(SB-D01). ERD의 users(provider, provider_user_id) UNIQUE를 따른다.
- F01-Q2: 이메일·이름 등 제공자 정보 중 필수 수집·선택 수집·미수집 항목은 무엇인가? 이메일이 없거나 바뀌어도 같은 subject를 유지하는가?
- F01-Q3: 최초 닉네임을 자동 생성하는가, 별도 입력 완료 후 가입하는가? 가입 도중 이탈 상태를 저장할 필요가 있는가?
- F01-Q4: 탈퇴한 제공자 ID 재로그인은 거부·재가입·복구 중 무엇인가? F04와 함께 결정한다.
- F01-Q5: 최초 회원 생성에 튜토리얼 발견·첫 방문 설정까지 포함하는가? 초기화 실패 시 회원 생성도 취소하는가, 재로그인으로 재시도하는가?

**계약 초안:** 제공자 식별 정보 → 내부 회원 ID·신규 여부·프로필 완료 여부. 제공자 원본 ID를 공개 프로필 응답에 포함하지 않는다. 중복 가입 방지는 제공자 식별 조합을 기준으로 정의한다.

**검증 사례:** 동일 ID 동시 첫 로그인 / 서로 다른 제공자의 동일 이메일 / 제공자 이메일 변경 / 필수 정보 누락 / 탈퇴 후 재로그인 / 튜토리얼 초기화 실패.

**범위 결정:** 초기 계정 연결·병합은 제외 확정. 계정 복구·추가 가입 단계는 미결정이다. OAuth 연결 설정과 인증 코드는 후속 구현이다.

### F02. 인증 상태·로그아웃·회원 상태

**확정 정책(SB-D14):** 세션 로그인, 마지막 유효 인증 API 요청부터 30분 유지·요청마다 연장. 자동 폴링 포함, 별도 5분 활동 갱신 없음. 현재 세션 로그아웃·다중 기기 로그인 허용. 만료 후 401, 닉네임 변경으로 재발급하지 않는다. 쿠키·CSRF·저장소·재시작 후 유지 정책은 후속 설계다.

**실행 구성:** 단일 Spring Boot 전제 유지. 서비스·Gold 본문은 PostgreSQL 배열, 잔차·주기도 캐시는 Redis를 사용한다. DB 접속·복제·배포 위치는 인프라와 합의한다. 로그인 세션 저장소는 별도 미정이다.

**2026-09-07 검토 반영:** 인증 없음/만료는 401이며 프론트가 재로그인을 안내한다. 인증됐으나 권한이 부족하면 기본 403과 권한 부족 안내를 사용한다(SB-D03). 존재를 숨길 자원의 404 적용 대상은 미결정이다. 요청 기준 30분 연장은 SB-D14로 확정했다. Redis는 세션 저장소 후보이며 서버 간 공유를 필수 도입 근거로 삼지 않는다(SB-D07). 프로필 변경과 탈퇴 등 회원 상태 변경은 구분하며, 프로필 변경 시 토큰 이중 갱신은 확정하지 않는다.

**과거안 대체:** 화면 조작을 5분마다 확인하던 안은 폐기한다. 요청 기준이므로 조작 없이 자동 호출만 있어도 로그인은 연장될 수 있다. 이미 만료된 세션은 연장하지 않는다.

**기준 확정:** 로그인·콜백 외 보호 요청은 인증 필요. 로그아웃 후 보호 데이터에 재접근할 수 없다. 서버에서 역할·소유권을 검사한다(ACC-03~04, NFR-06~07).

**결정 질문**

- F02-Q1: 회원 상태와 전이는 무엇인가? ERD는 active/withdrawn이다. 별도 이용정지 상태는 추가하지 않는다. 회원 차단과 운영 제재를 혼동하지 않는다.
- F02-Q2: 현재 세션만 종료·다중 로그인 허용 확정. 이미 종료된 세션 반복 로그아웃의 204·CSRF 계약을 인증 담당자와 검토한다.
- F02-Q3: 인증 없음/만료 401·일반 권한 부족 403은 확정(SB-D03). 존재를 숨길 자원의 404 적용 대상과 오류 응답 형식만 추가 결정한다.
- F02-Q4: 회원 상태 변경 시 기존 로그인 무효화 시점과 처리 중 요청의 허용 기준은 무엇인가? 탈퇴와 콘텐츠 작성의 경합은 SB-D04로 결정했다(F04). 로그인 무효화 구현과 그 외 상태 변경은 별도 합의한다.
- F02-Q5: 요청 기준 30분·폴링 포함·다중 로그인은 확정. 세션 저장소와 재시작 후 유지 정책만 별도 결정한다.

**계약 초안:** 인증 상태 조회는 내부 회원 식별·상태·권한·최소 프로필만 반환. 인증 실패와 권한 부족을 구분하며 토큰·비밀값은 응답·로그에 노출하지 않는다.

**검증 사례:** 만료 후 요청 / 로그아웃 반복 / 애플리케이션 재시작 후 요청 / 탈퇴 직전 시작된 쓰기 / 일반 회원의 운영 API 요청.

### F03. 닉네임·프로필·공개 설정

**ERD 정합화(2026-09-10):** 닉네임·기본 프로필은 P0, user_settings를 사용하는 내 별 목록 공개 설정 변경은 P1이다. P0에서는 기본 공개로 제공하고, 기존 설정 행이 있다면 해당 공개 값을 존중한다. 공개 설정 API를 P0에 선행 구현하지 않는다.

**기준 확정:** 닉네임은 중복·금칙어 검사만 거쳐 상시 변경 가능하며 기존 글·답글·반응에 즉시 반영한다. 내 별 목록은 기본 공개, 비공개 시 타인의 MY-02 목록과 별별 진행을 숨긴다. 게시글·판단 분포·성과 집계는 영향받지 않는다(ACC-05, MY-04, DEC-34).

**사용자 확정(SB-D23, 2026-09-11):** 타인 프로필은 인증 회원에게 회원 ID·최신 닉네임·별 목록 공개 상태·성과 요약(찾은 신호 수, 등급별 별 수)을 제공한다. 성과 요약은 MY-04·DEC-34에 따라 별 목록 비공개와 무관하게 공개한다. 별 목록·별별 진행은 공개 설정을 따르며, 비공개면 타인 조회를 403으로 거부한다(SB-D03 권한 부족 안내). 이메일·OAuth 제공자 정보, 로그인·세션·접속 기록, 개인 History·미공개 분석은 타인에게 제공하지 않는다. 가입일·팔로우 목록·활동 이력은 초기 응답에서 제외하고 필요할 때 추가한다. 별 목록 비공개 전환은 이미 공개한 글·분석·반응의 작성자/반응자 닉네임 표시를 숨기지 않는다.

**결정 질문**

- F03-Q1: SB-D14 확정: NFC·앞뒤 공백 제거 후 2~20자, 한글 완성형·영문·숫자·밑줄, 내부 공백 불허, 영문 대소문자 무시 중복. SYSTEM/ADMIN/관리자/운영자 예약어 제외. 추가 금칙어 목록·담당은 협의한다. lower(nickname) 유일 인덱스 등 DB 반영 필요.
- F03-Q2: 다른 회원이 동시에 같은 닉네임으로 변경하면 실패 응답은 무엇인가? 이전 닉네임은 즉시 재사용 가능한가?
- F03-Q3: SB-D23 확정: 성과 요약(찾은 신호 수·등급별 별 수)만 추가 제공. 가입일·팔로우 목록·활동 이력은 초기 제외.
- F03-Q4: SB-D23 확정: 별 목록 비공개여도 성과 요약은 공개하고, 비공개 목록 직접 조회는 403. 다른 API에서 별별 진행을 우회 조회하지 못하도록 대상 필드 점검은 구현 시 검증한다.
- F03-Q5: MY-02의 최근 활동 기준을 정한다. 무신호 별은 제공에서 제외한다. MY-03은 신호별 현재 공개 상태·최초 성과·새 미공개 분석을 구분하고 분석 공개/공개 취소/다시 풀기를 제공한다.
- F03-Q6: MY-01은 P0지만 팔로우 수와 설정 일부는 P1이다. P0 응답·화면에서 미구현 항목을 어떻게 처리하는가?

**계약 초안:** 본인 프로필과 타인 공개 프로필의 허용 필드를 분리. 설정 변경 대상 회원은 요청 본인으로 결정. 별 목록·결과·히스토리 소유권은 별도로 검증한다.

**검증 사례:** 중복 닉네임 동시 변경 / 비공개 전환 후 직접 별 목록 조회 / 공개 게시글의 작성자 이름 갱신 / 공개 취소 후 성과·완료 보존 / 설정 반복 요청.

### F04. 탈퇴·보관·익명화

**우선순위 변경(2026-09-08, SB-D05):** 탈퇴 데이터 처리는 P1로 미룬다. 보관·익명화·표시·재가입 정책은 지금 선택하지 않고 P1 착수 시 검토한다. SB-D04의 탈퇴·작성 경합 규칙은 유지하며, 이번 변경을 이유로 soft delete나 글 보존을 확정하지 않는다.

**구현 시점 구분:** 경합 규칙의 P0 표시는 인증·쓰기 설계에서 지킬 제약이며 탈퇴 API의 P0 출시 확정을 뜻하지 않는다. 탈퇴 API 제공 시점은 보류다. 탈퇴를 제공하는 시점에는 접근 차단과 경합 처리를 함께 적용하고, 보관 정책이 미정인 채 탈퇴 API만 먼저 출시하지 않는다. 현재 P0에서는 이 정책을 설계 조건으로 기록하며 미제공 기능을 위한 별도 처리 흐름을 선행 구현하지 않는다.

**2026-09-07 검토 반영:** 탈퇴 순간 처리 중인 작성 요청을 모두 완료시키는 안 대신, 탈퇴와 작성의 DB 저장 확정 순서로 처리하기로 결정했다(SB-D04). 회원 soft delete, 기존 글 보존, 프로필 접근 제한은 계속 검토한다. Soft delete는 기록을 남기는 방법이며 탈퇴 후 쓰기 권한을 유지한다는 뜻이 아니다. 프로필의 ‘비공개 계정’ 문구, 제공자 ID·개인정보 보관 정책도 별도 결정한다.

**부분 확정 — 탈퇴와 콘텐츠 작성의 동시 처리(SB-D04)**

- 기준은 클라이언트 요청/응답 시각이나 서버 접수 시각이 아니라 DB 저장 확정 순서다. 탈퇴 효력 발생 시점은 탈퇴 상태가 DB에 확정된 시점이다.
- 글·댓글 작성이 먼저 확정되면 작성은 성공한 것으로 처리한다. 그 콘텐츠의 이후 보존·익명화·공개 여부는 별도 탈퇴 정책을 따른다.
- 탈퇴가 먼저 확정되면 아직 확정되지 않은 글·댓글 작성은 거부한다. 탈퇴 전에 접수된 요청이라도 예외를 두지 않는다.
- 거부한 작성과 연결된 Post/Comment·첨부·성과·등급 변경·별 발견·알림 사건은 새로 생성하거나 반영하지 않는다. 연관 저장을 일부만 남기지 않는다.
- 이미 별도 요청으로 확정된 Submission·AnalysisHistory 등은 거부된 게시 요청 때문에 되돌리지 않는다. 기존 데이터의 탈퇴 처리는 F04-Q2~Q4에서 결정한다.
- 탈퇴 완료 후 작성 재요청으로 신규 콘텐츠가 생성되지 않아야 한다. 탈퇴 전에 성공한 요청도 재전송으로 중복 생성하지 않는다. 탈퇴 후 과거 성공 응답 재조회 허용 여부와 거부 응답 코드는 API 계약에서 별도 결정한다.
- 요청 시작 시 회원 상태 확인만으로 완료하지 않는다. 단일 백엔드 안에서 여러 요청이 동시에 실행돼도 탈퇴와 작성의 순서를 DB에서 보장하고, 탈퇴 확정 뒤 작성이 커밋되지 않도록 한다. 구체적인 잠금·트랜잭션 방식은 후속 설계 대상이다.
- 탈퇴 전에 확정된 글에서 이미 생성된 알림 사건의 지연 발송·취소 여부는 F15와 별도 결정한다. 이번 결정은 거부된 작성에서 새 사건을 생성하지 않는 범위다.

| 검증 사례 | 기대 결과 |
|---|---|
| 글 작성 확정 후 탈퇴 확정 | 작성 성공. 이후 콘텐츠 처리는 별도 탈퇴 정책 적용 |
| 탈퇴 확정 후 처리 중 글 작성이 저장 시도 | 작성 거부. 새 글·첨부·연관 성과·알림 사건 없음 |
| 분석글 게시와 탈퇴가 동시에 요청됨 | DB에서 순서 보장. 게시가 먼저면 연관 처리를 함께 확정, 탈퇴가 먼저면 게시와 연관 신규 반영 모두 거부 |
| 탭 A에서 탈퇴, 탭 B에서 댓글을 같은 Spring Boot로 동시 요청 | 동일한 확정 순서 규칙 적용. 요청 시작 때 확인한 회원 상태만으로 탈퇴 후 작성을 허용하지 않음 |
| 탈퇴 후 거부된 작성 요청 재전송 | 신규 콘텐츠와 연관 사건 생성 없음 |
| 탈퇴 트랜잭션이 실패하여 롤백됨 | 탈퇴 완료로 안내하지 않음. 확정된 회원 상태와 일반 작성 조건에 따라 처리 |

**기준 확정:** 탈퇴와 보관은 DEC-11 미결정. 히스토리 분석값은 불변이며 MVP 사용자 삭제 기능이 없다. 이 규칙을 탈퇴·별도 삭제 요구의 자동 거부 근거로 사용하지 않는다(HIS-06).

### F06. 일반 자유양식 글 작성·수정·삭제

**입력 확정(SB-D14):** 제목 1~100자(앞뒤 공백 제거·줄바꿈 불가), 본문 1~10,000자(줄바꿈 허용). Unicode 코드 포인트 기준, 공백만 입력 불가. HTML·Markdown 서식 없이 일반 텍스트로 표시. 글당 본인 History 3개·출처 카드 3개까지, 중복 및 첨부만 작성 불가.

**기준 확정:** 최종 게시 전 Post를 만들지 않는다. 별 게시판에서는 TIC 자동 선택, 전체 피드에서는 관련 별 하나를 선택할 수 있다. 별 연결을 변경·해제하면 첨부·출처 카드의 TIC 적합성을 다시 검사한다. 일반 글 작성자는 제목·본문·메모·첨부를 수정·삭제할 수 있지만 원본 History를 수정하지 않는다(COM-04~05·10). **이전의 게시판/TIC 변경 일괄 금지 규칙은 대체됐다.**

**구현 계획:** 본인 인증 → 일반 글 입력 검증 → 선택 TIC와 모든 첨부/카드 검증 → Post 저장. not_matched의 토론하기는 같은 TIC·DISCUSSION·본인 현재 히스토리를 채운 작성 화면으로 연결하되 최종 요청 전 저장하지 않는다. 일반 글·태그·첨부·링크는 공식 공개 분석이나 성과를 만들지 않는다(AT-110·112·114).

**결정 질문**
- F06-Q1: 입력 길이·일반 텍스트는 SB-D14 확정. 태그 변경·일반 URL 표시 세부만 합의한다.
- F06-Q2: 별 변경 시 부적합 첨부를 화면에서 제거할지 재선택하게 할지 정한다. 서버는 부적합 첨부가 남은 게시를 거부한다.
- F06-Q3: SB-D17로 엄격한 중복 작성 방지는 P1 이관. P0는 등록 중 버튼 비활성화·POST 자동 재시도 금지·결과 불명확 시 목록 확인 안내. 동시 수정은 SB-D19 확정. 삭제 복원 미제공·삭제 댓글 목록/개수 제외는 SB-D22 확정.
- F06-Q4: 숨겨진 일반 글의 작성자 조회·수정 불가, 본인 삭제 허용은 F12의 SB-D22를 따른다.

**계약 초안:** 제목·본문·태그·nullable TIC·본인 History 첨부 ID·공개 출처 참조. 작성자는 인증에서 결정. 공식 공개 분석 등록 요청과 분리한다.

**일반 글·댓글 수정 정책(SB-D19, 사용자 확정)**

| 상황 | P0 처리 |
|---|---|
| 같은 필드 동시 수정 | DB에서 마지막 저장값 적용. 다중 탭의 같은 필드 덮어쓰기 허용, 버전 충돌 감지는 초기 제외 |
| 서로 다른 필드 | 프론트가 변경 필드만 PATCH로 전송하고 서버도 해당 필드만 저장. 생략 필드 유지, 전달한 배열은 전체 교체 |
| 연관 자료 변경 | 최신 저장 상태에 변경을 적용한 결과로 TIC·첨부 적합성 재검증 |
| 저장 중·응답 유실 | 저장 버튼 비활성화·PATCH 자동 재시도 금지. 결과가 불명확하면 안내 후 상세 재조회 |

**검증 사례:** 다른 TIC 첨부 상태로 별 변경 거부 / 별 해제 후 자료 첨부 거부 / 타인 수정 거부 / not_matched 토론 게시에도 후보·성과·공개 통계 불변 / 탈퇴가 먼저 확정되면 작성 거부(SB-D04).

**제외:** 일반 파일 업로드·서버 임시저장·예약 게시를 자동 포함하지 않는다.

### F07. 공개 분석 등록·취소·미확정 성과

**기준 확정:** 미확정 고유 신호를 매칭한 본인의 불변 History를 공식 스레드에 최초 공개 등록할 때 사용자×고유 신호당 성과를 한 번 인정한다. 세 판단 모두 허용한다. 일반 Post 게시·첨부·댓글·링크·반응은 인정 조건이 아니다(GRD-04, COM-18).

**구현 계획**
1. 인증·회원 상태·History 소유·TIC·매칭 신호·공개 자격 검증.
2. F22 공식 스레드 확보. 운영 숨김이면 새 공개를 거부하고 미공개 기록 보존.
3. 작성자+History의 공개 기록을 확보한다. 같은 기록 재전송/재공개는 재사용, 새 제출은 별도 공개 기록이다.
4. 신호별로 공개 등록·최초 성과·진행 수·별 발견을 같은 PostgreSQL 트랜잭션으로 저장한다(SB-D15). 인정 대기 상태를 만들지 않는다. 공개 판단 분포는 커밋된 기록으로 조회하고 주기 집계·StatsSnapshot은 이 트랜잭션에 넣지 않는다.
5. 본인 공개 취소는 운영 숨김과 독립적으로 저장한다. 취소·숨김·복원 시 F16의 유효 공개 집합을 다시 계산한다.
6. 성과·개인 History·탐색 완료는 일반 공개 취소/숨김으로 되돌리지 않는다. 자동 댓글·반응을 생성하지 않는다.

**데이터·API 계약:** 공개 기록은 작성자·TIC·고유 신호·History·공식 스레드·공개 시각·본인 공개 여부·운영 숨김을 연결한다. 조회에는 선택 공개 필드·그래프·작성자·제출 시각·출처만 제공한다. 개인 History 전체 열람 권한을 주지 않는다. ERD의 published_analyses를 사용하고 history_id UNIQUE, post_id는 공식 posts를 참조한다.

**저장·동시 처리 확정(SB-D15)**

| 상황 | 구현 계획 |
|---|---|
| 공개 등록 | 회원 행 잠금·상태/자격 검증 → 공식 스레드 → 공개 기록 → 최초 성과 → 진행 수 → 별 발견을 신호 한 건의 트랜잭션으로 처리한다. 탐사 내부 호출도 같은 트랜잭션에 참여한다. |
| 중간 실패 | 해당 실행의 신규 저장·변경을 모두 롤백한다. 별도 제출에서 이미 저장된 Submission/History와 기존 스레드·성과는 유지한다. |
| 같은 회원의 동시 성과 | users 회원 행 잠금으로 성과 생성·진행 수 갱신·별 선택 순서를 보장한다. 미확정 공개와 확정/FP 성과 모두 공통 지급 함수를 쓰고, 다른 별 발견 경로도 같은 잠금 규칙을 적용한다. |
| 중복 공개·지급 | ERD의 공식 스레드 candidate_id 부분 유일 제약, 공개 history_id, 성과 (user_id, candidate_id), 별 (user_id, tic_id)·(trigger_achievement_id, seq) 유일 제약을 사용한다. 실제 신규 성과가 생성된 경우에만 진행 수·별 발견을 추가한다. |
| 최초 스레드 생성 경합 | 서로 다른 회원의 첫 공개도 공식 스레드는 하나다. 유일 충돌 후 기존 행을 안전하게 재사용하며 숨김 스레드 대신 새 스레드를 만들지 않는다. |
| 일괄 공개·응답 유실 | 신호별 독립 커밋으로 성공분 유지·실패분 롤백. 전체 재시도에도 기존 공개/성과를 재사용하고 취소된 기록은 재공개하지 않는다. |

상세 저장 계약과 검증 사례는 [API 명세 9.1절](../../backend/docs/service-api-spec.md#91-공개-등록)을 함께 확인한다. 팀 교차 검토에서는 동일 PostgreSQL·트랜잭션 참여, 모든 성과/별 발견 경로의 공통 잠금 순서, 충돌·시간 초과 시 롤백 처리를 확인한다. 미발견 별이 설정 개수보다 적거나 없는 경우의 지급 정책은 별도 협의한다. 사용자 방향 확정이며 팀 검토·구현 완료는 아니다.

**결정 질문**
- F07-Q1: SB-D23 확정: 공개 필드는 작성자 닉네임·회원 ID, TIC·신호 ID·제출 시각·최초 공개 시각, 판단, 근거 체크, **메모**(SRS COM-18), 판단 재현에 필요한 분석 수치(주기·기준 시각·통과 지속시간 등), 최신 판 그래프·제출 당시 스냅샷, 재현에 필요한 제거 후보 조합·데이터 판·계산 버전이다. 개인 History 전체·다른 제출·미공개 기록·성과 내부 처리 정보는 제외한다. 필드별 공개 선택 UI는 두지 않는다. 공개 검토 화면(COM-19)에서 메모를 그대로 보여주고 공개 직전 “닉네임·판단·근거·메모·분석 수치·그래프가 공개됩니다”를 안내한다. History는 불변이므로 메모를 공개하고 싶지 않으면 해당 기록을 공개하지 않거나 새로 제출해야 한다. 수치 단위·필드명은 탐사와 합의한다. 그래프 판 전환·캐시·실패 처리는 SB-D18을 적용한다.
- F07-Q2: 최초 공개 전에 라벨/후보 연결이 변경된 옛 제출의 최초 성과 자격은 어느 시점 기준인가? 기존 공개 기록의 라벨 변경 후 보존은 확정돼 있다.
- F07-Q3: ERD대로 published_at은 첫 등록 시각을 유지하고 재공개는 unpublished_at만 해제한다. 별도 재공개 이력은 추가하지 않는다. 응답 코드와 현재 성과/이번 신규 인정 필드는 API 초안에 따라 합의한다.
- F07-Q4: SB-D15로 신호별 단일 트랜잭션·공통 회원 잠금 방향 확정. 탐사·DB 담당자와 실제 호출의 트랜잭션 참여·잠금 순서·별 부족 정책을 교차 검토한다.

**검증:** AT-102·103·105·108·109·114. duplicate 재매칭도 새 공개 가능하되 성과 중복 없음. 동일 History 동시 공개·응답 유실, 다른 회원 최초 스레드 경합, 같은 회원의 확정/FP·미확정 동시 성과, 별 저장 실패 시 전체 롤백, 일괄 성공분 유지를 검증한다. 진행 수는 실제 성과 행 수와 같아야 한다. 탈퇴가 먼저 확정되면 신규 공개·성과·알림 사건을 반영하지 않는다(SB-D04를 새 공개 경계에 적용). 이미 저장된 Submission/History는 되돌리지 않는다.

### F08. 일반 글·공식 스레드 토론 댓글

**입력 확정(SB-D14):** 댓글 1~2,000 코드 포인트·일반 텍스트·줄바꿈 허용. 공백만 입력 및 첨부만 작성 불가. 댓글당 History 3개·출처 카드 3개까지, 중복 불가.

**기준 확정:** 공개 일반 Post 또는 공식 신호 스레드의 토론에 1단계 댓글을 작성·조회하고 본인 댓글을 수정·삭제한다. 공개 분석 등록은 댓글을 자동 생성하지 않는다(COM-06, AT-114).

**구현 계획:** 부모 종류/ID와 공개 상태·작성자 검사 → 본문 및 같은 TIC 자료 검사 → 댓글 저장. 분석 목록과 댓글 목록을 분리한다. 개인 History 첨부는 F09, 공개 출처는 F24 규칙을 적용하고 댓글 반응을 임의 추가하지 않는다.

**결정 질문**
- F08-Q1: 부모 관계는 ERD의 comments.post_id로 확정한다. 일반 글과 공식 스레드 모두 posts를 참조하고 kind를 검사한다. 개별 공개 분석 댓글·2단계 답글은 제공하지 않는다.
- F08-Q2: 길이·첨부만 작성 불가·일반 텍스트 확정. 정렬·페이지는 API 제안 검토 대상이다. 중복 작성은 SB-D17 적용: 버튼 비활성화·자동 재시도 금지·결과 불명확 시 부모의 댓글 목록 확인, 엄격한 방지는 P1이다. 동시 수정은 F06의 SB-D19와 동일하게 변경 필드만 저장·같은 필드 마지막 저장·결과 불명확 시 상세 재조회를 적용한다.
- F08-Q3: SB-D22에 따라 부모 숨김/삭제 시 조회·수정 차단, 본인 삭제 허용. 삭제 댓글은 목록·댓글 수에서 제외한다. 알림 발생 기준은 별도 협의한다.

**검증:** 부모 숨김과 동시 작성 / 2단계 답글 거부 / 타인 수정 거부 / 별 없는 일반 글의 자료 첨부 거부 / 탈퇴 선확정 시 작성·첨부·알림 거부 / 공개 분석 등록 후 댓글 수 불변.

### F09. 본인 히스토리 직접 첨부

**기준 확정:** 관련 별이 연결된 일반 글·댓글에 같은 TIC의 본인 History를 첨부할 수 있다. 원글은 카드, 댓글은 요약에서 분석 상세로 연결한다. 별 미선택 글·댓글은 별 자료 선택/첨부를 제공하지 않는다. 타인 개인 History는 직접 첨부할 수 없으며 공개 자료는 F24 출처 링크로 연결한다(COM-07, HIS-05, NFR-13).

**구현 계획:** 인증·History 소유·부모 TIC를 작성/별 변경/게시 시 검사 → 부모+History 참조 보존, submissions 절대값·analysis_histories 파라미터 조회 → 조회 시 부모 및 대상 공개 상태 검사. 원본 수정·성과 인정·공식 통계 갱신 없음. **일반 자유글도 별을 연결했다면 첨부 가능하다.**

**결정 질문**
- F09-Q1: 부모별 History 최대 3개·중복 불가 확정. 공개 필드는 SB-D23의 공개 분석 필드와 같게 하며 메모를 포함한다. 순서·교체 규칙만 합의한다.
- F09-Q2: SB-D18 적용: 동일 판 조회, 판 전환 시 최신 판 재조회 최대 1회, 실패 시 503, 스냅샷 부재 시 409, 은퇴 후보는 현재 원본 대체 표시. Redis 적중 여부와 관계없이 현재 공개 권한을 검사한다.
- F09-Q3: 개인 History 원본 API와 첨부용 제한 응답의 경계를 탐사 담당자와 합의한다.

**검증:** AT-110~112·114. 별 변경 후 부적합 자료 거부 / 타인 History 거부 / 공개 첨부로 원본 전체 조회 불가 / 글 삭제·숨김 후 첨부 직접 조회 차단. History는 제출 당시 절대 epoch·duration·주기와 버전을 보존하고 현재 Bundle로 위상을 재환산한다. 매칭 성공은 analysis_snapshots의 folded_flux/folded_err로 당시/최신 토글을 제공한다. 은퇴 후보로 잔차 재현 불가 시 현재 원본 곡선으로 대체하고 안내한다. 불일치 제출은 파라미터만 보존한다(HIS-02·03).

**그래프·Redis 구현 기준(SB-D18, 사용자 위임에 따른 문서 반영)**

| 기능 | 처리 기준 | 남은 작업 |
|---|---|---|
| 현재 그래프 | 한 응답의 곡선·모델·잔차·주기도를 같은 Bundle·계산 버전으로 조회. 실제 판 ID 반환 | DB 읽기 일관성·배열 정규화 검증 |
| 판 전환 | 응답 준비 시 current 여부 검사. 변경 확인 시 최신 판으로 전체 조회 최대 1회 재시도, 다시 실패하면 503. 다음 조회에서 판 변경 안내·그래프 교체 | 탐사 재조회 흐름 연계 |
| 당시 그래프 | PostgreSQL 제출 스냅샷 사용. 없으면 409 SNAPSHOT_UNAVAILABLE와 현재 그래프 전환 안내. 최신 결과를 당시 결과로 위장하지 않음 | 공개 필드·화면 연계 |

| 접근·장애 | 캐시 조회도 현재 공개 권한 검사. Redis 장애는 캐시 미존재와 구분해 503 안내. 기존 History·성과 유지 | 실패·복구 테스트 |

상세는 [API 명세 7.2절](../../backend/docs/service-api-spec.md#72-공개-첨부와-출처-카드)에 둔다. 로그인 세션 저장소와 계산 캐시는 별도이며 30분 세션 정책을 캐시 TTL로 사용하지 않는다. 계산 위치·자원 수치·탐사 상태 API는 담당자와 합의한다. 판 전환 후 진행 중 분석도 최신 판으로 재로드하는 최신 명세를 적용하며 과거 판 고정은 하지 않는다.

<a id="f10"></a>

### F10. 동의·비동의·반응자 목록

**v1.0 대상 제한:** 동의·비동의는 일반 Post에만 적용한다. 공식 신호의 세 판단은 F16 공개 분석 통계이며, 분석 공개로 반응을 자동 생성하지 않는다(COM-08).

**기준 확정:** 회원·Post당 agree/disagree 중 최대 하나. 변경·취소·멱등 처리 지원. 본인 글 반응 가능. 합계와 반응한 회원 닉네임 전원을 인증 회원에게 공개한다. 성과와 과학 판정에는 사용하지 않는다(COM-08, NFR-14).

**결정 질문**

- F10-Q1: 클릭을 ‘토글’로 처리하는가, API는 원하는 최종 반응/없음을 전달하는가? 동일 요청 반복 결과를 명시한다.
- F10-Q2: 여러 탭의 반응 변경이 순서가 바뀌어 도착할 때 최종 상태 기준은 무엇인가?
- F10-Q3: 삭제·숨김 대상의 새 반응·변경·취소와 복원 후 반응 유지 기준은 무엇인가?
- F10-Q4: 목록의 정렬·페이지 크기·최신 닉네임·탈퇴 회원 표시, 반응 변경 중 합계와 목록 조회 기준은 무엇인가?
- F10-Q5: 전원 공개는 전원 일괄 전송이 아니라 페이지 순회로 모두 볼 수 있게 해도 되는가?

**상태 분석:** 없음 → 동의/비동의, 동의 ↔ 비동의, 동의/비동의 → 없음. 같은 최종 상태 반복 요청은 수를 추가하지 않는다.

**검증 사례:** 본인 글 반응 / 같은 요청 반복 / 동시에 동의·비동의 / 취소 반복 / 닉네임 변경 / 숨김 후 목록 접근 / 탈퇴 회원 반응.

### F12. 숨김 상태 적용 — 운영 화면·감사는 v1 제외

**범위:** COM-13, OPS-01·06 v1.0. P0에는 숨김 상태의 접근 제어만 구현한다. 운영자는 DB에서 상태를 변경하며 서비스에 숨김·복원 API, 운영 화면, 감사 테이블을 만들지 않는다.

**구현 계획**
- posts/comments의 hidden 상태, published_analyses.hidden_at을 읽어 공개 여부를 판단한다. 본인 취소 unpublished_at과 독립이다.
- 스레드 숨김은 하위 공개 분석·토론·첨부·출처·검색·직접 URL에 적용하며 신규 공개·대체 스레드 생성을 막는다.
- DB에서 부모를 복원해도 개별 숨김·본인 취소를 해제하지 않는다. 기존 History·성과·탐색 완료는 보존한다.
- F16은 현재 유효 집합을 조회해 판단을 다시 선택한다. DB 직접 변경도 즉시 반영되도록 공개 접근 판정은 현재 DB 상태로 검사한다. 오래된 응답 캐시로 우회하지 않는다.
- 일반 글 삭제/숨김은 별도 공개 분석을 취소하지 않는다. 일반 회원은 hidden·운영 설정을 변경할 수 없다.

**확정(SB-D22):** 일반 글·댓글 삭제/숨김 시 작성자를 포함한 조회·수정은 404로 거부한다. 공개된 타인 콘텐츠 수정·삭제는 403. 본인 삭제는 비공개 상태에서도 허용하고 성공·소유권 확인 가능한 반복 삭제는 204, 그 외 비공개 타인/없는 자원 삭제는 404다. 부모 글 삭제는 댓글·첨부 공개 조회도 차단한다. 삭제 댓글은 목록·댓글 수에서 제외하고 삭제 자리 표시는 남기지 않는다. 삭제 복원·휴지통은 제공하지 않는다. 숨김 해제는 hidden에서만 가능하며 deleted를 되살리지 않는다. 부모 복원도 개별 숨김·삭제를 해제하지 않는다. DB 보관기간·물리 삭제 정책은 별도이며 History·기성과·등급은 유지한다. 검증에는 반복 삭제·비공개 본인 삭제·하위 직접 조회·삭제/숨김 해제 경합을 포함한다.

**남은 질문:** F12-Q2 공식 공개 분석의 본인 공개 취소 허용과 비노출 오류는 별도 계약으로 검토한다. 감사 보관·운영 조치 UI 설계는 v1 후속 범위다.

**검증:** AT-108·109. DB 직접 숨김 후 목록·카드·직접 조회 차단 / 최신 공개 숨김 시 이전 유효 판단 복귀 / 전부 무효면 제외 / 복원해도 본인 취소 유지 / 신규 공개·대체 생성 차단. AT-113의 운영 감사 검증은 v1 제외.

### F13. 전체 피드·검색·핫 토픽

**우선순위:** 최신 사용자 결정 SB-D08(2026-09-09)에 따라 전체 피드·검색·필터·핫 토픽은 P0다. v1.0 COM-03·09의 P1 우선순위만 상향하며 기능 정책은 유지한다. 팔로우는 계속 P1이다.

**구현 계획:** 일반 글과 SYSTEM 공식 스레드를 종류별로 구분해 반환한다. 공개 분석은 독립 작성자 기록이며 SYSTEM 원글 작성자로 사용자를 표시하지 않는다. 공식 스레드 카드/상세는 신호 요약·세 판단 통계·공개 분석·토론을 제공한다. 모든 경로에서 동일한 유효 공개 조건 적용.

**결정 질문**
- F13-Q1: P0 탭 노출과 내 스레드에 본인 일반 글·공개 분석·토론 참여를 어떻게 포함할지 정한다.
- F13-Q2: SB-D21로 일반 글·공식 스레드의 생성 시각→ID 내림차순과 기본 20/최대 100개 확정. SYSTEM 표시 세부와 커서·오류 계약은 팀과 검토한다.
- F13-Q3: 검색 일치 방식·조건 조합은 SB-D21, 핫 토픽 임계값·기간·정렬은 SB-D16으로 확정했다(DEC-09 보충).
- SB-D21 검색 확정: 일반 글·공식 스레드 대상, TIC 정확 일치·제목 부분 일치(영문 대소문자 무시), 앞뒤 공백 제거·내부 공백 유지, 두 조건 AND. 조건 없으면 접근 가능한 전체 피드, 결과 없으면 200 빈 목록, 삭제·숨김 제외. 본문·작성자·태그 검색·오타 보정·별도 검색 엔진은 초기 제외. COM-03 원본 반영·공식 제목 생성 규칙은 팀 협의 대상이다.

- F13-Q4: SB-D16 확정: 공개 취소·숨김·복원 후 현재 유효 참여자를 다시 집계한다. 일반 반응·댓글 변화는 핫 토픽 인원에 영향을 주지 않는다.

**검증:** 일반 글/공식 스레드 구별 / 숨김 하위 기록 검색 차단 / 취소된 출처 카드 미노출 / SYSTEM 작성 주체 / 새 글 사이 페이지 이동.

**최신 검색·핫 토픽 방향(SB-D10·13·16)**

| 순서 | Submission 접수 시각 내림차순, 동률 id 내림차순 | 접수 시각 오름차순, 동률 id 오름차순 |
| 재제출 | 미공개면 무영향. 새 기록 공개 시 최신 재선택 | 첫 매칭 기록 유지. 나중 판단 변경으로 일치율 변경 금지 |
| 취소·숨김 | 이전 유효 공개로 복귀, 없으면 회원 제외 | 공개 분석의 취소 규칙을 확대 적용하지 않음 |
| 표시 | 공개 분석의 판단 · 참여자 N명 | 이 신호를 찾은 사람 중 기록과 일치 N% · M명 |

공개 통계는 세 판단 인원 합이 N이고, 필터는 목록만 좁히며 전체 분모를 바꾸지 않는다. 0명은 ‘아직 공개된 분석이 없습니다’. 행성 확률로 표현하지 않는다. 조회자도 유효 참여자라면 포함한다. 오래된 제출의 늦은 공개는 최신 판단을 덮어쓰지 않는다.

채점형은 첫 매칭 판단과 planet_truth가 일치한 회원 수/M으로 계산하며 세 판단 막대·‘정답률’ 표현을 쓰지 않는다. 별도 제출 순번 열·성과 테이블 조인이 필요하지 않다. 공식 공개 기록은 라벨 변경만으로 삭제하지 않는다.

**남은 질문:** F16-Q1 반올림·0명 표시·API 필드, F16-Q2 탈퇴·수동 정정과 과거 라벨 영향, F16-Q3 후보 병합/분리 기준. 모집단·첫/최신 선택·쿼리 방식은 확정 사항이다.

**검증:** AT-103~106·108·116. 공개 8/4/3명은 15명 / 공개 취소 시 이전 기록 복귀 / 동일 시각은 id 순 / 채점형 첫 매칭 오판 뒤 정답 재제출에도 첫 매칭 일치율 불변 / 미매칭 제출 제외 / 성과 없는 매칭 회원 포함.

### F17. 주간 챌린지·튜토리얼 완료 연계

**우선순위:** P0. POL-24, CHL-01, 삭제된 CHL-02, DEC-10과 ChallengeRound v1.0를 따른다.

**기준 확정:** 회차별 미확정·AI 승인 별 하나를 제공한다. 튜토리얼 5개 완료 회원에게만 발견시킨다. 챌린지 전용 달성 조건·성공 판정·진행도·보상·소급 반영은 없다. 일반 별의 탐색 진행·성과는 별개로 적용한다. 튜토리얼은 1번부터 순차 발견하고 건너뛰기는 서버 설정 기준이며 무신호 별을 사용하지 않는다.

**구현 계획:** DB에 회차 대상·기간·상태를 설정 → 대상 회원의 튜토리얼 완료 확인 → 회차 별 발견 멱등 반영 → 기간·대상·소개·스레드 참여 수 조회. ERD 상태는 planned/active/closed. 취소의 closed 처리·기간 경계와 소개 필드 필요 여부는 합의한다. 완료 보상 Job·성공 사건 집계·사용자 챌린지 달성 테이블을 계획하지 않는다.

**남은 충돌:** CHL-03의 ‘목표 달성·완료 성과·마감 제출 반영’은 삭제된 기능의 문구다. [정합화 요청 R8](./planetory-doc-sync-requests.md)로 남기고 성공 기능을 재도입하지 않는다.

**결정 질문**
- F17-Q1: 기간 시간대·경계·진행 중 대상 변경·공개 중단 처리와 회차 종료 후 별 접근 정책은 무엇인가?
- F17-Q2: 회차 진행 중 튜토리얼을 완료한 회원의 발견 시점과 이미 발견한 대상의 경로 기록은 무엇인가?
- F17-Q3: 스레드 참여 수는 공개 분석 참여자인지 토론 참여자인지 정의한다. STA-02 참여 수도 같은 용어로 정합화한다.
- F17-Q4: P0 시작 안내는 아래 첫 접속 방식으로 한정한다. 브라우저별 안내는 SB-D20 확정이며 참여 자격 없는 회원에게 새 회차 안내를 하지 않는다. 요일·시각·시간대는 팀과 정한다.

**최소 챌린지 안내 정책(SB-D12·20, 사용자 확정)**

1. 운영 회차의 시작 요일·시각 이후 첫 인증 접속에서 현재 진행 중인 새 챌린지를 조회하고 ‘이번 주 챌린지가 새로 생겼습니다’를 안내한다. 해당 요일에 접속하지 못한 경우에도 회차 진행 중 다음 홈 진입에서 참여 자격을 확인해 안내한다.
2. **ERD 정합화(2026-09-10):** 서버는 회차 ID·기간·자격만 반환한다. 회원×회차 확인 테이블과 확인 API는 추가하지 않는다. 프론트가 회원별로 브라우저에 마지막 안내 회차를 저장해 반복 표시를 줄이는 최소안을 사용한다. 실제 안내 표시 후에만 회차를 기록하고 조회 성공만으로 기록하지 않는다. 같은 회원·브라우저의 같은 회차는 재안내하지 않고 새 회차는 다시 안내한다. 기기 변경·저장소 삭제·저장 실패 시 재노출을 허용하며 저장 실패가 이용을 막지 않게 한다. 여러 탭 동시 표시까지 정확히 한 번으로 보장하지 않는다. 기기 간 확인 공유는 P1 notifications의 challenge 유형·회차 참조·read_at으로 상세화한다.
3. 새 회차가 실제 공개·진행 중인지 확인한다. 종료·취소 회차를 새 챌린지로 안내하지 않는다. 안내 확인과 별 발견은 별개이며 튜토리얼 5개 완료 자격 검사는 유지한다. 참여 자격 없는 회원에게 새 챌린지 안내를 띄우지 않는다. 별도의 정적 소개 화면 여부는 후속 UI 협의다.
4. 접속 시 조회로 처리하며 정시 푸시·이메일·알림함·실시간 전송·일반 수신 설정은 P1이다. 안내를 위한 별도 예약 발송 Job은 계획하지 않는다. 이미 접속 중인 회원은 다음 홈 진입 등 재조회 시 확인하는 안이며 재조회 시점은 프론트와 합의한다.

**추가 검증:** 시작 경계 전후 / 시작일 미접속 후 주중 접속 / 같은 회차 재로그인·다중 탭 / 회원 전환 / 다른 기기·브라우저 저장소 삭제 시 재노출 / 종료·취소 / 튜토리얼 미완료·도중 완료. 서버 확인 요청은 없으며 정확히 한 번의 화면 표시를 보장하지 않는다.

**검증:** 미완료 회원 챌린지 발견 차단 / 5개 완료 후 별 1개 발견 / 반복 사건 중복 없음 / 챌린지 별 분석에 추가 챌린지 보상 없음 / CHL-02 관련 성공 Job 없음.

### F21. 운영 설정·데이터 적용 경계

**범위:** OPS v1.0. 운영 UI·서비스 관리 API·감사 테이블은 v1에 추가하지 않는다. DB 권한 분리, 규칙 참조, 배치 적용 시 데이터 무결성은 P0다.

- operation_settings는 rule_version별 values JSONB·applied_at·note를 보존한다. 값 변경 시 새 버전 행을 만들고 이전 행은 삭제하지 않는다. Submission은 판정한 규칙 버전을 참조한다.
- 성과 한 건마다 stars_per_achievement개(기본 1)를 발견한다. 등급은 TIC별 achievement_count 1/2/3/4 이상에 따른 A/S/SS/SSS 표시다. FP도 같은 성과이며 별도 상한이 없다.
- star_unlocks는 trigger_achievement_id와 seq의 유일성으로 중복을 막는다. 완료·등급 상승은 별 발견의 트리거가 아니다.
- 튜토리얼 순차 발견, 5번 multi_fp, 무신호 제외. tutorial_skip_after는 개발 3·운영 0(끔), 판단 불일치도 세며 상세 보기 경유 규칙을 따른다.
- 서비스 데이터는 PostgreSQL. Gold 곡선·주기도는 DB 배열, 잔차·주기도 캐시는 Redis, 과거 매칭 스냅샷은 PostgreSQL이다. 로그인 세션의 Redis 사용은 별도 미정이다.
- 새 Bundle 공개 시 진행 중 분석도 최신 판으로 전환한다. 제출 당시 Bundle·절대값·계산 버전은 기록으로 보존한다. 갱신 안내·요청 중 판 변경 오류는 SB-D18을 적용하고 탐사와 교차 검토한다.

**남은 질문:** 규칙 기본값·적용 경계, 공개 중단 영향, 후보 병합/분리·부정 사용 정정, 배치 재처리의 책임·실패 복구. 서비스에 범용 운영 API를 먼저 만들지 않는다.

**검증:** 회원의 운영 상태 변경 불가 / 규칙 변경 전후 Submission 버전 참조 / 같은 성과 재처리 중복 발견 없음 / FP 두 신호 성공 시 성과 2건·등급 S / 완료만으로 별 발견 없음 / 라벨 변경에도 기성과 유지.

<a id="f22"></a>

### F22. SYSTEM 공식 신호 스레드

**범위:** COM-17, OPS-01 P0.

**구현 계획:** 최초 유효 공개 분석 요청에서 TIC·고유 신호의 공식 공간을 확보한다. 사용자·판단·주기/고조파·Bundle별 새 스레드를 만들지 않는다. 첫 공개 성공과 생성은 원자적이며 posts.kind와 user_id=NULL로 SYSTEM을 표현한다. 별도 감사 사건은 저장하지 않는다. 관리자 로그인 계정은 자동 생성 조건이 아니다. 신호 요약·공개 분석 목록·별도 토론을 제공한다.

일반 회원은 공식 원글 수정/삭제 불가. 운영자는 DB에서 숨김/복원하며 서비스 관리 API는 없다. 숨김 중 새 공개는 실패로 안내하고 원본 미공개 기록을 보존하며 대체 스레드·성과를 생성하지 않는다.

**계약·결정:** 논리 유일성은 고유 신호당 하나(TIC 적합성 포함). 공식 공간은 posts.kind=system_thread, user_id=NULL, candidate_id 부분 유일 제약으로 확정한다. 공개 분석은 published_analyses, 댓글은 comments.post_id, 출처는 post_source_links다. 요약·재분류 표시와 동시 충돌 응답만 합의한다. 이미 생성된 스레드를 라벨 변경만으로 소급 삭제하지 않는다.

**검증:** AT-102·109. 두 회원 최초 공개에도 공간 하나 / 고조파·다른 Bundle 중복 없음 / 일반 회원 편집 거부 / 숨김 중 재생성 금지.

<a id="f23"></a>

### F23. 개별·일괄 공개 검토

**범위:** COM-19, HIS-04, MY-03 P0.

**구현 계획:** 개인 기록 기본 보존 → 분석 공개 또는 TIC 종료 화면의 모두 게시/나중에 → 신호별 대표 기록(기본 미공개 최신 제출)과 판단·그래프·수치·근거·메모 검토(메모도 공개됨을 안내, SB-D23) → 선택 항목 전송 → 항목별 성공/실패 반환. 이미 공개 중인 동일 기록은 제외하되 같은 신호의 새 분석은 가능하다.

원자성 단위는 신호별 최초 공간 확보·공개 등록·성과·통계 반영이다. 일괄 전체를 무조건 롤백하지 않는다. 성공 항목만 반영하고 실패 항목만 재시도한다. 다수 신호의 최초 성과/등급 상승/별 열림은 순차 개별 인정과 동등하게 보장한다. 공개 실패·나중에·취소는 탐색 완료를 되돌리지 않는다.

**결정 질문:** F23-Q1 요청 항목 상한·대표 기록 변경·동일 신호 복수 선택 처리, F23-Q2 항목별 멱등 키·공통/개별 오류, F23-Q3 동시 성과 반영의 성과당 별 발견 처리 순서와 서버 응답 계약.

**응답 초안:** 항목별 신호/History·공개 기록/스레드 ID·미게시/게시 중/공개됨/게시 실패 표시·최초 성과 여부·실패 원인·재시도 가능 여부. 전송 상태와 성과 인정 상태를 혼동하지 않는다.

**검증:** AT-103·107. UNSURE 공개 허용 / 일부 성공 뒤 실패만 재시도 / 성공분 중복 없음 / 순차 인정과 별 열림 동등 / 완료 상태 유지.

<a id="f24"></a>

### F24. 공식 신호·공개 분석 출처 링크

**범위:** COM-20, NFR-13~14 P0.

**구현 계획:** 별 연결 일반 글/댓글에 동일 TIC의 공식 스레드 또는 공개 분석 참조를 연결한다. 타인의 공개 분석은 작성자·출처를 보존하며 개인 History 첨부나 전체 조회 권한으로 바꾸지 않는다. 작성·별 변경·게시·조회 때 TIC·원본·상위 공간 공개 상태를 재검증한다.

스레드 카드는 신호 요약·F16 전체 통계·전체/세 판단 필터 링크를 제공한다. 필터는 통계 전체 분모를 바꾸지 않는다. 공개 취소/숨김 후 카드·직접 링크·캐시에서 내용 노출 금지. 일반 본문 URL과 별 자료 선택 기능은 구분한다. 출처 연결로 분석 등록·성과·반응·판단 통계 생성 없음.

**결정 질문:** F24-Q1 카드 개수·순서·중복·비공개 전환 시 안내 문구, F24-Q2 참조 종류/ID와 API 필드·캐시 무효화 구현.

**검증:** AT-106·110~112·114. 타인 같은 별 공개 분석 연결 / 다른 TIC 거부 / 취소 후 미노출 / 필터 분모 유지 / 개인 원본 API 우회 불가.

## 4. 공통 권한·상태·데이터 계약

| 자원·행동 | 본인 인증 회원 | 다른 인증 회원 | 운영자 |
|---|---|---|---|
| 일반 글 수정/삭제 | 본인만, 별 변경 시 자료 재검증 | 불가 | 서비스 대리 수정 API 없음 |
| 공식 스레드 생성 | 본인 분석 공개 요청으로 유발 | 동일 | 운영자 로그인·수동 생성 조건 아님 |
| 공식 원글 수정/삭제 | 불가 | 불가 | DB 숨김/복원, 서비스 관리 API 없음 |
| 공개 분석 등록/취소/재공개 | 본인 History만, 운영 숨김 해제 불가 | 불가 | DB 개별 숨김/복원; 본인 취소 유지 |
| 유효 공개 분석·출처 열람 | 선택 공개 필드만 | 동일 | 업무상 비공개 열람 범위 별도 |
| 개인 History 원본 | 본인 가능 | 불가 | 권한 있는 운영자만 |
| 일반 Post 반응 | 본인 글 포함 가능 | 가능 | 동일 인증 조건; 공식 분석 자동 반응 없음 |
| 신고 | v1 미제공 | v1 미제공 | 관련 운영 API 없음 |
| 비공개 별 목록 | 본인 가능 | 불가 | 업무상 범위 미정 |

SYSTEM은 로그인 가능한 운영자 역할이 아니라 자동 생성의 처리 주체다. F22의 최초 유효 공개 요청에서만 공식 스레드 생성을 수행하며, SYSTEM 표기 자체가 숨김·복원·개인 History 열람 권한을 부여하지 않는다. 운영 변경은 DB 권한으로 제한하며 서비스 관리 API·감사 사건은 v1에 없다. 신고도 v1 제외다.

비인증은 로그인/콜백 외 보호 자원에 접근 불가. 401 재로그인·기본 403 안내는 SB-D03 유지, 존재 비노출 404 대상은 미정이다. 상위 스레드 숨김은 하위 직접 조회·검색·첨부·출처 카드에도 적용한다.

**논리 데이터 관계**
- users.provider/provider_user_id UNIQUE, users↔user_settings 1:1(P1); ERD 기준.
- TIC↔고유 신호↔공식 공간 1개; Bundle/고조파별로 공간을 나누지 않는다.
- 작성자+History↔공개 기록 1개. 새 제출은 별도 기록, 취소·재공개는 기존 재사용.
- 공개 기록은 본인 공개 여부·운영 숨김을 독립 보존, 상위 공간 상태와 함께 유효 공개 판정.
- 일반 Post/Comment의 본인 History 첨부와 공식 공개 등록 및 공개 출처 참조는 서로 다른 관계.
- 사용자×고유 신호 성과는 최초 한 번. 공개 최신 판단·누적 수치 매칭·완료 상태와 분리.
- History는 판정 당시 Bundle ID·절대값·제거 조합·viewport·버전을 기록하고 현재 판으로 재현. 재도전은 새 초안/새 제출로 처리.
- 팔로우·알림·스냅샷은 ERD 관계를 따르고 세부 계약만 합의. 신고·감사 테이블은 v1 제외.

**교차 검증:** 동일 공개 동시 요청, 숨김 직전 등록, 공개 취소와 운영 복원, 최신 분석 취소, 과거 제출 늦은 공개, 탈퇴 경합, 응답 유실, 일괄 일부 실패. 클라이언트 상태만 신뢰하지 않고 저장/조회 시 서버가 자격을 검사한다.

환경·포맷·CI·관측 도구는 별도 공통 Task에서 처리한다. 서비스 DB는 ERD의 PostgreSQL을 따른다. 배포·권한은 인프라와 합의한다. 챌린지 성공·보상 Job과 일반 Post 게시에 의한 성과 처리는 후속 목록에서 제거했다.
