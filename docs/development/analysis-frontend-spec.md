## 3. 화면과 별개로 지킬 상태 원칙

| 상태 축 | 의미 | 프론트 불변조건 |
|---|---|---|
| 편집 단계 | 봉우리 선택 → 주기 맞추기 → 구간 선택 → 판단 → 제출값 확인 | 곡선 단계 번호와 구분한다. 예: 잔차 2단계에서도 편집 1단계부터 시작 가능 |
| 곡선 문맥 | TIC·현재 Bundle·곡선 단계·제거 후보 집합·계산 버전 | 단계 번호만으로 캐시를 찾지 않는다. 같은 단계라도 제거 집합이 다르면 다른 곡선 |
| 브라우저 접기 | 현재 문맥의 period·revision·마지막 성공 결과 | 이전 입력/이전 별/이전 판의 늦은 결과가 현재 화면을 덮지 않는다. |
| 서버 잔차 계산 | 대상 문맥·작업 단계·실패 사유 | 현재 표시 곡선과 계산 중인 목표 곡선을 섞지 않는다. |
| 제출 처리 | 제출 전·요청 중·결과 확인·응답 미확인 | 통신 오류를 `not_matched`로 표시하지 않는다. |
| 수치 매칭 | 서버가 고유 신호와 연결했는지 | 판단 실패·미게시도 매칭 사실을 유지한다. |
| 사용자 판단 | 행성 같음 / 아닌 것 같음 / 모르겠음 | 외부 상태·AI 값과 별개. 미확정 판단은 정답/오답으로 채점하지 않는다. |
| 성과 | 이번 최초 인정 / 미인정 / 추가 인정 없음, 기존 누적 성과 | 재도전 오판이 기존 성과를 없애지 않는다. `duplicate`만으로 이번 판단을 생략하지 않는다. |
| 공개 | 기록별 미게시·게시 중·공개됨·게시 실패, 본인 취소·운영 숨김 | 개인 기록 저장과 공개는 다르다. 일반 글·첨부·댓글·동의가 공개 등록을 대신하지 않는다. |
| 별 탐색 | 진행 중 / 완료, 완료 사유·재개 대기 | 서버가 현재 탐색 가능한 신호의 누적 매칭으로 결정한다. 보고 있는 과거 단계로 역산하지 않는다. |

근거: EXP-01·08·09·12, SUB-06·09·11, RES-01, GRD-01~04, COM-18·19.

- 무신호 별은 제공하지 않으며 「빈 별」이라는 분석 분기·진입 보상은 만들지 않는다. FP만 있는 별도 실제 신호를 찾고 판단하는 같은 분석 흐름을 사용한다.
- 완료는 판단·성과·공개와 독립이다. 마지막 확정 행성 또는 FP를 잘못 판단해도 「탐색 완료 / 판단 불일치 / 성과 미인정」을 함께 표시한다. `UNSURE`는 「판단 보류」로 표시한다.
- 확정 행성은 매칭+행성 같음, FP는 매칭+아닌 것 같음, 미확정은 매칭+본인 분석 공개 성공 시 최초 성과를 인정한다. 미확정은 세 판단 모두 공개할 수 있다.
- 고유 신호당 성과는 사용자별 최초 한 번이다. 이 별의 인정 성과 수 1/2/3/4건 이상을 A/S/SS/SSS로 표시한다. FP 상한·유형별 등급은 없다.
- 성과마다 서버가 새 별 열림을 처리한다. 완료 자체에는 추가 성과가 없으며, 프론트가 누적 등급 차이로 열릴 별을 계산하지 않는다.

### 4.2 SC-04 제출 결과

신호 매칭, 내 판단, 외부 기록과의 관계, 이번 성과와 사유, 기존 성과 수·등급, 탐색 완료, 공개 상태, 잔차 준비 상태를 각각 표시한다. 원본 주기와 고조파 정정값·배율·사유, 서버 최종 epoch·duration을 구분한다. 매칭된 신호의 AI 점수·실행 상태·모델 버전과 외부 출처·조회일을 함께 제공하며 AI는 성과 조건이 아님을 안내한다. 미매칭에는 임의 신호의 AI·통계를 연결하지 않는다.

행동은 서버 결과에 따라 [상세 보기]·[다시 풀기]·[다음 곡선]·[결과 보기]·[분석 공개]·[나중에]·[토론하기]를 제공한다. 노출 조건은 7장을 따른다. 카드의 개수·좌우 배열이나 모달/페이지 여부는 Q01에서 정한다. 근거: RES-01~11.

### 4.3 SC-05 별 결과와 히스토리 재현

- 별 요약, 탐색 상태·완료 사유·재개 대기, 매칭 신호 수, 인정 성과 수·등급·유형별 내역.
- 신호별 기록과 제출별 이력을 구분한다. 재제출 여러 건을 여러 발견으로 표시하지 않는다.

### 4.4 화면 배치를 결정하는 절차

**설계 제안:** SC-03의 주기 맞추기·구간 선택·제출값 확인, 세 상태를 같은 데스크톱 크기의 박스 배치로 먼저 검토한다. 차트의 위치/면적, 입력과 다음 행동의 위치, 한 화면에서 비교할 정보, 고정 영역, 전체/패널 스크롤 범위를 합의한 뒤 클릭 목업을 확장한다. SC-04·05와 공개 검토로 확장하기 전에도 해당 화면의 대표 배치·모달/페이지·복귀 구조를 합의한다. 색·서체·장식은 이 상세 명세의 완료 조건이 아니다. 1024px 이상에서 필수 요소가 가려지지 않아야 하며, 1024px 미만은 데스크톱 이용 안내를 제공한다(NFR-17).

2026-09-10 실험 기준으로 백지웅과 선택한 SC-03 시안은 좌상 밝기 곡선·우상 주기도·좌하 접힌 곡선·우하 판단의 네 패널이며, 별 정보·단계·보조 행동도 패널 안에 배치했다. 접힌 곡선은 기본 드래그로 구간 선택, Shift+드래그로 이동, 최대 20배 확대를 실험한다. 이 배치와 조작은 `analysis-lab`의 검토 시안이며 SRS 필수 수치나 팀 전체 디자인 확정으로 승격하지 않는다. 홈 배경은 비교용 이미지이고 실제 지도 위 통합은 후속 검증 대상이다.

2026-09-17 보완(#185): 사용자 재확인으로 이 시안의 **기본 드래그 선택·Shift+드래그 이동**을 실제 분석 화면 조작으로 채택한다(§6.4). 별도 그리기 모드 버튼을 두지 않는다. 위 문단의 20배는 과거 실험 기록이며 현재 확대 상한은 EXP-13의 32배다. 화면 배치·시각 디자인의 확정을 뜻하지 않는다.

### 5.1 메모와 미제출 초안 보존

2026-09-17 사용자 결정으로 분석 메모 상한은 **200 유니코드 코드포인트**로 적용한다. 초과 입력을 잘라 버리지 않고 제출값 확인 단계에서 오류를 안내한다. 서비스 댓글의 2,000자 상한과는 별개이며 실제 서버 DTO의 동일 상한·오류 응답은 Q07에서 확인한다.

새로고침·화면 이탈에 대비해 마지막 접기 성공 주기·봉우리 출처·드래그를 끝낸 원본 위상 구간·판단·근거·메모를 같은 탭의 `sessionStorage`에 저장한다. 서버 세션이나 제출 기록을 생성하지 않는다. 확인된 회원과 TIC별로 초안을 구분하고, 항성별 최신 곡선 문맥 한 건을 보관한다. 접기 진행 중에는 마지막 성공 주기와 초안을 함께 유지한다.

다시 진입하면 **초안 불러오기/저장된 초안 지우기**를 제공한다. 불러오기는 현재 자료·선택 규칙·접기 기준이 저장 당시와 일치할 때만 허용하며 주기를 검증하고 다시 접은 뒤 시간 미리보기를 재계산한다. 구간 확정·제출값 확인 상태와 파생 시간·요청 ID는 복원하지 않는다. 보기 배율·중심은 저장 대상이 아니며 복원 시 기본 보기로 시작한다. 이는 같은 화면 안에서 재접기 실패 시 표시 범위까지 복구하는 기존 동작과 구분한다.

새 Bundle·곡선 문맥·관측 배열 revision·계산 규칙이 달라지거나 저장 내용이 손상되면 초안을 적용하지 않고 안내한다. 로그아웃·인증 만료·확인된 회원 변경 때 분석 초안을 지운다. 저장소 차단·용량 부족은 현재 편집을 막지 않고 이탈 후 복구가 보장되지 않음을 알린다. 다른 기기 공유·영구 보관은 제공하지 않으며, 탭 종료/브라우저 세션 복원 시 저장 수명은 브라우저 정책을 따른다. 의도적 재도전과 여러 곡선 문맥별 보관은 Q05 후속 범위다.

### 5.2 Figma 분석 1–5단계 화면 적용 (#236)

2026-09-17 사용자 요청으로 [Figma 02 분석 단계 · 1–5](https://www.figma.com/design/khh8ZkqU7ivmUftKWrxSxn?node-id=25-2)의 네 패널 배치를 적용한다. 2026-09-18 기준 채택 스타일은 **은하 스타일**(`100:2`·`100:97`·`100:195`·`100:293`·`100:419`)이며 기본 스타일 5화면(`25:3` 외)은 구현 대상이 아니다. 색·간격 토큰과 컴포넌트 규약의 정본은 [분석 화면 디자인 토큰](../../apps/frontend/docs/design.md)이고 이 절에서 값을 중복하지 않는다. 적용 범위는 `/analysis/:ticId`뿐이며 전역 팔레트와 다른 화면은 바꾸지 않는다. 03 Dark Neumorphism은 이번 범위에 포함하지 않는다. 시간 곡선·주기도·접힌 곡선 위치는 단계 간 유지하며 오른쪽 아래의 안내·입력만 단계에 맞게 바꾼다. 1024px 미만의 데스크톱 이용 안내는 유지한다.

Figma는 봉우리 선택과 미세 조정을 1·2단계로 나누지만 구현은 한 단계로 합쳐 **4단계**로 둔다. 봉우리를 골라도 단계가 넘어가지 않아야 같은 화면에서 봉우리를 다시 고르고 주기를 다듬을 수 있기 때문이다(2026-09-18 사용자 결정).

- 1단계 주기 선택: 봉우리의 주기·power를 포인터/키보드로 확인하고 선택한다. 그래프 배경 클릭 또는 격자 조회 후 Enter는 직접 선택이다. 드래그 이동은 선택하지 않는다. 선택 후에도 이 단계에 머물며 봉우리를 몇 번이든 다시 고를 수 있다. 같은 화면의 연속 슬라이더로 서버 허용 범위 안에서 미세 조정한다. 방향키는 아래 미세 간격, PageUp/PageDown은 서버 격자 한 칸, Home/End는 양 끝이다. 임의 주기의 미세 조정은 기존대로 보류한다. 접기 완료 후 ‘이 주기로 구간 선택’으로 진행하며 그때부터 주기도는 조회 전용이 된다.
- 2단계 구간 선택: 기본 드래그로 구간을 선택하고 핸들로 수정한다. ‘키보드 구간 선택’을 펼치면 중앙 구간 생성 버튼을 사용할 수 있다. 유효 구간을 확정해야 판단 단계로 넘어간다.
- 3단계 판단: 판단 3개, 근거 체크, 접을 수 있는 200자 메모를 제공한다. 4단계는 표시용 요약이며 실제 제출 API 연결 전에는 제출을 비활성화한다. 표시 반올림값을 원본 선택값에 덮어쓰지 않는다.
- 미세 조정 간격은 서버 격자 한 칸을 128등분한 값이다. fixture 기준 약 8.0e-5일로 요구 정밀도 1e-4일보다 촘촘하고 허용 범위 전체가 768단계가 된다. 1440px에서 슬라이더 1픽셀이 약 한 단계여서 포인터로 끝까지 끌어도 화면 주사율(약 60회/초)만큼만 다시 접는다. 2의 거듭제곱이라 서버 격자 칸과 봉우리 원래 주기가 모두 정확히 선택된다.
- 이전 단계로 돌아가는 것만으로 선택값·작성 내용을 초기화하지 않는다. 재선택·미세 조정 성공과 구간 편집의 초기화 규칙은 §5 표를 그대로 따른다. 구간 단계 재방문 뒤에는 구간과 제출값을 다시 확인한다.
- 주기 선택과 미세 조정은 1단계, 구간 편집은 2단계에서만 활성화한다. 그래프 확대·이동·값 조회는 다른 단계에서도 가능하다. 재접기 실패/취소 시 마지막 성공 결과·초안을 유지하며 단계의 명시적 다음 행동으로 재확인한다.
- 전체 보기 아이콘은 표시 배율·중심만 초기화하고 휴지통은 구간·파생값·확정 상태를 지운다. 판단·근거·메모는 보존한다. EXP-13의 확대·축소 버튼은 ‘조작 도움말’에 두고 단축키·휠과 같은 표시 상태를 조작한다.
- 데이터 버전·세그먼트·실제 관측 간격은 ‘데이터 상세’, 개발용 응답 설명은 개발 모드의 샘플 안내에 둔다. 판별 도구는 #186 연결 예정임을 표시한다.

구현 범위와 검증 한계는 [분석 디자인 적용 기록](../../apps/frontend/docs/analysis-design.md)을 따른다. API·테이블·수치 계산 계약과 SRS 버전은 변경하지 않는다.

| 대상 | 표시·계산 규칙 |

| 원본 곡선 | 섹터별 기본 10분 비닝 배열을 사용한다. 세그먼트 점 수에 따라 간격이 달라질 수 있으므로 실제 `bin_minutes`를 읽는다. 세그먼트 ID·binning revision·관측 범위를 함께 식별한다. |
| 시간축 복원 | 규칙형 배열을 받는 계약이라면 `t[i] = start_btjd + (bin_minutes / 1440) × i`. 서버가 펼친 배열을 주는 경우는 그대로 사용한다. 전송 방식은 Q04. |
| 공백·결측 | 관측 공백을 선으로 잇거나 flux=0으로 채우지 않는다. 공백을 접은 표시 좌표와 실제 BTJD를 구분하며 위상·밴드 계산에는 실제 시각을 쓴다. |
| 밝기축 | 제공된 정규화 방식·flux 단위와 세그먼트 산포의 의미를 표시한다. 브라우저가 임의로 재정규화하거나 산포를 독립 점별 측정오차라고 단정하지 않는다. |
| 주기도 | ERD 기본 5,000점과 manifest의 실제 격자·범위·power를 사용한다. 화면 눈금과 계산 격자를 구분하고 선형/로그 간격을 임의 추정하지 않는다. |
| 주기 범위 | 0.5일부터 후보표의 최장 주기를 넉넉히 포함하는 상한(최소 40일). 관측 기간 절반 이후는 가려짐이 2번 미만일 수 있음을 구분한다. 실제 상한·경계는 서버 메타데이터와 맞춘다. |
| 접힌 곡선 | 현재 원본/잔차 곡선의 유효 비닝점 전체를 사용한다. 150구간 히스토리 스냅샷·기타 축약본으로 분석 선택을 계산하지 않는다. |
| 접기 기준 시각 | 서버가 같은 분석 문맥에 제공한 float64 `fold_reference_time_btjd` 사용. 브라우저에서 중간값을 다시 계산하지 않는다. 다중 섹터의 단일 기준 시각 계약은 Q04. |

근거: EXP-01·03·04·08, DAT-07·11, HIS-03, NFR-10, ERD LightCurveSegment·LightCurveManifest. 배열 길이/인덱스/단위/버전이 맞지 않으면 잘못된 분석으로 진행시키지 않고 데이터 오류와 재로드를 제공한다. 유효점이 없는 응답은 무신호 별의 완료·성과로 해석하지 않는다.

### 6.2 위상 선택과 서버 파생값

아래 값은 표시 반올림 이전의 정밀도로 계산한다. `P`는 사용자가 제출할 원본 주기(일), `T`는 현재 분석 문맥의 접기 기준 시각(BTJD)이다.

```text
positive_mod(x, 1) = ((x % 1) + 1) % 1
phase(t) = positive_mod((t - T) / P, 1)

0 <= phase_start < 1
phase_start < phase_end < phase_start + 1
center = positive_mod((phase_start + phase_end) / 2, 1)
duration_preview_days = (phase_end - phase_start) * P
duration_preview_hours = duration_preview_days * 24
epoch_preview_btjd = T + (center + k) * P
```

- `k`는 epoch가 관측 범위 안에 있는 정수 중 `abs(epoch - T)`가 가장 작은 값, 동률이면 더 이른 epoch를 고른다. 가능한 `k`가 없으면 제출 불가이다.
- 두 반복 구간에서 같은 가려짐을 선택하면 같은 `phase_start/end`로 정규화한다. `phase_end > 1`은 유효할 수 있으며, 두 끝을 각각 0~1로 잘라 역전시키지 않는다.
- 위상 폭의 추가 최소·최대와 관측점 없는 구간 허용은 DEC-19/Q03 미결이다. 과거 목업의 `0.001~0.25` 또는 DEC-19 기본안을 확정값처럼 쓰지 않는다.
- 선택 중 시간 영역 곡선의 모든 예상 구간은 중심 `epoch + n × P`, 폭 duration의 읽기 전용 띠로 동기화한다. 공백의 픽셀 압축이 실제 시간 계산을 바꾸지 않는다.
- 제출 요청에는 period와 위상 원본값을 보낸다. 서버가 다시 산정한 epoch·duration이 최종값이다. 고조파 정정값은 원본 선택과 별도이며, 원본값을 정정값으로 덮어쓰지 않는다.

근거: EXP-03·06·07, SUB-01~05. BTJD는 시각 체계의 일 단위이며 UTC 날짜로 임의 변환하지 않는다. 사용자 화면은 「기준 시각」과 「가려진 시간(시간)」을 쓰되 축/도움말에서 실제 단위를 확인할 수 있게 한다.

### 6.3 과거 선택의 현재 판 재환산

HIS-02·SUB-10의 절대값 복원을 양 끝 위상으로 구체화한 식이다. 저장된 사용자 원본 주기와 그 선택에 대응하는 서버 duration을 사용한다. 자동 정정 주기와 임의로 섞지 않는다.

```text
P = saved_user_period_days
width = saved_duration_hours / (24 * P)
center = positive_mod((saved_epoch_btjd - current_T) / P, 1)
phase_start = positive_mod(center - width / 2, 1)
phase_end = phase_start + width
```

| 검증 예 | 기대값 |
|---|---|
| `T=100`, `P=4`, 위상 `0.20~0.30`, 관측 범위 `95~110` | epoch `101`, duration `0.4일=9.6시간` |
| 같은 저장값, 현재 `T=101`로 변경 | 위상 `0.95~1.05`. 같은 물리적 반복 구간을 가리키며 옛 `0.20~0.30`을 그대로 쓰지 않음 |
| `T=100`, `P=4`, center `0.5`, 관측 범위 `95~105` | epoch 후보 `98`, `102`가 동률이므로 `98` 선택 |

재환산은 입력 복원이며 새 판에서 매칭 성공을 보장하지 않는다. 현재 허용 범위나 관측 조건에 맞지 않으면 해당 값을 유효한 제출로 취급하지 않고 재선택 안내를 제공한다. 저장된 epoch가 현재 관측 범위 밖이어도 같은 주기의 다른 통과를 선택할 수 있으므로 epoch의 숫자만으로 재도전을 막지 않는다.

### 6.4 조작·접근성과 깜빡임 방지

- 접힌 그래프 배경의 기본 드래그는 즉시 새 위상 구간 선택, Shift+드래그는 선택값을 유지하는 가로 이동이다. 조작 종류는 포인터를 누른 시점에 결정하며, 양 끝 핸들에서는 Shift 여부와 무관하게 경계 조정을 우선한다. 별도 선택 모드 전환은 제공하지 않는다. 단순 클릭·더블클릭은 구간을 폭 0으로 덮어쓰지 않는다. Esc·포인터 취소는 진행 중인 선택 또는 이동을 시작 전 상태로 되돌린다. 키보드 대체 경로로 중앙 구간 생성 버튼과 핸들 방향키를 제공하며, 기존 차트 방향키 이동·확대 조작을 유지한다. 재접기 중에는 새 구간 선택·핸들 편집을 잠근다.

- 접힌 곡선의 표시 범위·단계·위치 유지 규칙은 [SRS EXP-13](../requirements/planetory-requirements-spec.md#43-분석-화면)을 따른다. 휠은 포인터, 버튼·키보드는 화면 중심을 기준으로 ×1·2·4·8·16·32를 이동하고 축소는 역순이다. 새 주기 재선택·전체 보기는 ×1로 초기화하며, 미세 조정은 현재 배율과 화면 중심 위상을 함께 유지한다. 확대만 할 때 y축은 바꾸지 않는다. 중심 위상은 표시 중인 두 주기의 연속 좌표이며 위상 0·1을 넘었다고 다른 반복 구간으로 옮기지 않는다.
- 주기 선택·조정·범위 핸들을 키보드로도 조작할 수 있어야 한다(NFR-08). 2026-09-17 사용자 결정(#185)으로 위상 핸들 방향키 간격은 **현재 보이는 가로 위상 범위의 1/1000**, Shift+방향키는 그 10배로 한다. ←/↓는 감소, →/↑는 증가하며 확대할수록 간격이 작아진다. 포인터 선택값을 키보드 간격에 맞추어 반올림하지 않는다. 핸들에서 방향키를 누를 때 차트 보기 이동·관측점 탐색은 함께 실행하지 않는다. 구간 선택 시작 후 시작 핸들에 포커스를 두고 Tab 순서는 시작→끝으로 유지한다. epoch/duration 숫자 입력으로 대체하지 않는다. 나머지 단계 간 포커스·서버 수치 검증은 Q01·Q03 인수 대상이다.
- 버튼의 비활성 사유, 차트명·단위·현재 주기·선택 구간을 텍스트로도 제공한다. 로딩·실패·성과·등급을 색만으로 전달하지 않는다. 요청 상태 변경은 보조기술에도 전달하도록 설계한다.
- 재접기 중 마지막 완료 그래프를 지우거나 반복해서 흐리게 만들지 않는다. 갱신 안내와 입력 잠금을 사용하고 최신 계산 완료 시 주기·그래프·관련 미리보기를 일관되게 교체한다(EXP-08 구체화).
- 연속 미세 조정에서는 마지막 계산 완료 결과를 표시한다는 고정 안내를 유지하고, 짧은 계산마다 진행/완료 문구와 취소 버튼을 교체하지 않는다. 대기가 이어질 때 진행 안내·취소를 제공하며 오류·재시도는 즉시 표시한다. 안내 지연과 무관하게 후속 입력 잠금은 계산 시작 즉시 적용한다. 구체적인 표시 지연은 [접기 개발 안내](../../apps/frontend/docs/phase-folding.md#연속-미세-조정의-상태-표시)에서 관리하는 조정 가능한 UI 값이며 Q08 성능 목표가 아니다.
- **기존 실험 재사용 제안:** 같은 곡선의 Worker와 Canvas를 재사용하고 큰 시각 배열은 데이터가 바뀔 때만 전달한다. 입력은 revision으로 구분하며 오래된 작업을 폐기한다. 중간 주기 입력이 무한히 대기하지 않도록 최신 대기값 하나를 유지한다. Canvas 크기 재설정은 실제 크기·픽셀 배율 변경 때만 수행한다.
- 특정 차트 라이브러리·Worker 제한 시간·응답시간 목표는 이 문서로 확정하지 않는다. 주기 변경에 BLS·잔차 API 호출이 없다는 조건과 최신 결과만 반영한다는 조건은 구현 방식과 무관하다.

## 7. 제출·결과·상세 보기

### 7.1 제출 종류와 멱등 처리

| 종류/행동 | 입력·기록 규칙 |
|---|---|
| 신호 분석 `candidate` | 현재 문맥·period·위상·필수 판단·선택 근거/메모·표시 상태를 서버 검증 후 Submission과 History로 1:1 저장 |
| 더 없음 의견 `no_candidate` | 후보 분석의 period·위상·epoch·duration·판단·근거를 요청에 포함하지 않는다. 편집 중인 후보 폼을 그대로 직렬화하지 않는다. 남은 탐색 가능 신호 여부와 결과는 서버 판정 |
| 튜토리얼 `skipped` | 서버가 허용한 상세 해설 이후 행동으로만 요청. 일반 후보 분석 입력을 강제하지 않음 |
| 제출 응답 유실/통신 재전송 | 같은 요청 ID와 같은 본문으로 기존 처리 결과 확인. 자동으로 새 ID를 발급하지 않음 |
| 의도적 재판단/입력 변경 후 제출 | 새 요청 ID와 원 제출 참조. 이전 기록을 수정하지 않음 |

제출 중에는 중복 동작을 막고 전송한 입력 스냅샷을 보존한다. 수신 여부가 불명확하면 「처리 결과 확인 중」으로 구분한다. 이미 접수된 요청의 결과는 판 갱신 후에도 먼저 확인하고, 미접수·새 제출은 current 문맥에서 수행한다. 같은 ID에 다른 본문을 보낸 경우, 처리 중 응답과 조회 방법은 API 합의 Q07 대상이다. 근거: SUB-01·02·09·10·12, HIS-01, NFR-01·02.

### 7.2 결과 조합과 다음 행동

아래의 「다음 곡선」은 남은 탐색이 있고 서버가 허용하는 경우이다. 완료 시에는 결과 보기·재도전·선택 공개로 연결한다.

| 결과 조합 | 함께 표시할 상태 | 다음 행동·주의 |
|---|---|---|
| 확정+행성 같음 / FP+아닌 것 같음 | 매칭·판단 일치·최초 신호면 성과 인정. 마지막 신호면 완료 | 해당 신호 해설, 다음 곡선/결과 보기 |
| 확정+아닌 것 같음 / FP+행성 같음 | 매칭·판단 불일치·이번 미인정. 마지막이면 완료도 표시 | 방금 매칭한 신호 상세·다시 풀기. 남은 신호가 있으면 다음 곡선 가능 |
| 확정/FP+모르겠음 | 매칭·판단 보류·이번 미인정. 마지막이면 완료 | 불일치 문구 대신 보류. 상세·다시 풀기·남은 탐색 |
| 미확정 매칭+세 판단 중 하나 | 미채점·내 판단·미게시·미인정. 마지막이면 완료 | 개별 공개/나중에/다음 곡선. 공개 검토를 강제로 열지 않음 |
| `matched_harmonic` | 매칭 성공·원본/정정 주기·배율·이유 | 같은 고유 신호에 위 유형별 성과 규칙 적용 |
| 이미 인정된 신호 `duplicate` | 이번 판단·추가 성과 없음·과거 성과 유지 | 새 미확정 기록도 선택 공개 가능. 기존 미인정 신호를 duplicate로 막지 않음 |
| `not_matched` | 후보표와 일치하지 않음·개인 기록 저장 | 상세/다시 풀기/일반 토론. 임의 신호 연결·성과·제거 없음 |
| `ambiguous_match` | 여러 후보 중 하나를 정할 수 없음 | 임의 후보 공개·제거·성과 없음. 재선택/재제출 안내는 설계 제안(Q10) |
| 더 없음 의견에 `none_wrong` | 더 탐색 가능한 신호가 남음·의견 기록 | 상세/다시 풀기. 새로운 완료·성과 없음 |
| `all_found` | 탐색 가능한 신호를 모두 매칭했고 남은 미매칭 없음 | 더 없음 제출을 요구하지 않음. 완료 자체 추가 성과 없음 |
| `undiscoverable_only` | 남은 미매칭 신호는 현재 탐색 불가·완료·재개 대기 | 무신호로 표현하지 않음. 새 관측으로 탐색 가능해지면 서버의 재개 상태 반영 |
| 튜토리얼 `skipped` | 건너뜀 완료 사유·다음 순번 발견 | 성과 인정에 의한 별 열림과 구분. 후보 매칭 성공으로 표시하지 않음 |

근거: SUB-03~12, RES-01~11, GRD-02~04. 「기존 성과 있음」과 「이번 판단 일치」를 하나의 성공 플래그로 합치지 않는다.

### 7.3 상세 보기와 튜토리얼

- 매칭 후 판단 불일치/보류의 상세는 **방금 매칭한 신호**이다. 다른 미발견 신호로 바꾸지 않는다.
- `not_matched`·`none_wrong`의 힌트는 그 제출 단계에서 제거되지 않은 탐색 가능 후보 중 서버가 BLS 품질로 선택한 하나이다. 누적 미매칭 집합에서 프론트가 고르지 않는다.
- 상세 대상이 없으면 버튼을 비활성화하고 제공할 해설이 없음을 안내한다. 조회 시 대상이 달라지거나 현재 접근 불가하면 해당 결과를 안내한다. 구판 상세의 복원 정책은 Q10 대상이다.
- 외부 확정값·자체 BLS값·AI 점수·원본 제출값을 구분하고 출처·조회일·모델/규칙 버전을 표시한다. 미확정 대표값을 정답이라고 부르지 않는다.
- 실제 상세 열람은 서버의 `answer_viewed`에 기록한다. 단순히 [다시 풀기]를 선택했다고 해설을 공개하거나 열람으로 처리하지 않는다. 상세를 봐도 이후 최초 성과에 감점은 없다.
- 같은 튜토리얼의 수치/판단 불일치 횟수가 `tutorial_skip_after`를 충족할 때 **상세 해설 끝**에 [다음 튜토리얼로]를 둔다. 개발 기본 3, 운영 기본 0=비활성이다. 서버가 가능 여부를 반환하고 일반 별에는 제공하지 않는다.

근거: RES-02·03·09, SUB-10·12. `no_candidate`처럼 원본 선택이 없는 기록의 다시 풀기는 임의 period/phase를 만들지 않고 봉우리 선택부터 시작하는 안으로 Q05에서 확인한다.

## 8. 잔차 계산·새 데이터·복구

### 8.1 다음 곡선의 비동기 상태

```text
요청 → QUEUED → RESIDUAL_CALCULATING → RESIDUAL_READY
     → PERIODOGRAM_CALCULATING → COMPLETED
각 계산 단계의 실패 → FAILED (실패 단계·사유·재시도 가능 여부)
```

| 상태/사건 | 화면 행동 |
|---|---|
| 동일 문맥 캐시 있음 | 곡선과 주기도가 모두 준비됐는지·Bundle/제거 집합/계산 버전이 같은지 확인 후 사용 |
| 대기·잔차 계산·주기도 계산 | 단계별 안내. 정상 곡선 유지, 중복 요청 제한, 표시 곡선과 목표 곡선 문맥 구분 |
| `RESIDUAL_READY` | 잔차 준비 사실 표시. 곡선 선노출 여부는 Q08의 벤치마크로 결정하며 전체 준비 전 분석 가능한 새 단계로 확정하지 않음 |
| `COMPLETED` | 현재 요청과 일치하는 목표 곡선·주기도를 함께 전환. 화면 단계와 선택값도 같은 문맥으로 교체 |
| 명시적 실패 | 저장된 제출·매칭·완료·성과와 마지막 정상 곡선 유지. 실패 단계·재시도 제공 |
| 오랜 대기/통신 단절 | 실패 확정과 구분하여 상태 확인/재시도 안내. 서버 작업 실패를 프론트가 추정하지 않음 |
| Redis 결과 없음 | 재생성 가능한 캐시 소실로 처리. 저장된 제출을 없애지 않고 현재 문맥에서 재계산 요청 |

근거: EXP-09, DAT-14, NFR-01. 캐시 의미는 `(TIC, Bundle, 정렬한 제거 후보 집합, residual_model_version, periodogram_config_version)`이며 작업 ID와 동일하다고 가정하지 않는다. 실제 정규화·잠금·재생성은 서버 책임이다. 명시적 취소 API가 합의되기 전에는 화면 이탈을 서버 계산 취소로 표시하지 않는다.

### 8.2 최신 판으로 전환

1. 판 변경을 알게 되면 「새 데이터 판이 공개되었습니다 · 다시 불러오기」를 제공한다. 감지 방식은 Q07에서 정한다.
2. 구판을 편집 가능한 최신 데이터처럼 계속 사용하지 않는다. 구판의 새 제출·다음 계산을 막고 최신 문맥을 확보한다. 이미 접수한 제출의 결과 확인은 계속 가능해야 한다.
3. 서버가 반환한 현재 판·단계·제거 조합을 불러오고 주기·위상 및 후속 입력을 초기화한다. 다른 판의 늦은 Worker/잔차 응답은 적용하지 않는다.
4. 이전 판의 표시를 잠시 유지하더라도 갱신 전 자료임을 표시하고 편집에 사용하지 않는다. 재로드 실패 시 완료/성과를 초기화하지 않고 재시도를 제공한다.
5. 진행 중 판 교체에서 제거 후보가 은퇴한 경우의 단계 대체는 명세에 직접 정해져 있지 않다(Q09). 재도전 규칙을 자동 적용하거나 조용히 원본 단계로 보내지 않는다.

이 절차는 EXP-01·DAT-11·AT-117의 화면/판정 버전 일치 조건을 구체화한 설계안이다. 제출과 판 전환의 경합 판정은 서버 계약 Q07에서 확정한다.

## 9. 히스토리·재도전·선택 공개

### 9.1 읽기와 다시 풀기의 차이

| 상황 | 히스토리 열람 | 다시 풀기 |
|---|---|---|
| 일반 기록 | 불변 원본 입력·판정 당시 결과와 현재 공개/진행 상태를 구분 | 현재 판에 원본 period·절대 구간을 새 초안으로 복원. 판단·근거·메모는 비움 |
| 기록의 판이 현재와 다름 | 이전 데이터 판 제출 안내, 현재 곡선에 절대값 재현 | 현재 판·기준 시각으로 위상 재환산 후 검증 |

| 제거 조합에 은퇴 후보 있음 | CURRENT는 원본 곡선 위에 재현하고 잔차 재현 불가 안내. SUBMITTED는 당시 저장 배열 유지 | 해당 별의 현재 진행 단계에서 시작하며 이전 단계 복원 불가 안내 |
| 대상 신호 자체가 은퇴함 | 저장된 기록을 임의 삭제하지 않음. 현재 후보 상태와 구분 | 「최신 데이터에서 더 이상 후보가 아닙니다」 안내와 재도전 차단 |

근거: SUB-10, HIS-02·03·06. 복원 실패/열람 자체로 새 제출·성과가 생기지 않는다. `answer_viewed`, 현재 공개 여부 같은 부가 상태와 불변 분석값을 구분한다. 브라우저 저장소를 서버 히스토리의 정본으로 사용하지 않는다(NFR-19).

148 조회 구현의 목록 필터·커서·버전 매핑·`snapshotVersion`·공개 원본 대체·오류 계약은 [탐사 API 8.1~8.5](../../apps/backend/docs/exploration-api-spec.md#81-히스토리-목록)를 따른다. 190·191은 같은 Graph DTO를 사용하고, 196은 필터 변경 시 커서를 초기화한다. 공개 잔차 작업의 jobId는 null이므로 213 소비 화면도 개인 작업 API를 호출하지 않는다. `SUBMITTED`의 snapshot:null과 현재 판 부재의 503을 구분하고, 그래프 실패 시 공개 내용은 유지한다. 기존 스냅샷 배열을 새 버전으로 재해석하지 않는다. 이 인계 문구는 실제 프론트 종단 검증 완료를 뜻하지 않는다.

190·191·213의 모드별 선택 창·은퇴 안내와 188·189의 버전 미상 표시 기준은 [탐사 API 8.3절](../../apps/backend/docs/exploration-api-spec.md#83-히스토리-그래프-his-03-q11)을 따른다. SUBMITTED는 당시 original 창, CURRENT는 currentPhase를 사용한다. 목록의 최초 응답 누락 표시는 [8.1절 detailAvailable](../../apps/backend/docs/exploration-api-spec.md#81-히스토리-목록)을 따른다.

### 9.2 개별 공개·모두 게시

1. 개별 결과/히스토리의 [분석 공개], TIC 종료 결과의 [모두 게시]에서 검토 화면을 연다. 검토 진입은 공개 요청이 아니다.
2. 미확정 고유 신호마다 대표 기록을 고른다. 기본은 미공개 중 최신 제출이며 다른 본인 기록도 선택할 수 있다. 동일 기록이 이미 공개 중이면 제외하되 같은 신호의 새 제출은 가능하다.
3. 공개될 작성자·제출 시각·판단·수치·유효 근거·메모·곡선·버전·대상 스레드를 확인한다. 기록 내용을 바꾸려면 새 분석 제출로 이동하며 원본을 편집하지 않는다.
4. 최종 [게시]/[모두 게시] 선택 후에만 등록한다. 첫 유효 공개이면 시스템이 TIC×고유 신호의 공식 스레드를 확보한다. 판단별·사용자별·주기값별로 나누지 않는다.
5. 항목별 게시 중/공개됨/실패와 사유를 표시한다. 성공 항목만 서버의 최초 성과·별 열림·통계 갱신을 반영하고 실패 항목만 재시도한다. [나중에]·취소·실패는 매칭·완료를 되돌리지 않는다.
6. 공개 성공으로 사용자 일반 원글·토론 댓글·동의/비동의를 자동 생성하지 않는다. 첫 공개의 SYSTEM 공식 스레드 확보와 별개이며, 공개 분석은 별도 작성자 기록이다.

같은 History의 재전송·취소 후 재공개는 동일 공개 기록을 재사용한다. 같은 신호의 새 제출에 속한 History는 새 공개 기록으로 등록할 수 있지만 이미 인정된 고유 신호의 성과는 추가하지 않는다(COM-18).

본인 취소와 운영 숨김은 독립이다. 부모 스레드가 숨겨졌으면 새 공개는 실패·미게시로 남기며 대체 스레드를 만들지 않는다. 취소·숨김만으로 기성과·개인 기록·완료를 회수하지 않는다. v1에서 운영 숨김/복원 화면·신고 화면은 구현 범위가 아니지만 숨김 접근 제한은 유지한다. 근거: POL-15, GRD-04·06, COM-13·17~19.

### 9.3 다른 화면으로 전달할 컨텍스트

- 지도/별 상세 → 분석: TIC와 진입 경로. 실제 열림·인증·공개 상태는 서버 재검사.
- 결과/마이페이지 → 별 결과·기록 상세: TIC·History/Submission 식별자. 기록 소유권 검증은 서버 책임.
- 게시글 → 분석 → 복귀: 같은 TIC와 임시 `return_post_id`. 복귀 때 같은 TIC·공개·미삭제·미숨김 여부 재검사. Submission/History에 영속 관계로 저장하지 않음.
- 미매칭 [토론하기]: 같은 TIC·DISCUSSION·본인 현재 히스토리 첨부 상태로 글쓰기 진입. 최종 게시 전 Post 없음. 일반 글 게시가 성과·후보·곡선 단계를 바꾸지 않음.
- 공개 분석/공식 스레드 링크: 같은 TIC의 공개 출처로 연결. 타인의 공개 자료 링크가 타인의 개인 히스토리 조회권을 주지 않음. 상위 스레드 숨김·공개 취소를 링크/캐시에서도 반영.

근거: EXP-10, RES-07·08, COM-10~12·20, HIS-04·05, NFR-13·15. 실제 라우트 문자열과 컴포넌트 인터페이스는 Q02·Q07에서 합의한다.

## 10. 프론트-서버 계약 초안

**이 장의 DTO 이름·중첩 구조·응답 형식은 설계 제안이다.** 필요한 의미를 먼저 합의하고 실제 경로·HTTP 상태·전송 방식은 Q07에서 정한다. 과거 `/api/analysis/sessions` 초안이 영속 세션 테이블이나 구판 고정 요구사항을 뜻하지 않는다.

서버 접수 시각은 UTC 또는 명시적 offset이 있는 ISO 8601 문자열을 제안한다. 시간 순서와 Submission ID 동률 정렬은 서버가 수행한다. Candidate 고유성은 Bundle·고조파·사용자 주기값 때문에 새로 만들어지지 않는다.

DB의 `pending_publish`는 「미인정/미게시」로 매핑한다. 사용자 판단 `UNSURE`는 「모르겠음」이며, 확정·FP의 판단 평가에서는 「판단 보류」, 미확정의 평가에서는 「미채점」이다. 미확정 모르겠음 공개 성공은 「내 판단 모르겠음 / 미채점 / 성과 인정」으로 함께 표시할 수 있다. `duplicate`는 추가 성과 없음의 의미를 보존하면서 수치 매칭 방식과 이번 판단도 전달해야 한다. 외부 분류의 라벨 없음과 채택 신호가 0개인 무신호를 구분한다.

### 10.3 오류 응답에서 필요한 의미

공통 응답에 오류 종류, 사용자 안내에 필요한 이유, 재시도 가능 여부, 현재 판/문맥, 입력 오류 위치를 구분할 수 있어야 한다. 아래는 **의미 분류**이며 확정 HTTP 코드·서버 enum은 아니다.

제출의 실제 오류 코드·requestId 유지/갱신·응답 유실 복구·성공 연출 중복 방지는 [탐사 API 2.2절](../../apps/backend/docs/exploration-api-spec.md#22-요청-id와-멱등)을 따른다. 재전송 성공 본문과 현재 판 헤더가 다를 때는 같은 명세 2.3절 D-5의 당시 결과/최신 영역 분리 규칙을 따른다. 스냅샷 위상·계산 버전 표시는 [제출 계약](../api/exploration/submission-readiness.md#1-채택한-스냅샷-계산)을 따른다. 실제 187·188·189 화면 반영과 브라우저 검증은 담당 작업에서 수행한다.

| 오류 의미 | 프론트 행동 |
|---|---|
| 인증 필요·별 잠김·비공개/접근 불가 | 분석/첨부 데이터 노출 중단, 허용된 복귀 경로와 안내 |
| 유효하지 않은 주기/위상/근거·필수 입력 누락 | 입력 위치와 사유 표시. 성공 제출이나 History가 생겼다고 가정하지 않음 |
| Bundle/곡선 문맥 변경 | 기존 요청의 접수 여부 확인 후 최신 문맥 재로드. 다른 판으로 몰래 재제출하지 않음 |
| 같은 요청 처리 중·응답 유실 | 같은 요청 ID로 상태 확인/재전송. 새 ID 자동 생성 금지 |
| 계산 단계 실패·재현 자료 부족 | 마지막 정상 화면·저장 기록 보존, 단계별 재시도/대체 표시 |
| 공개 불가·부모 숨김·일부 등록 실패 | 항목별 사유, 성공분 보존, 실패분 재시도. 공개 성공/성과를 낙관적으로 확정하지 않음 |

## 11. 구현 구성과 기존 실험 활용

### 11.1 컴포넌트·데이터 경계 제안

React·TypeScript·Vite는 현재 [프론트 위치 안내](../../apps/frontend/README.md)를 따른다. 실제 버전·패키지 관리자·공통 라우팅·상태 라이브러리는 팀 실행환경에서 맞춘다. 이 상세 명세는 새 패키지 도입을 요구하지 않는다.

- 분석 컨테이너: 편집 단계·곡선 문맥·초안·비동기 요청을 조율한다.
- 차트/입력 컴포넌트: 시간 곡선, 주기도, 접힌 곡선, 주기/위상 조작, 확인 도구, 판단 폼, 제출 요약을 분리한다.
- 결과/히스토리 컴포넌트: 결과 상태 묶음, 신호 비교값, AI·통계, 곡선 재현과 공개 요약을 재사용한다.
- API 어댑터: DTO→화면 모델 변환·단위·오류 매핑을 맡는다. Mock과 실제 서버가 같은 화면 인터페이스를 구현하도록 제안한다.
- 순수 계산/Worker: 위상 접기·선택 환산·예상 띠 계산과 작업 revision을 관리한다. Mock의 성과 계산을 운영 프론트 로직으로 옮기지 않는다.

운영 코드는 `apps/frontend`에 두며 실험 소스를 직접 import하는 구조를 만들지 않는다. 서버 진행·성과·히스토리는 서버가 정본이다. 기존 실험의 sessionStorage 임시 분석 기록은 운영 저장 계약이 아니다(NFR-19).
