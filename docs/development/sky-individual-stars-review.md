## 1. 변경 이유와 판단 범위

204 개발 검증 화면에서 별을 군집 성운으로 치환하면 원래 선호했던 개별 별과 은하의 나선 팔이 흐린 덩어리로 보였다. 동일 원본 1,000개 별과 군집을 같은 카메라로 비교한 뒤 사용자는 개별 별 표현을 선택했다.

이는 현재 군집 표현에 대한 시각 판단이다. 군집 기술 자체가 언제나 은하를 표현할 수 없다는 결론이나 개별 별 10만 개의 성능 보증은 아니다. 비교 화면은 개발용이며 제품 코드와 기존 시제품은 이번 문서 작업에서 변경하지 않는다.

## 3. API 제공자와 소비자가 함께 검토할 내용

정확한 응답 예시는 [탐사 API 4.1절](../../apps/backend/docs/exploration-api-spec.md)을 따른다.

- 구 overview/clusters/clustered를 제거하는 호환성 변경이다. representation이 없거나 구 군집 응답이면 신규 소비자가 정상 빈 지도로 처리하면 안 된다.
- 메타에는 전체 목록을 넣지 않는다. 요청 bbox는 기존 tileSize×64 상한을 유지한다. 최대 축소 시 전체 별이 가시 범위에 포함되면 여러 응답의 합이 전체 별이 될 수 있다.
- limit 기본 1000·최대 2000은 제안하는 전송 페이지 규격이다. 성능 통과를 확인한 값이나 화면 별 수 상한이 아니다. 관련 담당의 응답 크기/집계 비용 검토 대상이다.
- cursor는 회원·version·level·원 bbox·limit에 묶고 불투명하게 처리한다. 범위의 모든 페이지가 같은 version과 rangeStarCount를 공유한다. 잘못된 cursor는 400, 버전 변경은 versionChanged=true 후 재시작이다.
- versionChanged=true는 빈 지도/페이지 완료가 아니다. 정상 범위의 nextCursor=null일 때 최종 적재 수와 rangeStarCount를 대조한다. 0개 정상 범위와 로딩/실패를 구분한다.
- 서버는 version/페이지/범위 수를 같은 스냅샷으로 읽는다. 회원별 version 갱신 누락, 동시 페이지 변경, 범위 수 집계 비용을 백엔드에서 검증한다.
- 현재 203/204 구현은 v1.2 기준이다. 문서를 바꿨다는 이유로 현재 구현이 v1.3에 맞다고 처리하지 않는다. 어댑터·fixture·렌더러·조작의 후속 변경이 필요하다.

## 5. 시각 및 성능 인수

1. 같은 데이터 판·저장 좌표·카메라·DPR로 전체/회전/확대/선택 네 장면을 캡처한다. 별 각각과 나선 팔이 보이고, 성운 덩어리로 치환하지 않는지 확인한다.
2. 1·10·100·1,000개는 적은 별/성장/기능 시각 검증에 쓴다. 가짜 발견 별로 외형을 채우지 않는다.
3. 100,000개 별·5,000개 궤도 시드에서는 현재 가시 범위 페이지 완료 후 프레임을 측정한다. 처음 일부 별이 뜬 시각과 전체 가시 범위 적재 완료 시각을 별도 기록한다.
4. p95≤16.7ms·최악≤33ms·첫 실제 별 표시≤2초·힙≤300MB 목표를 유지한다. 네트워크 바이트·CPU·GPU fill rate·draw calls·DOM·힙도 기록한다.
5. 목표를 못 맞추면 병목과 적용 가능한 표현 상세도/버퍼/페이지 조정을 별도 리뷰한다. 별을 잘라내거나 군집을 복원한 결과로 통과를 주장하지 않는다.
