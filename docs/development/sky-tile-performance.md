# 별 지도 타일 조회 비용 측정

> 대표 Jira: `S15P21C206-137`
>
> 상태: 측정 완료. 서버 조회 비용에 한한다. 클라이언트 프레임·힙·GPU 인수는 `S15P21C206-215`가 맡는다.
>
> 관련: [별지도 표현 계약](sky-presentation-contract.md), [개별 별 변경 검토 기록](sky-individual-stars-review.md), [탐사 API](../../apps/backend/docs/exploration-api-spec.md) 4.1절

`S15P21C206-137`은 "개별 별 타일·페이지·공간 인덱스 계약을 구현하고 10만 별 표본에서 서버 조회·범위 집계·전송 비용을 **검증한다**"이다. 서버 쪽 목표 수치는 이 티켓에 없다. `p95 ≤ 16.7ms`는 AT-71의 **클라이언트 프레임 시간**이며 `S15P21C206-215`가 인수한다.

이 문서는 그 검증의 실측 기록이다.

## 1. 결론

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 공간 인덱스 | **추가하지 않는다** | 3절 |
| 서버 타일 캐시 | **두지 않는다** | 4절 |
| 타일 한 변·경계 상자 상한 | **설정으로 뺀다.** 값은 그대로 | 5절 |
| 응답 스냅샷 일관성 | **고쳤다** | 6절 |

`S15P21C206-215`·W05로 넘기는 수치는 7절에 있다.

## 2. 실행 환경과 재현

```powershell
cd apps/backend
./gradlew perfTest
```

`perf` 태그로 기본 `test`에서 빼두었다. 시드에 시간이 걸려 매 빌드에 넣을 수 없다.

| 항목 | 값 |
| --- | --- |
| DB | PostgreSQL 18.6 (x86_64-pc-linux-musl, Alpine), 로컬 컨테이너 |
| JVM | 21.0.12 LTS |
| CPU | 20코어 |
| 측정 | 워밍업 5회 뒤 50회. p50·p95·최악 |
| 시드 | 개별 별 100,000개, 계정 전체 내 행성 항목 5,000개. 단계는 1·500·100,000 |

시드 규격은 `S15P21C206-215`(W18)와 맞췄다. 좌표는 **실제 배치 함수**(`personal-spiral-v1`)로 만든다. 나선팔은 균일 분포가 아니라서 임의 좌표로 재면 인덱스 선택도가 실제와 달라진다.

카메라 장면 네 가지(최대 축소·홈·확대 이동·선택)는 실측한 경계에서 만들어 시드 크기에 따라 함께 움직인다.

## 3. 공간 인덱스를 추가하지 않는 이유

후보 다섯을 같은 시드에서 번갈아 붙여 쟀다. 단위는 p95 ms.

| 후보 | 최대 축소 | = 페이지 | + 범위 수 | 확대 이동 |
| --- | ---: | ---: | ---: | ---: |
| 없음 | 174.1 | 88.5 | 72.5 | 91.0 |
| `(user_id, tic_id)` | 162.1 | 103.3 | 63.0 | 86.9 |
| `(user_id, world_x, world_y)` | 160.9 | 84.0 | 66.8 | 83.8 |
| `(user_id, float8 식)` | **247.0** | **213.5** | **24.1** | **54.3** |
| `(user_id, float8 식, tic_id)` | 240.6 | 241.4 | 32.3 | 52.2 |

근거 세 가지다.

**(1) `(user_id, tic_id)` 인덱스가 이미 있다.** V1의 `UNIQUE (user_id, tic_id)`가 만든 `star_unlocks_user_id_tic_id_key`다. 같은 정의를 새로 추가해도 아무 변화가 없다.

**(2) `world_x`·`world_y`가 `NUMERIC`이라 일반 B-tree를 쓸 수 없다.** 파라미터가 `double precision`이라 계획에 `(world_x)::double precision`이 찍힌다. 열에 함수가 씌워지면 인덱스를 타지 못하고, 통계 추정도 망가진다(예상 3행 vs 실제 100,000행).

**(3) 경계 상자가 거를 것이 없다.** 10만 별의 좌표 범위가 `x[-1397, 1419]`, `y[-1362, 1313]`인데 상한은 32,768이다. **지도 전체가 한 상자에 들어온다.** 실제로 최대 축소에서 필터가 거른 행은 100,250 중 **250개**였다.

식 인덱스는 범위 수 집계를 3배 빠르게(72.5 → 24.1) 하지만 넓은 범위 페이지 질의를 2.4배 느리게(88.5 → 213.5) 만든다. 집계는 힙을 건드리지 않아 이득이고, 페이지는 10만 행을 `tic_id`로 정렬하느라 힙 랜덤 접근이 늘어난다. 넓은 범위가 가장 비싼 장면이므로 순손실이다.

### 남겨두는 선택지

`world_x`·`world_y`를 `DOUBLE PRECISION`으로 바꾸면 캐스팅이 사라지고 통계가 정상화돼 플래너가 좁은 뷰에서 올바로 선택할 수 있다. 지금은 필요하지 않다고 본다. 좁은 뷰가 이미 90ms 안쪽이고 병목인 넓은 뷰는 타입을 바꿔도 10만 행을 다 읽는다. 열 타입 변경은 ERD 개정과 V4의 `> '-Infinity'` CHECK 교체를 동반하므로 필요해질 때 별도로 다룬다.

## 4. 서버 타일 캐시를 두지 않는 이유

**(1) 첫 적재에서 적중이 0이다.** 전체 보기는 50페이지인데 cursor가 달라 **50개가 전부 다른 키**다. 한 번의 적재 안에서 재사용이 일어나지 않는다.

**(2) 회원마다 별이 달라 공유되지 않는다.** 회원 N명이면 22MB × N을 쌓아두고 적중은 같은 회원의 재적재에만 난다. 서버 부하 관점에서도 서지 않는다 — 10명이 각자 첫 적재하면 캐시가 있어도 DB를 10번 다 친다.

**(3) 전송량이 줄지 않는다.** Redis에서 꺼내도 22MB는 그대로 나간다. 아끼는 것은 DB 시간뿐이다.

재방문에 필요한 유지는 **브라우저가 맡는다.** 응답에 `version`이 있어 버전이 같은 동안 받아둔 별은 유효하다. 프론트가 메모리에 쥐고 버전이 바뀌면 버리면 되며, 서버가 더 할 일이 없다.

## 5. 전송 규격을 설정으로 뺀 이유

```properties
planetory.sky.tile-size=512
planetory.sky.max-box=32768
```

타일 한 변은 **응답 범위의 최소 단위**다. 코어처럼 조밀한 곳에서는 이보다 좁게 요청해도 이만큼 받는다. 실측은 아래와 같다(정중앙 기준, 스냅을 거치지 않은 직접 집계).

| 한 변 | 별 수 | 이전 대비 | 추정 바이트 |
| ---: | ---: | ---: | ---: |
| 512 | 26,822 | — | 5.9MB |
| 256 | 11,852 | 44% | 2.6MB |
| 128 | 3,692 | 31% | 816KB |
| 64 | 978 | 26% | 216KB |

넓이 비례라면 25%다. 512 → 256이 44%인 것은 정중앙이 특히 조밀하기 때문이다.

값을 지금 바꾸지 않는다. **최적값은 프론트가 실제로 어떤 크기 상자를 요청하는지 봐야 정해지고**, 그것은 `S15P21C206-215`·W05 측정이 나와야 안다. 근거 없이 상수를 바꾸면 나중에 또 바꾼다.

`MAX_BOX = TILE_SIZE * 64` 결합은 끊었다. 타일은 응답의 최소 단위이고 상한은 한 요청이 지도를 통째로 끌어오지 못하게 막는 값이라 서로 다른 것을 막는다. 타일을 잘게 쪼갠다고 요청 상한까지 줄어들 이유가 없다.

성립하지 않는 조합은 기동 때 거절한다. 상한이 타일보다 작으면 어떤 요청도 통과하지 못하고, 격자의 배수가 아니면 상한 크기 요청이 스냅 뒤 상한을 넘는다.

## 6. 응답 스냅샷 일관성

`tiles()`가 버전·페이지·범위 수를 **문장마다 다른 스냅샷**에서 읽고 있었다. 페이지를 읽은 뒤 범위 수를 읽기 전에 발견이 커밋되면 마지막 페이지인데도 `rangeStarCount`가 하나 더 크게 나온다. 프론트는 그 수로 적재 완료를 판단하므로 영원히 기다린다.

`REPEATABLE READ`로 묶어 첫 문장의 스냅샷을 트랜잭션 끝까지 유지한다. 기본 `READ COMMITTED`로는 문장마다 다시 떠서 막지 못한다. 메타도 같은 이유로 묶었다.

검증 테스트가 실제로 이 결함을 잡는지 어노테이션을 빼고 확인했다. 뺀 상태에서 `expected: <52> but was: <51>`로 실패하고, 넣으면 통과한다.

## 7. `S15P21C206-215`·W05로 넘기는 수치

### 장면별 비용 (별 100,000개, 인덱스 없음)

| 장면 | 범위 안 별 | 첫 페이지 p95 | 페이지 수 | 전송량 | 전체 적재 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 최대 축소 | 100,000 | 174.1ms | 50 | 22.1MB | **6,970ms** |
| 홈 | 95,772 | 149.4ms | 48 | 21.2MB | 6,242ms |
| 선택 | 42,852 | 121.8ms | 22 | 9.5MB | 2,045ms |
| 확대 이동 | 16,443 | 91.0ms | 9 | 3.6MB | 628ms |

전체 적재 7초 중 대부분이 DB 시간이다(50 × 약 160ms). 전송 자체는 100Mbps에서 약 1.8초다.

### 시작 위치가 배율보다 영향이 크다

| 상자 한 변 | 중심에서 | 코어 바깥에서 |
| ---: | --- | --- |
| 512 | 42,852개 · 2,176ms | 9,266개 · **288ms** |
| 1,024 | 66,177개 · 3,986ms | 25,172개 · 1,081ms |
| 2,048 | 97,860개 · 7,921ms | 67,817개 · 4,312ms |
| 4,096 이상 | 100,000개 · 약 8,000ms | 100,000개 · 약 8,000ms |

- **4,096각부터는 어디서 시작하든 전체가 들어온다.** 은하 지름이 2,800 남짓이다.
- **중심에서는 최소 타일(512각)로도 2.2초다.** 타일 한 변이 512라 더 좁힐 수 없다.
- 코어에서 비껴나면 같은 512각이 288ms다. 4.6배 적은 별, 7.5배 빠르다.

### 확인이 필요한 것

**메타의 `centerTicIds`가 가장 비싼 자리를 가리킨다.** 지금은 가장 먼저 열린 별(튜토리얼 1번)을 주는데, 배치에서 순번 0은 고정 자리이고 코어 근처다. 프론트가 메타대로 첫 카메라를 잡으면 가장 조밀한 곳에서 시작한다. `S15P21C206-136`에서 "전체 보기의 처음 초점"으로 정한 값이며 성능을 고려하지 않았다.

선택지는 세 가지다.

| | 방향 | 비고 |
| --- | --- | --- |
| A | `centerTicIds`를 밀집도가 낮은 쪽으로 | 서버가 정한다. "내 첫 별"이라는 의미는 잃는다 |
| B | 메타에 권장 첫 상자를 추가 | 계약 변경. 프론트가 그대로 쓴다 |
| C | 프론트가 판단 | 서버 변경 없음. 밀집도를 모르면 어렵다 |

### 범위 밖

전송량 자체를 줄이는 방법(필드 코드화, 좌표 정밀도 절삭, 배열 직렬화)은 모두 응답 계약 변경이라 이 티켓에서 다루지 않는다. 별 하나가 221바이트이고 필드 이름이 별마다 반복된다.

## 8. 유의

- 100,000개는 `S15P21C206-215`가 정한 **상한 시나리오**다. 성과당 별 1개이므로 실사용자는 수십~수백 개일 가능성이 크다. 그 규모에서는 어느 장면이든 즉시 뜬다.
- 로컬 컨테이너 단일 측정이다. 운영 EC2의 디스크·메모리·동시 접속에서 다시 재야 한다.
- 클라이언트 프레임·힙·GPU는 측정하지 않았다. AT-71 인수는 `S15P21C206-215`가 맡는다.
