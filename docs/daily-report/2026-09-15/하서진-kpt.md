- 백엔드 MR이 아직 병합되지 않았어도 별도 폴더와 DB에서 실행해 프론트와 연결할 수 있다는 점을 확인했다. 201번 공통 요청에 CSRF 처리를 연결하고, 실제 화면에 로그아웃 버튼과 실패 처리를 보완했다.
- 실제 SSAFY와 Google 계정으로 가입·회원 정보 조회·새로고침·로그아웃·재로그인을 확인했다. Google은 최신 DB 변경까지 적용한 환경에서 회원과 첫 별이 중복 생성되지 않는 것도 확인했다. 제공자별로 검증한 코드 버전과 환경을 기록하고, 비밀키와 개인정보는 보고서에 넣지 않았다.
- 팀원의 로그인 MR을 명세 및 실제 동작과 비교했다. 첫 별 좌표 저장 방식과 DB 초기화 안내의 문제를 댓글로 전달하고, 수정된 코드와 문서를 다시 확인했다. 검증 결과를 팀원의 AI도 구체적으로 이해할 수 있도록 정리했다.

## Problem

- 명세대로 구현했어도 팀이 원하는 은하 모습이 그대로 나오지는 않았다. 이전 방사형 배치나 군집 관련 설명이 남아 있으면 AI와 팀원이 서로 다른 결과를 만들 수 있어, 기준 시제품과 문서·티켓을 함께 맞추는 작업이 필요했다.
- 201~204번의 남은 일을 확인하는 과정에서 215번 성능 검증까지 범위가 넓어져, 순서대로 진행한다는 기준이 흐려졌다. 10만 별에서는 일부 성능 기준을 충족하지 못했으며, 이번에는 추가 개선을 보류했다. 보류한 항목을 완료로 볼 수는 없다.
- 화면이 만들어진 것, 가상 응답으로 동작하는 것, 실제 백엔드와 연결된 것은 서로 다른 단계였다. 특히 201번 공통 기반의 확인 화면과 202번 로그인 화면의 역할, 백엔드 코드와 OAuth 앱 설정의 차이를 처음에는 명확히 구분하지 못했다.
- 자동 테스트 통과와 실제 제공자 로그인 성공도 같은 의미가 아니었다. 검증한 버전과 환경이 다르면 결과를 구분해야 했고, Firefox·Docker 같은 실행 환경 문제도 기능 코드 문제와 별도로 확인해야 했다.
- MR 설명에는 이전 DB 버전과 미검증 상태가 남아 있었고, 별 지급 기록만 삭제하라는 안내는 기존 회원에게 첫 별이 없는 상태를 만들 수 있었다. 승인 여부를 판단할 때 실제 실행 문제와 문서 보완 사항을 구분해 전달할 필요도 있었다.
