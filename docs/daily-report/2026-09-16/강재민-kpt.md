# 2026-09-16 KPT

## Keep

- 타일 성능(-137)에서 타일 크기 축소를 제시해 측정했다. 한 변 512→128이면 코어 첫 화면이 5.9MB→816KB로 줄었고, 최적값은 프론트 뷰포트를 봐야 정해지므로 상수를 설정으로 빼고 `MAX_BOX = TILE_SIZE × 64` 결합을 끊는 방향을 택했다.
- "별이 사용자마다 다르니 서버 캐시는 필요 없다"고 짚어 Redis 타일 캐시를 제외했다. 첫 페이지는 확대해 빠르게 그리고 백그라운드로 받은 별을 브라우저가 `version` 기준으로 들고 있는 구조로 정리했다. 시작 배율 상향과 별 간격 확대도 제시해 재봤고, 배율보다 시작 위치가 크다는 것과 별 간격은 비용 대비 효과가 없다는 결론을 얻었다.
- 별 상세(-138)의 미결 10은 "세 값 다 주고 프론트가 골라 쓴다"로 정했고, 내 별과 타인 별을 다르게 주는 이유를 물어 4.5절에 "비공개가 아니라 자리가 없어서"를 명문화했다. 별도 티켓이나 Draft 없이 -138 첫 커밋으로 넣고 최종 리뷰만 받기로 했다.

## Problem

- "전송량 22MB"가 무엇을 어디서 어디로 보내는 것인지 몰랐다. 백엔드→브라우저 HTTP 응답이고, 50페이지가 순차라 DB 시간이 누적돼 7초가 된다는 것을 설명을 듣고 이해했다.
- 캐시가 DB 시간은 없애지만 전송량은 못 없애고, 캐시 위치(브라우저 vs 서버)에 따라 효과가 갈린다는 점을 처음엔 구분하지 못했다.
- 스냅샷 일관성을 몰랐다. 버전·별 목록·범위 수를 따로 읽으면 사이에 커밋된 별 때문에 프론트 로딩이 끝나지 않고, 한 트랜잭션에서 REPEATABLE READ로 읽어야 한다.

## Try

- 성능 수치를 볼 때 요청 수·DB 시간·전송 바이트를 나눠 읽고, 개선안이 그중 무엇을 줄이는지 먼저 말한다.
- 캐시를 제안하기 전에 데이터가 사용자별인지 공유되는지, 첫 적재에 적중하는지, 캐시가 어디에 있어야 하는지를 따진다.
- 한 응답에 함께 나가는 값은 같은 트랜잭션에서 읽고, 다른 조회 API에서도 같은 문제가 없는지 -138 구현에서 확인한다.
- 미결 항목은 명세 본문의 예제와 근거를 먼저 읽고 내가 결정안을 적어 리뷰받는다.
