# Jira Task·Bug 작성 가이드

## 이 문서를 읽는 경우

`티켓 만들어줘`, `이슈 만들어줘`, `Task 작성해줘`, `Bug 등록해줘`, `상태 바꿔줘`, `Story Point 정해줘`

## 원칙

- 작업 관리는 Jira가 정본이며 GitLab Issue에 중복 등록하지 않는다.
- 구조는 `Epic → Task` 2단계만 사용한다. Story와 Sub-task는 사용하지 않는다.
- 기능, 개발 중 결함, 문서, 조사와 실험은 Task다.
- Bug는 `main`의 배포 버전에서 발견되어 `hotfix/*`가 필요한 긴급 문제에만 사용한다.
- 실제 Jira 생성·상태 변경은 사용자가 명시적으로 요청하고 연결 도구가 있을 때만 수행한다. “내용 작성” 요청이면 복사할 내용만 제공한다.

## Task 작성

제목은 `[영역] 작업 목적` 형식이다. 영역은 `기획 데이터 수집 저장 Hadoop Spark 분석 ML 인프라 백엔드 프론트 테스트 문서`를 시작점으로 사용한다.

```markdown
## 목적

## 작업 내용

## 완료 조건
- [ ] 확인 가능한 완료 조건
- [ ] 결과물 또는 문서 위치

## 검증 방법

## 관련 정보
- 선행 작업:
- 관련 문서:
- 데이터 또는 환경:
```

Bug는 `발생 환경`, `재현 방법`, `예상 결과`, `실제 결과`, `영향 범위`, `수정 및 검증 방법`을 작성한다.

## 상태와 Story Point

- 상태는 `해야 할 일 → 진행 중 → 완료`만 사용한다.
- 브랜치를 만들고 작업을 시작하면 `진행 중`, MR 병합·인수 조건·결과물 등록이 끝나면 `완료`로 바꾼다.
- 검증 자료가 없으면 MR이 병합되어도 완료하지 않는다.
- Story Point 방식은 아직 팀 확정 전이다. 임의로 강제하지 않으며 다음 규모를 후보로 사용한다.

| 점수 | 후보 기준 |
| ---: | --- |
| 1 | 문구·작은 설정·단일 조건처럼 매우 작고 명확함 |
| 2 | 영향 범위가 제한된 단일 로직 |
| 3 | 일반적인 단일 기능과 테스트 |
| 5 | 여러 구성요소 연동 또는 데이터 파이프라인 한 단계 |
| 8 | 여러 시스템을 연결하는 복잡한 통합·실험 |

8을 넘는 작업은 여러 Task로 분리한다. 의견이 다르면 가장 높은 점수를 제안한 팀원이 위험 요소를 설명한 뒤 다시 산정한다.

브랜치 생성은 [브랜치 가이드](branch.md), 긴급 Bug 처리는 [Release·Hotfix 가이드](release-hotfix.md)를 따른다.
