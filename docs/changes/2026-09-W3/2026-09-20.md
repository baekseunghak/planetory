## [S15P21C206-187] 제출 클라이언트를 탐사 API 2.2절 확정 계약과 맞춤

- 수정자: 백지웅 (Claude 보조)
- 유형: API · 오류 정정
- 상태: 구현 완료 · 실제 API 인수 대기
- 변경 범위: [분석 제출 개발 안내](../../../apps/frontend/docs/analysis-submission.md), 오류 분류·접수 사다리·요청 ID 저장·제출 대화상자.
- 목적: MR !100 리뷰와 143 병합으로 확정된 「제출 복구·ID 수명」 표대로 클라이언트를 맞춘다.
- 결정·근거: **ID 폐기를 사다리에서 들어냈다.** 2.2절이 새 ID 발급을 사용자의 선택으로 정했으므로, `BUNDLE_CHANGED`의 [최신 자료 불러오기]와 `IDEMPOTENCY_CONFLICT`의 [별도 제출로 보내기]를 눌렀을 때만 버린다. `submitAnalysis`의 `releaseRequestId` 인자가 죽은 코드가 되어 없앴다.
- 결정·근거: `IDEMPOTENCY_CONFLICT`가 조회도 없이 ID를 갈고 있었다. 그러면 **원래 접수된 제출을 사용자가 찾을 수 없다.** 기존 ID·원본 본문을 보존하고 무엇이 접수됐는지 먼저 묻는다.
- 결정·근거: 거절(`STAR_LOCKED`·`STAR_ALREADY_COMPLETED` 등)도 ID를 버리고 있었다. **앞선 전송이 응답만 잃고 접수돼서 그 별이 완료됐을 수도 있다.** 확인할 길이 그 ID뿐이므로 버리지 않는다.
- 발견(재발 방지): **새로고침이 미해결 요청을 지웠다.** 요청 ID는 저장소에 남는데 화면이 늘 `idle`로 시작해 복구 경로가 사라지고, 다른 제출이 그 기록을 덮어썼다. 저장 기록에 `kind`·`body`·`state`·`sentAt`을 더해 판 2로 올리고 진입 때 되살린다. **`state`가 없으면 되살릴 수 없다** — 접수에 성공해도 기록은 남으므로 기록의 존재만으로는 미확인인지 알 수 없다.
- 발견(계약): `SUBMISSION_CONTEXT_NOT_READY`(409)가 이름 없는 거절로 떨어져 ID를 버렸다. 계약은 `keep`이며 `residual`로 잔차 준비를 안내한 뒤 같은 본문·ID로 재전송이다.
- 검증: 타입 검사·운영 빌드 통과, 단위 274개, Chrome 회귀 148개 통과(GPU 3건 건너뜀). 화면 검사가 유실→새로고침→복구, 404 뒤 같은 ID·본문 재전송, 충돌 뒤 별도 제출, 판 교체 후 실제 재조회를 각각 따라간다.
- 관련 문서: [탐사 API 2.2·2.3](../../../apps/backend/docs/exploration-api-spec.md), [분석 제출 개발 안내](../../../apps/frontend/docs/analysis-submission.md), Jira `S15P21C206-187`.
- 후속 작업: 실제 제출 API 인수 뒤 `residual.status` 값과 잔차 준비 경로를 대조한다. 잔차를 준비시키는 UI는 `S15P21C206-189`와 겹칠 수 있다.

## [S15P21C206-188] 결과 화면을 6.4절·D-5 확정 계약과 맞춤

- 수정자: 백지웅 (Claude 보조)
- 유형: API
- 상태: 구현 완료 · 실제 API 인수 대기
- 변경 범위: [제출 결과·해설 개발 안내](../../../apps/frontend/docs/analysis-result.md), 다음 행동 목적지, 결과 축 표시, 성과 연출.
- 목적: 143 병합으로 확정된 힌트 제공 조건·D-5 재전송 성공 예외·연출 기준을 화면에 반영한다.
- 결정·근거: **연출을 `outcome`으로 가르지 않는다.** 2.2절이 회원·`submissionId`별 표시 이력으로 정했다. 201만 연출하면 최초 201을 잃고 200으로 처음 복구한 사용자는 성과를 한 번도 보지 못한다. 사실(「성과로 인정되었습니다」)은 언제나, 연출(「축하합니다」)은 처음 한 번이다. 서버가 이력을 주지 않아 `localStorage`에 두고 회원별 200건으로 자른다.
- 결정·근거: D-5 재전송 성공 예외에서 **최신이 필요한 축에만** 「접수 당시 기준」을 붙인다. 진행·공개·통계·다음 행동이고, 매칭·판단·성과·서버 계산값은 당시 값이 정본이라 붙이지 않는다. 145가 연결 전이라 최신인 척하지 않고 모른다고 말한다.
- 발견(계약 불일치): `GO_HOME`을 건너뛴 별에만 주고 있었다. 6.4절은 정반대로 `matched`·`matched_harmonic`·`duplicate`에 주고 `none_wrong`·`skipped`에는 붙이지 말라고 한다(RES-08). `DISCUSS`도 게시판 목록으로 보내고 있었으나 계약은 작성 초안을 여는 동작이다(COM-10).
- 검증: 타입 검사·운영 빌드·대비 검산 통과, 단위 296개, Chrome 회귀 166개 통과(GPU 3건 건너뜀).
- 관련 문서: [탐사 API 6.4](../../../apps/backend/docs/exploration-api-spec.md), [제출 결과·해설 개발 안내](../../../apps/frontend/docs/analysis-result.md), Jira `S15P21C206-188`.
- 후속 작업: `DISCUSS`의 `historyId` 첨부는 글쓰기 화면이 그 값을 읽지 않아 커뮤니티 담당(하서진)과 조율이 필요하다. 145 연결 뒤 최신 영역 재조회를 잇는다. `foldedError`의 null/0 구분은 [분석 기록 그래프](../../../apps/frontend/src/features/history/HistoryGraph.tsx) 담당 티켓 몫이다.
