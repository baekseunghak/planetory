## [S15P21C206-76] Sector 1~13 HDFS coverage와 원자 커밋 보강

- 수정자: Codex (사용자 요청)
- 유형: 데이터 · HDFS 운영 · 오류 정정
- 상태: 구현 완료 · 오프라인 검증 완료 · 실환경 Sector 1~13 적재 진행 중
- 변경 범위: TESS HDFS plan·감사·커밋 도구, Sector 1~13 runner, Hadoop 용량 설정·롤링 반영 단계와 데이터 운영 문서
- 목적: 75의 두 Run 최종 coverage를 76의 유일한 입력으로 연결하고, 기존 Sector 3~5를 재사용하면서 Sector 1·2·6~13을 같은 불변·감사 계약으로 적재한다. 동시에 final 경로가 이미 존재할 때 HDFS `mv`가 하위 디렉터리로 중첩할 수 있는 경쟁 조건을 제거한다.
- 결정·근거: FinalCoverage의 schema·sidecar·전체 247,824개·Sector 1~13·기존/확장 Run 분리와 Sector별 source SHA를 검증해 원천 run·source SHA·개수·바이트를 plan v2에 고정한다. 현재 HDFS `release_id`는 원천 `run_id`와 같은 저장 계약을 사용한다. 기존 v1 Sector 3~5 marker는 호환 재감사하고, 신규 bundle은 첫·중간·마지막 레코드를 복원한다. 확정은 Java `FileContext.rename(..., Rename.NONE)`만 사용하며 13개 Sector가 모두 성공한 뒤 각 `_READY.json` digest를 묶은 HDFS coverage marker를 별도 원자 확정한다. SequenceFile compression은 원본 바이트 복원 단순성을 위해 `NONE`을 유지하고 benchmark 전에는 바꾸지 않는다.
- 용량·복구 경계: Sector마다 적재 직전 safe mode·Live DataNode·RF2·Worker 가용 공간을 다시 확인하고 RF2 예상 사용률 70% 이하를 요구한다. `dfs.datanode.du.reserved`는 DataNode당 100GiB로 선언·검사한다. uploader의 `NRestarts`는 0을 불변 조건으로 두지 않고 관측값으로 기록하며, 재시작 뒤 최종 감사 통과 여부로 완료를 판정한다.
- 설정 적용 경로: `ConfigureCapacity`는 현재 HDFS 설정에서 예약값 외 속성이 저장소 정본과 다르면 변경 전에 중단한다. 정합하면 Node 1~6에 같은 설정을 배치하고 Worker 2~6 DataNode를 한 대씩 재시작하며 각 단계에서 Live DataNode 5대 복귀를 확인한다.
- 적재 속도 개선: `RunAll`의 첫 Sector는 설치 전 Preflight 결과를 재사용하고, 업로드 뒤 별도 `Audit`과 `Commit` 내부의 동일 전수 감사를 연속 수행하던 중복을 제거한다. `Commit`의 checksum·manifest·RF2·FSCK 감사와 원자 rename은 그대로 유지한다. Sector 병렬 실행·압축·writer 증가는 동일 환경 benchmark와 장애 복구 영향이 확인되지 않아 적용하지 않았다.
- 서버 자율 실행: 로컬 PowerShell이 Worker 상태를 polling하던 `RunAll` 외에 Node 1 enabled systemd 조정기 `ServerRunAll`을 추가했다. 조정기는 재부팅·실패 후 같은 staging에서 재개하고 Worker 기동·감시에는 source `10.20.1.10`, destination `10.20.2.10`~`10.20.6.10`의 내부 SSH만 사용한다. 전용 키는 Node 1 `/etc/planetory/tess-hdfs-runall/`에 root 전용으로 두고 Worker authorized key도 source IP와 forwarding 금지 옵션으로 제한한다. Tailscale은 최초 배치와 운영자 조회에만 사용한다.
- 검증: Python 단위 검사 11개와 PowerShell parser·계약 검사를 통과했다. FinalCoverage lineage·중복/누락 Sector, plan cache exact match, first/middle/last 복원, 알 수 없는 artifact 거부, legacy marker, HDFS coverage와 `Rename.NONE`, 정확한 Worker 내부 IP, HA safe-mode 출력, Spark manifest 스크립트의 immutable release 직접 mount 계약을 검사했다. 75의 최종 coverage는 247,824개·441.62GiB·`.part` 0, Worker 5대 동일 SHA-256 `df6bfa638a0d70913b0d0bade11f0c5335bf9c505a9fbe256fa8552f0623bd94`로 완료됐다. 저장소 설정은 Node 1~6에 반영했고 Worker 2~6 DataNode를 순차 재시작해 매 단계 Live DataNode 5대와 최종 예약값 100GiB를 확인했다. 첫 `RunAll`은 HDFS 변경 전에 로컬 `coverage-map`의 Python package 경로 누락으로 중단됐고, 호출 범위 `PYTHONPATH` 설정·복원과 직접 CLI 회귀 검사를 추가했다. CodeReleaseId `20260920T040219Z` 재실행은 FinalCoverage와 Sector 1 Preflight를 통과하고 15,889개·32,398,643,520바이트·63개 bundle의 uploader 5개를 시작했다.
- 서버 적용: 1차 CodeReleaseId `20260920T120026Z`, 내용 SHA-256 `c357018ae7be69966fef07731703f797218780b0f363a9216ac5614e0d93ee84`를 6개 노드에 동일하게 설치했다. Node 1의 내부 IP SSH 5개는 실제 hostname까지 일치했다. 적용 중 root 전용 키를 일반 bootstrap 세션으로 읽은 실패, 내부 `ssh`의 파이프 stdin 소비로 enable/start 이후 줄이 실행되지 않은 실패, HA safe-mode endpoint 접미사를 엄격 비교한 실패, `ProtectSystem=strict` 아래 `/tmp` 쓰기 실패를 확인했다. 각각 `sudo ssh -n`, safe-mode 접두사 검증, systemd `RuntimeDirectory`로 정정했으며 모두 신규 Worker upload 전에 차단돼 HDFS staging·final 영향은 없다.
- Sector 7 재개 수정: Sector 1~6 확정 뒤 Sector 7은 19,995개·70개 bundle·35,818,706,880바이트 upload와 전수 audit을 통과했다. 이후 `UMask=0027`인 조정기 임시 디렉터리에 복사한 `manifest_to_parquet.py`를 Spark 컨테이너 사용자가 읽지 못해 Parquet 생성 전에 중단됐다. Sector 7 staging은 보존됐다. 임시 복사 대신 설치 시 권한 검증을 마친 immutable release 파일을 read-only bind mount하도록 수정하고 CodeReleaseId `20260920T152934Z`, 내용 SHA-256 `5916e7913c65f4e49ecfbed93d821c80146233db4b613b3dbc00bde180bcbc88`를 6개 노드에 설치했다. 같은 Spark image의 파일 읽기 canary `MANIFEST_SCRIPT_READ_OK 2018`, HA `active:standby`, Live DataNode 5대, Worker 내부 IP SSH 5개를 통과했다. Node 1 조정기는 새 release로 enabled·active/running, `NRestarts=0`이며 cached Sector 재감사 뒤 Sector 7 staging을 재개한다. Sector 7 확정과 Sector 8~13, 최종 HDFS coverage marker는 아직 완료되지 않았다.
