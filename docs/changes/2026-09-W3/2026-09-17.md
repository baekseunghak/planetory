- 유형: API
- 상태: 구현 완료 (F08의 1단계 댓글 작성·목록·수정·삭제 범위. History·출처 첨부는 미구현)

- 목적: 기존 `comments` 테이블 위에 일반 글과 공식 신호 스레드의 토론 댓글을 열고, 부모 종류·상태·소유권·본문 길이를 서버에서 고정한다.
- 결정·근거: 일반 글은 `POST`와 `p-` ID, 공식 신호 스레드는 `SIGNAL_THREAD`와 `st-` ID만 허용해 같은 `posts` 테이블 안에서도 부모 의미를 섞지 않는다. 댓글 작성은 부모 Post 행을 `FOR UPDATE`로 잠가 부모 삭제가 먼저 확정되면 새 댓글을 저장하지 않는다. 수정은 삭제·숨김 부모에서 거부하고, 삭제는 본인에게 반복 204를 유지한다. 댓글 본문은 Unicode 코드 포인트 2,000자까지 받고 공백만 입력은 거부한다. 일반 글 상세의 `commentCount`는 visible 댓글 수를 직접 센다.
- 검증: `./gradlew cleanTest test` 134건 통과(실패 0, 오류 0). 일반 글 댓글 작성·목록·수정, 부모 종류 불일치 404, 타인 수정 403, 공백·2,001자·항목 첨부 배열 400, 삭제된 부모의 새 댓글 404, 부모 삭제 뒤 본인 댓글 반복 DELETE 204와 삭제 후 PATCH 404를 확인했다. `system_thread` 행을 직접 만들어 `st-` 접두사 작성·목록이 되는 것과 같은 행을 `p-`로 부르면 404가 되는 것, 목록 `size`의 0·101 거부도 확인했다. 커서는 댓글 5개를 2개씩 넘겨 순서·중복·누락이 없는 것, 마지막 페이지의 `nextCursor`가 null인 것, 다른 `size`나 깨진 값으로 이어읽으면 400인 것을 확인했다.
- 관련 문서: [서비스 API 명세](../../../apps/backend/docs/service-api-spec.md) 6장, [백엔드 README](../../../apps/backend/README.md), Jira `S15P21C206-159`
- 커서 페이지네이션: 목록을 `size`만 받던 것에서 `cursor`를 더해 피드 4.1과 같은 `{items, nextCursor, hasNext}` 구조로 바꿨다. 커서는 기존 `SkyCursor`·`StarListCursor`와 같은 방식으로 불투명 Base64이며 `parentType`·`parentId`·`size`에 묶어 조건이 다르면 400으로 거절한다. 위치는 정렬 키 두 개(`createdAt`, `id`)를 함께 담는다. 같은 시각에 만들어진 댓글이 있으면 시각만 비교했을 때 동률이 통째로 밀리거나 빠지기 때문이다. 다음 페이지 여부는 `size + 1`건을 읽어 판단하며 별도 count 질의를 하지 않는다. 첫 페이지와 이어읽기 질의를 나눈 이유는 PostgreSQL이 `? is null` 형태에서 파라미터 타입을 추론하지 못해 실패하기 때문이며, null을 넘기지 않으면 캐스팅도 필요 없다. 보는 사람에 따라 목록이 달라지지 않아 회원 ID는 커서에 묶지 않았다.
- 구현 후 정정: 목록이 `findVisibleByPostId`로 그 글의 visible 댓글을 모두 읽은 뒤 `stream().limit(size)`로 잘라, 20개를 돌려주려고 전체 행과 작성자 조인을 읽었다. `Pageable`을 받아 LIMIT을 SQL로 내려 `ix_comments_post_created`를 역방향으로 요청한 만큼만 읽게 했다. 작성자가 to-one이라 메모리 페이징으로 되돌아가지 않는다. 쓰이지 않던 `DEFAULT_LIST_SIZE` 상수와 컨트롤러의 `defaultValue = "20"` 문자열이 따로 있던 것도 상수 하나로 합쳤다. 수정 경로의 부모 확인은 같은 Post에서 꺼낸 종류를 같은 Post와 비교하는 무의미한 조건을 포함하고 있어, 실제로 필요한 공개 상태 확인만 하는 `requireOpenParent`로 이름과 범위를 맞췄다.
- 도메인 경계: 처음에는 `PostService`가 `commentCount` 집계로 `CommentRepository`를, `CommentService`가 부모 검증으로 `PostRepository`를 참조해 두 서비스가 서로를 가리켰다. 여러 도메인에 걸친 읽기 모델을 쓰기 서비스가 조립하던 것이 원인이라, `GET /me`가 회원과 탐사 요약을 합치는 방식대로 조립을 컨트롤러로 올렸다. `PostService.Detail`에서 `commentCount`를 빼고, 세는 규칙은 `CommentService.countVisible`이 소유하며, `PostController.PostDetailResponse`가 둘을 합친다. 응답 필드 순서는 명세 5.2 예시 그대로여서 JSON 계약은 바뀌지 않았다. 이로써 서비스 계층은 `comment → post` 한 방향이 되어 F07 반응·F09 첨부가 붙어도 `PostService`에 집계 의존이 쌓이지 않는다. 다만 댓글이 부모 글에 종속이라 `PostController → comment.service` 참조가 남아 패키지 그래프 자체는 여전히 서로를 가리킨다. 이를 없애려면 조립 책임을 두 도메인 밖의 제3 패키지로 빼야 하며, 새 디렉터리 추가 기준을 따로 판단해야 해서 이번 범위에 넣지 않았다.
- 후속 작업: F09·F24에서 댓글의 History·출처 첨부 검증과 실제 응답을 채운다. F22의 공식 스레드 생성 구현 뒤 `SIGNAL_THREAD` 실제 부모 fixture를 추가로 검증한다. 댓글 테스트는 기존 `AuthIntegrationTest` 컨텍스트를 재사용했으므로 회원·게시글 테스트를 별도 커뮤니티 통합 테스트로 옮길 때 함께 분리한다. 탐사 도메인은 이미 `StarDetailTest`·`StarListTest`처럼 기능별 클래스를 쓰고 `src/test/java/.../domain/post/`도 비어 있는 채로 만들어져 있어, 옮길 자리는 준비돼 있다. ## [S15P21C206-158] 일반 게시글 CRUD와 별 연결 검증

- 수정자: 백승학
- 유형: API
- 상태: 구현 완료 (F06 작성·상세·수정·삭제 범위. 반응·댓글·첨부는 미구현)
- 변경 범위: `PostController`, `PostService`, `Post`, `PostRepository`, `AuthIntegrationTest`, `apps/backend/docs/service-api-spec.md` 5장, `apps/backend/README.md`
- 목적: 기존 `posts` 테이블 위에 일반 글 CRUD를 열고, 별 연결 가능 여부·소유권·입력 한도를 서버 판정으로 고정한다.
- 결정·근거: 부분 수정은 `JsonNode`로 받아 "필드 없음"과 "값이 null"을 구분한다. 필드가 없으면 기존 값을 유지하고 `{"ticId":null}`은 연결 해제로 처리하므로, 레코드 역직렬화로는 표현할 수 없는 PATCH 의미를 지킨다. 별 연결 가능 여부는 `StarService.publicSummary`를 재사용해 공개·발견 판정을 탐사 도메인 한 곳에만 둔다. 삭제는 상태 전환이며 SB-D22에 따라 작성자도 조회할 수 없고 반복 요청은 204다. 타인 글은 보이면 403, 안 보이면 404로 존재를 숨긴다. 글자 수는 `codePointCount`로 세어 이모지 한 자를 한 자로 본다.
- 검증: `./gradlew test` 130건 통과(실패 0, 오류 0). 제목 100자·본문 10,000자 경계와 초과 거부를 이모지·한글로 확인했고, 공백만 입력·줄바꿈 제목·미정의 태그 거부, 미공개 TIC 404 `STAR_NOT_PUBLISHED`, 발견자가 생긴 뒤 다른 회원의 작성 201, 타인 수정 403, 삭제 후 본인 조회 404·반복 삭제 204, 5.2절 연결 해제 예제의 200과 `board` 전환, 항목이 담긴 첨부 배열의 400을 확인했다.
- 구현 후 정정: 생성 시각과 갱신 시각의 출처가 달라 새 글의 `updatedAt`이 `createdAt`보다 과거가 되던 문제를 고쳤다. `created_at`은 DB DEFAULT, `updated_at`은 앱 `Clock`이었는데 테스트가 고정 시계를 쓰면 두 값이 역전됐다. `updated_at`도 INSERT에서는 같은 DB 시계가 채우도록 `insertable = false`로 두고 갱신에서만 서비스가 정한다(`BaseTimeEntity` 주석의 기존 정책). 잠금 조회의 `join fetch`도 제거했다. PostgreSQL에서 조인된 `SELECT ... FOR UPDATE`는 `users` 행까지 잠가 발견 트랜잭션의 회원 행 잠금과 순서가 엇갈릴 수 있다. PATCH가 빈 첨부 배열까지 거절해 5.2절 예제와 어긋나던 것도 항목이 있을 때만 거절하도록 바꿨다.
- 관련 문서: [서비스 API 명세](../../../apps/backend/docs/service-api-spec.md) 5장, [백엔드 README](../../../apps/backend/README.md), Jira `S15P21C206-158`
- 후속 작업: 반응 F07·댓글 F08·History 첨부 F09·출처 카드 F24를 구현할 때 현재 고정값 응답과 `TIC_MISMATCH`를 실제 값으로 채운다. 연결 불가 TIC의 404를 400으로 바꿀지는 별 도메인 담당과 정한다. 게시글 테스트가 `AuthIntegrationTest`에 있어 OAuth 테스트 파일과 목적이 섞였다. `S15P21C206-157`의 회원 테스트와 함께 별도 통합 테스트로 옮긴다. 이 작업 브랜치 이름에 한글이 들어가 브랜치 가이드와 어긋나며 다음 브랜치부터 규칙을 지킨다.
