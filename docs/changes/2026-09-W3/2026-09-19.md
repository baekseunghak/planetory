- 수정자: Codex (사용자 요청)
- 유형: 데이터 · HDFS 운영 · 자동화
- 상태: 전체 승인 범위 적재·검증 완료
- 변경 범위: TESS HDFS Raw runner의 `RunAll`, 회귀 계약, 실행 문서와 실환경 Sector 4·5 적재
- 목적: 단일 단계 수동 호출로 Sector 3에서 멈춘 실행 경로를 고쳐, 전체 선행 gate와 실패 중단·재실행 경계를 유지하면서 Sector 3→4→5를 자동 처리한다.
- 결정·근거: 기존 `Preflight`, `Install`, `Build`, `Upload`, `Audit`, `Commit`을 재사용하고 uploader systemd 상태만 대기하는 최소 orchestration을 추가했다. 세 Sector download audit을 변경 전에 모두 검사하고, final이 있는 Sector는 `Commit` 재감사로 건너뛴다. 신규 Sector는 다섯 uploader가 모두 success일 때만 Audit과 Commit으로 진행하며 실패나 3시간 timeout이면 다음 Sector를 시작하지 않는다.
- 검증: 오프라인 PowerShell parser·필수 계약·WhatIf와 Python 4개 검사가 통과했다. 실환경 `RunAll`은 86.7분에 완료됐고 Sector 3은 `COMMIT_CACHED`, Sector 4·5는 각각 19,997·19,996개와 75·75 bundle을 `COMMIT_OK`로 확정했다. Sector 4·5 upload는 937.7·868.9초였고 10개 unit 모두 success·exit 0·재시작 0이다. 최종 release 55,986개 원본 범위는 논리 108,471,409,680바이트·RF2 물리 216,942,819,360바이트이며 FSCK `HEALTHY`, 1,259 blocks, under·missing·corrupt 0, HA `active:standby`, Live DataNode 5개다. 세 staging은 모두 없다.

## [S15P21C206-75] TESS Sector 1~13 확장 수집과 두 Run 최종 coverage

- 수정자: Codex (사용자 요청)
- 유형: 데이터 수집 · 장애 복구 · 운영
- 상태: 구현·로컬 검증·canary·실환경 실패 주입 완료 · Sector 1·2·6~13 수집 진행 중
- 변경 범위: TESS source 설정, source list 불변 계약, 다중 Run coverage 감사, PowerShell 실행기·계약 검사와 Ingestion·분산 시스템 운영 문서
- 목적: 검증 완료된 Sector 3·4·5를 다시 받지 않고 새 Run으로 1·2·6~13을 추가 수집하며, 로컬 세션이나 네트워크 연결이 끊겨도 서버가 다운로드·전수 감사를 계속하도록 한다.
- 결정·근거: 기존 RunId `20260918T080417Z`와 source SHA `5781b664...efc789`는 변경하지 않는다. expansion Run `20260919T005932Z`는 공식 Sector 1~13 source list 247,824개와 SHA `8c6c2370...fe2c38`을 고정하되 실행 대상은 191,838개인 `1→2→6→7→8→9→10→11→12→13`으로 제한한다. 각 서버는 Sector별 audit·complete marker를 자율 생성하고, 모두 완료된 뒤 `FinalCoverage`가 두 Run의 source·audit·complete·실제 FITS 집합·바이트·잔여 part와 최종 247,824개를 결합한다. HDFS 적재는 이 변경과 최종 manifest에서 제외한다.
- 검증: Python 39개와 PowerShell 오프라인 계약 검사 통과. 공식 목록의 Sector별 개수와 총 247,824개, Worker 5대의 preflight·동일 source hash, 기존 Run 55,986/55,986개·100.94GiB·part 0을 재확인했다. 기존 Progress 명령도 인자 변경 없이 같은 범위를 재현했고, Sector 1·13과 expansion 전체 인자 경계, 비 ASCII·잘못된 숫자 FITS header와 손상 final·part, 문자열 내 `/`, RunId를 넘는 Worker 잠금과 충돌 종료 코드를 회귀 검사했다. 보완 ReleaseId `20260919T015748Z`, 내용 SHA `3d22c384455e6d2dd2c2049ea92ffe88b7725d63444bc571eb3770e13f54d298`의 worker-2 canary는 기존 2,964개를 재사용하고 supervisor `SIGKILL` 뒤 PID `134505→134706`, `NRestarts=0→1`로 같은 Run을 재개했다. 이후 Worker 3~6을 한 대씩 재시작했고 5대 모두 새 release `enabled/active/running`, Worker 전역 lock PID 일치, 이전 완료 unit disabled를 확인했다. 롤링 직후 15분 창은 17,273/191,838개(9.00%), 32.76GiB, 합산 9.63MiB/s, 현재 실패율 0%, 429·전체 HTTP·기타 재시도 0이다. 전송 중 `.part`는 2.91MiB이며 이 속도 기준 추가 범위 ETA는 약 9시간 46분이다.
- 안전 경계: systemd 재시작·watchdog·네트워크 backoff·75/70% 용량 hysteresis·원자적 part 재개 계약을 유지한다. 새 unit 설치는 이전 state가 `COMPLETE`이고 unit이 inactive일 때만 이전 unit을 disable하며, Worker 전역 잠금 충돌은 종료 코드 75로 재시도된다. 실제 VM 전체 재부팅과 디스크 75% 채우기는 공유 HDFS/YARN과 비용 영향 때문에 재실행하지 않았다. 운영자 연결이 끊기면 수집은 계속되며, 두 Run 통합 `FinalCoverage`만 연결 복구 뒤 멱등 재실행한다.
