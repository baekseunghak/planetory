## [S15P21C206-187] 분석 제출 요청 ID·복구 계약 확정

- 수정자: 백지웅 (Claude 보조)
- 유형: API
- 상태: 채택 · 구현 전
- 변경 범위: [분석 제출 개발 안내](../../../apps/frontend/docs/analysis-submission.md) 신규.
- 목적: 제출 응답 12종을 프론트가 어떻게 처리하고 요청 ID를 보존·폐기·재발급할지 한 표로 고정한다.
- 결정·근거: 요청 ID 규칙이 코드 여러 곳으로 흩어지면 어긋나므로 응답별로 ID 처리를 같은 행에 적었다. **새 ID는 사용자가 본문을 바꿔 의도적으로 다시 제출할 때와 `BUNDLE_CHANGED`·`IDEMPOTENCY_CONFLICT`로 본문을 새로 만들 때만** 생성하고, 응답 유실·`REQUEST_IN_PROGRESS`·by-request 404·타임아웃·새로고침은 모두 같은 ID를 유지한다. 미해결 ID가 남아 있는 동안 초안을 잠근다. 잠그지 않으면 사용자가 메모를 고친 뒤 복구 재전송이 `IDEMPOTENCY_CONFLICT`가 되어 이미 접수된 결과를 확인할 길이 사라진다.
- 결정·근거: 요청 ID는 `sessionStorage`에 `planetory:analysis-draft:` 접두사를 공유해 저장한다. 기존 로그아웃 정리가 함께 지우므로 공용 파일 [`session-draft-storage.ts`](../../../apps/frontend/src/auth/session-draft-storage.ts)를 수정하지 않는다. 저장값에 본문 지문을 함께 두고 복구 재전송 직전에 대조한다.
- 발견(계약 불일치)·정정: 처음에 「명세 6.2절 예제와 C02 계약 예제가 `{field, message}`」라고 적었으나 **명세 쪽은 사실이 아니다.** 구판에서 읽은 것이고 현재 판에는 그런 예제가 없으며, 탐사 API는 [서비스 API 2장](../../../apps/backend/docs/service-api-spec.md)의 오류 본문을 그대로 상속한다고만 적는다. 그 정본이 `{field, reason}`이고 구현된 [`ErrorResponse.FieldError`](../../../apps/backend/src/main/java/com/planetory/backend/global/error/ErrorResponse.java)와 같다. 틀린 것은 [C02 계약 예제](../../api/exploration/contracts.json) 3건뿐이다. **C02 소관이라 고치지 않고 전달한다.** 함께 전달할 것이 하나 더 있다. [검증기](../../api/exploration/validate.cjs)가 `fieldErrors`의 배열 여부만 보고 항목의 모양을 보지 않아 이 오류가 `PASS`로 통과한다.
- 정리(충돌 아님): 명세 6.6절의 「404 미접수, 같은 ID로 재전송」과 Jira A06-1의 「조회 404를 무조건 미접수로 단정하지 않는다」는 같은 결론이다. 어느 쪽이든 새 ID를 만들지 않고 같은 ID로 재전송하면 접수돼 있었으면 200 재현, 아니면 201이 온다. 지킬 것은 404를 근거로 "제출되지 않았습니다"라고 단정해 안내하지 않는 것이다.
- 검증: 문서 확정 단계이므로 실행 검증 없음. 근거는 저장소의 명세·계약 예제·백엔드 DTO 원문 대조다.
- 관련 문서: [탐사 API 2.2·2.3·6.1~6.6](../../../apps/backend/docs/exploration-api-spec.md), [분석 제출 개발 안내](../../../apps/frontend/docs/analysis-submission.md), Jira `S15P21C206-187`.
- 후속 작업: 실제 제출 엔드포인트가 아직 없어(C10 = `S15P21C206-142`·`143` 「해야 할 일」) fixture로 구현한다. 요청 ID 보존 기간은 C10 연동 때 확정한다.

## [S15P21C206-187] 분석 제출 접수·복구 구현

- 수정자: 백지웅 (Claude 보조)
- 유형: API · 운영
- 상태: 구현 완료 · 실제 API 인수 대기
- 변경 범위: [분석 제출 개발 안내](../../../apps/frontend/docs/analysis-submission.md), 제출 본문·파서·요청 ID·복구 사다리·화면 연결, 개발용 제출 응답과 검증.
- 목적: 제출을 요청 ID 하나로 추적하고, 응답을 받지 못해도 중복 접수를 만들지 않고 결과를 확인한다.
- 발견(재발 방지): **브라우저는 재사용된 연결이 응답 한 바이트도 없이 닫히면 POST를 스스로 다시 보낸다.** 앱의 `fetch` 호출 횟수에는 잡히지 않고 앱이 막을 수도 없다. 개발용 응답에서 소켓만 끊었더니 접수 결과가 `replayed`로 돌아와 드러났다. **응답 유실을 소켓 끊기로 재현하면 안 되고**, 헤더를 보낸 뒤 본문을 끊어야 한다. 헤더가 실제로 소켓에 나간 뒤 끊어야 하며 `writeHead` 직후 `destroy`하면 Node가 버퍼째 버린다. 이 경우를 `reset-connection` 시나리오로 남겨 Submission이 하나만 남는지 확인한다.
- 결정·근거: 요청 ID 규칙을 「응답과 처리」 표 한 곳에 모으고 `classifySubmissionError`가 그 마지막 열(`keep`·`renew`·`discard`)을 코드로 옮긴다. 새 ID는 `reserveRequestId` 한 곳에서만 만든다. 조회 실패는 「접수 안 됨」이 아니라 「여전히 모름」이므로 ID를 버리지 않는다.
- 결정·근거: **201과 200은 본문으로 구분할 수 없다.** 재전송 응답은 접수 당시 값을 그대로 담아 성과가 있었다면 `newlyRecognized`가 다시 실려 온다. `outcome`을 HTTP 상태에서 읽어 한 번만 일어나야 하는 처리를 `created`로 제한한다.
- 결정·근거: 특수 제출 생성기는 선택·판단·근거를 **인자로 받지 않는다.** 만든 뒤 지우는 방식이면 필드가 늘었을 때 지우는 쪽을 빠뜨린다. 건너뛰기는 서버의 허용 표시가 있을 때만 제안하고, 더 없음은 완료한 별에만 막는다. 잘못 막으면 할 수 있는 일을 못 하게 되지만 잘못 보내면 409를 받고 끝이다.
- 결정·근거: 접수 결과와 되돌릴 수 없는 동작의 확인을 가운데 대화상자로 옮겼다. 브라우저 기본 `confirm`은 쓰지 않는다. Figma에 없는 패턴이라 [design.md](../../../apps/frontend/docs/design.md)의 「Figma에 반영이 필요한 것」에 8번으로 적었다.
- 발견(재발 방지): 네이티브 `<dialog>`에서 **React의 `onClose`·`onCancel`이 발화하지 않는다.** 브라우저는 닫혔는데 상태는 열린 채로 남는다. 네이티브 리스너를 쓰고, 요소는 항상 그려 두어야 리스너를 붙일 시점에 ref가 비지 않는다. 닫은 뒤 포커스는 갈 곳을 지정해야 한다. 연 버튼이 그사이 비활성이 되면 문서 맨 위로 떨어진다. 뼈대를 [use-modal-dialog.ts](../../../apps/frontend/src/features/analysis/use-modal-dialog.ts)로 모았다.
- 검증: 타입 검사·운영 빌드 통과, 단위 266개, Chrome 회귀 141개 통과(GPU 3건 건너뜀). 대비 검산 통과. axe WCAG 2 A/AA·2.1 AA를 특수 제출·확인·접수·거절·결과 불명 다섯 상태에서 돌려 위반 0건. 계약 검사가 개발 서버의 실제 응답을 파서에 통과시킨다. **실제 백엔드를 띄운 종단 검사는 하지 않았다.**
- 관련 문서: [탐사 API 2.2·2.3·6.1~6.6](../../../apps/backend/docs/exploration-api-spec.md), [분석 제출 개발 안내](../../../apps/frontend/docs/analysis-submission.md), Jira `S15P21C206-187`.
- 후속 작업: 제출 엔드포인트가 아직 없어(C10 = `S15P21C206-142`·`143` 「해야 할 일」) **이 작업으로 티켓을 닫지 않는다.** 실제 API 인수와 강재민의 DB 증거(접수된 유효 요청당 Submission/History 각 1건, 재전송으로 추가 생성 없음)가 남아 있다. 요청 ID 보존 기간과 자동 복구 한도(전송 2회·재조회 3회)는 C10 연동 때 확정한다.

- 정정(같은 날): 위 두 항목의 계약 근거를 **구판 명세**에서 읽었다. 메인 체크아웃이 `docs/week-05-report` 브랜치였고 그 사본은 Draft 0.3 / SRS v1.2다. develop의 현재 판은 Draft 0.4 / v1.3.1이다. 6장·2.2·2.3절을 전수 대조해 결과 DTO·복구·상세는 같고 **셋이 달랐다.** (1) `memo`는 이미 `0~200`이라 「명세 2,000 vs 구현 200」 미결은 존재하지 않는다. 개발용 응답의 상한도 2000에서 200으로 내려 초과 전송을 잡게 했다. (2) `BUNDLE_CHANGED`의 현재 판은 **본문**의 `currentBundleId`가 정본이다. (3) `X-Current-Bundle` 헤더는 5.2·5.3 응답부터 붙었고 나머지 API는 각 구현 때 붙이므로 제출 응답에는 아직 없을 수 있다. 본문을 먼저 읽고 헤더를 보조로 쓰도록 고쳤으며, 이를 위해 공용 클라이언트의 `ApiError`에 오류 본문을 그대로 싣는 `details`를 더했다. **재발 방지: 명세는 작업 중인 worktree에서 읽는다. 메인 체크아웃은 다른 브랜치일 수 있다.**

## [S15P21C206-144] 신호별 성과 인정·새 별 발견 공통 함수와 성과 조회

- 수정자: 강재민 (Claude 보조)
- 유형: API
- 상태: 구현 완료 · 리뷰 대기
- 변경 범위: 탐사 API 9.1·9.2절, 성과 인정 함수와 `GET /me/achievements`, 발견 공통 함수, 탐사 요약 집계, 운영 규칙 런북
- 목적: 제출(S15P21C206-143)과 공개 분석 등록(백승학 담당)이 같은 트랜잭션에서 부를 성과 인정·별 열림 함수와 9.1절 성과 조회를 제공한다.
- 결정·근거: 시드 정책 `hash-user-achievement-seq-v1`을 계산식으로 정했다. SHA-256(`회원:성과:순번`) 앞 8바이트를 부호 없는 정수로 읽고, TIC 오름차순 후보에서 `seed mod 후보 수`번째를 고른다. 후보 수 세기와 고르기는 한 SQL 문장에서 해 둘이 어긋나지 않는다. 별 저장의 충돌 대상은 9.4절과 같은 `(user_id, tic_id)`다. PostgreSQL은 충돌 대상을 하나만 받고, 같은 성과의 재처리는 성과 INSERT 충돌에서 이미 멈추므로 `UNIQUE(trigger_achievement_id, seq)`는 위반 시 예외를 내는 안전망으로 둔다. 성과 행은 앱이 지울 수 없어(V5) 인정 근거를 넣기 전에 검사한다. `/me` 요약과 9.1절 `summary`는 한 집계를 쓴다.
- MR !99 리뷰 반영: 호출자가 공개 기록부터 저장하고 인정 함수가 처음 회원 행을 잠그면, 외래 키 검사의 KEY SHARE와 `FOR UPDATE`가 맞물려 교착한다(리뷰어 재현). 호출자가 기록 저장·진행 행 갱신 전에 같은 트랜잭션에서 회원 행을 먼저 잠가야 한다는 조건을 9.2절과 함수 주석에 적었다.
- 검증: 백엔드 전체 테스트 311개 통과. 새 테스트 28개가 인정·재인정·등급·제외 규칙·부족·별 저장 실패 롤백·동시 실행 3종·앱 역할 권한·조회·커서를 본다. 리뷰 반영 테스트 2개는 올바른 호출 순서의 동시 제출·공개(10회)가 교착 없이 끝나는 것과, 순서를 어기면 한쪽이 교착(40P01)으로 끝나는 것을 고정한다.
- 관련 문서: [탐사 API 9장](../../../apps/backend/docs/exploration-api-spec.md#9-성과등급별-열림완료재개), [운영 규칙 런북](../../operations/operation-rule-runbook.md), [Jira](https://ssafy.atlassian.net/browse/S15P21C206-144)
- 후속 작업: 제출(S15P21C206-143)·공개 분석 등록의 호출 연결과 공동 통합 테스트. 공개 분석 등록은 `published_analyses` 앱 역할 쓰기 권한 마이그레이션이 필요하다(V11은 읽기 전용이라 지금은 42501). 추가한 뒤 앱 역할로 전체 경로를 검증한다. `relabel.newDisposition`의 값 대응(`pc`·`none` → `UNCONFIRMED`)은 6.4절 `signal.disposition`을 구현할 때 같은 규칙으로 맞춘다.

- 목적: 저장 좌표를 배치 함수가 계산한 값과 비트 단위로 같게 한다(S15P21C206-139 리뷰 후속).
- 결정·근거: 좌표를 double로 바인딩하면 PostgreSQL의 float8→NUMERIC 변환이 유효숫자 15자리로 반올림한다(18.6에서 `(1/3::float8)::numeric` = `0.333333333333333`). `BigDecimal.valueOf`로 넘겨 최단 10진 표현을 그대로 저장한다. 이미 저장된 좌표는 API가 같은 저장값을 읽으므로 고치지 않는다.
- 검증: 배치 함수의 순번 0~5는 정수 고정 좌표라 반올림이 드러나지 않는다. 그래서 회귀 테스트는 순번 6 이상까지 열어 비트 단위로 비교한다. double 바인딩으로 되돌리면 이 테스트가 실패하는 것을 확인했다.
- 관련 문서: [Jira](https://ssafy.atlassian.net/browse/S15P21C206-144)
- 후속 작업: 없음

## [S15P21C206-143] 제출 처리·멱등 응답·스냅샷 산포 구현

- 수정자: 백승학
- 유형: API
- 상태: 사용자 채택 · 본체 구현·격리 DB 검증, 실제 141·147 연결은 인계 대기

- 경합 보완: 리뷰의 psql 재현 보고는 첫 SELECT의 스냅샷 생성과 advisory lock 획득 사이 커밋에서 기존 행이 보이지 않지만 INSERT는 중복 키로 실패함을 보였다. 이 실행 기록을 이번 작업에서 직접 재현했다고 주장하지 않는다. 코드에서는 DuplicateKeyException도 트랜잭션 전체 재시도에 포함했고, 추가 테스트는 타이밍 자체가 아니라 그 실패 후 복구·기존 기록 보존을 결정적으로 검사한다.
- 관련 문서: [제출 준비](../../api/exploration/submission-readiness.md), [Jira](https://ssafy.atlassian.net/browse/S15P21C206-143)

## [S15P21C206-188] 제출 결과 표시의 독립 축 확정

- 수정자: 백지웅 (Claude 보조)
- 유형: API
- 상태: 채택 · 구현 전
- 변경 범위: [제출 결과·해설 개발 안내](../../../apps/frontend/docs/analysis-result.md) 신규.
- 목적: 서버가 따로 주는 결과를 화면이 하나로 합치지 않도록, 무엇을 구분해야 하는지 먼저 고정한다.
- 결정·근거: 매칭·판단 채점·성과·진행·공개·AI **여섯 축을 독립으로 둔다.** 한 축의 값으로 다른 축을 추측하지 않는다. 매칭에 성공해도 성과가 없을 수 있고 성과가 없어도 탐색이 끝날 수 있다. 완료 조건의 「마지막 확정/FP 오판·UNSURE도 완료와 미인정이 함께 보인다」가 그 경우이며, 매칭 `matched`·채점 `DISAGREES`·성과 `judgment_mismatch`·진행 `completed`가 동시에 참이다.
- 결정·근거: **없음을 0으로 바꾸지 않는다.** AI 실행 불가를 0점으로, 공개 참여자 0명을 0%로 그리지 않는다. 미매칭에는 임의 신호의 통계를 붙이지 않는다. `ambiguous_match`는 서버가 어느 후보도 고르지 않은 상태이므로 신호·AI·통계를 하나도 붙이지 않는다. 「가장 가까운 후보」를 프론트가 고르면 서버가 일부러 고르지 않은 것을 뒤집는다.
- 결정·근거: 통계는 미확정(`public_analyses`, 최신 유효 공개 분포)과 확정·FP(`graded`, 첫 매칭 회원 일치율)의 **분모가 달라** 같은 문구를 쓸 수 없다.
- 결정·근거: 상세 보기는 **열람 기록을 남기므로** 사용자가 누르지 않았는데 대신 호출하지 않는다. 그 기록이 튜토리얼 건너뛰기 조건에 쓰인다.
- 결정·근거: **판정 어휘는 계층마다 다르다.** `signal.disposition`은 API의 표시 어휘로 대문자 `CONFIRMED`·`UNCONFIRMED`·`FP`이고, 같은 응답의 `achievement.star.byType` 키는 소문자 `confirmed`·`unconfirmed`·`fp`이며, DB `candidate_dispositions`는 소문자 `confirmed`·`fp`·`pc`·`none`이다. 탐사 명세·구판 분석 명세·예제 5개가 일관되므로 불일치가 아니라 계층 차이다. 파서는 각각의 표기 그대로 대조하고 한쪽에 맞춰 대소문자를 바꾸지 않는다.
- 발견(혼동 주의): `signal.external[].disposition`은 우리 열거형이 아니라 [ERD](../../architecture/database-erd.md)가 정의한 **「원천 표기」**다. TOI의 `PC`처럼 출처가 쓰는 말이 그대로 오므로 출처 이름·조회일과 함께 받은 문자열을 그대로 보여 주고 우리 판정으로 번역하지 않는다.
- 검증: 문서 확정 단계이므로 실행 검증 없음. 근거는 저장소의 명세·스키마 CHECK 원문 대조다.
- 관련 문서: [탐사 API 6.4·6.5·6.7](../../../apps/backend/docs/exploration-api-spec.md), [제출 결과·해설 개발 안내](../../../apps/frontend/docs/analysis-result.md), Jira `S15P21C206-188`.
- 후속 작업: 제출·결과 조회·상세 보기가 모두 미구현이라(C10 = `S15P21C206-142`·`143`, C12-1 = `S15P21C206-145`) fixture로 구현하며 **이 작업으로 티켓을 닫지 않는다.**
