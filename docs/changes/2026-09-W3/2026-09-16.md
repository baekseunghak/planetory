# 2026-09-16 주요 변경

## [S15P21C206-157] 마이 프로필 P0 — 닉네임 변경·첫 방문 안내 완료·타인 공개 프로필

- 수정자: 백승학
- 유형: API
- 상태: 구현 완료 (P0 범위. 최신 닉네임의 커뮤니티 반영과 튜토리얼 첫 제출 연동은 미검증)
- 변경 범위: `MemberController`, `MemberService`, `Member`, `MemberSettingsRepository`, `ErrorCode`, `AuthIntegrationTest`, `apps/backend/docs/service-api-spec.md` 3.1절, `docs/development/service-backend/account.md` F03
- 목적: `GET /me`와 탐사 성과 요약을 재사용해 MY-01 마이페이지의 P0 경로를 열고, SB-D14·SB-D23의 확정 입력·공개 기준을 실제 응답으로 고정한다.
- 결정·근거: 닉네임 중복은 사전 조회 없이 `lower(nickname)` 유일 인덱스 위반을 409 `NICKNAME_CONFLICT`로 변환해 동시 변경에서도 한쪽만 성공하게 했다(F03-Q2 확정). 첫 방문 안내 완료는 `INSERT ... ON CONFLICT DO UPDATE`로 단방향 true만 쓰므로 설정 행이 없어도 ERD 기본값으로 생성되고 기존 공개·알림 설정을 덮어쓰지 않으며 병렬 요청이 서로를 되돌리지 않는다. 타인 프로필은 미존재와 탈퇴를 모두 404로 응답해 탈퇴 여부가 드러나지 않게 했다(존재를 숨길 자원의 404 중 이 경로만 확정). 성과 요약은 별도 산식 없이 `ExplorationSummaryService`의 같은 조회에서 공개 범위만 투영한다.
- 검증: `./gradlew test --tests "*AuthIntegrationTest*"` 통과. 닉네임은 앞뒤 공백 제거·대소문자 무시 중복 409·예약어/1자/내부 공백/기호 거부와 함께, NFD 입력이 NFC 3자로 저장되고 완성형 재요청이 409가 되는 정규화 동작, 20자 통과·21자 거부·공백 제거 후 20자 통과의 길이 경계를 확인했다. 온보딩은 최초/반복 true·false/null 400·설정 행 미존재·기존 `star_list_public`·`notification_prefs` 보존·다른 기기 조회 유지와 두 스레드 동시 호출 후 행 1개를 확인했다. 타인 프로필은 별 목록 비공개에서도 성과 요약 제공·이메일/제공자/온보딩 필드 미노출·미존재 404·탈퇴 404·미인증 401을 확인했다.
- 관련 문서: [서비스 API 명세](../../../apps/backend/docs/service-api-spec.md) 3.1~3.2절, [회원·인증](../../development/service-backend/account.md) F03, Jira `S15P21C206-157`
- 경로 분리: 첫 방문 안내 완료를 `PATCH /api/v1/me/settings`에서 `PATCH /api/v1/me/onboarding`으로 옮겼다. onboardingDone은 true로만 가는 단방향 사건 기록이라 false를 400으로 거부하는데, 3.2절 P1 공개 설정은 양방향이므로 한 경로에 두면 "필드 없음"과 "값 오류"를 구분하는 분기가 필요해진다. 본문·응답·검증 규칙은 바꾸지 않아 기존 검증 항목이 모두 유지된다. 호출부가 아직 없어 지금 옮기는 비용이 가장 낮다고 판단했다.
- 후속 작업: 게시글·댓글·반응자 표시의 최신 닉네임 반영과 탐사 D-8 튜토리얼 첫 제출의 온보딩 동시 완료는 해당 구현에서 검증한다. 추가 금칙어 목록과 담당은 미협의이며 현재는 SYSTEM/ADMIN/관리자/운영자 정확 일치만 거부한다. `docs/api/exploration/contracts.json`의 `onboarding-done`·`onboarding-reject-false`·`onboarding-reject-null` 세 case는 옛 경로를 쓰지만 #133 리뷰용 고정 예제라 이 작업에서 고치지 않았다. 같은 파일이 400 본문에 `fieldErrors`를 기대하는 것도 현재 구현과 다르며, 두 문서의 오류 본문 계약 정합은 별도 확인이 필요하다. 요청 DTO의 위치·`@Operation` 누락·타인 프로필의 불필요한 튜토리얼 조회는 후속 정리 대상이다.
