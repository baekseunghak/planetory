## [S15P21C206-73] YARN 호스트 준비와 Spark HDFS sample 실환경 검증

- 수정자: Codex (사용자 요청)
- 유형: 운영 · 오류 정정
- 상태: 검증 완료
- 변경 범위: YARN 설정·systemd 설치·단계형 기동·UFW·Spark sample·정적 검증, 분산 인프라·운영·진행 상태 문서
- 목적: Node 1 ResourceManager와 Node 2~6 NodeManager를 안전하게 설치·기동하고 Spark 3.5.5 cluster mode가 HDFS를 읽고 쓰는 경로와 Node 2 자원 상한을 검증한다.
- 결정·근거: 서버 기본 파일이던 `capacity-scheduler.xml`을 단일 `root.default` queue 정본으로 저장소에서 관리한다. Node 1의 Docker 설치 책임은 제출 경로를 소유한 73번에 포함한다. Spark driver는 `7078`, block manager는 기본 재시도 범위 `7079~7095`로 고정하고 Worker 사설 IP 사이에서만 허용한다. 단일 `7079`만 허용하면 같은 노드의 추가 executor가 증가된 포트를 사용해 remote broadcast fetch가 멈췄다. Hadoop 3.5 daemon PID 실제 이름 `hadoop-yarn-*`과 unit 기대값 불일치, 고정 3초 준비 대기, HDFS 기본 staging 권한도 설치·기동·sample 스크립트에서 바로잡았다. Worker Python 사전 검사는 보안 patch 갱신을 허용하도록 3.12.x로 통일했다. sample의 HDFS `root`·`1777`은 검증 전용이며 배치 서비스 사용자와 경로 소유·그룹 권한은 `S15P21C206-76`에서 확정한다.
- 검증: ResourceManager 1개와 NodeManager 5개가 active이며 `worker-2`~`worker-6`은 모두 `RUNNING`이다. `application_1789675115055_0005`는 5개 Worker에 executor를 하나씩 배치해 HDFS 입력을 읽고 part 5개와 checksum을 남긴 뒤 `SUCCEEDED`, 로그 집계 `SUCCEEDED`로 끝났다. Node 2의 16GiB/2 vCore 한도에서 executor 1개 실행 중 호스트 used 약 2.7GiB, available 약 32.5GiB, swap 0, OOM 없음과 Standby NameNode RSS 약 556MiB를 확인했다. 성공 run 시작 뒤 6개 YARN daemon 로그의 새 ERROR·FATAL은 0건이고 HDFS Active/Standby·Live DataNode 5개도 유지됐다. Python 정적 검사, PowerShell parser, Bash 구문, 원격 변경 없는 회귀 검사도 통과했다.
- 관련 문서: [분산 시스템 운영 절차](../../../infra/distributed-system/README.md), [GCP 분산 인프라](../../architecture/gcp-distributed-infrastructure.md), [GCP 노드 운영 런북](../../operations/gcp-node-runbook.md), [분산 PoC 상태](../../project/distributed-poc-status.md), [Jira S15P21C206-73](https://ssafy.atlassian.net/browse/S15P21C206-73)
- 후속 작업: 실제 Sector workload의 메모리·처리시간 상한과 재시도를 별도 PoC에서 측정한다. Node 2~6 Docker 설치는 수집 컨테이너 배포 작업에서 수행하고, YARN unit 부팅 자동 시작은 HDFS 재부팅·수동 Active 절차와 함께 운영 결정한다.

## [S15P21C206-73] YARN MR 재실행 안전성 리뷰 반영

- 수정자: Codex (사용자 요청)
- 유형: 운영 · 오류 정정
- 상태: 구현 완료 · 서버 재적용 대기
- 변경 범위: YARN 단계형 기동·sample·설치·정적 검증 스크립트, YARN XML, 분산 인프라·운영 문서
- 목적: OOM 검사의 권한 실패 은폐, UFW 기본 정책 미검사, HDFS HA 역할 하드코딩과 비파괴 검증 누락을 수정하고 재실행 경계를 명확히 한다.
- 결정·근거: OOM은 비대화식 관리자 권한 kernel journal 조회 성공을 먼저 단정한다. HDFS는 `nn1`·`nn2` 중 정확히 하나가 Active이고 하나가 Standby이면 정상으로 보며 입출력은 `hdfs://planetory` 논리 URI를 유지한다. UFW는 기본 incoming deny에서만 규칙을 추가한다. `/yarn-logs`는 배치 데이터 경로와 분리해 7일 보존하며 기존 권한을 매번 덮어쓰지 않는다. Node 2의 16GiB/2 vCore와 전역 24GiB/3 vCore는 의도된 이기종 배치이고 OS 하드캡은 아직 없다.
- 검증: `validate.py`, Bash 구문, PowerShell parser, `test-yarn.ps1` 오프라인 모의, `git diff --check`가 통과했다. 변경된 Bash 전달 방식으로 실서버 `Preflight`와 `ValidateNodes`를 읽기 전용 실행해 ResourceManager 1개·NodeManager 5개 active, Worker 5대 `RUNNING`, 6개 노드의 광고 호스트 사설 IP 해석을 확인했다. Node 2의 `sudo -n journalctl -k` 접근과 현재 `nn1=active`, `nn2=standby`도 확인했다. 변경 XML 재설치와 Spark sample 재실행은 하지 않았다.
- 관련 문서: [분산 시스템 운영 절차](../../../infra/distributed-system/README.md), [GCP 분산 인프라](../../architecture/gcp-distributed-infrastructure.md), [GCP 노드 운영 런북](../../operations/gcp-node-runbook.md), [Jira S15P21C206-73](https://ssafy.atlassian.net/browse/S15P21C206-73)
- 후속 작업: YARN을 통제 중지한 유지보수 시점에 변경 설정을 6대에 재설치하고 `Start`·sample·`FinalAudit`을 다시 실행한다. HDFS 선행 자동 기동·health gate는 `S15P21C206-74`에서 결정한다.
