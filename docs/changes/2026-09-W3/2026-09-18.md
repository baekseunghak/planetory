## S15P21C206-84 서비스 진입 Cloudflare Tunnel 최초 도입과 backend 비가동 시 frontend 기동

- `infra/service/compose.yaml`에 `cloudflared` 서비스를 추가했다. 외부 인바운드 개방 없이 edge에서만 트래픽을 받으며 connector 토큰은 서버 `.env`로 주입한다. 절차는 [EC2 서비스 배포](../../../infra/service/README.md)를 따른다.
- `apps/frontend/nginx.conf`가 backend 호스트명을 리터럴로 두어 기동 시점에 해석했다. GitLab 배포가 `docker compose up -d --no-deps`를 쓰므로 backend를 함께 올리지 않는 배포에서 frontend 컨테이너 자체가 기동에 실패했다. Docker 내장 DNS(`resolver 127.0.0.11`)와 변수 upstream으로 바꿔 요청 시점 해석으로 정정했다.
- 세션 조회 `/api/v1/me`는 502·504일 때만 401로 낮춘다. backend 없이도 SPA가 오류 화면 대신 로그인 화면에 도달한다. 장애를 인증 만료처럼 보이게 하는 절충이며 상태 구분은 헬스체크(S15P21C206-93)에서 다룬다. 다른 `/api/*`는 502를 그대로 전달한다.
- 검증: `docker compose -f infra/service/compose.yaml config -q`, `nginx -t`, backend 부재 시 `/` 200 · `/api/v1/me` 401 · `/api/v1/other` 502, stub backend 연결 시 `/api/v1/me` 200 통과.
- 상태: Tunnel 진입과 frontend 기동만 구현 완료다. Redis runtime, 메모리 상한·eviction, health/readiness, 남용 제어 위치, connector 처리량 실측은 S15P21C206-84에 미완료로 남는다.

## [S15P21C206-83] `users` GRANT 구문 작성을 백엔드로 분리

- 수정자: 김동혁 (Claude 보조, 사용자 판단)
- 유형: 계약 · 소유 경계
- 상태: 확정 (구현은 `S15P21C206-238`)
- 변경 범위: Jira `S15P21C206-83` 포함·제외·완료 조건·선행, 신규 `S15P21C206-238`(백승학), [EC2 서비스 진입·장애 경계](../../architecture/ec2-service-entry-failover.md) 5·7절
- 목적: 인프라 티켓이 백엔드 마이그레이션의 GRANT 구문을 쓰게 되어 있던 경계를 바로잡는다.
- 결정·근거: 사용자가 「서비스 DB는 백엔드가 하는 게 맞지 않나」로 문제를 제기했고 확인 결과 맞았다. ① 83은 제외 항목에 이미 「C04 소유 DDL」을 두고 있는데 GRANT도 DDL이고 그 구문이 들어갈 파일은 `apps/backend/src/main/resources/db/migration/`이다 — 자기모순이었다. ② **필요한 동사 집합을 데이터 접근 코드를 쓰는 사람만 안다.** `users`는 SELECT만이 아니라 OAuth 최초 가입의 INSERT(`MemberService:39`)와 저장 경로의 UPDATE(`MemberService:82`)도 필요해서, 인프라가 추측으로 `GRANT SELECT`를 넣었으면 두 군데서 틀렸다. ③ 앞으로 쓰기 경로가 늘 때마다 GRANT도 늘어야 하는데 그 유지보수가 인프라 티켓에 있으면 드리프트가 난다. V5가 테이블 정의와 GRANT를 같은 파일에 둔 이유와 같다.
- 근거 사실(측정): 마이그레이션 15커밋이 전부 백엔드에서 나왔다(강재민 9, 백승학 6). GRANT 블록을 담은 `V2__gold_roles.sql`·`V5__exploration_domain_constraints.sql`도 백엔드 티켓 `S15P21C206-134`·`-135`가 작성했다. **인프라가 쓴 마이그레이션은 0건이다.** `member` 도메인 코드는 백승학 단독이라 238을 백승학에게 배정했다.
- 경계 정리: 인프라(83)는 역할 모델 적용(계정 생성·비밀 주입·접속 설정)·마이그레이션 실행 주체·볼륨·loopback 바인드와 **인수 검증**을 맡는다. 백엔드(238)는 테이블별 GRANT 구문을 쓴다. 83의 완료 조건 「`planetory_app`으로 42501 없이 동작」은 그대로 남아 238을 강제하는 게이트가 된다.
- 검증(실행하지 않은 것): GRANT 구문을 쓰거나 적용하지 않았다. `planetory_app` 역할로 접속한 검증도 하지 않았다. 결손 사실만 확인했고 필요한 동사 집합은 238이 코드로 확정한다.
- 관련 문서: [EC2 서비스 진입·장애 경계](../../architecture/ec2-service-entry-failover.md) 5·7절, Jira `S15P21C206-83`·`S15P21C206-238`

- 결정·근거: `experiments/distributed-pipeline/compose.yaml`의 `service-db`가 이미 마이그레이션 9개로 검증된 설정이라 그대로 옮기고 EC2용으로 셋만 바꿨다. ① 비밀번호를 `${POSTGRES_PASSWORD:?}`로 필수화해 로컬 기본값이 배포에 새지 않게 했다. ② 호스트 포트 노출을 없애 backend가 `service` 네트워크로 `service-db:5432`에 붙게 했다(외부 인바운드 0개). ③ named volume `planetory-service-db-data`를 쓰고 마운트 경로는 `postgres:18`의 `/var/lib/postgresql`을 유지했다. 17 이하의 `/var/lib/postgresql/data`로 되돌리면 깨진다.

## S15P21C206-84 Tunnel 뒤 프로토콜 전달 정정

- Google OAuth 콜백 뒤 복귀가 `http://planetory.space:8080/...`으로 깨졌다. `apps/frontend/nginx.conf`가 `X-Forwarded-Proto`를 `$scheme`(평문 구간이라 항상 `http`)으로 덮어썼고, Backend가 `X-Forwarded-*`를 반영하지 않아 Tomcat이 상대 리다이렉트를 자기가 본 스킴·포트로 절대화했다.
- nginx는 Cloudflare가 준 `X-Forwarded-Proto`를 보존하고(없으면 `$scheme`으로 대체) `X-Forwarded-Host`를 함께 전달한다. `apps/backend/.../application.properties`에 `server.forward-headers-strategy=framework`를 추가했다.
- 검증: stub backend로 `X-Forwarded-Proto: https` 전달 시 `proto=https host=planetory.space`, 헤더 없이 호출 시 `proto=http`. backend 부재 시 `/` 200 · `/api/v1/me` 401 회귀 확인. 외부에서 `redirect_uri=https://planetory.space/login/oauth2/code/google` 확인.
- 상태: 구현 완료, 실환경 로그인 성공 여부는 재배포 후 확인 필요.
