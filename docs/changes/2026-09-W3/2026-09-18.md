## [S15P21C206-71] tailnet 접속을 전 서버 `tailscale ssh`로 통일

- 수정자: 김동혁 (Claude 보조, 사용자 요청)
- 유형: 운영
- 상태: 검증 완료(실측)
- 변경 범위: [Tailscale 팀 서버 접근 가이드](../../operations/tailscale-team-access.md) 2·3절
- 목적: GCP 노드에만 적용돼 있던 `tailscale ssh` 기본 경로를 `donh-vnic`·`ec2-a`·`ec2-b`까지 넓혀 접속 방법을 하나로 맞춘다.
- 결정·근거: 2026-09-17 `fde9198`이 GCP `node-1~6`만 `tailscale ssh`로 바꾸고 EC2·CI 노드는 OpenSSH 표기로 남겨 두 방식이 섞여 있었다. `tailscale ssh`는 대상에 개인 SSH 키를 배포하지 않아도 되고 접속 주체가 tailnet 신원으로 남으므로 관리 접속의 기본으로 통일한다.
- 검증(실행한 것): `tailscale ssh <계정>@<이름> hostname -s`를 실제로 실행해 `donh-vnic`·`ec2-a`·`ec2-b`가 모두 응답하는 것을 확인했다. 표기만 바꾼 것이 아니라 세 대상에서 Tailscale SSH 서버가 실제로 켜져 있음을 확인한 뒤 반영했다. 호스트명·사설 IP는 문서에 적지 않는다.
- 검증(실행하지 않은 것): `node-2`~`node-6`은 이번에 다시 확인하지 않았다. 2026-09-17 `fde9198`의 기록을 그대로 따른다.
- 후속 작업: `tailscale ssh` 실패 시 확인 순서(대상의 `tailscale up --ssh` 여부)를 3절에 적었다. ACL 허용과 대상의 SSH 서버 활성화는 별개라는 점이 실패 원인 대부분이다.
- 관련 문서: [Tailscale 팀 서버 접근 가이드](../../operations/tailscale-team-access.md), Jira `S15P21C206-71`

## [S15P21C206-83] `users` GRANT 구문 작성을 백엔드로 분리

- 수정자: 김동혁 (Claude 보조, 사용자 판단)
- 유형: 계약 · 소유 경계
- 상태: 확정 (구현은 `S15P21C206-238`)
- 변경 범위: Jira `S15P21C206-83` 포함·제외·완료 조건·선행, 신규 `S15P21C206-238`(백승학), [EC2 서비스 진입·장애 경계](../../architecture/ec2-service-entry-failover.md) 5·7절
- 목적: 인프라 티켓이 백엔드 마이그레이션의 GRANT 구문을 쓰게 되어 있던 경계를 바로잡는다.
- 결정·근거: 사용자가 「서비스 DB는 백엔드가 하는 게 맞지 않나」로 문제를 제기했고 확인 결과 맞았다. ① 83은 제외 항목에 이미 「C04 소유 DDL」을 두고 있는데 GRANT도 DDL이고 그 구문이 들어갈 파일은 `apps/backend/src/main/resources/db/migration/`이다 — 자기모순이었다. ② **필요한 동사 집합을 데이터 접근 코드를 쓰는 사람만 안다.** `users`는 SELECT만이 아니라 OAuth 최초 가입의 INSERT(`MemberService:39`)와 저장 경로의 UPDATE(`MemberService:82`)도 필요해서, 인프라가 추측으로 `GRANT SELECT`를 넣었으면 두 군데서 틀렸다. ③ 앞으로 쓰기 경로가 늘 때마다 GRANT도 늘어야 하는데 그 유지보수가 인프라 티켓에 있으면 드리프트가 난다. V5가 테이블 정의와 GRANT를 같은 파일에 둔 이유와 같다.
- 근거 사실(측정): 마이그레이션 15커밋이 전부 백엔드에서 나왔다(강재민 9, 백승학 6). GRANT 블록을 담은 `V2__gold_roles.sql`·`V5__exploration_domain_constraints.sql`도 백엔드 티켓 `S15P21C206-134`·`-135`가 작성했다. **인프라가 쓴 마이그레이션은 0건이다.** `member` 도메인 코드는 백승학 단독이라 238을 백승학에게 배정했다.
- 경계 정리: 인프라(83)는 역할 모델 적용(계정 생성·비밀 주입·접속 설정)·마이그레이션 실행 주체·볼륨·loopback 바인드와 **인수 검증**을 맡는다. 백엔드(238)는 테이블별 GRANT 구문을 쓴다. 83의 완료 조건 「`planetory_app`으로 42501 없이 동작」은 그대로 남아 238을 강제하는 게이트가 된다.
- 검증(실행하지 않은 것): GRANT 구문을 쓰거나 적용하지 않았다. `planetory_app` 역할로 접속한 검증도 하지 않았다. 결손 사실만 확인했고 필요한 동사 집합은 238이 코드로 확정한다.
- 관련 문서: [EC2 서비스 진입·장애 경계](../../architecture/ec2-service-entry-failover.md) 5·7절, Jira `S15P21C206-83`·`S15P21C206-238`

## [S15P21C206-82] Redis를 `redis-session`·`redis-cache` 두 인스턴스로 분리 — MR !55 리뷰 반영

- 수정자: 김동혁 (Claude 문서 반영 보조), 제안자 백승학
- 유형: 아키텍처 · 운영
- 상태: 채택 (D1 개정, 1.1절 신설. 구현은 `S15P21C206-84`·`-237`)
- 변경 범위: [EC2 서비스 진입·장애 경계](../../architecture/ec2-service-entry-failover.md) D1·D8·D10·1.1절·2·3·4·4.1·6·7절, [시스템 아키텍처](../../architecture/system-architecture.md) 2장, [서비스 백엔드 계약](../../development/service-backend/contracts-and-acceptance.md) SB-D07, [회원·인증](../../development/service-backend/account.md), [OAuth 설정](../../../apps/backend/docs/oauth-setup.md), [서비스 API 명세](../../../apps/backend/docs/service-api-spec.md), [CI/CD](../../operations/cicd.md)
- 목적: 계산 캐시의 eviction이 로그인 세션을 지우는 경로를 없앤다.
- 결정·근거: 백승학님 지적대로 `maxmemory`와 `maxmemory-policy`는 **인스턴스 단위 설정**이라 키 접두사나 논리 DB(`SELECT 0/1`)로는 메모리 예산과 eviction이 분리되지 않는다. 한 인스턴스에 두면 `allkeys-*`는 세션을 후보로 삼고 `volatile-*`도 세션이 30분 TTL(SB-D14)을 가져 그대로 후보다. 증상이 「로그인한 회원이 이유 없이 튀김」이라 재현도 진단도 어렵다.
- 추가로 확인한 이득: **분리가 D10의 대가를 일부 되돌린다.** 세션을 Redis로 옮기며 「Redis 장애 = 인증 전면 중단」을 수용했는데, 나누면 그 범위가 `redis-session` 장애로 좁아지고 **`redis-cache` 장애는 이관 전과 똑같이 온라인 계산만 멈춘다.** 4장 장애표의 Redis 행을 두 행으로 나눈 이유다.
- 정책 분리: `redis-session`은 30분 idle TTL·`noeviction`·persistence 필요, `redis-cache`는 결과 TTL·캐시 eviction 허용·persistence 불필요.
- 기각한 대안 3건을 표로 남겼다. 키 접두사 분리와 논리 DB 분리는 메모리·eviction을 나누지 못하고, 단일 인스턴스 `noeviction`은 세션은 지키지만 재계산하면 그만인 캐시 때문에 계산 쪽 쓰기를 실패시킨다.
- 비용: 인스턴스 하나 추가이고 EC2-A 안이라 작다. **다만 메모리 예산을 둘로 쪼개야 하고 한쪽 여유가 다른 쪽을 돕지 못한다.** 각 상한과 합계가 PostgreSQL을 OOM으로 밀어내지 않는지는 84가 확인한다. `noeviction`인 `redis-session`이 상한에 닿으면 새 로그인과 세션 연장이 실패하므로 세션 크기·동시 접속 추정이 상한 산정 입력이다.
- 검증(실행한 것): 저장소 전수 grep으로 단일 Redis를 전제한 서술 14곳을 찾아 모두 갱신했다.
- 검증(실행하지 않은 것): 두 인스턴스를 실제로 띄우지 않았다. 포트·메모리 상한·eviction·persistence 값은 전부 미정이며 84가 정한다. 백엔드의 두 연결 분리 구성도 미구현(237).
- 관련 문서: [EC2 서비스 진입·장애 경계](../../architecture/ec2-service-entry-failover.md) 1.1절, Jira `S15P21C206-82`·`-84`·`-237`
- 후속 작업: `S15P21C206-84` — 두 컨테이너 기동, 포트·메모리 상한·eviction·persistence 확정. `S15P21C206-237` — Spring Session 연결과 계산 캐시 연결을 따로 구성(Boot 기본은 단일 Redis 가정).
