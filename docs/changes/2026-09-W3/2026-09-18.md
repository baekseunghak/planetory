## [S15P21C206-82] Redis를 `redis-session`·`redis-cache` 두 인스턴스로 분리 — MR !55 리뷰 반영

- 수정자: 김동혁 (Claude 문서 반영 보조), 제안자 백승학
- 유형: 아키텍처 · 운영
- 상태: 채택 (D1 개정, 1.1절 신설. 구현은 `S15P21C206-84`·`-237`)
- 변경 범위: [EC2 서비스 진입·장애 경계](../../architecture/ec2-service-entry-failover.md) D1·D8·D10·1.1절·2·3·4·4.1·6·7절, [시스템 아키텍처](../../architecture/system-architecture.md) 2장, [서비스 백엔드 계약](../../development/service-backend/contracts-and-acceptance.md) SB-D07, [회원·인증](../../development/service-backend/account.md), [OAuth 설정](../../../apps/backend/docs/oauth-setup.md), [서비스 API 명세](../../../apps/backend/docs/service-api-spec.md), [CI/CD](../../operations/cicd.md)
- 목적: 계산 캐시의 eviction이 로그인 세션을 지우는 경로를 없앤다.
- 결정·근거: 백승학님 지적대로 `maxmemory`와 `maxmemory-policy`는 **인스턴스 단위 설정**이라 키 접두사나 논리 DB(`SELECT 0/1`)로는 메모리 예산과 eviction이 분리되지 않는다. 한 인스턴스에 두면 `allkeys-*`는 세션을 후보로 삼고 `volatile-*`도 세션이 30분 TTL(SB-D14)을 가져 그대로 후보다. 증상이 「로그인한 회원이 이유 없이 튀김」이라 재현도 진단도 어렵다.
- 추가로 확인한 이득: **분리가 D10의 대가를 일부 되돌린다.** 세션을 Redis로 옮기며 「Redis 장애 = 인증 전면 중단」을 수용했는데, 나누면 그 범위가 `redis-session` 장애로 좁아지고 **`redis-cache` 장애는 이관 전과 똑같이 온라인 계산만 멈춘다.** 4장 장애표의 Redis 행을 두 행으로 나눈 이유다.
- 정책 분리: `redis-session`은 30분 idle TTL·`noeviction`·persistence 필요, `redis-cache`는 결과 TTL·캐시 eviction 허용·persistence 불필요.
- 기각한 대안 3건을 표로 남겼다. 키 접두사 분리와 논리 DB 분리는 메모리·eviction을 나누지 못하고, 단일 인스턴스 `noeviction`은 세션은 지키지만 재계산하면 그만인 캐시 때문에 계산 쪽 쓰기를 실패시킨다.
- 비용: 인스턴스 하나 추가이고 EC2-A 안이라 작다. **다만 메모리 예산을 둘로 쪼개야 하고 한쪽 여유가 다른 쪽을 돕지 못한다.** 각 상한과 합계가 PostgreSQL을 OOM으로 밀어내지 않는지는 84가 확인한다. `noeviction`인 `redis-session`이 상한에 닿으면 새 로그인과 세션 연장이 실패하므로 세션 크기·동시 접속 추정이 상한 산정 입력이다.
- 검증(실행한 것): 저장소 전수 grep으로 단일 Redis를 전제한 서술 14곳을 찾아 모두 갱신했다.
- 검증(실행하지 않은 것): 두 인스턴스를 실제로 띄우지 않았다. 포트·메모리 상한·eviction·persistence 값은 전부 미정이며 84가 정한다. 백엔드의 두 연결 분리 구성도 미구현(237).
- 관련 문서: [EC2 서비스 진입·장애 경계](../../architecture/ec2-service-entry-failover.md) 1.1절, Jira `S15P21C206-82`·`-84`·`-237`
- 후속 작업: `S15P21C206-84` — 두 컨테이너 기동, 포트·메모리 상한·eviction·persistence 확정. `S15P21C206-237` — Spring Session 연결과 계산 캐시 연결을 따로 구성(Boot 기본은 단일 Redis 가정).

- 유형: 운영 · 오류 정정

- 검증: `validate.py`, Bash 구문, PowerShell parser, `test-yarn.ps1` 오프라인 모의, `git diff --check`가 통과했다. 변경된 Bash 전달 방식으로 실서버 `Preflight`와 `ValidateNodes`를 읽기 전용 실행해 ResourceManager 1개·NodeManager 5개 active, Worker 5대 `RUNNING`, 6개 노드의 광고 호스트 사설 IP 해석을 확인했다. Node 2의 `sudo -n journalctl -k` 접근과 현재 `nn1=active`, `nn2=standby`도 확인했다. 변경 XML 재설치와 Spark sample 재실행은 하지 않았다.

- 검증: Python 정적 검사, PowerShell parser, Bash 구문, 원격 변경 없는 회귀 검사와 `git diff --check`를 실행한다. 실환경 읽기 전용 검사에서 6개 노드 모두 `NTPSynchronized=yes`, `Timezone=Etc/UTC`이고 Node 2 kernel journal cursor를 비대화식으로 읽을 수 있음을 확인했다. 실서버 재설치와 Spark sample 재실행은 이 수정에서 수행하지 않는다.
- 관련 문서: [분산 시스템 운영 절차](../../../infra/distributed-system/README.md), [Jira S15P21C206-73](https://ssafy.atlassian.net/browse/S15P21C206-73)
