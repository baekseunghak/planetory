## [S15P21C206-78] needrestart 예외 설치·자동 업데이트 타이머 복구와 Node 5·6 CPU 플랫폼 교체

- 수정자: Claude
- 유형: 운영 변경
- 상태: 적용·검증 완료
- 변경 범위: 노드 6대 `/etc/needrestart/conf.d/50-planetory.conf`, `apt-daily-upgrade.timer`·`apt-daily.timer` 재시작, worker-5·6 VM 정지·시작(머신 타입 유지), [GCP 분산 인프라](../../architecture/gcp-distributed-infrastructure.md), [GCP 프로비저닝 안내](../../../infra/provisioning/gcp/README.md)
- 목적: 자동 보안 업데이트가 Hadoop 서비스를 재시작하지 않게 하면서 업데이트를 다시 켜고, 느린 Intel Broadwell 노드를 AMD 호스트로 옮긴다.
- 결정·근거: 전체 Silver run 종료 뒤 YARN 실행 앱 0개에서 6대에 예외를 설치하고(`NEEDRESTART_OVERRIDE_READY`) 타이머를 켰다. 타이머가 `Persistent=true`라 master-1·worker-2·4·6에서 밀린 업그레이드가 즉시 실행됐다(01:14~01:15 UTC, worker-4·6은 전날 장애를 일으킨 `curl`/`libcurl` 포함). e2는 CPU 플랫폼을 고를 수 없어 비용·할당량 변경이 없는 정지·시작 재시도를 택했고, 노드당 최대 5회·매 회 서비스와 HDFS 회복 확인을 조건으로 했다.
- 검증: 업그레이드 전후 Hadoop 관련 서비스 17개의 시작 시각이 같아 재시작 0건이었다. 다만 이번 업그레이드에서 needrestart는 `hadoop-*`를 재시작·미룸 대상으로 판단하지 않았다(클러스터가 비어 있어 옛 라이브러리를 쓰는 executor가 없었던 것으로 추정). 예외가 재시작을 막는 동작은 작업 중 업데이트에서 확인해야 한다. worker-5(02:15 UTC)·worker-6(02:57 UTC)은 각각 1회 만에 AMD Rome에 배치됐고 서비스 중단은 약 2~3분이었다. 두 노드 모두 내부 IP·`/mnt/data`·DataNode·NodeManager·YARN 메모리가 그대로이며 Live DataNode 5개, 복제 부족·누락 블록 0이다. `gcloud` 활성 계정은 6개 프로젝트 모두 `roles/owner`이고 N2D 할당량은 0005가 16, 0006이 8이다.
- 관련 문서: [GCP 분산 인프라](../../architecture/gcp-distributed-infrastructure.md), [인프라 안내](../../../infra/distributed-system/README.md), [78 인계](../../project/s15p21c206-78-handoff.md)
- 후속 작업: 작업 중 업데이트에서 `hadoop-*`가 deferred로 남는지 확인한다. 미뤄진 재시작 점검 주기를 정한다. VM 정지·시작 뒤에는 CPU 플랫폼을 다시 확인한다.
