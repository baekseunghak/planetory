- 결정·근거: (1) **인증 우회**는 필터가 `getRequestURI()`(디코딩 전)를 비교하고 인가·라우팅은 디코딩된 경로를 쓰는 차이에서 나왔다. `/%69nternal/…`이 토큰 없이 200·`applied=true`를 냈다. 인가 설정·CSRF 예외·토큰 검사가 **같은 `PathPatternRequestMatcher` 인스턴스 하나**를 쓰게 하고 문자열 비교를 없앴다. 경로 판별을 두 곳에서 각자 하면 그 차이가 그대로 우회 통로가 된다. (2) **교착**은 재개가 진행 행을 먼저 잠그고 알림 INSERT의 외래 키 검사로 회원 행을 뒤에 요구해, 제출의 `users → user_star_progress` 순서와 반대가 되어 생겼다. `apply()`가 회원 행부터 잠근다. `AchievementService`가 이미 경고해 둔 순서를 어긴 것이다. (3) **정리 범위**는 「현재 판 말고 전부」에서 **DB가 지목한 판만**으로 바꿨다. 현재 판 확인과 삭제 사이에 새 판이 current가 되면 그 판의 계산까지 지웠다. 정리는 늦어도 되지만 살아 있는 계산을 지우면 사용자가 기다리던 결과가 사라진다. (4) **표식 복원** — `confirmed → fp → confirmed`로 되돌아오면 현재 판정과 성과 유형이 같아져 UPDATE 대상에서 빠지고 옛 표식이 남았다. 표식은 「무엇이 바뀌었나」가 아니라 「지금 판정이 인정 당시와 다른가」이므로 UPDATE가 현재 판정에 맞춰 채우거나 비운다. (5) 김동혁 참고 의견에 따라 재개가 `completion_reason`을 비운다 — 진행 중 행에 완료 사유가 남으면 단계와 사유가 어긋난다. 표식 복원은 두 리뷰어 의견이 갈렸으나(김동혁 「지금 고칠 일 아님」, 백승학 수정 요청) 사용자 조회의 `newDisposition`에 옛 판정이 나가고 수정 비용이 SQL 한 문장이라 고치는 쪽을 택했다.
- 검증: Backend 전체 스위트 60개 클래스 667 passed·0 skipped·0 failures. 지적 4건을 **먼저 재현한 뒤** 고쳤다 — 인증 우회는 실제 HTTP 서버(RANDOM_PORT)로 200을 확인했고, 교착은 두 스레드로 PostgreSQL `deadlock detected`를 받았으며, 정리 범위는 현재 판 조회에 스파이를 걸어 전환을 끼워 넣었고, 표식은 판정 왕복으로 잔존을 확인했다. 넷 다 회귀 테스트로 남겼다. 실제 Publisher·운영 Redis 경로는 여전히 미검증이다.
