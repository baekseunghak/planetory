## [S15P21C206-262] 봉우리 power를 주기도와 같은 float32로 내보냄

- 수정자: 김동혁(Claude Code 보조)
- 유형: API
- 상태: 구현 완료
- 변경 범위: `CandidatePeaks.Peak.power`, `AnalysisViews.PeakView.power`(`double` → `float`), `CandidatePeaksTest`
- 목적: 봉우리 응답의 `peaks[].power`가 주기도 `power[gridIndex]`와 같은 JSON 숫자로 나가게 한다.
- 결정·근거: float32 값을 `doubleValue()`로 넓히면 `239.87599`가 `239.87599182128906`으로 나가고, 화면은 두 값을 상대 1e-9로 대조해 봉우리 전체를 `peak/grid mismatch`로 거절했다. 값은 같은 float32이고 **응답 숫자 표기만 바뀐다**(Gold 배열 계약 `array-f32le-null7fc00000-v0`의 DB REAL → float32 왕복과 맞춘다). API 필드·DB는 그대로다.
- 검증: `CandidatePeaksTest` 17/17(두 JSON 숫자 동일 회귀 포함), `AnalysisDataTest` 35/35. 목업 적재 격리 환경에서 실제 로그인으로 주기도·봉우리 10개 표시 확인.
- 관련 문서: [탐사 API](../../../apps/backend/docs/exploration-api-spec.md) 5.4절, MR !206(`c78f24ff`), 강재민 리뷰 승인
- 후속 작업: 없음

## [S15P21C206-262] 화면이 봉우리 추천값 null을 계약대로 받음

- 수정자: 김동혁(Claude Code 보조)
- 유형: API
- 상태: 구현 완료
- 변경 범위: `apps/frontend/src/features/analysis/periodogram-data.ts`, `phase-selection.ts`, 단위 테스트 2건
- 목적: API 5.4의 `suggestedDurationHours`·`suggestedPhaseCenter` null을 소비자가 받게 한다.
- 결정·근거: 2026-09-21 합의(141·128)로 두 값은 출처가 생길 때까지 항상 null인데, 화면 타입은 `number`만 받아 주기도가 열리지 않았다. **소비자 계약을 `number | null`로 바꾸고** null은 "모른다"로 받는다. 6.2에 따라 duration 상한만 생략하고 폭·source·fineTune 검사는 유지한다.
- 검증: `npm run typecheck` 통과, `npm test` 450/450. 격리 환경 화면에서 봉우리 선택 → 접힌 곡선 → 구간 선택 → 판단 → 제출 검토까지 동작. 브라우저 회귀(`tests/browser`)는 실행하지 않았다.
- 관련 문서: [탐사 API](../../../apps/backend/docs/exploration-api-spec.md) 5.4·6.2절, MR !206(`34d7d606`)
- 후속 작업: 255(백지웅)에서 가져갈지 이 MR에 둘지 확인

## [S15P21C206-262] 화면 검증에서 찾은 계약 불일치 2건 인계

- 수정자: 김동혁(Claude Code 보조)
- 유형: 데이터
- 상태: 제안
- 변경 범위: 기록만. 코드·스키마·fixture는 바꾸지 않았다.
- 목적: 262 범위 밖이라 고치지 않은 불일치를 담당자에게 넘기고 결정 대기로 남긴다.
- 결정·근거:
  - **봉우리 제출 500.** V4 `ck_submissions_source_peak_all_or_none`은 봉우리 제출에 제안 duration·상한을 NOT NULL로 요구하는데, 위 null 계약으로 봉우리 제출이 모두 INSERT에서 거절된다. 2026-09-21 변경 때 `SubmissionMatching.Peak`만 바뀌고 DB 제약이 남았다. 스키마·ERD 변경이라 강재민에게 인계했다.
  - **`manifest.period_grid` 키와 `periodogram_config_version` 형식.** DB 열(`period_min_days`·`period_max_days`·`n_periods`)은 모두 같다. 그러나 manifest 안의 키는 117 예제·로컬 시드(!201)·262 목업이 `period_*`·`n_periods`이고, Gold 계약 예제와 Worker 계약 3.3절은 `min_days`·`max_days`·`count`다. 버전은 예제 JSON이 `bls-log-v1`, 데이터 정본은 "형식 미정, 제안 `pg-log5000-v1`"이고, 123 제공 해상도 규칙과 125 Gold 직렬화 DB 재생은 계산 설정이 같은 `provided-bls-1.0.0`을 쓴다. 88 Worker가 버전 하나만 받으면 실제 파이프라인 판의 잔차 작업을 거절한다. 지금 Backend는 manifest에서 `spacing`만 읽어 깨지지 않지만 88 Worker 어댑터가 manifest를 그대로 넘기면 깨진다. 한 곳만 고치면 세 산출물이 갈라지므로 262 목업만 바꾸지 않는다.
- 검증: 격리 환경에서 봉우리 제출 500 재현(DB 로그의 제약 위반), 키·버전은 계약·예제·코드 대조
- 관련 문서: [문서 정합화 요청](../../project/planetory-doc-sync-requests.md#s15p21c206-262-목업-화면-검증의-계약-불일치-2026-09-25), [Gold 계약](../../../contracts/gold/README.md), [파생 계산 내부 계약](../../../contracts/derived-compute/README.md) 3.3절, MR !206
- 후속 작업: 제출 제약 신규 migration(강재민), 격자 키·버전 확정(Gold 계약 113·117 담당 윤성용) 뒤 세 산출물 일괄 정렬, 88 어댑터 매핑
