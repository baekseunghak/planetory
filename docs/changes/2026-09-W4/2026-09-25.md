## S15P21C206-88 — Backend 잔차 실행기 연결

- 수정자: 김동혁 (Claude 보조)
- 유형: API
- 상태: 구현 완료
- 변경 범위: `WorkerResidualComputeRunner`, `application.properties`의 `planetory.residual.worker-url`·`operation-timeout-seconds`, compose backend `DERIVED_COMPUTE_URL`, 탐사 API 7.1·7.2·7.3절
- 목적: 잔차 요청이 실제 Worker 계산으로 이어지게 한다.
- 결정·근거: 주소가 있을 때만 실행기를 띄워 미연결 503 동작을 유지한다. 채택 전과 단계 사이마다 판이 current인지 다시 보고, 아니면 `BUNDLE_ARCHIVED`로 끝낸다. 자동 재시도는 하지 않는다. 실패는 `retryable`로 끝내고 재시도는 7.1절 재요청(새 작업)이므로 attempt 증가 함수는 88에 필요 없다. 한 작업 안의 재계산은 90이 맡는다. flux는 float32 값을 그대로 보내려고 double로 직렬화한다. Backend 동시 계산 수는 compose에서 Worker 용량(1대 × 1)과 같은 1로 둔다. 기본값 2로 두면 두 번째 동시 작업이 대기 없이 Worker 503으로 실패한다. 응답 값은 숫자인지 확인하고, 예상하지 못한 실패도 그 단계(잔차·주기도)로 기록한다. Worker `runtime`은 Backend 저장 결과(`ResidualJobStore.Result`)에 넣지 않고 로그에만 남긴다. 화면이 쓰지 않고, 131 인계는 Worker 캡처가 요청·응답 전체를 담기 때문이다.
- 검증: 새 테스트 11개(가짜 Worker: 성공·Worker 거절·503·시간 초과·주기도 실패·숫자 아닌 결과·읽을 수 없는 주기도 응답·attempt 불일치·계산 중 판 교체·사라진 후보·없는 판)와 기존 `ResidualJobTest` 18개·`ResidualJobUnavailableTest` 2개 통과. 테스트가 조립한 실제 요청을 Worker 컨테이너에 보내 residual `ok=true`를, periodogram은 검증을 통과한 뒤 BLS 최소 점 수에서만 거절되는 것을 확인했다. JDK `HttpClient`로 Worker 컨테이너를 불러 HTTP/1.1 200 3회를 확인했다. Backend 전체(`SourceCardTest` 제외 724개)는 4개 실패인데 모두 이 변경과 무관하다. `GoldCatalogSchemaTest`·`StatisticsCommandTest`·`StatisticsMigrationTest`는 `origin/develop`(`2ff9476f`)에서도 같은 메시지로 실패하고, `PlanetoryApplicationCommandModeTest`는 한글이 든 작업 경로에서만 실패한다(ASCII 경로에서 통과). `SourceCardTest`는 develop에서도 `SourceCardTest.java:348`의 executor `close()`에서 무기한 멈춘다. 실제 Gold·EC2 경로는 실행하지 않았다.
- 관련 문서: [탐사 API](../../../apps/backend/docs/exploration-api-spec.md), [온라인 파생 계산](../../architecture/online-derived-compute.md), [infra/service](../../../infra/service/README.md)
- 후속 작업: EC2-A 배포(Worker → `DERIVED_COMPUTE_URL` → Backend 순서), 목업 판으로 종단 확인, 프론트 문서의 「88 전 503까지만」 문구 정리(프론트 담당), 131 인계.
