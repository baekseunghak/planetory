## [S15P21C206-78] 재기동 전 실패 attempt staging 정리와 코드 결함 예외 분류

- 수정자: Claude
- 유형: 운영 안정성·오류 정정
- 상태: 구현·로컬 검증 완료, 실클러스터 Canary 재실행 전
- 변경 범위: `distributed-system/spark/tess_silver_ctl.py`(`discard_failed_attempt`), `tess_silver.py`(`process_tic` 예외 분류), 회귀 검사, Spark README, 78 인계
- 목적: 며칠짜리 전체 run이 중간에 실패해 재기동될 때 디스크가 쌓여 멈추지 않게 하고, 코드 결함이 입력 오류로 보이지 않게 한다.
- 결정·근거: 전체 run은 결과를 끝에 한 번에 확정하고 `maxAppAttempts=1`이며 systemd가 5분 뒤 새 attempt로 재기동한다. 실패한 attempt의 부분 출력이 남아 반복 실패 시 HDFS 75% 점검에서 멈췄다. 처음부터 다시 도는 비용은 감수하고, 재기동 전 자기 attempt staging만 지운다. YARN CLI의 일시적 `UNKNOWN`에서 살아 있는 앱의 출력을 지우지 않도록 앱이 종료 상태일 때만 지운다. 계약 실패(exit 65)는 재기동하지 않으므로 진단용 staging을 남긴다. TIC 묶음별 확정은 후속 소비 계약이 바뀌어 택하지 않았다. 2026-09-23 Canary 1 첫 실행의 NaN 직렬화 결함이 `invalid_bronze_row`로 보였으므로, Bronze 행 읽기 이후의 코드 결함은 `unexpected_processing_error`(retryable)로 분리했다.
- 검증: `pytest -q libs/astro-kernel/tests distributed-system/spark` 353 passed·14 subtests, Airflow 계약 테스트·설치 전 계약 검사 통과. 새 검사는 앱 상태 RUNNING·UNKNOWN에서 정리 생략, FAILED·KILLED에서 정리, 예상 밖 경로 거부, 재기동 가능한 실패만 정리하고 계약 실패는 보존함을 확인한다.
- 관련 문서: [Spark 계약](../../../distributed-system/spark/README.md), [78 인계](../../project/s15p21c206-78-handoff.md)
- 후속 작업: 수정 release로 Canary 1·2를 다시 실행한 뒤 전체 run 여부를 결정한다.

- 검증: `pytest -q libs/astro-kernel/tests distributed-system/spark` 355 passed·19 subtests, Airflow 계약 테스트 통과. 새 검사는 spark-submit 명령의 executor 설정과, `run()`에서 `results.count()`가 첫 `coalesce`보다 앞에 있는지 확인한다.
- 관련 문서: [Spark 계약](../../../distributed-system/spark/README.md), [78 인계](../../project/s15p21c206-78-handoff.md)

## [S15P21C206-78] YARN vcore 상한에 맞춘 executor 재구성과 실패 attempt 정리 실측

- 수정자: Claude
- 유형: 오류 정정·운영 검증
- 상태: 수정·로컬 검증 완료, 실클러스터 Canary 재실행 전
- 변경 범위: `distributed-system/spark/tess_silver_ctl.py`(executor 설정), 회귀 검사, Spark README, 78 인계
- 목적: 처리량 보강 release의 Canary가 YARN에서 거부된 원인을 고친다.
- 결정·근거: executor 5개 × core 4개 요청을 YARN이 `InvalidResourceRequestException`(요청 vCores 4, 최대 3)으로 거부했다(`application_1790067725443_0062`). YARN이 `DefaultResourceCalculator`로 메모리만 보고 배치하더라도 컨테이너당 `maximum-allocation-vcores`는 따로 검사한다. 앞서 vcore가 제약이 아니라고 판단한 것은 틀렸다. 클러스터 설정을 바꾸지 않고 executor를 10개 × core 2개(검증된 memory 6g + overhead 2g)로 늘려 동시 20작업을 유지한다. 8 GiB executor 2개는 가장 작은 16 GiB NodeManager에도 들어가고, driver를 합쳐 83 GiB다.
- 검증: 이 실패에서 재기동 전 staging 정리가 실클러스터에서 처음 동작했다. 제어기가 `SILVER_FAILED_ATTEMPT_DISCARDED`를 남기고 상태 파일에 `status=failed`·`staging_discarded=true`를 기록했으며, 검증 staging과 Spark staging이 모두 0개였다. 수정 뒤 회귀 검사는 executor 설정과 core ≤ 3을 확인한다.
- 관련 문서: [Spark 계약](../../../distributed-system/spark/README.md), [78 인계](../../project/s15p21c206-78-handoff.md)
- 후속 작업: 수정 release로 Canary를 다시 실행해 executor 10개 기동과 과학 결과 동일성을 확인한다.
