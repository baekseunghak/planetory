## [S15P21C206-226] 배포 접속을 SSH 키 없이 tailnet 신원으로 한다

- 수정자: 김동혁, Claude
- 유형: 아키텍처
- 상태: 검증 완료(실측)
- 변경 범위: `.gitlab/ci/common.yml`, `infra/provisioning/provision-deploy-user.sh`, `docs/operations/cicd.md`
- 목적: deploy job이 대상 노드에 접속할 수 있게 한다.
- 결정·근거: 대상 노드가 `tailscale up --ssh` 상태라 **tailscaled가 22번을 직접 처리한다.** `authorized_keys`를 설치해도 쓰이지 않고 tailnet 신원으로 인증하므로, SSH 키를 배포하는 설계 자체가 성립하지 않았다. 키페어를 만들어 7개 호스트에 넣어 봤으나 `tailnet policy does not permit you to SSH to this node`로 거부됐고, 이는 키 문제가 아니라 ACL 문제였다. ACL에 `tag:hadoop → tag:hadoop`의 `deploy` 계정 ssh 규칙을 더하자 즉시 통과했다. 그래서 키를 폐기하고 `.remote-compose-deploy`의 키 처리 6줄과 File 타입 변수 두 개(`DEPLOY_SSH_KEY`·`DEPLOY_KNOWN_HOSTS`)를 없앴다. 관리·회수할 키가 사라지고, 접근 차단은 ACL 한 줄 삭제로 끝난다. 접속 계정은 사람의 관리 계정 대신 CI 전용 `deploy`를 쓴다. `sudo`는 주지 않는다. `docker` 그룹이 이미 root에 준하므로 그 위에 더 얹지 않는다.
- 검증: 7개 호스트(EC2-A, GCP Node 1~6) 전부에서 job 컨테이너와 같은 조건으로 SSH·`mkdir`·`docker compose version`·`docker pull`이 통과했다. `authorized_keys`를 삭제한 뒤 다시 확인해 키가 실제로 쓰이지 않음을 확정했다. 대체 안이던 2222번 별도 sshd는 채택하지 않았다.
- 관련 문서: [CI/CD](../../operations/cicd.md)
- 후속 작업: `DEPLOY_HOST`에는 MagicDNS 이름이 아니라 Tailscale IP를 넣어야 한다. 컨테이너 안에서 MagicDNS가 해석되지 않는다. GitLab CI/CD 변수 15개(`DEPLOY_USER`, `EC2_A_HOST`·`EC2_A_DEPLOY_PATH`, `GCP_NODE_1~6_HOST`·`GCP_NODE_1~6_DEPLOY_PATH`) 등록이 남았다.

  1. **GC 중 push 가능.** `docker exec -e`의 환경변수는 exec한 프로세스에만 붙고 이미 떠 있는 레지스트리 서버는 그대로 쓰기를 받는다. 수집 도중 올라온 블롭이 회수돼 이미지가 깨질 수 있었다. 컨테이너를 정지한 뒤 일회용 컨테이너로 스토리지를 청소하고 다시 띄우도록 바꿨다. 수집이 실패해도 레지스트리는 반드시 되살린다.
  2. **삭제된 레이어의 비밀 누락.** `docker export`는 평탄화된 최종 파일시스템만 준다. `docker save` 기반 레이어별 검사로 바꿨다. 문서가 보장한다고 적어 둔 동작을 실제로는 하지 않고 있었다.
  3. **생성 시각 실패 시 최신 삭제.** schema1(`v1+prettyjws`)에서 시각을 읽었는데 `registry:3`은 OCI 매니페스트를 써서 **항상 404**였다. 엣지 케이스가 아니라 상시 경로였고, 보존 대상이 생성순이 아니라 태그 문자열 역순으로 정해졌다. 시각을 이미지 config 블롭에서 읽도록 바꾸고, 하나라도 읽지 못하면 그 저장소의 삭제를 건너뛴다. JSON은 `python3`로 파싱한다. 무엇을 지울지 정하는 입력이라 sed·grep 파싱이 어긋나면 곧바로 잘못된 삭제가 된다.
  4. **`set -e`로 인증서 알림 침묵.** 실패한 `tailscale cert`가 `_ok=$?`에 닿기 전에 스크립트를 끝내, 갱신 실패를 알리려고 만든 점검이 갱신 실패 때문에 침묵했다. `if`로 감쌌다.
- 검증: 4번은 수정 전 코드에서 새 테스트가 실패(exit 1, 알림 0건)하고 수정 후 통과하는 것을 확인했다. 2번은 `COPY .env` 후 `RUN rm`한 이미지로 회귀 항목을 추가했고 수정 전 "발견 없음"이던 것이 탐지로 바뀌었다. 실제 이미지 4종은 여전히 발견 0건이라 오탐이 늘지 않았다. 3번은 **태그 사전순과 생성순을 반대로** 만들어 `--keep 4 --apply`로 시험했고 가장 오래된 태그만 지워지고 최신 태그가 남는 것을 확인했다. 1번은 정지 기반 GC로 실제 수집과 재기동(`GET /v2/` 200)을 확인했다.
- 관련 문서: [EC2-B 설정](../../../infra/service/ec2-b/README.md), [CI/CD](../../operations/cicd.md)
- 후속 작업: **재발 방지가 핵심이다.** 3번과 4번은 초판 테스트가 하필 깨진 경로를 스텁으로 우회해 통과했다. 4번은 실제 명령을 실행하지 않고 결과만 흉내냈고, 3번은 테스트 태그의 사전순이 생성순과 우연히 일치해 망가진 정렬이 정답을 냈다. 앞으로 외부 명령·외부 응답에 의존하는 경로는 **결과를 흉내내지 말고 실제로 실패하는 명령과 순서가 어긋나는 데이터**로 시험한다.
