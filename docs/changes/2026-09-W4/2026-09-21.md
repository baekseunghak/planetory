- 검증: 제출 조회 20개와 백엔드 전체 453개 통과, 실패·오류·건너뜀 0. AT-118 예제를 그대로 재현했다(기준 시각 100 → 101에서 0.20~0.30이 0.95~1.05로 복원). 힌트 규칙은 누적 매칭을 빼도록 바꿔 보니 해당 검사만 정확히 실패했다. 초안 조회가 제출·성과·기록 행을 늘리지 않는 것도 확인했다.
- 관련 문서: [탐사 API 6.6·6.7·6.8절](../../../apps/backend/docs/exploration-api-spec.md#66-조회와-요청-id-복구), [Jira](https://ssafy.atlassian.net/browse/S15P21C206-145)
- 후속 작업: **`signal.explanation`의 출처가 없다.** 명세 6.7절 예시에는 문장이 있는데 저장할 열도 생성 규칙도 없어 `bls.sde`·`bls.snr`과 같은 이유로 null로 두었다. 후보표 열인지 운영 규칙인지 AI 평가인지 정해야 한다. 티켓의 차단 조건이던 「은퇴 제거 조합 처리」는 명세의 C02-R1 결정으로 이미 풀려 있어 그대로 구현했다. 실제 프론트 연동은 별도다.

## [S15P21C206-145] 제출 조회 리뷰 반영: 해설 자리와 힌트 대상 고정

- 수정자: 강재민 (Claude 보조)
- 유형: 오류 정정 · DB 스키마
- 상태: 검증 완료
- 변경 범위: 상세 보기 응답의 `signal.explanation`, 힌트 대상 보존 열(V16), 제출 조회 테스트, 탐사 API 6.7절
- 목적: MR !125 리뷰(백지웅)가 짚은 병합 전 수정 2건을 반영한다.
- 결정·근거: **`signal`에 `explanation` 키를 남긴다.** 값은 여전히 null이지만 키가 아예 없어 프론트 파서가 응답을 거절했다. 「해설 없음」과 「모르는 응답」은 다르다. 이 자리는 6.7절에만 있고 6.4절 `signal` 블록에는 없으므로 공용 빌더를 넓히지 않고 6.7 응답에서만 더한다. 출처를 지어내지 않는다는 판단은 그대로다.
- 결정·근거: **처음 고른 힌트 대상을 제출에 남긴다.** 매 호출마다 현재 후보에서 최대 세기를 다시 고르고 있어, 후보표가 갱신되면 같은 제출의 답이 바뀌었다. 명세 6.7절의 「반복 호출은 같은 대상」과 어긋난다. `submissions.detail_target_candidate_id`(V16)에 최초 선택을 남기고 `COALESCE`로 덮어쓰지 않는다. 한 번 보여 준 신호는 뒤에 은퇴해도 그대로 보여 준다 — 상태로 다시 거르면 같은 증상이 은퇴 경로로 돌아온다.
- 검증: 제출 조회 23개(20 + 신규 3)와 백엔드 전체 456개 통과, 실패·오류·건너뜀 0. 두 수정을 되돌리면 해당 검사 3개가 정확히 실패한다 — 해설 키 누락, 세기를 올린 뒤 대상이 바뀜, 은퇴 뒤 대상이 사라짐.
- 관련 문서: [탐사 API 6.7절](../../../apps/backend/docs/exploration-api-spec.md#67-상세-보기), [MR !125](https://lab.ssafy.com/s15-bigdata-dist-sub1/S15P21C206/-/merge_requests/125), [Jira](https://ssafy.atlassian.net/browse/S15P21C206-145)
- 후속 작업: V16이 develop 최신 번호와 겹치지 않는지 병합 직전에 다시 확인한다. `signal.explanation`의 출처는 여전히 미정이며, 프론트가 이 필드를 nullable로 받고 대체 안내를 두는 것은 소비자 쪽 작업이다.
