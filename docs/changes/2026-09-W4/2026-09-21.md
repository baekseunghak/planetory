## [S15P21C206-226] CI 레지스트리 자체 호스팅과 amd64 빌드 노드 분리

- 수정자: 김동혁, Claude
- 유형: 운영
- 상태: 구현 완료(레지스트리·빌드 노드), Runner 등록과 배포 노드는 미완
- 변경 범위: `.gitlab/ci/common.yml`, `docs/operations/cicd.md`, `docs/operations/docker.md`, 빌드 노드의 레지스트리·Runner 컨테이너
- 목적: `docker login` 실패로 CI 도입 이후 한 번도 통과하지 못한 build 스테이지를 되살린다.
- 결정·근거 보강: `docker buildx`를 쓰지 않고 `docker build`+`docker push`로 되돌렸다. buildx의 container driver는 dind 안에 buildkit 컨테이너를 따로 띄우고 push를 그 컨테이너가 수행하는데, Runner의 `extra_hosts`가 거기까지 닿지 않아 레지스트리 이름 해석에 실패한다. 빌드는 성공하고 push만 실패해 원인을 찾기 어려운 형태다. 실측으로 확인했고, 빌드 Runner가 x86_64라 교차 빌드가 필요 없어 buildx를 유지할 이유도 없다.
- 결정·근거: 티켓의 GHCR 공개 패키지 안을 폐기하고 자체 레지스트리를 쓴다. 전 노드가 같은 tailnet에 있어 `tailscale cert` 정식 인증서로 HTTPS를 서빙하면 배포 노드에 `insecure-registries`도 자격 증명도 배포할 필요가 없다. 기존 CI 노드는 aarch64라 amd64 이미지를 qemu로 에뮬레이션해야 했는데, 놀고 있는 x86_64 노드를 빌드 Runner로 세워 에뮬레이션 자체를 없앴다. 그 결과 `.docker-build`에서 `tonistiigi/binfmt` 설치와 amd64 확인 두 줄을 걷어냈고, 대신 `tags: [amd64-docker]`로 빌드 job을 x86_64 Runner에 고정했다. 레지스트리는 빌더와 같은 노드에 둬서 push가 tailnet을 타지 않는다.
- 검증: 레지스트리 `GET /v2/` 200, `ec2-a`·`node-1`·`node-3` 인증서 검증 통과, push 후 `ec2-a` pull 성공. 빌드 Runner에서 privileged dind가 뜨고 `docker info`가 `x86_64`를 보고하는 것을 확인했다. build job을 CI와 같은 dind 경로로 재현해 frontend(19초)·backend(75초)를 실제로 빌드·push했고 frontend 이미지가 `linux/amd64`임을 확인했다. GitLab 파이프라인 자체는 Runner 태그 미지정으로 아직 실행하지 않았다.
- 관련 문서: [CI/CD](../../operations/cicd.md), [Docker 개발·배포 기준](../../operations/docker.md), [S15P21C206-226](https://ssafy.atlassian.net/browse/S15P21C206-226)
- 후속 작업: `REGISTRY_IMAGE_PREFIX` 변수는 등록 완료. 빌드 Runner는 등록됐고 privileged·`extra_hosts`·`/certs/client`를 설정했으나 GitLab UI에서 `amd64-docker` 태그 지정과 untagged 미수행 설정이 남았다. `node-2`~`node-6` Docker 미설치, `node-1` 배포 계정의 docker 권한 없음 — deploy job 실행 전 해소 필요. `build:spark`는 `distributed-system/spark/requirements.txt`가 없어 `rules:exists`에 걸려 한 번도 실행되지 않았다. 인증서 재발급과 SHA 태그 정리 정책도 미정.

## [S15P21C206-226] D4 범위 한정과 외부 관찰 EC2-B 이관

- 수정자: 김동혁, Claude
- 유형: 아키텍처
- 상태: 채택
- 변경 범위: `docs/architecture/ec2-service-entry-failover.md`, `docs/architecture/system-architecture.md`, `docs/operations/tailscale-team-access.md`
- 목적: EC2-B를 CI 빌드 노드로 쓰기로 한 결정과 확정 정본의 "EC2-B는 사용하지 않는다"를 정합화하고, 별도 CI 노드를 프로젝트 구성에서 제거하면서 그 노드가 맡던 외부 관찰을 EC2-B로 옮긴다.
- 결정·근거: D4를 폐기하지 않고 **범위를 한정**했다. D4가 막으려던 것은 앱·복제·백업과 서비스 관측 스택을 두 노드에 벌려 노드 로컬 상태 판정을 모든 개발에 부과하는 일이다. 사용자 요청 경로 밖의 CI 빌드·레지스트리와 **알림 전용** 외부 관찰은 그 부담을 만들지 않으므로 허용한다. 「CI 노드를 헬스체크로 쓰지 않는다」 기각은 **전환 판정** 용도에 대한 것이며, 사람에게 알리기만 하는 관찰은 판정이 아니라 해당하지 않는다. 이 구분을 기각 항목 본문에 명시했다. 별도 CI 노드는 프로젝트에서 제거하고 인계 100은 EC2-B로 재배정했다.
- 검증: 활성 문서에서 구 CI 노드 참조가 0건인지 확인했다. 두 EC2의 가용 영역을 인스턴스 메타데이터로 조회해 **둘 다 `ap-northeast-2a`**임을 실측했다. 상대 링크 경로를 확인했다.
- 관련 문서: [EC2 서비스 진입·장애 전환 경계](../../architecture/ec2-service-entry-failover.md), [시스템 아키텍처](../../architecture/system-architecture.md), [Tailscale 팀 서버 접근](../../operations/tailscale-team-access.md)
- 후속 작업: **수용한 축소 — 관찰 범위가 좁아졌다.** 폐기한 노드는 다른 리전이라 리전 장애를 덮었으나, EC2-B는 EC2-A와 같은 AZ라 인스턴스·앱·터널 장애만 덮는다. 가용 영역·리전 단위 장애는 관찰자도 함께 죽어 감지하지 못한다. PoC 기간에는 인스턴스·앱 장애가 훨씬 잦아 수용하며, 리전까지 덮으려면 EC2 밖의 수단이 필요하다. 관찰 구현 자체는 아직 없다(폴링 주기·알림 채널·판정 기준 미정, 인계 100). 구 CI 노드의 GitLab Runner 등록 해제도 남았다.
