## [S15P21C206-249] 잔차 503의 원인 구분과 미연결 안내 문구

- 수정자: 강재민 (Claude 보조)
- 유형: API · 오류 정정
- 상태: 구현 완료 (화면 분기 반영은 S15P21C206-88 연동 때 백지웅과 함께)
- 변경 범위: `ResidualJobService`, 잔차 작업 테스트 3종, 탐사 API 2.3·7.1·7.2절
- 목적: 잔차 요청의 503 `DEPENDENCY_UNAVAILABLE`이 서로 다른 두 원인을 한 코드·한 문구로 덮어, 화면이 다시 시도해도 되는지 판단할 수 없던 것을 고친다.
- 결정·근거: 503 본문에 `retryable`을 더해 계산 기반 미연결은 false, 실행기 시작 실패는 true로 답한다. 오류 본문에 코드별 추가 필드를 싣는 방식은 `BUNDLE_CHANGED`의 `currentBundleId`·`RESIDUAL_QUEUE_FULL`의 `retryAfterSeconds`와 같고, 뜻은 7.2절 `failure.retryable`과 같아 화면이 규칙 하나로 읽는다. 값이 없는 503은 참으로 읽는다 — 모르는 것 때문에 나갈 길을 막지 않는다. 미연결 문구는 기본 문구("잠시 후 다시 시도해 주세요") 대신 재시도를 권하지 않는 문장으로 바꿨다. 화면(S15P21C206-189, MR !122)이 이 거절에 재시도 버튼을 주지 않아 문구와 화면이 어긋나 있었다. 어떤 기반이 없는지는 내부 사정이라 여전히 적지 않는다.
- 검증: 백엔드 전체 테스트 438건 통과. 잔차 관련 25건이 미연결 거절의 `retryable: false`와 재시도를 권하지 않는 문구, 시작 실패의 `retryable: true`와 `START_FAILED` 작업 종료, 503 응답 본문에 추가 필드가 실리는 HTTP 표현을 본다. 결함 주입 3건(미연결 본문에서 `retryable` 제거, 미연결 문구를 기본 문구로 되돌림, 시작 실패 본문에서 `retryable` 제거)을 모두 검출했다. 변경 문서 상대 링크와 `git diff --check`를 확인했다.
- 관련 문서: [탐사 API 명세](../../../apps/backend/docs/exploration-api-spec.md) 2.3·7.1·7.2절, Jira `S15P21C206-249`
- 후속 작업: 화면은 이 신호가 붙은 뒤 503 분기를 `retryable` 기준으로 바꾼다(백지웅, S15P21C206-88 연동 시점). 88이 붙으면 미연결 경로 자체가 사라지고 남는 503은 대체로 일시적이다.

## [S15P21C206-249] 잔차 503 리뷰 반영: 문구 정본과 분기 시점

- 수정자: 강재민 (Claude 보조)
- 유형: API 문서
- 상태: 검증 완료
- 변경 범위: 탐사 API 2.3·7.1절
- 목적: MR !128 리뷰(백지웅)의 요청 두 건과 반대 의견 한 건을 반영한다. 코드 동작은 바꾸지 않는다.
- 결정·근거: **문구를 명세에 문자열 그대로 적는다.** 프론트 개발용 응답이 서버 문구를 복제하고 화면 검사가 그 상수와 비교하므로, 서버만 바꾸면 검사는 통과하면서 화면은 낡은 문구를 보여 준다. 양쪽이 가리킬 단일 출처가 없던 것이 원인이라 7.1절에 두 문장을 그대로 적었다.
- 결정·근거: **화면 분기를 88이 아니라 필드가 생긴 시점에 맞춘다.** 제가 88 연동 때 함께 바꾸자고 제안했으나 리뷰가 반대했고 그쪽이 맞다. 88이 붙으면 미연결 경로가 사라지므로, 그때 맞추기로 하면 재시도해야 할 503이 전부 「준비되지 않았습니다 + 버튼 없음」으로 그려진다. 지금 바꿔도 오는 값이 전부 `false`라 동작 차이가 없다. 값이 없는 503을 참으로 읽기로 했으므로 **배포는 서버가 먼저**이며 그 순서를 7.1절에 적었다.
- 결정·근거: `retryable`이 7.2절 `failure.retryable`과 오류 본문 최상위 두 자리에 있는 이유를 2.3절에 적었다. 합치면 작업 없는 거절에 빈 `failure`를 만들거나 작업 실패의 `stage`·`code`를 최상위로 끌어올려야 한다. 나중에 누가 「통일」하다 한쪽을 놓치는 것을 막는다.
- 검증: 문서만 바뀌어 동작 검증을 다시 하지 않았다. 앞선 커밋의 백엔드 검사가 이미 두 문구와 `retryable` 값을 고정하고 있으며, 7.1절에 적은 문자열이 `ResidualJobControllerTest`·`ErrorCode`의 값과 같은지 대조했다.
- 관련 문서: [탐사 API 2.3·7.1절](../../../apps/backend/docs/exploration-api-spec.md#71-계산-요청), [MR !128](https://lab.ssafy.com/s15-bigdata-dist-sub1/S15P21C206/-/merge_requests/128), [Jira](https://ssafy.atlassian.net/browse/S15P21C206-249)
- 후속 작업: 프론트가 상수를 새 문구로 맞추고 분기를 `retryable`로 바꾼다(`S15P21C206-189`). 88이 붙은 뒤 실행기 시작 실패가 실제로 어떤 예외로 오는지 보고 `failure.code`를 나눌지 정한다.

## [S15P21C206-189] 화면이 503을 retryable로 가르고 정본 문구를 비춘다

- 수정자: 백지웅 (Claude 보조)
- 유형: 오류 정정
- 상태: 구현 완료 · **실제 잔차 API 인수 대기**
- 변경 범위: [곡선 단계 전환 개발 안내](../../../apps/frontend/docs/analysis-curve-step.md), 단계 이동 상태, 개발용 잔차 응답, 화면 회귀.
- 발견(검사 도구): **개발용 응답이 모든 실패의 `message`를 코드 이름으로 채우고 있었다.** 화면은 503 `message`를 사용자에게 그대로 보여 주는데, 검사는 「DEPENDENCY_UNAVAILABLE 보고 있던 곡선은 그대로입니다」를 보고 통과했다. 그래서 **재시도 버튼을 숨겨 놓고 문구로는 다시 시도하라고 말하는 상태**를 아무도 보지 못했다(`S15P21C206-147` 리뷰에서 드러남).
- 결정·근거: 개발용 응답이 **정본 문구를 비춘다.** 명세 7.1절이 두 문장을 그대로 적고 정본임을 선언했으므로(`S15P21C206-249`), 백엔드 검사와 개발용 응답이 같은 값을 든다. 화면 검사는 특정 문구를 박지 않고 그 상수가 **그대로 나오는지**만 본다 — 서버 문구가 바뀌어도 검사가 거짓으로 깨지지 않는다. **문구를 주지 않은 실패는 코드 이름을 그대로 둔다**: 화면이 옮겨 보여 주는 자리에만 실제 문장이 필요하고, 나머지는 개발용임이 드러나는 편이 낫다.
- 결정·근거: **503을 원인이 아니라 서버가 준 `retryable`로 가른다.** 같은 코드가 화면의 할 일이 반대인 두 경우를 덮는다 — 미연결은 다시 요청해도 같은 결과이고, 실행기 시작 실패는 다시 요청하는 것이 맞다. 값이 없으면 참으로 읽는다(7.2절 `failure.retryable`과 같은 규칙).
- 결정·근거: **`S15P21C206-88`을 기다리지 않는다.** 88이 붙으면 미연결 경로가 사라지므로 그때 맞추기로 하면 재시도해야 할 503이 전부 「준비되지 않았습니다」로 그려진다. 방향만 바꾼 같은 어긋남이고, 코드에 방아쇠가 없는 약속이라 잊으면 조용히 남는다. 249 리뷰에서 이 의견을 냈고 명세 7.1절에 시점이 적혔다.
- 결정·근거: **문구를 덧붙이지 않는다.** 일반 실패 경로는 뒤에 「잠시 후 다시 시도해 주세요.」를 붙이는데 시작 실패 503의 서버 문구가 이미 그 문장으로 끝난다.
- 발견(검사 도구): **기본값을 지키는 검사가 없었다.** 「값이 없으면 참」은 내가 직접 조건으로 단 규칙인데, 개발용 503 둘이 모두 `retryable`을 싣고 있어 **필드가 없는 503을 그리는 경로가 검사에 한 번도 오지 않았다.** 기본값을 `=== true`로 뒤집어도 전부 통과한다(리뷰에서 지적됨). 249 전의 서버를 흉내 내는 `unavailable-legacy` 시나리오와 그때 [다시 시도]가 뜨는지 보는 검사를 더했다 — 배포 순서의 창에서 실제로 걸리는 칸이다.
- 검증: 타입 검사·운영 빌드 통과, 단위 344개, Chrome 회귀 201개 통과(GPU 3건 건너뜀). **되돌려 깨지는 것까지 확인했다** — 개발용 응답을 코드 이름으로 되돌리면 문구 검사가, 분기를 없애면 재시도 버튼 검사가, 문구를 덧붙이면 중복 검사가, 기본값을 `=== true`로 뒤집으면 필드 없는 503 검사가 각각 깨진다.
- 관련 문서: [탐사 API 7.1절](../../../apps/backend/docs/exploration-api-spec.md), [곡선 단계 전환 개발 안내](../../../apps/frontend/docs/analysis-curve-step.md), Jira `S15P21C206-189`·`S15P21C206-249`.
- 후속 작업: 시작 실패 503의 종단 확인은 `S15P21C206-88` 뒤다. 그전까지 실제 API로는 미연결 503만 볼 수 있다. 서버 문구가 바뀌면 명세의 정본 줄과 백엔드·개발용 응답을 한 번에 바꾼다.

- 결정·근거: **최소 간격 = `2h+1`칸** (h는 판 manifest `fine_tune.half_width_cells`). 미세 조정 범위가 겹치는 두 봉우리는 사용자에게 같은 선택이다 — 어느 쪽을 골라도 같은 주기로 맞출 수 있어 목록에서 자리만 차지한다. 새 설정을 만들지 않고 이미 정해진 h에서 유도한다.
- 결정·근거: **고조파 제외는 `matching.harmonic_multipliers`를 그대로 쓰고 허용 오차는 `h`칸이다.** 제출이 「2배 맞음」이라 판정하는 배수와 목록이 거르는 배수가 다르면 화면과 채점이 어긋난다. 오차를 겹침 기준(`2h+1`)으로 두었더니 배수 자리에서 한참 떨어진 봉우리까지 고조파로 몰려 목록이 비어 갔다(첫 구현에서 시험이 잡았다). 「그 봉우리를 조정해 정확히 그 배수에 닿을 수 있는가」가 기준이므로 `h`가 맞다.
- 결정·근거: **`peakRuleVersion`은 운영 규칙 버전이다.** 봉우리를 정하는 두 값이 운영 규칙에서 오고 h는 판에서 오는데 판은 이미 `curveContext.bundleId`에 있다. 둘이 같으면 결과가 같으므로 `peak-N`을 새로 만들지 않는다.
- 결정·근거: **`suggestedDurationHours`·`suggestedPhaseCenter`는 null로 답한다.** `periodograms`는 주기별 `power`만 싣고 duration·위상 배열이 없다(ERD). 주기만으로 추정하려면 항성 밀도 같은 새 가정을 넣어야 하고, 그러면 아무도 정하지 않은 숫자가 기본값으로 굳는다. 6.2절 duration 상한은 이 값이 있을 때만 걸도록 `SubmissionMatching.Peak.suggestedDurationHours`를 `Double`로 바꿨다. 상한이 빠져도 위상 폭 상한과 최소 창은 그대로 적용된다.
- 결정·근거: **제출 검증용 봉우리를 저장하지 않고 다시 계산한다.** 판·문맥·규칙 버전이 같으면 결과가 같다. 저장하면 제출마다 행이 늘고 판이 바뀔 때 지울 책임이 생긴다. `PeriodogramPeakReader`를 등록해 `sourcePeakGridIndex`가 있는 제출의 503(`SubmissionPeakReader` 미등록)을 닫았다.
- 변경 파일: `CandidatePeaks`(신규), `PeriodogramPeakReader`(신규), `AnalysisService`(5.4절 경로와 주기도 스냅샷 공용 헬퍼), `AnalysisViews`, `AnalysisRepository`, `AnalysisController`, `SubmissionMatching`
- 검증: 백엔드 전체 486건 통과. 규칙은 고정 power 배열 단위 시험 14건(`CandidatePeaksTest`)과 통합 시험 10건(`AnalysisDataTest` 5.4절)으로 본다. 돌연변이 검사로 배선을 확인했다 — 상위 N을 상수 10으로, 반폭 h를 상수 1로, 고조파 배수를 빈 목록으로, 잔차 단계 power를 원본으로, 고조파 허용 오차를 `2h+1`로, 국소 최대 조건을 완화한 여섯 경우 각각에서 해당 시험만 실패했다.
