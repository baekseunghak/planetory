## [S15P21C206-252] 실행 토큰 만료 원인 규명과 LocalExecutor 병렬도 조정

- 수정자: Claude
- 유형: 운영·오류 정정
- 상태: 운영 배포·회귀 검증 완료
- 변경 범위: Node 1 Airflow Compose `AIRFLOW__CORE__PARALLELISM` 2 → 8, DAG 계약 문서
- 목적: Sector 19·21·22·23 `check_download`와 발견 `reconcile` 1차 시도의 `Invalid auth token: Signature has expired` 실패를 없앤다.
- 결정·근거: Airflow 3.2.2는 Task를 queue에 넣는 시점에 실행 토큰을 발급하고 만료는 `execution_api.jwt_expiration_time=600`초다. `parallelism=2`에서 `commit_raw`(약 30분)와 `cleanup_local`(약 14분)이 두 슬롯을 점유하면, Temporal 대기에서 깨어나 다시 queue에 들어간 `check_download`가 10분 넘게 대기한다. 이후 슬롯을 얻은 시점에는 토큰이 이미 만료된 상태다. 실패 4건 모두 queued 후 약 10~13분이 지나 앞선 `cleanup_local`이 끝난 같은 초에 실패했다. 각 단계 DAG가 `max_active_runs=1`이라 동시 Task는 최대 5개이므로 `parallelism=8`로 대기열 자체를 없앤다. 토큰 만료 연장이나 다운로드 Task 재시도 추가는 대기 적체를 숨기므로 채택하지 않았다.
- 검증: metadata `task_instance`의 `queued_dttm`·`start_date`·`end_date`와 Scheduler 설정값(`execution_api.jwt_expiration_time=600`, `core.parallelism=2`, `scheduler.task_queued_timeout=600`)을 읽기 전용으로 대조했다. Node 1은 6코어, 가용 메모리 약 31 GB다. 22:05 UTC에 drain을 시작해 활성 DagRun 0건을 확인했다. 22:34 UTC에 불변 release `20260922T220731Z`를 `--update`로 배포했고 결과는 `AIRFLOW_UPDATE_READY`였다. import 오류 0건, 네 서비스 healthy, `core.parallelism=8`을 확인했다. 22:36 UTC 재개 후 23:27 UTC까지 `commit_raw`·`cleanup_local`·`commit_bronze`와 `reconcile`이 동시에 실행되는 동안 `check_download` 대기가 반복됐다. 이 구간에서 failed·up_for_retry·upstream_failed는 0건이었고 queue 최대 대기는 0초, 발견 `reconcile`은 모두 1차 시도에 성공했다. 수정 전 배포에서는 Sector 24~27 `check_download`가 같은 오류로 실패했다.
- 관련 문서: [DAG 계약](../../../distributed-system/airflow/dags/README.md), [Airflow 운영 절차](../../../infra/distributed-system/README.md#airflow-db)
- 후속 작업: 임시 핸드오프는 이 기록으로 대체하고 삭제했다. `reconcile` 소요가 약 1.5~2분에서 3~4분으로 늘었다(원인 정정은 아래 리뷰 반영 기록). RAM·Executor 병렬도 튜닝과 Raw 감사 추가 가속은 별도 실측으로 판단한다. Node 1에 중지된 Airflow 2 webserver orphan 컨테이너가 남아 있다.

## [S15P21C206-252] MR !194 리뷰 반영

- 수정자: Claude
- 유형: 파이프라인·운영·CI 오류 정정
- 상태: 코드·문서 반영, 단위 테스트·Airflow 3.2.2 이미지 import 검증 완료, 운영 미배포
- 변경 범위: 발견·단계 DAG, HDFS coverage 명령, Airflow 배포·업그레이드 스크립트, GitLab CI, `.gitignore`
- 목적: 리뷰에서 확인된 결함을 병합 전에 해소한다.
- 결정·근거:
  - `reconcile`은 Sector 14부터 상한까지 모든 Sector를 매 주기 SSH로 조회했다. 앞 기록의 소요 증가는 병렬도 때문이 아니라 완료 Sector 수가 늘어난 결과다. 영속 Variable `tess_pipeline_completed_through`로 연속 완료 구간을 건너뛴다.
  - 앞 단계가 다음 단계를 자기 시도 번호로 trigger하면 번호에 틈이 생긴다. 그러면 조정 DAG의 연속 조회가 실행 중인 run을 놓치고 중복 run을 예약한다. 다음 단계는 항상 r0으로 시작한다.
  - 분리된 독립 `coverage` 명령이 Sector 감사를 항상 재사용하던 경로를 막았다. 감사 재사용은 방금 전 Sector를 감사한 coordinator 내부에서만 허용한다.
  - 배포 rollback·신규 설치·3.x 업그레이드에서 Triggerer를 함께 기동하고 health에 포함했다.
  - CI `validate:compose`에 `AIRFLOW_JWT_SECRET` 검증 전용 값을 추가했다. 활성 run·Triggerer 검사가 없는 CI의 Airflow 2 구성 배포 job은 제거했다.
  - 추적 중이던 `__pycache__/*.pyc` 15개를 제외하고 무시 규칙을 추가했다. 1~13 전용 `sector_inputs` 죽은 코드도 제거했다.
  - 동적 매핑 `trigger_stage`가 병렬도를 넘겨 토큰 만료를 재발시킨다는 지적은 채택하지 않았다. 긴 작업은 최대 3개이고 매핑 인스턴스는 수 초 안에 끝나므로 긴 대기가 생기지 않는다. 대신 DAG 계약의 근거 문구를 정정했다.
- 검증: Airflow 테스트 18건, HDFS 테스트 36건 통과. Node 1의 Airflow 3.2.2 이미지에서 네트워크 없이 DAG 5개를 import했고 오류 0건이었다. 다음 단계 run ID 템플릿 `_r0`과 conf의 `attempt=0` 렌더링을 확인했다. CI 검증 변수로 한 `docker compose config`도 통과했다. Sector 20 `check_download`의 `start_date`가 wake-up 뒤에도 최초 값으로 유지되어 14일 deadline이 늘어나지 않음을 운영 metadata로 확인했다.
- 관련 문서: [DAG 계약](../../../distributed-system/airflow/dags/README.md), [Airflow 운영 절차](../../../infra/distributed-system/README.md#airflow-db)
- 후속 작업: drain 후 불변 release로 운영 반영하고 `tess_pipeline_completed_through` 전진과 `reconcile` 소요 감소를 확인한다.
