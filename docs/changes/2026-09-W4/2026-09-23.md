- 결정·근거: Airflow 3.2.2는 Task를 queue에 넣는 시점에 실행 토큰을 발급하고 만료는 `execution_api.jwt_expiration_time=600`초다. `parallelism=2`에서 `commit_raw`(약 30분)와 `cleanup_local`(약 14분)이 두 슬롯을 점유하면, Temporal 대기에서 깨어나 다시 queue에 들어간 `check_download`가 10분 넘게 대기한다. 이후 슬롯을 얻은 시점에는 토큰이 이미 만료된 상태다. 실패 4건 모두 queued 후 약 10~13분이 지나 앞선 `cleanup_local`이 끝난 같은 초에 실패했다. 각 단계 DAG가 `max_active_runs=1`이라 동시 Task는 최대 5개이므로 `parallelism=8`로 대기열 자체를 없앤다. 토큰 만료 연장이나 다운로드 Task 재시도 추가는 대기 적체를 숨기므로 채택하지 않았다.
- 검증: metadata `task_instance`의 `queued_dttm`·`start_date`·`end_date`와 Scheduler 설정값(`execution_api.jwt_expiration_time=600`, `core.parallelism=2`, `scheduler.task_queued_timeout=600`)을 읽기 전용으로 대조했다. Node 1은 6코어, 가용 메모리 약 31 GB다.
- 관련 문서: [DAG 계약](../../../distributed-system/airflow/dags/README.md), [임시 핸드오프](../../project/tess-airflow-handoff-2026-09-23.md)
- 후속 작업: drain 후 불변 release로 배포하고, 두 슬롯이 긴 작업에 점유된 상태에서도 `check_download` wake-up과 `reconcile`이 실패하지 않는지 확인한다.
