- 변경 범위: `distributed-system/spark/tess_silver_ctl.py`(`hdfs_glob`)·`test_tess_silver.py`, [Spark README backlog 버킷 결과](../../../distributed-system/spark/README.md#backlog-버킷-01-결과-2026-09-27-확정)·검증 상태 절, [Airflow DAG README](../../../distributed-system/airflow/dags/README.md) Sector 14+ 문단
- 목적: 2026-09-27 `plan`·Canary·버킷 0·1 실측 결과를 남기고, 병합 전에 남은 일의 담당을 정한다.
- 결정·근거:
  - `plan`이 첫 증분을 `through 70, delta 15`, K = 15(TIC 413,764개, 추정 RF2 2,804.1 GB)로 정했다. 버킷 0·1은 모두 확정됐고 기존 attempt 4개의 `_READY` SHA는 바뀌지 않았다. 실제 출력은 추정의 97.3%·97.1%라 추정 계수를 유지한다.
  - `--plan-only` job은 Sector 1~70 입력 검사를 약 3분에 끝냈다. 개선 전에는 Sector 1~14에도 약 30분이 걸렸다. 제어기 확정은 80의 checksum 개선으로 24분에서 약 2.5분이 됐다.
  - 최초 탐색 실패율이 1.3%·1.4%로 1~13(0.08%)보다 높다. 실패 코드 종류는 같고 모두 재시도 불가이며, 원인은 확인하지 않았다.
  - Silver DAG conf·`start-unit` sudoers 확장은 275에 두기로 했었으나 81로 넘긴다. 이를 부를 쪽이 81 조정 DAG뿐이어서, 호출하는 쪽 없이 운영 sudoers만 넓히지 않는다. 그때까지 증분은 운영자 경로로 실행한다.
  - 나머지 버킷 2~14는 103 용량 결정 뒤 `plan`으로 이어 간다. 80% 예산은 약 1,118 GB가 남아 버킷 5~6개만 들어간다.
  - TIC별 선택 인덱스는 보류다. Gold `silver_input`은 coverage 필드를 대조하므로 Sector snapshot attempt(Sector 14, backlog 버킷)를 거부한다(fail-closed). 따라서 14 이후 Silver는 인덱스와 그것을 읽는 Gold 입력이 생길 때까지 Gold·운영 DB로 가지 않는다.
  - 자체 리뷰 반영: `plan`의 Bronze·Silver 목록 조회가 "없음"이 아닌 이유로 실패하면 `idle`이나 Sector 1부터의 재계획으로 읽지 않고 멈춘다(`hdfs_glob`). unit 목록 조회 실패도 무시하지 않는다.
- 검증: `test-tess-silver.ps1` 통과(Silver 57), CI `validate:astro-kernel` Spark 묶음 통과, 버킷별 `_READY` 필드, manifest 실패 코드 집계, `hdfs dfs -du`·`-df`, staging 잔여 0, 기존 attempt `_READY` SHA·수정 시각 대조(모두 Node 1 읽기 전용)

## [S15P21C206-292] 루트 Compose에 로컬 세션·캐시 Redis 추가

- 수정자: 김동혁(Claude Code 보조)
- 유형: 운영 · 오류 정정
- 상태: 검증 완료
- 변경 범위: 루트 `compose.yaml`(`session-redis`·`cache-redis` 추가, `backend`에 `SESSION_REDIS_*`·`CACHE_REDIS_*`·`depends_on`), `docs/operations/docker.md` 「로컬 개발」, `apps/backend/README.md`, `apps/backend/docs/development-setup.md` 3장, `exec/1-porting-manual.md` 4.7절
- 목적: `docker-compose -f compose.yaml --profile service up --build`로 뜬 `backend`가 로그인 가능한 상태가 되게 한다.
- 결정·근거: `S15P21C206-257`이 로컬 Compose를 구현하지 않고 종료한 남은 범위다. 237 이후 local 프로필은 세션·캐시 Redis를 `localhost:16379`·`16380`에서 찾는데 루트 Compose에는 Redis가 없었다. 컨테이너 안의 `localhost`라 연결이 실패하고 앱은 뜨지만 health `DOWN`(503)과 세션을 쓰는 요청 전부 503이었다. 두 Redis를 `service` 프로필에 넣고 호스트에는 local 기본 포트로 열어, 호스트 `bootRun`·IDE 실행도 `docker run` 대신 같은 정의를 쓴다.
- 검증: 별도 프로젝트 이름으로 격리 기동했다. 수정 전: `Started PlanetoryApplication`, health 503 `DOWN`, CSRF 조회 503, `RedisConnectionException: Unable to connect to localhost/<unresolved>:16379`. 수정 후: health 200 `UP`, CSRF 조회 200, 세션 키 1개가 `session-redis`에만 생기고 `cache-redis`는 0개, Redis 연결 예외 0건. `docker compose -f compose.yaml config -q` 통과. `frontend`는 기동하지 않았다.
- 관련 문서: Jira `S15P21C206-292`, [Docker 개발·배포 기준](../../operations/docker.md), [백엔드 개발 환경 안내](../../../apps/backend/docs/development-setup.md), [Redis 연결과 저장 경계(237)](../../../apps/backend/docs/oauth-setup.md#redis-연결과-저장-경계237)
- 후속 작업: 예전 안내대로 `docker run`으로 만든 `planetory-local-session`·`planetory-local-cache`가 떠 있는 PC는 16379·16380이 겹치므로 그 둘을 멈춘다.
